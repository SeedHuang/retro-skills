下面是议会（parliament）的主流程，按 [SKILL.md](file:///d:/Seed/retro-skills/skills/parliament/SKILL.md) 的总流程 0–7 步和 [debate-protocol.md](file:///d:/Seed/retro-skills/skills/parliament/references/debate-protocol.md) 的回环判据画的。

主流程里有三条“过不去就停”的关卡：议会并非只“提意见”，每个阶段结束都要通过一道检查，通过后才能继续。这三道关卡分别决定了流程中的哪些分支。

除了主流程，还有两件事需要说明：

**谁在干活**（六类角色，角色卡由 `agents/` 生成，不许手改）
- 主持人：点将组队、汇总去重、跑计数；**不能自己给自己的记录签字**，审计表必须由审计员本人填写
- 评委：并行独立出卡，防止互相看齐；每个评委都走「固定清单 + 自由探索 3–5 问」
- 答辩方：架构师 leader + 4 名研发，先核实问题真存在，再逐卡作答（承认 / 带依据反驳 / 部分承认带修法）
- 侦探：只记录不裁决，按机械判据核对“评委刁难、答辩回避、主持人丢卡”
- 审计：按两档审核清单（轮际 + 交付），证据栏为空即不通过
- 用户：只有你有中断权和最终决断权；技术分歧在前 3 轮内不升级

**三个容易误读的地方**
1. 回环最多进行 3 轮：问题清零或全部裁决关闭就结束，否则第 3 轮后带双方摸查记录升级给你，没有摸查记录的争端侦探会驳回。
2. 每次修复都要重新执行一遍“跨章节一致性”检查（手法 3，见 [debate-protocol.md](file:///d:/Seed/retro-skills/skills/parliament/references/debate-protocol.md)），然后做同族扫描，以免修好一处又撞坏另一处。
3. 执行路径分 A/B/C 三种（调度用户级子代理 / Task 派通用子代理 / 主持人串行扮演），报告里必须标注实际走的是哪条；走 C 时叫“降级模式”，质量要打折扣。

组队与送审的矩阵依据在 [assembly-matrix.md](file:///d:/Seed/retro-skills/skills/parliament/references/assembly-matrix.md) 和 [submission-matrix.md](file:///d:/Seed/retro-skills/skills/parliament/references/submission-matrix.md)：前者按“项目类型”定人选，覆盖矩阵必须零缺口；后者按“文档类型”定必带件，只有 spec 类文档必须带 testcase。

还不够细，那我把流程拆成三段，逐段画到“谁、在什么时刻、交什么、卡在哪一步”。

**第一段：开评前的六道准备**（少任何一步，评审都不能开始）

这六步的实质是：**先把“审什么、谁来审、带没带齐、拿什么当证据”固定下来**。比如“点将核零缺口”是指：这次文档涉及哪些关注面（逻辑、前端、后端、测试、安全、成本），每个关注面都要有人负责；只要有一个面没有人，就不允许开评。再比如“机器证据”，证据必须是命令加输出；写“已核对”就等于空栏。

**第二段：一轮内部，七个动作按顺序发生**

这七个动作中有两处容易漏：一，问题卡有八个字段（编号、角色、维度、描述、证据、级别、解法、无问题时的显式声明），少“证据”或“解法”就直接作废；二，侦探只管行为异常，不管观点对错；发现异常后按处置表执行（废卡率 ≥1/3 就让该评委本轮产出全部复审）。

**第三段：收敛、升级与收口**

三条出口的判据如下。

**出口一：清零或全部裁决关闭**
走“修复纪律”四步：每处修复都要带落点（改哪个文件、哪一节）；修完立刻重跑“跨章节一致性”检查（手法 3，防止修了 A 节、B 节还留着相反的写法）；再做同族扫描（同类问题在别处还有没有）；最后做“修复引入自查”（新改动有没有带来新矛盾）。这四步不跳，是因为实测里最容易出的错不是没改，而是改了一半。

**出口二：未满 3 轮**
回到下一轮的“评委出卡”，但带着上一轮的账：审计第 0 项“轮际对账”就是把上轮承诺的改动和本轮开卷清单逐项对齐；对不上，就不许开下一轮。

**出口三：第 3 轮仍有未决**
写升级报告交给你，格式固定：争议焦点一句话 + 甲方（评审方）和乙方（答辩方）各写立场 / 赞成原因 / 反对对方原因 / **摸查记录（查了什么 + 命令 + 结果）** + 各自的具体解法。任何一方只提问题、不给解法，就不许升级；没有摸查记录，侦探直接判为“臆想争端”退回。**用户终裁之后才继续**，中断和终裁权只在你手里。

**收口只有一种合法方式**：交付审计通过才允许宣布交付。
- A 节查过程闭环六项：终态对账、P0/P1 清零、落点抽查 ≥3、P2 三态齐（采纳/关闭/候选）、数字一致、升级项有终裁
- B 节按文档类型逐交付物核完成判据（`references/doc-taxonomy.md` 是唯一权威，例如 spec 要求“Backlog 三表齐、P2 全落态、P0/P1=0”，skill 要求“check 脚本 0 findings”）
- 结论只能三态：通过 / 有条件通过（必须列明候选项与触发信号）/ 不通过（附打回清单）

报告结构固定：结论先行（X 矛盾 + Y 盲点 + Z 优化）→ 分级详述 → 自洽确认区 → 团队名单与轮间变更 → 实际执行路径（A/B/C）标注；账本（`progress.md` 过程账 / `problems.md` 族级台账 / `cards.md` 原始卡）落 `.session/reviews/<时间戳>-<名字>/`。

如果需要更细的某一格（例如某席评委的固定清单、`round-check` 六项怎么取数、十三病根表逐层核对），告诉我具体是哪一段，我展开到那一步。

## 二、长远账：每条改动能解决什么，不能解决什么

**改名主持人 → 议长**

这是纯**语义对齐**。收益：你看着舒服。成本：3 个改动点，其中 docgen 源动了必须重跑全体 agents 生成——实测 docgen 生成器有 4 个组件（`agentData.mjs` / `outputFormats.mjs` / `sharedBlocks.mjs` / `triggerTable`）和 2 个测试，重跑后要审输出差异。**不解决任何流程问题**，只解决认知违和。短期成本中等，长期收益极低。

**答辩方从 leader 一人 → leader + 4 研发独立子代理**

这是**治本**。实测现状：`host-duties.md` 第 32 行明写“研发 4 人：测试开发 / 前端 / 后端 / AI 研发”，但 `agents/` 目录只有 `senior-sdet` 一个独立子代理。另外 3 个是主 agent 在同一上下文里串行扮演——**等于一个人既出问题又自己答**，和“spec 作者自己写 testcase”是同一个结构病。

补 3 个子代理的收益不是“多了 3 个视角”，而是**把“核实问题客观存在”这一步从 leader 脑子里拆出去**。leader 可以压自己的判断，但压不掉 4 席里有 2 席都确认“问题存在”的证据。成本是 210 行新卡 + 重生成——**摊到每轮评审的质量收益，远高于一次性写 3 个 agent 的成本**。

但光补 3 个 agent 不够。还要加一条：**leader 的统一口径必须附带 4 席核实表（每条问题：确认存在 / 确认不存在 + 证据 + 署名 agent 名）**，否则 leader 还是可以在汇总时压掉。这条落在 `host-duties.md` 和 `issue-card.md` 的八字段里各加一列。

**交互 + UI 合并为体验席**

这是**结构性减人**，但收益被高估了。

先看数据：assembly-matrix 里 6 行项目类型，交互+UI 同时必选的只有 **H5 前端** 1 行（共 6 席必选 + 侦探 = 7 席），合并后变 5 席必选 + 侦探 = **6 席**，减 1 席。另外 5 行里，微信小程序必 UI/交互、Electron 两者都是“按需”、Node/纯文档/记录型文档 UI 都是明确不选——也就是说，**这个合并只让一种项目类型减 1 席**，其它类型本来就不触发。

而且，交互（流程/状态）和 UI（视觉/规范）是两种不同的问题：交互关心“用户走得到吗”，UI 关心“用户看得清吗”。合并后体验席的固定清单会膨胀——要么把两席的清单全并进来（≥20 条，粗读容易糊），要么挑重点（挑什么 = 丢覆盖）。

**我的成本收益判断：这笔账不值得现在做。** 先把答辩方 4 席补齐（解决结构病），跑两轮议会看实际意见分散程度——如果两轮下来 H5 项目真的出现“交互和 UI 两席各提同一张卡”的重复，再合并；否则先不动。**减人的前提是“人真的多了”，不是“名字看起来多”。**

## 三、你说“收敛三条建议没意义”——我想清楚为什么了

之前那三条（每席限 5 必修项 / 按族合并 / 审计裁定级别冲突）**错在它是“补丁思维”**——先承认人多，再加三道闸把人数的副作用压下去。这本质上是“加规则来对抗前一条规则的副作用”，和仓库里已经出现过的“靠自觉的规则必然漂移”是同一个病。

**真正治本的收敛只有一条：按项目类型点将就是收敛。** 矩阵里已经写死了不同类型的必选/按需/不选，这个动作本身就把 H5 项目的 7 席、Node 的 6 席、纯文档的 3-4 席卡死了——不会 13 席一起开评。**实测跑过的议会里，从来没有 13 席全上的情况。** 所以“意见太分散”的根因不是“开了 13 个席位”，而是“哪些席会提同一张卡但没人合并”——后者已经由议长按族合并来管，是议长的活，不是评委的活。

那三条补丁就**不需要写进规则**。

## 四、精算师的最终建议（P1 · 有条件通过）

**优先级排序：补答辩方 > 改名 > 合并交互 UI**

| 动作 | 建议 | 账 |
|---|---|---|
| 补 `dev-frontend` / `dev-backend` / `dev-ai` | **现在就干**。改 host-duties、加 3 张 agent 卡、改花名册、在 issue-card 八字段里加“核实表”列 | 治本，摊长远值 |
| 改名主持人 → 议长 | **跟着答辩方一起改**。两者都动 docgen 生成源，合一次重生成比分两次改省钱；文件重命名（host-duties → speaker-duties）也在这一轮做 | 纯语义，搭车不单独起 |
| 合并交互 + UI | **暂缓**。先跑两轮答辩方 4 席独立核实的议会，看 H5 项目交互/UI 是否真的重复；实测再定 | 收益 1 席、代价覆盖可能丢，不值得先干 |
| 之前说的“收敛三条” | **丢掉**。补丁思维，不写进规则 | 零收益，还加一层 |

有一条要说明：这三件事一起改属于议会核心机制变更（答辩方构成 + 花名册 + 议长身份），按仓库既有约束，要走 spec + testcase 送议会，不能只改几行文档。所以下一步应该是把这三件事写成一份设计 spec，派 senior-sdet 独立写用例，走议会评审通过后再落地。

## 一、直接回答：意义很薄，只剩一条，而那条机器能查

## 二、plan 的三类缺陷，只有一类不可自愈

| 缺陷类型 | 会不会静默漏过 | 谁能查出来 |
|---|---|---|

| 粒度不对（太大 / 太小） | **不会**——卡住立刻知道 | 执行时自愈 |
| **覆盖缺口**（spec 的功能点没有对应任务） | **会**——静默漏到交付验收才暴露 | 机器（集合比对） |

| 权 | 谁 | 只能做什么 |
|---|---|---|
| **申报权** | 做事的人 | 只陈述事实，**不能定性** |
| **定性权** | 独立于做事的人 | 按机械判据分类，**不能选择** |
| **核对权** | 第三方 | 抽查是否漏报或错报 |

## 二、问题 1：内部对齐失败后回退到哪里

### 推荐：用「举证责任」替代「裁量」

不规定「回哪一步」，而是规定：**每条分歧必须指明「被推翻的是哪一栏结论」**。

| 分歧指向 | 机械路由（回退节点） |
|---|---|
| 「痛点不成立、外部事实有误」 | 回 **市场调研** |
| 「不值得做、成本收益算错」 | 回 **精算师初判** |
| 「形态/范围不对」 | 回 **产品写 PRD** |
| 「依据不可核、数字没有来源」 | 回 **该栏签署人补证据** |
| 「用户根本不想要」 | **不走回路**，直接用户终裁 |

规则只有一条：**如果指不出哪一栏错了，该分歧就不成立，直接关闭并记录**。

这条规则的巧妙之处在于：它把「由谁判断」变成了「由谁举证」。提出分歧的人必须自己说明是哪一栏错了，不需要任何第三方来分类。**举证不出来的分歧，本来就不该占用讨论时间。**

### 两个配套

1. **用户豁免举证**——他是委托人，「我不想要」本身就是依据，不需要指明哪一栏错。其他人（市场 / 精算 / 产品 / sdet）都必须举证。
2. **停损条件**——同一分歧点回退 2 次仍不收敛 → 升级用户终裁。这里直接复用仓库已有的停损句式（「同一红项修复 2 次仍红 → 停止，写复盘」），不另造新词。

### 谁记录

**审计**。它本来就在 PRD 阶段（核 §0），职责扩一项：把分歧条目落盘，并记录它指向哪一栏。审计不做价值判断，只做记录和机械路由——这完全在它的定位之内，不需要新增角色。

## 三、问题 2：谁来判定漂移是「细节」还是「功能增删」

### 推荐：先机械分类，再三权分离

先把「漂移」按**机械判据**分成三类（判据全部可执行，不靠感觉）：

| 类型 | 机械判据 | 归属 |
|---|---|---|
| **细节偏差** | 功能点集合不变 **且** testcase 判据不变 | 记 spec |
| **行为偏差** | 功能点集合不变 **但** testcase 判据需改 | 回 PRD 补功能点定义（说明原来没定义清） |
| **功能增删** | 功能点集合变了 | 回 PRD + **重签 §0** |

第三类由**脚本**判：PRD 的功能点清单是结构化字段，集合比对没有歧义。

第二类才是需要人判断的，而它恰好有一个天然的独立判定者——**sdet**：

> testcase 是 sdet 写的。判据要不要改，只有 sdet 最清楚，而且 sdet **不是实现者**（实现者是主 agent）。让 sdet 判断「你的改动会不会让我的判据变红」，这是独立于当事人的。

### 三权分离的落法

| 动作 | 谁 | 产出 |
|---|---|---|
| **申报** | 主 agent（实现者） | 漂移条目：改了什么 / 影响哪些功能点 / 影响哪些 testcase |
| **定性** | sdet（独立于实现者） | 按上表三类归档；判据变不变由 sdet 定 |
| **核对** | 审计（第三方） | 抽查漂移记录 vs 实际 git diff，查漏报、错报 |

**主 agent 只有申报权，没有定性权。** 它不能说「这只是细节」，只能写「我改了什么」，由 sdet 定性、审计核对。

这条同时堵住一个更隐蔽的漏洞：主 agent 可能**漏报**（自己都没意识到改了功能边界）。所以审计的核对必须比对 **git diff**，不能只核漂移清单——清单是主 agent 自己写的，自证无效。

## 四、成本账

| 新增动作 | 成本 | 不做的话 |
|---|---|---|
| 分歧必须指明哪一栏错 | ≈ 0（写一句话） | 讨论发散，回退无规则，每次多 1–2 轮 |
| sdet 定性漂移 | 每功能点几分钟 | 漂移静默累积，交付时才发现 → 返工整个功能 |
| 审计比对 diff | 每轮几分钟 | 漏报不可发现 |

按之前实测的账（有精确记录的 7 轮共 294 分钟，9 轮 ≥ 5 小时），**这些新增动作的成本，远低于多跑一轮议会的成本（约 25–50 分钟）**。所以这是纯收益，不是权衡。

## 五、统一原则（可推广）

这两个问题加上议长问题，本质是同一条：

> **做事的人可以申报，但不能定性；定性的人必须独立于做事的人；定性结果必须被第三方核对。**

这条原则后面还会用到的地方（现在能预见的）：
- 主 agent 判断「这个改动不算破坏性」→ 同理不能自判
- 产品经理判断「这个变更不需要进评审」→ 已是自判，需要议长复核 + 判错记点将缺口（前面已定）
- 精算师评审阶段复核自己的需求结论 → 已定为侦探核对项（前面已定）

## 核对脚本伪代码（图 / 表 / 清单 三方一致）

先说清一个前提：**要能机械核对，功能点必须有稳定 ID**（如 `F-01`）。没有 ID 就只能按名称模糊匹配，判据立刻失效。所以「功能点带 ID」是这个脚本的前置约定。

```ts
// scripts/check-prd-graph.mjs（零依赖，与 run-eval.mjs 同风格）
// 用法：node scripts/check-prd-graph.mjs --prd <path> [--base <git-ref>]

// ============ 数据模型 ============
type FunctionPoint = { id: string, name: string, stage?: string, line: number }
type MermaidBlock  = { line: number, diagramType: string, nodes: Node[] }
type Node          = { id: string | null, label: string, line: number }
type StepRow       = { id: string, step: string, why: string, line: number }

// ============ 主流程 ============
main(argv):
    prd  = argv.prd
    base = argv.base            // 可选，用于「同批更新」检查

    doc = read(prd)

    fences    = parseCodeFences(doc)                        // 所有 ``` 块
    mermaid   = fences.filter(f => f.lang == 'mermaid')
    images    = parseImageRefs(doc)                         // ![..](..)

    fps       = parseFunctionPointTable(doc)                // §4 清单表，列含 ID
    rows      = parseStepTables(doc)                        // | 步骤 | 干什么 | 为什么 |

    findings = []

    // ---------- A 形态门 ----------
    // A1 只收文本图：PRD 内不得用图片表达流程
    for img in images:
        findings += IMAGE_NOT_ALLOWED(img.line, img.src)

    // A2 图类型白名单
    for b in mermaid:
        if b.diagramType not in ['flowchart', 'sequenceDiagram']:
            findings += BAD_DIAGRAM_TYPE(b.line, b.diagramType)

    // A3 必须同时有时序图（阶段交互）与流程图（功能点级）
    if not exists(mermaid, type == 'sequenceDiagram'):
        findings += MISSING_SEQUENCE_DIAGRAM()
    if not exists(mermaid, type == 'flowchart'):
        findings += MISSING_FLOWCHART()

    // ---------- B 图 ↔ 清单 ----------
    flowcharts = mermaid.filter(type == 'flowchart')
    nodes      = flowcharts.flatMap(parseNodes)             // 含 subgraph 内节点
    nodeIds    = nodes.map(n => n.id).filter(n => n != null)

    findings += checkUnique(fps.ids,   'DUPLICATE_FP_ID')
    findings += checkUnique(nodeIds,   'DUPLICATE_NODE_ID')
    findings += checkIdFormat(fps.ids, /^F-\d{2}$/)

    // B1 清单 → 图：每个功能点必须有节点
    for fp in fps:
        if fp.id not in nodeIds:
            findings += FP_MISSING_IN_GRAPH(fp.id, fp.line)

    // B2 图 → 清单：不许有孤儿节点
    for id in nodeIds:
        if id not in fps.ids:
            findings += ORPHAN_NODE(id)

    // B3 节点必须带 ID（否则无法核）
    for n in nodes:
        if n.id == null:
            findings += NODE_WITHOUT_ID(n.line, n.label)

    // ---------- C 图 ↔ 表 ----------
    // 每个功能点在步骤表里有一行，且表里没有多余行
    for fp in fps:
        if fp.id not in rows.ids:
            findings += FP_MISSING_IN_TABLE(fp.id)
    for r in rows:
        if r.id not in fps.ids:
            findings += ROW_WITHOUT_FP(r.id, r.line)

    // ---------- D 同批更新（需要 --base）----------
    if base != null:
        oldDoc   = parse(git_show(base, prd))
        oldFps   = oldDoc.fpIds
        oldNodes = oldDoc.nodeIds

        dFp   = setDiff(oldFp, fps.ids)          // 清单的变化集合
        dNode = setDiff(oldNodes, nodeIds)      // 图的变化集合

        // 判据：两个变化集合必须相等
        // 只比「是否同一 commit」是弱判据——一起提交不等于改对了
        if dFp != dNode:
            findings += UNSYNCED_UPDATE(dFp, dNode)

    // ---------- 输出 ----------
    printReport(findings)       // 每条：码 + 行号 + 具体 ID
    return findings.hasError ? 1 : 0
```

| 判据（上一轮） | 脚本落点 | 错误码 |
|---|---|---|
| 1 每个功能点在图里有节点 | B1 | `FP_MISSING_IN_GRAPH` |
| 2 图里无孤儿节点 | B2 | `ORPHAN_NODE` |
| 3 图 / 表 / 清单同批更新 | **D** | `UNSYNCED_UPDATE` |

第 4 条不需要单独判据——**过期图在 B1/B2 下必然暴露**：清单改了而图没改，旧节点就成了孤儿；图改了而清单没改，新节点就是孤儿。两条合起来就是「无过期图」。

## 三个设计取舍（需要你确认的实质决定）

**1. 时序图不参与功能点核对，只有 flowchart 参与**

`sequenceDiagram` 里是 participant（角色）和消息（交互），跟功能点不是一一对应关系，硬套会大量误判。所以分工写死：

| 图类型 | 表达什么 | 参与核对 |
|---|---|---|
| `flowchart` | 功能点级流程，**节点 = 功能点，必须带 ID** | ✅ |
| `sequenceDiagram` | 阶段 / 角色交互 | ❌ |

**2. D 判据用「集合差异相等」，不用「同一 commit」**

「同 commit 提交」只能证明一起交，不能证明改对了——图改错、清单也一起改错，一样同 commit。所以判据是：**清单的变化集合 == 图的变化集合**。这个更强，也更便宜（都是集合运算）。

**3. 退出码与输出格式沿用仓库既有约定**

`0` 全绿 / `1` 有红项 / `2` 环境或解析失败。每条 finding 必须带**行号 + 具体 ID**，不许只说「不一致」——否则人还得回头自己找。

## 一、我上一轮把「同批更新」写错了

我写成「改功能点必须同批改图与表」——翻译过来就是**每次改动立即同步三处**。这是成本最高的做法：高频小改时，同步开销会压垮产出本身。你这条纠正对。

## 二、先把三种成本分开（否则永远在治标）

| 成本 | 表现 | 性质 |
|---|---|---|
| **同步不足** | 漂移，交付时才发现 | 显性、痛 |
| **同步过度** | 每次改一行都要动三处 | 隐性、更常见 |
| **同步面积** | 重复表达越多，任何改动要动的地方越多 | **根因**，前两项都是它的派生 |

「精明的当家人」先算的是第三项——**不是优化同步节奏，是减少需要同步的地方**。

## 三、第一层（治本）：先减面积

| 手段 | 做法 | 效果 |
|---|---|---|
| **不重复表达** | 清单只写「是什么」，图只写「流程怎么走」，表只写「步骤干什么」——三者**不重叠** | 改描述不用改图，改图不用改表 |
| **节点用 ID + 短名** | 图节点写 `F-03 提交申请`，不写完整描述 | 改完整描述时图不用动 |
| **分区** | §0/§1 是低频区（签完基本不动），§4 是高频区 | 只对高频区做强同步 |
| **不强制全画** | 清单加一列「进流程图：是/否」，只核标记为「是」的功能点 | 不为满足判据硬画无意义的图 |

| **语义变化**（ID 不变，只改文字或图内短名） | 脚本**不红** | 可以攒批 |

## 五、三权分离怎么套在「攒批」上（关键）

| **边界权** | 脚本 | 送审时必须一致 —— 不可协商 |
