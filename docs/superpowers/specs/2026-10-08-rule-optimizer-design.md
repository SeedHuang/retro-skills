## 0. 已确认的边界（实现时不得推翻）

这几条是用户当场定的，**不是待选项**，实现时按它们写，别再加「灵活性」：

| # | 边界 | 含义 |
|---|---|---|
| B1 | **删判据 = 绝对禁止** | 删行为边界规则的核心判据，**没有「问用户然后就能删」这一档**。判据不可触碰。 |
| B2 | **体积不是硬门槛，是防废话的秤** | 规则随场景增多而长大是正常的、应允许。体积超预算**只触发一次废话审查**，不强制砍到线下。 |
| B3 | **规则格式统一的原因不是「官方要求」** | 官方（Anthropic）只管 `SKILL.md`，**管不到 rules**。统一格式的依据是自定义规则「同一含义用同一标记，AI 才能稳定定位核心判据」。 |
| B4 | **来源行保留「类型+日期」，砍掉历史叙述** | 保留：来源类型（决定优先级）、日期。砍掉：合并记录、多段用户原话、补记日期。 |
| B5 | **skill 是「判据驱动的改稿器」，不是「报告生成器」** | 每条违规要配「可复制的改法」，不能只给诊断。 |
| B6 | **语义判断不自动化** | 脚本只查形式；「判据变没变模糊」由 AI 按本 spec 的三检验逐条验证并写进报告。 |
| B7 | **三类官方标准不存在，别去外部找** | 已查证：skill 有官方规范（agentskills.io），**rule 没有**；质量打分器（Schliff 4 stars / PromptQC 0.2.0 / instruction-lint Alpha）**权威性不足，不引入**。 |

## 3. 头部模板与层级规范

### 3.1 头部模板（进 `assets/rule-template.md`）

```
# <标题：一句话可执行判据>

> 来源：<类型>（<YYYY-MM-DD>）｜[证据：<一句话，仅实测/踩坑类>]｜落地：<YYYY-MM-DD>
```

| 字段 | 必需 | 说明 |
|---|---|---|
| 标题 | ✅ | 必须是「可执行判据」，不是主题名。`# 测试踩坑笔记` ❌（是目录，且内含两条不相关规则） |
| 来源类型 | ✅ | 四类枚举，见 §3.3。决定 AI 执行力度 |
| 日期 | ✅ | 一个就够，不写「补于 X、落地于 Y」两段 |
| 证据 | ⚠️ | **仅「实测/踩坑」类写一句话现象**，其余三类不写 |
| 落地 | ✅ | 来源行三要素之一（见 D1）：`来源类型 / 日期 / 落地` 必须齐全，缺一即 D1 扣分 |
| 来源行总长 | ⚠️ | **来源行 ≤ 2 渲染行**（D3 判据的归属定义，超 2 行每多 1 行 −3）。「渲染行」= 编辑器/终端 wrap 后的实际行数，**依赖环境**，不规定字符/行；给个操作锚点：来源行字符数 **> 200 即视为超 2 行**（`how-i-must-reason` 的来源行实测 329 字符），不许用「物理 1 行」糊弄 |

**砍掉的（对照现状）**：合并记录（「合并 no-unverified-claims.md」）、多段用户原话（「不要考虑成本，最重要的是考虑对不对…」）、补记日期。

**依据**（B4）：来源行的功能是**权限标记 + 可审计**，不参与运行期约束力 —— 约束力来自「每轮加载」本身。所以保留类型和日期即可，历史归 git。

### 3.2 层级规范（判据：同一含义用同一标记）

| 层级 | 装什么 | 备注 |
|---|---|---|
| `#` | 规则名 = 一句话可执行判据 | 每条规则恰好一个 |
| `##` | 大节：核心约束 / 例外 / 豁免 / 反例 | **核心判据必须由 H2 或列表承载** |
| `###` | 小节：编号规则、分类、表格标题 | 不用 emoji 装饰 |
| `**加粗**` | **仅句内强调** | ⚠️ 不承担结构职责 |

**现状要修的**：`global-ask-before-acting` 用 `**加粗**` 承载核心约束、`no-git-write` 用 `## 核心约束` —— 同一含义两种标记，AI 每次都要重新猜核心判据在哪。统一为 H2。

**依据**（B3）：这**不是官方要求**（官方只管 SKILL.md 不管 rules），依据是自定义规则 `rules-single-source`「一个用途一个地方」的同构逻辑 —— 内容不许两处说，标记也不许两处用。

### 3.3 来源类型枚举（四类）

| 类型 | 约束力 | 现有规则 |
|---|---|---|
| `用户当场指令` | 最高，不可越权 | `global-ask-before-acting`、`plain-language-to-user`、`docs-convention`、`how-i-must-reason` |
| `评审第 N 轮` | 中，已验证的问题 | `landing-sweep` |
| `实测/踩坑` | 中，有证据背书 | `powershell-file-encoding`、`import-guard`、`skill-assets-convention` |
| `项目约定` | 低-中 | `poll-deferred-at-start`、`no-git-write`、`code-style`、`testing-pitfalls`、`rules-single-source` |

## 4. 「冗余措辞」的可执行定义

**这是本 spec 的核心判据**，替代「凭感觉精简」。

### 4.1 三检验（定义「可删」）

一条文字是「冗余措辞」、可删，**当且仅当删掉它以下三条全部不变**：

| # | 判据 | 检验方法 | 能否脚本化 |
|---|---|---|---|
| 1 | **判据本身不变** | 删后「什么时候该做什么」的核心句一字未变 | ❌ 需 AI 逐条判断 |
| 2 | **边界例子不变** | `✅正例`/`❌反例` 都还在，覆盖场景没少 | ❌ 需 AI 逐条判断 |
| 3 | **引用关系不变** | 指向其它规则的文件名（`no-git-write` 等跨规则钩子）没被删 | ✅ 可脚本查 |

**三条全过 → 可删。任一不过 → 属核心内容，agent 不得自行删除。**

### 4.2 判定结果（三类）

| 内容 | 依据 | 处置 |
|---|---|---|
| 来源行的合并记录 / 多段用户原话 / 补记 | 三检验全过 | **可删** |
| 重复说理（「为什么要有这一档」的展开段） | 判据句已在前文 | **可删** |
| 已定稿但仍挂在规则里的历史叙述 | 是历史不是判据，git 里有 | **可删** |
| **行为边界规则的判据句** | 检验 #1 直接变 | **绝对禁止删**（B1） |
| **边界例子** | 检验 #2 卡住 | 禁止删 |
| **跨规则指针** | 检验 #3 卡住 | 禁止删 |

### 4.3 「防越权公式」——判定一条规则该不该被精简

> **防越权 = body 行为边界规则的判据（核心）+ 判据的精确度（决定效果强弱）+ 头部来源类型（决定优先级，辅助）+ 验证（闭环）**

**这个公式决定精炼时的取舍线**：

| 规则类型 | 精炼时的处置 |
|---|---|
| **行为边界规则**（管「AI 什么时候该停、该问、该等确认」）——如 `global-ask-before-acting`、`no-git-write` | **判据一个字不能模糊**。只删外围说理 |
| **领域规则**（管具体技术动作）——如 `code-style` | 可适度精简 |

**公式的诚实边界**（写进 `criteria.md`，防止误用）：公式防的是「AI 执行层越权」。它**防不了**「规则本身是假的」——没有任何判据能证明「用户当场说过」，来源行是自称的章。这靠 `global-ask-before-acting` 的授权流程兜底，不靠评分。

## 5. 优化流程与硬闸门

### 5.1 触发条件

用户说「优化 rules / 用 rule-optimizer 改规则」时触发。**不自动触发** —— 优化活规则是高影响动作，按 `global-ask-before-acting` 必须先拿到指令。

### 5.2 执行顺序（按优先级，一次一条）

1. **先确认可回滚**：`git -C D:\Seed\my-rules status --porcelain` 应为空（规则改动靠 git 回滚，工作区脏则先收口再优化）
2. **先跑基线**：`node scripts/score.mjs --dir <rules目录>`，记录优化前总分与每条得分
3. **按体积降序**排队（当前：`docs-convention` 129 → `how-i-must-reason` 114 → `code-style` 105 → `import-guard` 96）
4. **一条一条改**，每条内部按 §3 头部 → §3.2 层级 → §4 三检验删冗余 的顺序
5. **每条改完立刻跑一次脚本**，确认分数上升；分数没涨 → **回退这条（`git restore` 该文件）**，不带着分数下降的改动进下一条
6. **全部改完跑总验证**：脚本总分 + 人工过 §5.3 硬闸门 + 确认体积变化符合 B2（长大允许，只查新增是否冗余）

### 5.3 硬闸门（写在 SKILL.md 顶部，agent 读）

> ## 不可越过
> 1. **禁止删除行为边界规则的判据句** ——没有「问用户然后就能删」这一档。判据不可触碰（B1）。
> 2. **禁止改动判据措辞**，除非：报告「改前 vs 改后」两版 → **等用户确认** → 才落地。
> 3. **禁止为凑分数改规则** —— 分数是体检报告，不是验收标准。脚本会给出「健康/预警/超标」，但**超标不要求砍到线下**（B2）。
> 4. **禁止把语义判断交给脚本** —— 三检验里的 #1 #2 由 AI 逐条判断并写进报告，不能只写「已检查」（B6）。
> 5. **删冗余必须在报告里写出三检验的验证过程** —— 不能只报「已精简」。

### 5.4 既存缺陷的处理方式（§1.3 那两条）

| 缺陷 | 处理 |
|---|---|
| 规则矛盾（`GetDiagnostics`） | **人工判断题**：两条规则各管什么范围，判断是「真矛盾」还是「范围不同但没写清」。若真矛盾 → 按 `landing-sweep` 改两处 + 报告；若范围不同 → 各自补一句范围说明。**脚本不查语义** |
| 项目事实混入全局规则（`import-guard` 的编译错误清单、`code-style` 全篇） | **按范围裁剪**：项目特定事实移出全局规则（移到项目内文档或规则内标注「仅适用于 X 项目」）。本项**只提出建议，不自动搬** —— 涉及跨仓搬移，需用户确认 |

## 6. 评分体系（形式层，确定性，可复现）

### 6.1 五个维度（脚本可全查）

每维 0–20 分，总分 100。

| # | 维度 | 判定规则（写进 `criteria.md`，脚本照此实现） | 分值 |
|---|---|---|---|
| D1 | **头部规范** | 来源行三字段齐全（**来源类型 / 日期 / 落地**，定义见 §3.1）+ 来源类型在枚举内 + 日期格式合法 = 20；缺任一必填字段 −10；来源行错位在文末 −5 | 20 |
| D2 | **层级规范** | 核心判据由 H2/列表承载（不靠加粗）+ 无 emoji 装饰 H3 + H1 唯一 = 20；每违一处 −5 | 20 |
| D3 | **来源精简** | 来源行 ≤ 2 渲染行（口径见 §3.1）且无用户原话引用 = 20；每多 1 渲染行 −3；含原话引用 −5 | 20 |
| D4 | **体积健康** | 见 §6.2 —— **只查「新增是否冗余」，不设总量上限** | 20 |
| D5 | **引用完整** | 跨规则指针指向的文件都存在（脚本能查）= 20；每个失效指针 −5 | 20 |

### 6.2 D4 体积维度（B2 的落地：秤，不是栏杆）

**明确不设总量上限。** 规则随场景增多而长大是正常的。D4 只查两件可判定的事：

| 检查项 | 得分逻辑 |
|---|---|
| **单条是否有可执行判据**（H1 是判据不是主题名） | 有 = 20；是「笔记」「规范」「说明」等目录式标题 = 0 |
| **超预算时是否触发过废话审查** | 体积超基线 ×1.5 时，报告里必须有「本次新增部分的冗余审查」小节，缺失 −20；有且写明审查结论 = 20 |

**基线**（2026-10-08 实测，总 670 行 / 21979 字符）：单条行数基线 = 全库中位数 ≈ 30 行；总量基线 = 670 行。**基线随每次优化后重取**（不是固定常量），记在脚本输出的 JSON 里，便于对比。

### 6.3 健康分级

| 总分 | 级别 | 含义 |
|---|---|---|
| 90–100 | 健康 | 达标 |
| 70–89 | 预警 | 有可清理项，不紧急 |
| < 70 | 超标 | **触发一次废话审查**（不是强制砍） |

⚠️ **分级只用于提示，不构成「必须优化到某分」的目标**。一条 75 分但每条判据都很硬的规则，优于一条 95 分但判据模糊的规则。

## 7. 脚本规格（`scripts/score.mjs`）

### 7.1 基线取数命令（写进 `criteria.md`，供读者复算）

```powershell
Get-ChildItem -Path 'D:\Seed\my-rules\rules' -Filter *.md |
  ForEach-Object { '{0,-32} {1,5} lines {2,7} chars' -f $_.Name, (Get-Content -LiteralPath $_.FullName).Count, (Get-Content -LiteralPath $_.FullName -Raw).Length }
```

### 7.2 CLI 契约

```
node scripts/score.mjs --dir <规则目录> [--json] [--baseline <基线文件>]
```

| 参数 | 说明 |
|---|---|
| `--dir` | 规则目录（默认 `D:\Seed\my-rules\rules`）。**目录不存在 → 报错退出（退出码非 0），不静默空跑** |
| `--json` | 输出 JSON（含每条五维得分、当前基线、总分、级别）——**供优化前后 diff**；把输出重定向存成文件，即为下次的基线文件 |
| `--baseline` | 读取上次 `--json` 保存的基线文件做对比（输出见 §7.3 的 `previous` / `diff` 字段）。**文件不存在 → 报错退出（退出码非 0）**，提示先不带 `--baseline` 跑一次 |

**确定性要求**（B7 的延伸）：同样输入必同样输出。**不引入 LLM 判断、不引入随机、不访问网络** —— 这条是从 Schliff 的优点里学来的（它的 README 原话「A score you can't reproduce isn't a measurement」）。语义维度（B6）不在脚本职责内。

### 7.3 输出示例（形状示意，数值以实跑为准）

```json
{
```

**字段语义**（参数 `--baseline` 与字段名不撞名：字段叫 `currentBaseline`）：

| 字段 | 含义 |
|---|---|
| `currentBaseline` | **本次测量算出的基线**（总量 / 中位数 / ×1.5），不是上次的 |
| `previous` | `--baseline` 读入的上次基线；未带参数时为 `null` |
| `diff` | 与上次基线的变化（`lines` / `chars` 增减）；未带 `--baseline` 时为 `null` |

**基线的生命周期**：上次跑 `--json` 时把输出**重定向保存为文件**（`> baseline.json`），本次 `--baseline baseline.json` 读它做对比。基线文件由用户/流程保存，脚本**只读不写**——脚本没有「存基线文件」的动作，避免引入写状态。

### 7.4 依赖接入

- **跑一次 `node --test skilldependencies/validate.test.mjs`** 确认通过（这是本仓既有验证命令，取自 `2026-10-08-review-loop-finish.md` 交接词的验证基线）

## 8. 测试要求

| 测试 | 方法 | 通过标准 | 验证方式 |
|---|---|---|---|
| **同输入同输出** | 同一目录连跑两次 `--json`，diff 结果 | 完全一致（确定性硬要求） | 自动 |
| **维度判定正确** | 拿已知违规做输入（如 `testing-pitfalls.md` 无来源行 → D1 应扣分） | D1 扣分命中 | 自动 |

| **BOM 容错** | 对带 UTF-8 BOM 的规则文件跑分 | 解析正常、输出与去 BOM 版本一致（BOM 是既有踩坑，见 `powershell-file-encoding`） | 自动 |
| **依赖清单有效** | `node --test skilldependencies/validate.test.mjs` | 全 pass | 自动 |
| **闸门人工过审** | 按 §5.3 硬闸门 1–5 逐条人工核对报告 | 每条闸门都有对应报告段落 | 人工 |

## 9. 明确不做的事（防跑偏）

| 不做 | 理由 |
|---|---|
| 引入 Schliff / PromptQC / instruction-lint | 权威性不足（B7）：4 stars / 0.2.0 / Alpha |
| 设规则总量硬上限 | B2：体积是防废话的秤，不是限高栏杆 |
| 让脚本判断语义（判据糊没糊） | B6：机器测不了语义 |
| 为统一格式而单独改 13 条规则 | 格式规范随新规则生效，旧规则**在精炼时顺手对齐**，不单独为对齐而改 |
| 动 `my-rules` 仓库的规则内容 | 本次只交付 skill；实际优化是**后续独立指令**，按 §5 闸门走 |
| 自动改判据措辞 | §5.3 闸门 2：必须报告改前改后 + 等确认 |

## 10. 未决问题（需实现时向用户确认）
