### 0.2 判读口径（先声明再测，防 plan 期静默换口径）

1. **用例只经 CLI 子进程驱动**：spec 只定义 CLI 面（R2 `spec:51`、§4.1 `spec:63-80`），**没有**定义任何导出函数契约。故所有用例一律 `spawnSync(process.execPath, [CLI, …])`，**不 import 脚本内部函数**；若实现额外导出了纯函数，用例不依赖它（也不因它不存在而红）。
2. **路径解析基准**（已澄清，Q18 `spec:159` / §4.1 `spec:72`）：`resolve(process.cwd(), 参数)` —— 相对路径以**调用 cwd** 为基准、**绝对路径合法**。故夹具一律传**绝对路径**（同时把 `cwd` 设成临时根，使两种写法都能跑通）；P44 单独钉相对路径形态。
3. **`coverage` 首行的 `plan <b>` = 交集数**（已澄清，R7 `spec:56` / Q13 `spec:154`）：`b = a − gap`，故 `gap = prd − plan` 自洽。P03（plan 多一个 `F-99`）因此有判别力：若实现把 `b` 打成 plan 全文 ID 数（5），自洽断言立刻不成立。
4. **`deps` 的 `edges <b>` = 去重后两端都存在的边**（已澄清，§4.2 `spec:92` / Q14 `spec:155`）：指向不存在任务的引用计入 `dangling`、**不计入** `edges`。故 P15 的首行是 `edges 1`（不是 2）、`dangling 1`；自洽判据 = `dangling ≤ nodes`、`edges ≤ nodes²` 与「`edges + dangling` = Consumes 引用的去重后条数」。
5. **plan 侧功能点宽松取**（R3 `spec:52` / Q2 `spec:143`）：plan 全文 `F-\d{2}` 全取，不要求出现在任何映射表里；误差方向 = 多算覆盖 → 只漏报不误报。用例 P03 钉的是「多算不红」，P02 钉的是「少一个必红」。
6. **用例 ID = 双载体并集去重**（R5 `spec:54`）：`^#{3,4}\s+([A-Z][\w-]*?\d{2})\b` ∪ `^\|\s*([A-Z][\w-]*?\d{2})\s*\|`，同一 ID 在多处出现只算一次（Q5 `spec:146`；§0.1-5/-6 是真实重复样本）。
7. **`size` 的存量不追溯**（R6 `spec:55` / D2 `spec:124`）是**执行范围**口径，不是脚本白名单：脚本对「显式点名的文件」一律照判（故对 S2 testcase 跑 `size` **必然红**，84 > 80）；「不追溯」靠「门行不去跑存量」实现。P65 钉这一点。
8. **阈值分母逐字**（Q7 `spec:148`）：即使数值为 0，分母也必须出现（`/350`、`/80`、`/3`）；**`--rounds` 必传**（C-18 / C-27），缺 → exit 2，故分子恒为数字、`n/a` 这一值已不存在（R7 `spec:56` 的格式里也不再写 `|n/a`）。
9. **`exit 2` 与 `exit 1` 必须可区分**（R2 `spec:51`）：exit 2 = 用法错、exit 1 = 判据红；**原因清单单源 = spec §4.1 + §4.2**（本文件不复述，C-16）。**已澄清（§4.1 `spec:79` / Q19 `spec:160`）**：exit 0 / 1 时首行恒为 R7 计数行；**exit 2 只打印一行用法/结构错，不得出现任何计数行**（`gap ` / `cycle ` / `missing ` / `size:` 四种形态都不得出现）。
10. **判据里的「恰 N 条」一律同时断「条数」与「内容」**（防「有输出就算核了」）：只断条数会被「报错文本对了但编号错了」蒙混。

12. **门行证据只认首行**（`spec:56` / `stage-2b:17`）：所以每条子命令的正例都断言**首行逐字**（含全角括号 `（）`、**半角**斜线 `/`（两侧各一空格）、空格位置与**行尾 ` => ok|fail`**），不只断言 exit code。
12b. **行尾结论位 = 唯一出口判据**（R7 `spec:56` / C-28）：四条首行一律以 ` => <ok|fail>` 收尾，`fail` ⇔ exit 1、exit 0 ⇔ `ok`。**为什么不是 per-子命令加位**（`stage ok` / `nodes-ok`）：那样每加一条判据就要改一次首行格式，格式本身成了第二处维护；行尾结论位是唯一能覆盖「将来新增任何一类红」的槽位——空输入类红没有自然计数（`--stage` 0 命中、0 节点），只能靠它表达。

14. **覆盖第二半 = 「功能点→任务映射表」**（已澄清，§4.2 `spec:90` / D10 `spec:132` / C-17）：plan 内**必须**有该表（首列值为 `F-\d{2}`、另有列值含 `Task N` / `T<N>`），每个被覆盖功能点该列非空、且指向的任务都存在；**无表 → exit 1**（`无「功能点→任务映射表」，第二半不成立`）；缺行/空单元格 → exit 1（`<F> 无任务落点`）。**没有「不适用」这一档**（v3–v5 的那一档已被 D10 取消）。
15. **`size` 不判「有没有用例」**（已澄清，R6 `spec:55` / Q17 `spec:158`）：0 条 ID 照常输出 `tc 0/80` 且**不红**；「0 条」是 `map` 的判据（P28 红），两条语义不同、必须并存。
16. **映射表的识别按单元格值、不按表头**（已澄清，Q21 `spec:162` / §4.2 `spec:90` / D10 `spec:132`）：判据 = 某表内存在「首列含 `F-\d{2}`」的数据行，且该表任一单元格含 `Task\s*\d+` / `T\d+`。真实表头是「PRD 功能点 / 一句话 / 本 plan 落点 / 覆盖用例（附录 A）」（不含 `F` / `Task`），故按表头认会判成「无表 → 不适用」→ 半条判据静默失效；**P69 专门钉这一点**。

```js
import { mkdtempSync, mkdirSync, writeFileSync, readdirSync, statSync, rmSync } from 'node:fs'
import { spawnSync } from 'node:child_process'
import { join, resolve, dirname } from 'node:path'
import { fileURLToPath } from 'node:url'
import os from 'node:os'

const HERE = dirname(fileURLToPath(import.meta.url))          // = <仓根>/scripts
const CLI = resolve(HERE, 'check-plan.mjs')

// 建一个临时根，把若干 { 相对路径: 内容 } 落盘；返回根
const mkRoot = (files = {}) => {
  const r = mkdtempSync(join(os.tmpdir(), 's4-plan-'))
  for (const [rel, text] of Object.entries(files)) {
    const abs = join(r, rel)
    mkdirSync(dirname(abs), { recursive: true })
    writeFileSync(abs, text)
  }
  return r
}
// 一律传绝对路径（§0.2-2）；cwd 也设成临时根，保证两种基准判定下都一致
const run = (root, args) => spawnSync(process.execPath, [CLI, ...args], { cwd: root, encoding: 'utf8' })
const firstLine = (x) => (x.stdout ?? '').split(/\r?\n/)[0]
const R = (root, rel) => join(root, rel)                      // 拼绝对路径
// 「同一夹具换一处参数跑一次」的通用助手（P20 的五种破折号、P38 的非法值、P38③ 的 --stage 形态共用）
const runWith = (root, mutate) => run(root, mutate())
```

## 2 用例明细

编号 `P01`–`P76` 连续不跳号，每条只测一件事，五要素齐（覆盖 / 前置 / 步骤 / 预期 / 判据）。「取法」行只在 §0.2 / §0.3 有口径分歧处出现；「构造与复位」只对**会写全局态或要动仓内文件**的用例单列——纯文本 / 纯读用例的构造写在「前置」里，复位 = 无副作用（全程不写仓内文件）。**物理位置**：P01–P10（A 组）、P11–P23（B）、P24–P32（C）、P33–P41（D）、P42–P47（E）、P48–P56（F）、P57–P63（G）、P64–P65（H「验收」）、P71–P76（I 组）；**P66–P70、P73–P76 紧随 A 组 / P70 之后的补入块**（编号按写作顺序，不按物理相邻）。

### 10.2 判别力水位（诚实声明——本 testcase 拦不住什么、哪两条最弱）

**最弱的 2 条**：

1. **P68（无映射表 → exit 1 + `steps fail => fail`）**：它证明「实现会按 D10 红并给出固定文案」，但**证明不了「实现认得表」**——按表头认的实现会把 S3 形态那张真实表误判「无表」，P68 照样绿（假阴性）。该缺口由 **P69**（正向识别）+ **P70**（缺任务侧特征）补齐；孤立时判别力低。
2. **P39 / P73 / P75 三条行数边界**：它们分别钉「带尾换行 / 无尾换行 / 纯换行 1 字节」，但**都不覆盖「文件里有 `\r\n` 与裸 `\n` 混排」**（Windows 编辑器与 `writeFileSync` 混用时会出现）。真值靠实现直接用同一条正则 `/\r?\n/` 切（P39 已要求 CRLF）；混排形态**未钉**，属已知空白。

**整份 testcase 拦不住的共性**：
- 全部用例只覆盖**结构关系**，不覆盖「这份 plan / PRD 的内容是否成立」（§10.1-⑨）。
- 首行结论位已完整（「通过与否」可只读首行判），但**「红在哪一半」**仍要读 stderr——这是诊断层，不是通过层，可接受。
- R1 的「不跑 git 子进程」靠 P46 静态正则，正则漏写的等价写法（如 `import('node:child_process')`、动态 `eval`）拦不住；需要 sdet 在 ④ 段人工读一遍源码。
