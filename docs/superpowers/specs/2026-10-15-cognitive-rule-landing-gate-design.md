> 状态：设计已按用户 2026-10-15 三轮讨论收敛 + round-2 自评修正（2 P0 / 3 P1 / 2 P2，见 §1.5），待用户批 plan 后执行｜路径：Architectural｜来源：review-all-to-death R12 复盘 + 用户追问「rule 定了为什么不执行」的根因链

## 1. 背景与问题

### 1.1 起点事件

`rules/core-working-principles.md`（事前三步：画全貌/写计划/算账）在 review-all-to-death 的 R10-R12 修复轮中**从未被执行**——整个 review 账本 grep「全貌确认 / 画全貌」0 命中。用户连续追问三轮，定位出一条完整的失效链。

### 1.2 失效链（四层，均有实测证据）

| 层 | 病根 | 证据 | 机器可查吗 |
|---|---|---|---|
| ① 规则文本缺落点 | 认知动作有产物声明（「全貌确认」块）但**无落点路径**，progress.md 模板里也没有对应槽位 | `Select-String '全貌确认' skills/review-log/assets/review-progress-template.md` → 0 命中 | ✅ 可（文件断言） |

### 1.3 工具链的三处同源缺陷（①层的三个载体）

对「规则定了不执行」，工具链本该拦截，实测全部放行：

1. **rule-inspector 的 X 组是假判据**：`score.mjs` L36-37 用关键词 regex（`/产物|清单|确认块|输出块/`、`/必经|核销|检查点|…/`）判 X1/X2——core 恰好含「确认块」「检查点」字样，实测 `--cognitive` 跑出 **27/28（96% 健康）**。「提到关键词」≠「落点存在」，这是 R9 假闸门（`checkFallbackInSync`）的同款病。
2. **rule-writer 三层漏**：`SKILL.md` L28 自查只列「8 项」（X 组在 reference 里，入口不自查）；`writing-guide.md` X 组自查问题本身是关键词式；`rule-skeleton.md` 无认知动作专属节（起草时没地方写产物落点与路径绑定）。
3. **无持久标注**：认知动作判定（哪条规则该跑 X 组）不落仓内文件。

## 4. 方案设计

### 4.1 X1 真判据（动作产物化；半机械——诚实声明见 §7 短板表）

**机械定义**：产物声明 = 产物模式 + 去处动词 + 去处，三者**同句或相邻句**成对出现（顺序不敏感）：
- **产物模式**（封闭）：`/产物|清单|报告|spec|输出块|「[^」]{2,12}」(?:块|节|表)/`——含「引用名 + 块/节/表」形态（如「全貌确认」块），**字面词表「确认块」作废**（P0-α：与定稿文本脱节）
- **去处动词**（封闭）：`写进 / 落到 / 记入 / 落盘 / 挂进 / 绑进`——**「随」不入表**（保证现状的「随任务记录可查」判红：它正是「声称有落点实际无锚点」的原型）
- **去处**（二选一）：
  - a) **仓内路径**（反引号内含 `.md` / `.mjs`，**全部**无占位符 `<…>` 的路径都要断言）→ 文件存在（相对仓库根 resolve；任一不存在 = 红，fail-closed）
  - b) **载体词**（封闭）：`回复 / 回答 / 报告 / commit body / 账本 / 对话记录`——对话类产物不可文件断言，载体词表内即认可（产物形态明确）

**窗口语义（钉死，防实现漂移）**：句 = 正文按 `。；\n` 切分；成对 = 同句或紧邻下一句；产物模式与去处动词之间不再限定字符距离（句内任意位置）。

### 4.2 X2 真判据（必经路径绑定 = 本设计的核心闸门）

**机械定义**：绑定声明 = 绑定动词（`挂进 / 绑进 / 写进 / 落到 / 核销`，封闭）+ 反引号仓内路径 + 槽位词（路径后**同句**内首个 `「…」` 短词），三段齐全后执行**双重文件断言**：
1. 路径 resolve 到仓库根后**存在**（占位符路径 `<…>` 跳过不断言）；
2. 目标文件内容 **grep 命中槽位词**。

任一不成立 = 红。这意味着：规则声称「挂进 `skills/review-log/assets/review-progress-template.md` 的「全貌确认」节」而模板没有该节 → 红——**这正是要抓住的洞**。

**多路径策略（钉死）**：正文内**全部**无占位符的反引号仓内路径都必须存在——不留「只查第一个」的口子（防止声称两个落点、只验一个）。

**X3**：删除现行 `PATHBIND_RE.test(body)` 的机械判定，改为 annotations 内 `x3Done`（AI 判，同 triCheckDone 模式）；criteria.md §3.3b 同步标注「X3 = AI 判」。

## 6. 验收标准（全部实跑，写进 plan 的验收 Task）

> **预期与实测不符时的裁决规则（写进 plan Global Constraints，防 executor 宽松处理）**：实测结果 ≠ 本节预期 → 先定性——**预期错**（判据正确、场景理解错）→ 修正本节预期并留痕；**判据漏**（该红的没红 / 该绿的没绿）→ 收严或修正判据（词表改动回 Task 3 同批）。**两条路都不许「改判据凑预期」，更不许看到意外绿就默默接受**——意外绿且查无判据依据 = 判据漏，走第二条路。

1. **修前红基线**：score.mjs 判据改完、core 未修、模板未加节时：`node score.mjs --file rules/core-working-principles.md --cognitive` → **X2 fail**（无绑定声明，必红）；X1 预期 fail（现状零反引号路径、「随任务记录可查」无合法动词/载体——实测已核：当前 core 全文无反引号 span）；X3 依赖 Task 2 的 x3Done 标注，若 Task 2 已先行则过、未先行则此步只看 X1/X2。
