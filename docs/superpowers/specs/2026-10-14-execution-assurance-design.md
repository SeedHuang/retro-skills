# 执行保障设计：让「定了的行动点」真正执行到

> 状态：已定稿（2026-10-14）｜路径：Architectural｜来源：用户当场指令（2026-10-14 对话）
> 本文是「认知动作执行不到 + 判据盲区」的解决方案设计。

## 1. 背景与问题

**现象**：规则里写着「动手前先画全貌」「列全同族」「先深度思考」，但实际处理问题时这些动作经常被跳过——不是不想做，是**做了没做根本看不出来**。

**根因**：规则的动作分两类——

| 类型 | 定义 | 例子 | 可检查性 |
|---|---|---|---|
| 机械动作 | 有外部行为触发，做了有可观测效果 | 提交前跑 lint、测试 stuck 时跑替代验证 | ✅ 有产物（命令输出），没做抓得到 |
| 认知动作 | 脑内活动，无外部产物 | 画全貌、列同族、深度思考、自省、追根、算账 | ❌ 无产物、无核销，条件满足也可能被惯性带跑 |

**判据盲区**：rule-inspector 的执行力度 8 项（极性/动作具体/适用条件/来源覆盖/冲突裁决/例外从严/触发机制/验证闭环）全部评估的是**规则文本可执行性**（写没写清极性、触发时机、验证小节），**不评估「规则动作在运行时会不会被真正经过」**。铁证：core-working-principles 拿 24/25 健康，但执行缺口（认知动作无产物、触发在应激时刻、依赖无校验、没挂必经路径）一个没被扣分。**评分高 ≠ 执行到**。

**触发→动作鸿沟**：判据的「条件触发」模型是 `if(E) => A`（原子假设：E 可观测即 A 会执行）。该假设对机械动作成立（E 发生大概率会走），**对认知动作不成立**（E 发生了也可能被惯性带跑）。判据只验证了 E 可观测（⑦ 触发机制），没验证「E 满足后 A 是否被强制经过」。

## 2. 目标与非目标

**目标**：
1. 判据体系加「执行保障」维度，评估「认知动作型规则的动作是否声明了产物 / 必经路径 / 触发前置」。
2. 给认知动作造「产物化」样板（修复前同族清单 + 逐项核销），挂进既有必经路径。
3. 两条核心规则（core-working-principles / how-i-must-reason）补执行保障声明，重评验证。

**非目标**（诚实边界）：
- 不承诺 100% 机械验证「agent 真执行了」——产物化把缺口压到最小，最后一层靠「产物核销」（有产物才能查），执行者仍是 agent/用户。
- 不做「工具自动枚举同族」（AST/代码搜索可辅助「分支路径/读写处」，但「调用点/语义同族」靠判断）。

## 3. 方案设计

### 3.1 判据升级：执行保障维度（仅认知动作型规则适用）

**认知动作 vs 机械动作判定（AI 判，同三检验模式）**：
- 机械动作：动作有外部行为触发、做了有可观测效果（跑命令/写文件/调用）——不适用执行保障维度。
- 认知动作：动作是脑内活动、无外部产物（画全貌/深度思考/自省/追根/列同族/算账）——适用。

**三个检查点（每项 1 分，AI 判 + 正则辅助）**：

| # | 检查点 | 判定 | 处方 |
|---|---|---|---|
| X1 | **动作产物化** | 认知动作是否声明「可观测产物」（清单 / 确认块 / spec 文件 / 输出块） | 补产物声明：动作完成后留下什么可查 |
| X2 | **必经路径绑定** | 动作是否声明挂进既有必经路径（skill 核销步骤 / 流程检查点） | 补绑定：挂进哪条核销步骤 |
| X3 | **触发前置** | 触发点是否在应激时刻（被质疑 / 出错时）；是则需「前置显式化」声明才给分 | 应激时刻触发 = 需前置显式化（任务开头先声明） |

**判定方式**：X1/X2/X3 的「声明」用正则匹配（产物 / 清单 / 核销 / 必经 / 确认块 / 前置 等词）+ AI 判认知动作类型。认知动作类型判定 AI 标注（同三检验/单判据模式，脚本只接收）。

**认知动作是叠加轴，不与现有双轴互斥**：现有类型 = 适用方式（持续/条件触发/模式门控）× 极性（禁令/义务）。认知动作轴独立：规则被 AI 判为「含认知动作」（任一关键动作是脑内活动、无外部产物）时，执行力度组**追加** X1/X2/X3 三个检查点（满分 +3）；判为纯机械动作的规则不追加。两条规则（core-working-principles / how-i-must-reason）均为认知动作型。

**满分口径变化**（§3.5）：认知动作型规则执行力度组 +3（X1/X2/X3 适用），机械动作型不加。满分表更新见 §5。

### 3.2 认知动作产物化样板：修复前同族清单 + 逐项核销

挂进 review-loop 修复纪律（loop.md A1），作为「列全同族」的可检查化：

**第 1 步 · 修复前，先输出「同族清单」（强制产物）**，按固定维度枚举受影响位置：

| 维度 | 要问的 |
|---|---|
| 分支路径 | 这个逻辑的所有 if/else / switch / early return 分支都覆盖了吗 |
| 调用点 | 谁在调用这个函数/逻辑？每个调用方都影响吗 |
| 读写处 | 同一个字段/参数的所有读写位置 |
| 边界 | 空值 / 不存在 / 越界 / 取反 等边界路径 |

**第 2 步 · 修复后，对照清单逐项核销**：每项标「已处理 / 不适用（理由）」，清单上有没处理的必须给理由。

**第 3 步 · 绑定必经路径**：挂进 review-loop 锁基线核销——「没有同族清单 + 核销记录 = 修复不算完成，不锁基线」。

产物：`review-loop/assets/fix-checklist-template.md`（输出用模板）。

**用 tracked 案例验证**：第 11 轮修 tracked 时先列同族清单（分支路径维度 → 追加分支 + 创建分支），创建分支就不会漏。

### 3.3 两条规则补执行保障声明

**core-working-principles**（事前三步，认知动作）：
- 产物声明：「动手前先输出『全貌确认』块（本质/同族/边界/验收/影响面 + 联动四问答案）」
- 必经路径绑定：「全貌确认块是动笔前必经，未输出不得动笔」

**how-i-must-reason**（回答前验证，认知动作）：
- 产物声明：「回答带断言的结论时，附可复核来源（文档位置 / 命令输出 / 源码行号）」
- 必经路径绑定：「回答前必经验证自检，产物缺失 = 未完成」

## 5. 评分口径变化

- 认知动作型规则：执行力度组满分 +3（X1/X2/X3），§3.5 满分表加「认知动作」行。
- 机械动作型规则：不加检查点，满分不变。
- 既有认知动作型规则重评会因缺 X1/X2/X3 声明而掉分 → 补声明后回涨（这正是「让规则执行到」的驱动）。

## 6. 验证方式

1. `node skills/rule-inspector/scripts/score.mjs` 全量重评：确认执行保障维度生效、两条规则补声明后分数。
2. review-loop 相关测试（如有）通过；check.mjs 0 findings。
3. tracked 案例回归：按新清单流程走一遍，确认创建分支不再漏。

## 7. 与现有机制的关系

- 单源：判据权威仍在 `criteria.md`（§3 扩展），writing-guide 不复制判据全文。
- 层级：执行保障是执行力度维度的扩展组，不新增独立评分维度（保持「执行力度 8 项 + 执行保障 3 项」合并计算，认知动作型满分相应 +3）。
