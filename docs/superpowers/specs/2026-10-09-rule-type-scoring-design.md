## 0. 背景与动机

| # | 问题 | 证据 |
|---|---|---|
| 1 | **判据没有「规则类型」维度**——执行力度 8 项按「硬禁令模板」设计，机械代理认死措辞（在…时/开工时/只有…才算/不因来源），模式门控规则的语言（模式开关/这条消息…控制/唯一豁免/不得↔禁止）全部识别不出 | 实测（2026-10-09）：global-ask-before-acting 重写后机械评分 16/24（执行力度 2/8、标题 2/4），8 个失败项中 6 个是代理假阴性，仅 ⑤⑧ 是真缺口 |
| 2 | **类型判定是语义归类，该 AI 做、脚本只该接收**——此前担心「脚本不能判类型」是伪问题；正确分工 = AI 先判类型，作为输入传给脚本（同 `triCheckDone`），脚本只做机械计算 | 用户裁决：「AI 应该先判断是哪种模式，再用对应的评分标准，script 只管到输入，然后计算分数」 |
| 3 | **分数语义需澄清**——分数是「每种类型还缺多少检查点」的缺口指示器，不是横向质量排名；跨类型不可比，只同类型比 | 用户裁决：「2/3、2/24 这些告诉我还有多少需要补，并不代表谁比谁更差，硬要比只能同类型比较」 |
| 4 | **类型专属检查点该补**——模式门控是一台状态机，现有检查点量的是「一条禁令写得好不好」，量不到「状态机全不全」 | 用户裁决：需要补，且不必做细颗粒度横向对比 |

## 1. 双轴模型（规则类型 = 适用方式 × 极性）

**两个正交轴，一条规则各取一个值。**

### 1.1 适用方式轴（3 值）——规则怎么被触发/适用

| 值 | 定义 | 特征 |
|---|---|---|
| **持续适用** | 无条件、无触发时机，任何时候都适用 | 无「在…时/开工时/落地后」类条件与时机词；通用型禁令或纪律 |
| **条件触发** | 由特定条件/事件/时机触发，触发一次执行一次 | 有明确触发条件（编辑时/开工时/落地后/测试 stuck 时） |
| **模式门控** | 有一个**持久的模式状态变量**，规则一直在线，按当前模式裁决同一动作；状态切换是独立的转移逻辑 | 含「模式/适用/退出/回到/重新适用」等状态转移描述 |

> 模式门控与条件触发的本质区别：条件触发 = `if(事件E) => 动作A`（一次性，事件不发生则规则不存在）；模式门控 = 持久 `state`（跨时刻延续）+ 按当前 state 裁决同一动作 + 独立的 state 转移逻辑（如红绿灯：灯色是状态，走不走按灯色，灯色切换是信号系统的事）。

### 1.2 极性轴（2 值）——规则要求做还是不做

| 值 | 定义 | 判定词（封闭词表） |
|---|---|---|
| **禁令** | 要求**不做** | 禁止/不得/不要/严禁 |
| **义务** | 要求**做** | 必须/应/要/一律 |

> 「规范」不是极性，是体裁——以「约定/标准长什么样」形式写的规则；写成「必须做 Y」= 义务，写成「禁止做 Z」= 禁令。
> **极性必须单一**：一个文件一个核心判据、一个极性。混合极性（同一文件既有禁令句又有义务句且无单一核心判据）= 结构缺陷，该拆（见 §7 parking「单判据」）。
> **判定词是封闭词表**：规则正文极性一律用表内词，不引入表外词（不允许/不可/切勿等 → 读懂语义后归一成表内词）。rule-writer 写/改规则时强制归一；inspector 体检发现表外词 → 给处方（换表内词），改动按硬闸门 2 确认后落地。

### 1.3 澄清：此前的「4 类型」是跨乘结果

此前口头分类「硬禁令 / 模式门控 / 事件触发 / 正向义务」**不是同一层的 4 类**，是两轴的跨乘结果：硬禁令 = 持续或条件 × 禁令，事件触发 = 条件 × 义务，正向义务 = 任意 × 义务。真正新增的第三种**适用方式**只有「模式门控」。本 spec 以双轴为准。

## 2. 类型判定流程（AI 判，脚本只接收）

### 2.1 判定责任与传递

- **类型判定是 AI 的职责**（语义归类），在体检流程中完成，作为输入传给 `score.mjs`（`opts.type`，同 `triCheckDone` 模式）。
- 脚本**不做**类型归类；只按收到的 type 选检查点、机械算分。确定性保持（同输入必同输出）。
- 判出的类型写进体检报告（可复算证据）。

### 2.2 适用方式判定线索（判定顺序：门控 → 触发 → 持续）

| 判定为 | 线索（正文/标题出现即优先） |
|---|---|
| 模式门控 | 含「模式 / 适用 / 退出 / 回到 / 重新适用」等状态转移描述，或明显按「某条消息/某状态」裁决同一动作 |
| 条件触发 | 含「开工时 / 落地后 / 编辑时 / …时 / …后 / …前」的时机或条件标记 |
| 持续适用 | 以上皆无，规则无条件持续适用 |

### 2.3 极性判定

| 判定为 | 线索 |
|---|---|
| 禁令 | 正文含「禁止 / 不得 / 不要 / 严禁」 |
| 义务 | 正文含「必须 / 应 / 要 / 一律」且无禁令词 |
| 混合（缺陷） | 既含禁令词又含义务词，且无单一核心判据 → 按 §7 parking 处理（该拆） |

> 判定词封闭：正文极性词应全在表内；出现表外词（不允许/不可/切勿…）= 该归一的缺口（规则优化时处理，见 §7）。

## 3. 各类型检查点归属 + 满分口径

### 3.1 通用 16 项（所有类型共用，不变）

头部规范 3 + 层级规范 2 + 来源精简 2 + 引用完整 1 + 冗余度 4 + 标题 4 = **16**。

### 3.2 执行力度适用项表（类型 × 极性 → 适用检查点）

| 类型 | 极性 | 执行力度适用项 | ③⑦ 口径 | 执行力度组 max |
|---|---|---|---|---|
| 持续适用 | 禁令 | ①②④⑤⑥⑧（③⑦ 不适用） | — | 6 |
| 持续适用 | 义务 | ①②⑧（③④⑤⑥⑦ 不适用） | — | 3 |
| 条件触发 | 禁令 | ①②③④⑤⑥⑦⑧ | ③=触发条件明确；⑦=有可观测时机词 | 8 |
| 条件触发 | 义务 | ①②③⑦⑧（④⑤⑥ 不适用） | 同上 | 5 |
| 模式门控 | 禁令 | ①②③④⑤⑥⑦⑧ + 模式专属 6 | ③=模式归属可判定；⑦=切换信号可观测 | 14 |
| 模式门控 | 义务 | ①②③⑦⑧ + 模式专属 6 | 同上 | 11 |

> ④⑤⑥ 仅禁令类适用（沿用 Spec A §2.4 禁令类判定：正文含禁止/不得/不要/严禁）。不适用项**不计入满分**。

### 3.3 满分 = 通用 16 + 执行力度适用项 + 类型专属

| 类型 × 极性 | 满分 |
|---|---|
| 持续适用 · 禁令 | 22 |
| 持续适用 · 义务 | 19 |
| 条件触发 · 禁令 | 24 |
| 条件触发 · 义务 | 21 |
| 模式门控 · 禁令 | 30 |
| 模式门控 · 义务 | 27 |

### 3.4 模式门控 6 个专属检查点（每项 1 分，AI 判）

| # | 检查点 | 判定（查什么） | global-ask 对照 |
|---|---|---|---|
| M1 | **状态集合完整** | 定义了规则管辖的全部模式（≥2 态）；漏一态 = 该态下规则没交代 | 沟通 + 执行，两态齐全 ✓ |
| M2 | **每状态行为明确** | 每个状态都规定了动作裁决（该态做/不做）；空态 = 0 | 沟通→只回应不写；执行→放行 ✓ |
| M3 | **切换判据明确** | 状态转移由可观测信号驱动，无「感觉/大概/酌情」 | 「这条消息是不是用户主动发起的对话」控制 ✓ |
| M4 | **回到逻辑完整** | 有「退出 → 重新适用」回转路径；单向退出 = 规则形同失效 | 执行中用户再发消息 → 回沟通 ✓ |
| M5 | **模式边界封闭** | 每态覆盖情形可判定、不用执行者做语义归类（防掠过） | 「提问/讨论/给意见/等决策」枚举 ✓ |
| M6 | **退出后由谁接管** | 规则让位时指明动作按什么管；退出不留空档 | 「按具体领域规则管（如 no-git-write）」✓ |

> 判定方式：这 6 项查「状态机完整性」，靠 **AI 判**（同三检验报告），每项 0 分进 findings 并给处方。类型本身是 AI 标注，检查点同源。

## 4. 计分与级别（复用 Spec A §2.4）

- 每检查点 1 分；满分 = 该类型适用检查点数（§3.3）；得分率 = 得分 ÷ 满分。
- 级别：健康 ≥90% / 预警 70–89% / 不及格 <70%。
- **只同类型比较**，跨类型不比（不同类型满分不同是设计使然）。
- 分数 = 缺口指示器：告诉「这种类型还差哪几个检查点」，全满足 = 合格。

## 7. 明确不做 / parking

- **「单判据」检查点**（一个文件一个核心判据；code-style 类多判据该拆）——所有类型通用的**结构**检查，与类型评分正交，**另定 spec**，不在本 spec 动作里。
- **code-style 拆分**——属规则修订，**待用户决定**（拆成 3 条独立规则），不在本 spec 动作里。
- **事件触发「触发后闭环」检查点**（触发→该做什么→收尾/验证）——当前 7 条条件触发规则样本足够但缺口不痛，**暂不补**，等体检暴露真缺口再说。
- **类型专属检查点的自动判定**——类型与 M1–M6 均 AI 判，脚本不判语义；不引入外部打分器。
- **旧规则判定词归一与优化**——表外极性词经 rule-writer 优化时归一成表内词（rule-writer 是写规则的，自然也改规则）；旧规则整体优化由用户单独发起（一次一条，rule-writer 流程 + 硬闸门 2 确认），不在本 spec 动作里。
