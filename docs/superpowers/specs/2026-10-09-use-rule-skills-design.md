# use-rule-skills 入口技能设计（入口编排 + rule-writer 纯粹化 + 草稿箱）

> 上承：Spec A `2026-10-09-rule-suite-design.md`（rule-inspector + rule-writer 判据体系）｜`2026-10-09-rule-type-scoring-design.md`（类型感知评分）｜用户当场设计讨论（2026-10-09，本文 §3 草稿箱交互经多轮悖论/盲点收敛）。

## 0. 背景与目标

三个问题驱动本设计：

1. **rule-writer 职责不纯**：它内置了 inspector 评分（步骤 4）+ 二次审查循环（步骤 6）——"写作"和"验收循环"混在一起。再做入口串联就重复。
2. **草稿位置不合理**：草稿曾放 `.superpowers/`（retro-skills 项目的 git-ignored 工作区）——打包给别人时 `.superpowers` 不存在，草稿无处安放。
3. **判据知识多处复制**：判定词封闭表 / 来源类型枚举 / 标题三句在 criteria.md 与 writing-guide.md 各有一份 → 漂移（B 批次给 criteria 加了冗余度/判定词封闭，writing-guide 自查表漏了冗余度——用户当场发现）。

**目标**：新建入口技能 `use-rule-skills` 承担"意图判定 + 流程编排 + 草稿箱 + 报告"；rule-writer 纯粹化为"只写作"；判据知识单源收敛到 criteria.md。

## 1. 职责划分（三分）

| 技能 | 职责 | 不做 |
|---|---|---|
| **use-rule-skills**（新） | 入口路由（判意图）+ 两路径编排（起草→评分→循环→报告）+ 草稿箱管理 + 采纳落地 | 不写判据正文、不评具体分数 |
| **rule-writer**（纯粹化） | 起草（四要素）+ 自查（执行力度 8 + 冗余度 4 + 判定词归一 + 标题三句）→ 产出**草稿** | **不再跑 inspector、不再自带循环**；SKILL.md 明写"产出草稿，验收/循环走 use-rule-skills" |
| **rule-inspector**（基本不动） | 评分（score.mjs）+ 判据权威（criteria.md） | 不管对比、不管草稿 |

**循环和对比是入口的职责，不是写作者的。**

> **自查 ≠ 跑 inspector**：rule-writer 的"自查"是写作期 AI 对照判据清单（执行力度 8 + 冗余度 4 + 归一 + 标题三句）的自检，主观、不产分数、不跑任何脚本；客观评分由入口调 rule-inspector 兜底（`--file` 单文件，见 §9.1）。两者不同，不矛盾。

## 2. 入口路由（意图判定）

| 调用形态 | 判定 |
|---|---|
| 显式「新建 / 我要建 rule」 | 新建 |
| 带路径 /「帮我优化这个 rule」 | 优化（路径指向 `my-rules/rules/<name>.md`） |
| 裸调用（什么都没说） | **默认新建** |

## 3. 草稿箱管理（经悖论/盲点收敛后的最终版）

### 3.1 位置与脚本

- **位置**：`<用户目录>/.retro-skills/rule-drafts/`（`os.homedir()` 解析，跨平台；Windows = `C:\Users\<名>\.retro-skills\rule-drafts\`）。
- **脚本**：`use-rule-skills/scripts/drafts.mjs`，三个子命令：
  - `drafts ensure` —— **幂等**：目录存在则跳过，不存在则新建（含父级 `.retro-skills`）。入口每次运行第一步必跑。
  - `drafts ls [规则名]` —— 列出草稿；可按规则名过滤；**按文件名时间戳倒序**；每行显示 `<名字>（创建 <时间>）`。
  - `drafts rm <草稿>` —— 删除指定草稿。
  - `drafts rm --rule <规则名> [--keep <草稿>]` —— 按规则删除：不带 `--keep` = 删该规则名下所有草稿（采纳清箱、答"不用"全删）；带 `--keep <草稿>` = 保留指定草稿、删其余（"删其余"场景用）。

### 3.2 命名约定

```
<规则名>--<YYYYMMDD-HHMMSS>.md
```

- **优化路径**：规则名 = 现有文件名（如 `global-ask-before-acting--20261009-1830.md`）。
- **新建路径**：规则名未定 → 用主题 slug 占位（落地时才定正式文件名）。
- 一规则可多草稿（时间戳区分、可排序）；`--` 分隔安全；符合 kebab-case（无中文/空格）。

### 3.3 入口交互（唯一识别机制 = 用户选择）

**入口不自动认领任何草稿**——识别权全给用户。时间戳只用于排序展示，绝不用于自动选择（"最新的"不自动用；出现更新的草稿只是排前面，用不用由用户决定）。

```
入口处理规则 X：
  drafts ls X：
  ├─ 无草稿 → 直接新建
  └─ 有（N 个，全部列出，带创建时间）→ 问「是否继续使用？」
       ├─ 选了一个 → 续用（保留它）；若 N>1 再问「删除其余的？」
       │    ├─ 是 → 删除该规则名下【除选中的之外】的所有草稿（`drafts rm --rule X --keep <选中>`）
       │    └─ 否 → 都留着
       └─ 不用 / 新建 → 删除该规则名下所有草稿，重新建
```

### 3.4 生命周期与删除规则

| 时机 | 动作 |
|---|---|
| 入口启动 | `drafts ensure`（幂等建目录） |
| 发现旧草稿 | **永不静默删**：列出（带时间）→ 问继续/不用（见 3.3） |
| 采纳落地 | 删除该规则名下所有草稿；**删前提示一次**「将删除该规则名下所有草稿，要保留的先移出草稿箱」→ 用户确认后删 |
| 多草稿收敛 | 选续用 → 答"删其余"= 删除除选中外的全部；答"否"= 保留 |

**硬约束**：
- 删除永不静默（有草稿必问；采纳删除必确认）。
- 无哈希/归属机制（内容一动哈希就变，无法当身份确认用——已否决）。
- 采纳删除按规则名 scope（只删该 rule 名下草稿，跨 rule 不动）。

## 4. 新建路径流程

```
1. 收需求        用户先写出他想表达的 rule 内容（需求原文）
2. 澄清四要素     AI 明确范围/条件/动作极性/宾语四要素的内容；只问真正缺的、一次一个、
                  给 2-3 推荐选项 + 自定义出口（不逐字段盘问）
3. 草稿箱交互     drafts ensure；草稿名 = 主题 slug + 时间戳；有同主题旧草稿 → 按 §3.3 交互（继续=选一个 / 删掉重生成 / 取消）
4. 起草 + 自查    rule-writer 按已澄清的四要素落成规则文档 + 判定词归一 + 标题三句 + 冗余度自查（产出草稿，不跑 inspector）
5. 评分           use-rule-skills 调 inspector 对草稿评分
6. 异常循环       有 findings → 逐项：现状 + 推荐修改方案 / 用户自定义 → 改 → 再评
                  → 核销干净（0 findings）或用户明确接受残留
7. 报告           入口报告（意图/评分明细/改动清单/落地结论；新建无"改前"，对比段写"不适用"）
8. 落地           确认最终 rule 名 → 写 my-rules/rules/ + aas sync → 删该 rule 名下所有草稿（删前提示，见 §3.4）
```

## 5. 优化路径流程

```
1. 先诊断         use-rule-skills 调 inspector 对现有规则评分 → 处方（findings）
2. 草稿箱交互     drafts ls <rule>：
                   无 → 直接起草
                   有（列带时间）→ 问「继续 / 删掉重生成 / 取消」（3.3）
3. 起草修订版     rule-writer：按处方 + 四要素 + 归一 + 标题三句 + 冗余度（产出草稿）
4. 评分 + 异常循环  同新建（改 → 再评 → 核销干净或用户接受残留）
5. 报告           入口报告：评分明细 + 【before/after 对比表】+ 改动清单 + 落地结论
6. 落地           写 my-rules + aas sync → 删该 rule 名下所有草稿（删前提示，见 §3.4）
```

## 6. 报告模板（use-rule-skills/assets/report-template.md）

新建与优化共用骨架，优化多"对比"段：

```
# 规则（新建/优化）报告 · <规则名>

> 路径：新建 ｜ 优化（源：my-rules/rules/<规则名>.md）
> 草稿：<草稿文件名>（新建 / 续用 / 删旧重生成）

## 一、最终评分（inspector）
类型：<适用方式 × 极性>｜满分：<N>｜得分：<X>/<N>｜得分率：<r>｜级别：<健康/预警/不及格>
组 Summary 表（头部/层级/来源/引用/冗余度/单判据/执行力度/模式专属/标题）

## 二、优化前后对比（仅优化；新建写"不适用"）
总览：<X1>/<N1>（<r1>，<级别1>）→ <X2>/<N2>（<r2>，<级别2>），涨 <+Δ> 分
| 维度（总分/得分率/级别/各组） | 优化前 | 优化后 | 变化 |
逐项修复：| 检查点 | 改前 | 改后 | 变化 |

## 三、改动清单（改前 vs 改后）
| # | 改动 | 改前 | 改后 | 类型（判据措辞-已确认 / 判定词归一 / 新增小节） |

## 四、落地结论
- 落地：my-rules/rules/<规则名>.md + aas sync ✓ / 待确认
- 草稿：已删除 / 保留
- 残留 findings：无 / 用户接受：<清单>
```

**设计要点**：
- **涨/掉都列**，不藏负变化（某项下降要明示）。
- 对比两层：总览（总分/得分率/级别/组）+ 逐项修复（检查点 0→1）。
- **数字必须实测**（inspector 跑出来的真数，不是估算）；不附取数命令（报告是摘要，不是操作手册）。
- 改动清单"类型"列对应硬闸门：判据措辞类标"已确认"（落地前提），归一/新增小节不改变判据。

## 7. 单源抽取：判据知识收敛到 criteria.md

| 知识 | 现状 | 收敛后 |
|---|---|---|
| 判定词封闭表 | criteria §2.4/§3.1 + writing-guide §二 各一份 | **只留 criteria**；writing-guide 引用节号，不复制表格 |
| 来源类型枚举 + 来源行模板 | criteria + writing-guide §三 | **只留 criteria**；writing-guide 引用 |
| 标题一致性三句 | criteria §2.4 + writing-guide §四 | **只留 criteria**；writing-guide 引用 |
| 冗余度 4 项（自查版） | criteria §2.4 有；writing-guide 自查表漏了 | criteria 权威；**writing-guide 自查表补上冗余度 4 项**（引用 criteria） |

**做法**：criteria.md 唯一权威；writing-guide 只写"写作怎么落地"（引用节号 + 简短提示），不复制判据表格全文；报告模板只引用数据不内嵌判据定义。criteria 改动后跑 grep 核销（writing-guide/README 无残留旧表格）。

## 8. rule-writer 纯粹化改造（同批次）

- **SKILL.md**：去掉步骤 4（inspector 评分）与步骤 6（二次审查重跑）；流程改为「1 需求澄清/处方确认 → 2 起草 → 3 自查（执行力度 8 + 冗余度 4 + 归一 + 标题三句）→ 4 交付草稿」；**明写"产出是草稿，验收/循环走 use-rule-skills"**（防止单独直用 writer 拿到未验收草稿而不知）。
- **writing-guide.md**：自查表补冗余度 4 项；判据表改引用 criteria（§7）。

## 9. 落位与打包

### 9.1 落位

```
skills/use-rule-skills/
├── SKILL.md                 # 入口路由 + 两路径流程 + 草稿箱交互
├── scripts/drafts.mjs       # ensure / ls [rule] / rm（os.homedir() 定位）
├── assets/report-template.md
└── references/              # 路由判定规则 + 流程口径
skilldependencies/use-rule-skills.json   # 依赖 rule-inspector + rule-writer
skilldependencies/manifest.json          # skills 数组更新
skills/rule-writer/          # 纯粹化改造（同批次，§8）
```

**硬约束**：新增技能必须登记 manifest（validate 防漏测试同步）；**必须 `aas sync`**（否则运行时无链接 = 未生效，L-020 教训）。

**工具补强（对单草稿评分）**：score.mjs CLI 增加 `--file <path>`（单文件评分）+ `--rules-dir <dir>`（规则库目录，评分草稿时必给）。理由：草稿箱是多规则混合目录，入口对单个草稿评分不能用 `--dir`（会误扫全部）；`--file` 只评指定文件。`--rules-dir` 供跨规则引用检查（crossRuleMiss）：评分草稿时须指规则库 `my-rules/rules`，否则草稿在草稿箱、引用会全部误判；评分现有规则时可不给（默认 `dirname(file)`=规则库）。配测试覆盖（`--file` 输出 = scoreFile 输出）。

### 9.2 打包给别人用

- 交付物 = 整个 retro-skills 仓库（skills + skilldependencies + docs）。
- 对方：node + aas；clone 后 `aas sync` 建链接。
- **草稿箱不打包**——每台机器自己的运行时数据，首次运行 `drafts ensure` 自动建。
- `my-rules`（规则库）独立仓库，按需一起交付。
- `drafts.mjs` 用 `os.homedir()` 解析用户目录，不硬编码路径。

## 10. 验收标准

1. `use-rule-skills` 技能建好：SKILL.md（路由 + 两路径流程）+ drafts.mjs（ensure/ls/rm 可运行）+ 报告模板 + references；manifest 登记；`aas sync` 后运行时链接存在。
2. `drafts.mjs`：`ensure` 幂等（首次建目录、二次跳过）；`ls` 按时间倒序带创建时间、可按规则过滤；`rm` 删除指定草稿。
3. 草稿箱交互符合 §3.3/§3.4（有草稿必问、选续用保留选中、答删其余只删非选中、不用则全删、采纳删前确认）。
4. 新建路径：四要素补全只问缺项、给选项 + 自定义；产出草稿 → inspector 评分 → 异常循环 → 报告 → 落地。
5. 优化路径：先诊断现有规则 → 草稿 → 评分循环 → 报告含 **before/after 对比表**（总分/组/逐项，涨掉都列）→ 落地。
6. rule-writer 纯粹化：SKILL.md 不再含 inspector 步骤、注明"产出草稿"；writing-guide 自查表含冗余度 4 项。
7. 判据单源：判定词表/来源枚举/标题三句只在 criteria.md 定义；writing-guide 只引用（grep 核销无复制表格残留）。
8. 无回归：rule-inspector 测试全量通过（validate + score；当前 46 条，随 `--file` 新增会 +N）；基线可重跑。

## 11. 明确不做（parking）

- **不自动认领草稿**（无哈希/会话归属机制）——识别权全在用户（§3.3）。
- **草稿箱不做搜索/标签/归档**——ls/rm 足够，YAGNI。
- **rule-inspector 报告模板不加对比段**——对比是入口职责，inspector 保持纯粹。
- **不做自动删冗余**——语义冗余由 AI 三检验 + 用户确认（沿用硬闸门）。
- **不把草稿箱塞进 my-rules 仓库**——用户目录是运行时数据，随仓库交付的是技能不是草稿。
