# review 分支方案设计（review-loop 进化 spec）

> 目标：根治 L1（全量重审、审查面只增不减）——用 review 分支给每一轮一个 git 基线，
> 让下一轮 OCR 只审「上一轮之后的新增 diff」，而不是全部未提交改动。
> 关联分析：`2026-10-10-config-layering-review-accounting.md`（18 轮案例，L1 实锤）
> 演进：本文件整合用户裁决（例外前置条款 / rebase 合并 / 暂不支持并行）。

---

## 一、总流程（一张图看懂）

```
触发 review 命令（review-md-to-death / review-code-to-death / review-all-to-death / 一切走 review-loop 的功能）
  ↓
① 入口守卫：查有没有残留的 review 分支
  ├─ 有 → 阻塞式询问「是否删除残留分支 xxx」→ 删 or 终止本次 review
  └─ 无 → 继续
  ↓
② 建 review 分支 + 记母分支名
  ↓
③ 循环（每轮）：
    审增量 diff（上一轮 commit 之后）
    → agent 修
    → commit 到 review 分支（message 带 【review】标记）
    → 记 commit hash 进 progress
    → 回到 ③（下一轮）
  ↓
④ 收敛判定：**按 loop.md §1 停机判据** —— 修复轮 + 复查轮都清单核销干净才收敛（P0/P1/采纳 P2 = 0；**不是**「连续 2 轮 ≤2 条」这种轮数/条数阈值——轮数不是停止条件，判据详见 review-loop 技能 `references/loop.md` §1）
  ↓
⑤ 收尾：
    展示 review 分支相对母分支的全部改动 → 用户确认
    → rebase 合回母分支 → 删除 review 分支 → progress 记「已合并删除」
```

## 二、分支命名与记账

| 项 | 规则 | 说明 |
|---|---|---|
| review 分支名 | `review/<yyyyMMdd-HHmm>-<短摘要>` | 带日期防撞车（同名 review 不同日期不会冲突） |
| 母分支名 | 触发 review 时的当前分支 | 必须记进 progress.md |
| 记账位置 | `.session/reviews/<id>/progress.md` | 每轮结束时补两行：本轮 commit hash + 分支名 |

**入口守卫的检查方式**：不靠猜，直接列 `git branch --list 'review/*'` + 查 reflog。
判断「是否已在 review 分支上」：`git branch --show-current` 开头是 `review/` 就算。

**不支持并行（用户已拍板）**：同一时间只允许一个 review 运行。
因此触发时只要出现 `review/*` 分支，一律视为残留 → 阻塞。技能执行中不会重复触发，无需活跃登记表。

## 三、每轮 commit 约定（关键）

### message 格式

```
<标准前缀>: 【review】<改动摘要>

- 第 N 轮修复 OCR 评论 x 条
```

- **前缀**：按改动性质选（Conventional Commits：`feat:` / `fix:` / `refactor:` / `test:` / `docs:` 等）
- **【review】**：固定标记，必须紧跟「冒号空格」后出现，保证 review 分支的提交一眼可辨、可 grep
- **正文**：写明这是第几轮、修了几条（与 progress 轮次账对应）

### 范围边界（必须遵守）

每轮 commit **只 add 本次审查清单里的文件**（progress「范围」一节列出的那批），
**禁止 `git add -A`**——否则会把工作区里「与审查无关的改动」（用户 review 期间自己改的别的东西）卷进分支，合并时污染母分支。

### 顺序约束（写死）

每轮收尾必须是：**commit → 记 hash → 下一轮**。
OCR 的 workspace 模式审的是「HEAD vs 工作区」的 diff——只有 commit 了 HEAD 才前进，
下一轮 OCR 才只看得到本轮新增。**不 commit = 分支白建 = L1 依然存在。**

**md 模式与 code 模式统一**：md 模式同样多轮重审（agent 每轮重读文档），
同样有「重复审已修部分」的风险（9 轮案例第 8/9 轮同一批问题处置两遍），
因此 md 模式也执行「每轮 commit」——每轮 commit 后 `git diff <上一轮commit>..HEAD`
就是纯增量，agent 只审增量。不分模式、逻辑统一。

### 问提交的边界（严格限定，只此一场景）

**循环过程中的 commit 是流程动作，不许问、不许提示**（沿用禁令原文：提交从来不在 agent 的选项里，
现在它是 review 分支内的流程必需，但「要不要提交」这个问题依然不成立——必须提交，没有要不要）。

**唯一允许问「是否提交/合并」的场景 = 收尾合并回母分支**（第五节）。
其他任何时刻，沿用「不许问要不要提交」。

## 四、git 写权限例外（进 no-git-write 规则）

原禁令：除非用户明确要求，禁止主动 git 写操作。

新增例外，**分两段**（用户已拍板「例外加前置条款」）：

### 段 1：入口动作（建分支前）

当 review-loop 技能声明正在执行入口（建分支）时，**允许创建 `review/*` 分支这一个动作**。
—— 创建发生在进入分支之前，例外条件「在分支上」覆盖不到，必须单独放行这一个动作。

### 段 2：分支内操作（已在 review 分支上）

两个条件同时满足才成立：

1. 当前分支是 review 分支（`git branch --show-current` 以 `review/` 开头）
2. 操作对象属于本次审查的 diff 范围（文件在 `git status` 的本次审查清单内，或操作是收尾流程）

允许的操作：commit、checkout（切回母分支）、branch（建/删 review 分支）、**rebase（仅限 review 分支合回母分支时，用户已拍板）**。

**不覆盖**：push（review 分支不推送远程）、reset、merge 等，除非用户当场点名。
（注：合回母分支用 rebase，故 rebase 是本例外的合法操作；merge 不在此列。）

> 话术（写进规则时的样子）：
> 「在 review 分支上、且操作仅涉及本次审查的代码时，允许 commit、建分支、删分支、
> rebase 回母分支。这是为了给每一轮审查锁基线，是 review-loop 能工作的前提。
> 除此之外，禁令不变。」

## 五、收尾流程（合并 + 删除）

1. **范围预检**：`git diff <母分支>..<review分支>`，只应包含本次审查涉及的文件
   - 超出范围（审查期间混入的无关改动）→ 先单独列出，逐项问用户「这个也合回去吗」
2. **展示 diff + 用户确认**：把改动摘要给用户看，用户点头才合（不自动合）
3. **合并**：切回母分支 → **rebase** review 分支（用户已拍板）
4. **删分支**：合并成功后删除 review 分支，progress.md 记「已合并删除」
5. **异常**：rebase 冲突 → 停下，把冲突文件列给用户，等用户裁决（不擅自解冲突）
   - 用户选择继续 → 由用户口述每个冲突文件的取舍，agent 执行
   - 用户选择放弃本次合并 → `rebase --abort` 恢复原状，改动留在 review 分支不动（不丢不乱），分支暂不删除

## 六、残留分支的阻塞式守卫（用户已拍板）

**规则**：下次触发任何 review 类命令时，先查 `git branch --list 'review/*'`：

- 有残留 → **阻塞**，弹确认：
  > 「发现上次 review 的残留分支 `review/xxxx`，不删掉会越来越多，也没法给本轮锁基线。
  > 是否删除？选「是」删除后继续 review；选「否」本次 review 取消。」
  - 用户选「是」→ 删除 → 继续
  - 用户选「否」→ 终止 review，不降级、不硬来
- 无残留 → 正常开始

**为什么阻塞**：不删 → 下轮又新建一个 → 分支越堆越多 → 且残留分支里的旧基线会污染新 review 的 diff 判断。
（用户坚持此设计：不删就终止，避免分支堆积。）

## 七、实现归属（哪些进技能、哪些进规则）

| 内容 | 放哪 | 理由 |
|---|---|---|
| 建分支、命名、记账（母分支/分支名进 progress） | **review-loop 技能** | 核心执行流程 |
| 每轮 commit（message 带 【review】、范围边界、顺序约束） | **review-loop 技能** | 锁基线实现细节 |
| 残留分支检查 + 阻塞式确认 | **review-loop 技能** | 技能入口守卫 |
| 合并前 diff 展示 + 用户确认 + rebase + 删分支 | **review-loop 技能** | 收尾流程 |
| 「review-loop 入口建分支 + review 分支上限本次审查范围 → 允许 git 写」 | **no-git-write 规则例外** | 跨技能禁令，不写进例外任何技能都会被拦 |

## 八、风险与应对

| 风险 | 应对 |
|---|---|
| review 中途插队切回母分支（单人场景偶发，非并发） | 收尾 rebase 前范围预检，冲突时停下等裁决；abort 兜底保留（保险丝，触发概率低） |
| agent 在 review 分支顺手改了无关文件 | commit 阶段禁止 `git add -A`（范围边界）+ 收尾范围预检双重兜底 |
| 用户手动改名 / 删分支，命名规则失效 | 守卫用 `git branch --list` 全量查，不靠猜；命名撞车靠日期前缀规避 |
| 用户忘了有残留分支就切回母分支 | 下次 review 触发时守卫兜底，阻塞式提醒 |
| 并行 review 被误判残留 | 暂不支持并行（用户已拍板），出现第二个 `review/*` 一律视为残留 |
