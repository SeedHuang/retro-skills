## 0. 失败场景（先立靶子，全部可检验）

| # | 现状拦不住的场景 | 新体系拦截机制 |
|---|---|---|
| F1 | 长文档评审后半程，单 agent 演第 8 个角色时第 1 个角色的必问已模糊 → 漏问无记录 | 每角色独立上下文子代理；必问逐条显式作答（含「问过，无问题」） |
| F2 | 拿旧 skill 审账本类文档：假 ✅、时间失真、计数对不上全数漏网（10-16 报告 N1/N5 实锤） | doc-taxonomy 按类型换关注点 + 点将换主责评委 |
| F3 | 评委只提问题不给解法；答辩「感觉不对」无依据；3 轮吵不完直接丢给用户 | 问题卡 8 字段（缺解法=废卡）+ 答辩三字段 + 升级报告必附双方摸查记录与各自解法 |
| F4 | 想统一改评委特质，要手改 13 个文件、必漏 | 编译式单源：模板+角色数据一处改 → 脚本重新生成 → 守卫逐字比对 |
| F5 | 审计表被主持人代填 / 证据栏空着也「通过」 | 审计两表必由审计员本人实例完成；证据空=不通过；侦探核「假审计」 |

## 2. 三方结构与一次评审的生命周期

```
主 agent（执行议会技能的会话）
 ├─ 主持人（主 agent 兼）       组队、调度、汇总、跑机械计数、维护评审记录
 ├─ 评审团（子代理，12 席花名册） 独立上下文，只读，出问题卡
 ├─ 答辩方（主 agent 扮演）      架构师 leader（7 方向选一）+ 研发 4 人（按文档类型换编制）
 ├─ 观察团（子代理）            侦探 1 名：盯评委刁难 / 答辩回避 / 主持人丢卡压卡
 └─ 审计专员（子代理，评审团席位）标准核对 + 轮际对账 + 终局交付审计

生命周期：Step0 组队（点将矩阵 → 用户确认名单）
        → [评审（并行独立出卡）→ 答辩（≤3 轮）→ 侦探行为核对 → 轮间审计（含轮际对账）] × N
        → 修复与同族扫描 → 终局交付审计 → 呈交用户
```

**权力分置**：侦探只记录、主持人只裁决程序、审计只核标准、技术分歧走答辩、**中断权与终裁权只在用户**。

## 4. doc-taxonomy（8 类 × 四列，references/doc-taxonomy.md 正文）

| 类型 | 判据一句话 | 评审关注点（主责评委） | 完成判据（终局审计 B 节） |
|---|---|---|---|
| spec | 已定稿设计文档 | 逻辑闭环、无第二份真相、失败面画全（前端+后端+审计） | Backlog 三表齐、P2 全落态、P0/P1=0 |
| plan | 排期的执行步骤 | 步骤原子、依赖顺序、验收与 spec 对齐（测试+后端） | 勾选框全终态、每任务有验收命令 |
| rule | 条文化约束 | 13 病根表：在必经路上/判据可判定/执行留痕/冲突裁决/例外从严（AI+审计） | 触发时机+验证节存在、可证伪 |
| skill | 流程方法文档 | 读→产出闭环、路径纪律、<500 行、description 只写触发（AI+审计） | check 脚本 0 findings、资产三档合规 |
| agents | 子代理定义（.trae/agents/*.md 或本仓 agents/*.md） | description 具体度、tools 最小化、双清单在位、格式闭环（AI+审计） | frontmatter 合法、生成物与源一致 |
| 描述性文档 | README / guide | 任意章节可进入、术语有定义、与现状一致（读者代表） | 抽查计数/路径与实测一致 |
| 记录型文档 | 账本 / progress / handoff | 手抄数字/时间/✅ 与权威记录一致、处置闭环、引用真实（读者代表+审计） | 计数可复算、无悬空引用、每个 ✅ 有证据 |
| 探索稿 | docs/after | 「未决」标记在位、搬走条件写明（读者代表） | 阶段标记正确、待办可执行 |

硬规矩（assembly-matrix.md 逐条展开）：
1. **最低法定人数 = 覆盖矩阵零缺口**：本文档类型涉及的关注面，被点名者每面有人；缺口 = 名单不合法，不得开始（侦探核漏点）。
2. 主持人出提议名单 → **用户确认后**才开评。
3. 轮间补点必须留痕（第 N 轮补点 X，原因 Y）。
4. 名单 + 轮间变更记录附进最终报告（评审质量对账凭据）。

## 6. agent-template.md（模板全文）与生成契约

### 6.1 模板（生成器占位符用 `{{ }}`，共享段逐字唯一）

```markdown
---
name: {{NAME}}
description: {{DESCRIPTION}}
tools: Read, Glob, Grep
---

# 角色：{{ZH_NAME}}（{{DIMENSION}}）

## 你是谁
{{IDENTITY}}

## 共享特质（所有议会成员同一份措辞，禁止自行改写）
包容、客观、理性、自省、诚实；眼光长远，做正确的事；用最简单、容易理解的方式表达，让非专业人员也能听懂；不空谈，善于把所有事情按极高标准落地；不满足于现状，执行中主动发现问题、判断重要性、给出最合适的判断与处置；采纳周围人的意见，也基于项目长远发展保持自己的主见。

## 固定必问清单（每条必答，"问过，无问题"也要显式记录；缺答 = 不合格）
{{FIXED_LIST}}

## 自由探索（必做，与固定清单同等重要）
固定清单之外，针对这份文档和这个项目的具体情况，现场生成 3-5 个你认为最值得问的问题（先写出来，再逐条回答）。只答固定清单 = 不合格。

## 输出格式
{{OUTPUT_FORMAT}}

## 通用纪律
- 证据可复算：引用文件:行号或命令输出，禁止凭印象断言
- 没问题不制造问题：没问题时显式写「固定 N 条全过，自由 M 条，均无问题」
- 只提问题不给解法 = 无效产出
- 超出职责的事：记录进产出，不自行处置
{{SHARED_BLOCK}}
## 边界
你是只读评审角色：不得创建、修改、删除任何文件；不裁决他人分歧；无中断评审的权力。
```

### 6.2 生成契约

- frontmatter：`name` = 文件名主干（字母开头，仅字母/数字/连字符，≤50 字符）；`description` 只写触发条件（「在议会评审中担任 X。当主持人调度对 Y 做 Z 视角评审时调用」），**不写流程摘要**；不配 `model`（跟随主对话模型）；`tools` 恒为 `Read, Glob, Grep`。
- 共享块（SHARED_QUALITIES / 通用纪律 / 六手法块）在脚本中定义一次，拼进所有用到它的角色——同措辞想漂移都不可能。
- `{{OUTPUT_FORMAT}}`：评委类 = 问题卡格式（源自 assets/issue-card.md，由脚本读模板内联）；审计 = 轮间核对单+交付审计表节选（源自 assets/round-check.md、delivery-audit.md）；侦探 = 观察记录格式（源自 assets/issue-card.md 同文件的观察记录节）。
- `{{SHARED_BLOCK}}`：技术维度评委（前端/后端）追加六手法块；侦探追加侦探判据表；审计追加审计机械判据表。

### 6.3 守卫（gen-agents.test.mjs，随 `npm run check` 自动跑）

1. agents/ 下恰好 13 个文件，name 与文件名一致、合法、唯一；
2. `tools: Read, Glob, Grep` 逐字出现在全部 13 个文件；
3. 共享特质段在全部 13 个文件中逐字一致（与模板常量比对）；
4. 重跑生成 → 全部文件 diff 为空（确定性）；
5. `--check` 模式：任一文件被手改 → 退出码 1 并报文件名；
6. frontmatter 无 BOM（首字节非 EF BB BF）。

**固定清单（FIXED_LIST 全量条目，逐条进生成数据）**：

```text
reviewer-product：
1. 目标用户完整旅程有断点吗？重点扫「第一次使用」与「被拒绝时」——每个不支持的场景，用户当下的替代路径是什么、体验如何？
2. 每个边界/异常场景，文档说了「怎么办」吗？
3. 交付节奏：有中间可用节点吗？最小可用集是什么？
4. 工具失效时用户怎么逃生（不依赖本工具的手工路径）？
5. 有没有隐含前置条件没写出来（目标项目已有某配置/某状态）？
6. 收益有可验证的成功指标吗（写了「更好」但没写怎么算更好）？
7. 非目标（明确不做的事）列了吗？每条非目标背后假设了用户的什么状态？

reviewer-interaction：
1. 所有打断用户的时机，能前置的都前置了吗？（执行中途弹选择 = 大忌）
2. 列表/选项里有无效选项吗（选了也白选）？
3. 每条错误信息带可执行的下一步吗？
4. 加法/减法混在同一界面时，模式区分了吗？
5. 有没有静默发生的状态变化（用户不可见）？
6. 输出可被脚本/自动化消费吗（--json 等）？
7. 高频操作反馈即时吗？长操作可取消吗？

reviewer-ui：
1. 视觉变量（颜色/间距/字号）单源吗（design token）？有没有硬编码散值会漂移？
2. 可访问性：对比度、键盘可达、读屏语义，三项都核了吗？
3. 同一组件是复用还是复制改样式（组件在膨胀吗）？
4. 多端断点行为定义了吗？触控目标 ≥44px 吗？
5. 空态/加载/错误三态都设计了吗？（antd 项目空态必须用 Empty——以此为准绳）

reviewer-frontend：
1. 每条「用 X 实现 Y」的平台机制断言在目标平台验证过吗（symlink/junction、路径分隔符、CRLF/BOM、编码、大小写）？
2. 接管时刻：工具接管前用户可能手动制造过任意脏状态——接管逻辑校验前提了吗？
3. 并发/重入：两实例同跑、同命令重跑（幂等）会怎样？
4. 中断恢复：任意步骤崩溃后重跑收敛吗？
```

## 8. 流程协议（references/debate-protocol.md 正文）

- **评审轮**：被点评委并行独立出卡（防从众）→ 主持人汇总、去重、按族分组 → 追问轮把清单发全体评委补视角（互补 = 结构性动作，不是口号）。
- **答辩**：≤3 轮；收敛 = 问题清单清零或全部裁决关闭；第 3 轮后仍有未决 → 进升级。
- **升级协议**（仅 3 轮不收敛触发）：争议焦点一句话 + 双方各自【立场 / 赞成原因 / 反对对方原因 / 摸查记录（查了什么 + 命令 + 结果，必填）】+ 双方各自具体解法（都必填）+ 侦探驳回记录（无摸查 = 臆想争端，退回不升级）。**任何一方只提问题不给解法 = 不许升级。**
- **两档审计**：
  - 轮间核对单（每轮必过，不过 = 下一轮不得开始）：第 0 项轮际对账 + 卡片字段齐 + 答辩字段齐 + 本轮终态对账 + 侦探观察存在且卡号真实 + 汇总未丢卡。机械计数由主持人跑命令、审计员核对并抽查 1-2 项语义（审计员不从头数数，主持人不自签自己的账，侦探盯两边）。
  - 交付审计表（终局一次）：A 节过程闭环 6 项（终态对账 / P0P1 清零 / 落点抽查 ≥3 / P2 三态齐 / 数字一致 / 升级项有终裁）+ B 节按 doc-taxonomy 完成判据逐交付物核对。结论三态：通过 / 有条件通过（候选项+触发信号列明）/ 不通过（打回清单）。**审计两表必由审计员本人实例完成；证据栏空 = 不通过，不是待补。**
- **修复纪律**（继承旧 skill）：每修复带落点 → 修复即二次评审重跑手法 3（跨章节一致性）→ 同族扫描 → 修复引入自查。

## 9. 病根表与判据分配（references/failure-modes.md 正文）

### 9.1 「写了规则但 AI 没执行」13 病根（四层）

加载层：①没同步从未生效 ②写在 AI 读不到的地方 ③调度词不匹配。

执行层：⑧不在必经路上 ⑨成本太高被绕过 ⑩例外太宽吞掉规则 ⑪角色不清。
验证层：⑫执行了没留产物 ⑬假验 / 编证据 / 两份漂移。

**试金石**：任何指令写完问一句——「它被执行了，我怎么知道？」答不出产物/命令的，指令还没写完。
