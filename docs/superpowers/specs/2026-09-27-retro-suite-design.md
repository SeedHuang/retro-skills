## 1. 目标与非目标

### 1.1 目标

把「每次开发都会重复踩的流程坑」沉淀成**不依赖记忆的机制**：

```
多源问题采集                    ┌╌╌ 自迭代（回流）╌╌ 非本期 ╌╌╌╌╌┐
(OCR / multi-lens /             ╎                                    ╎
 session 总结 / 复盘)            ↓                                    ╎
        │                    错题集 KB（累积账本）                    ╎
        └──────────────────►     │                                    ╎
                                 ▼                                    ╎
                        复盘分析（根因 / 普遍性 / 优先级）              ╎
                                 │                                    ╎
                                 ▼                                    ╎
                     归置落地（自动化 / rule / skill / memory）         ╎
                                 │                                    ╎
                                 └──► 载体 = skill 的那部分 ╌╌╌╌╌╌╌╌╌╌╌┘

改进三维度：健壮度 · 用户体验 · 性能
「改进三维度」的**统计**（趋势）属 L3，非本期
```

### 1.2 本期范围

| 层 | 内容 | 本期 |
|---|---|---|
| **L1 数据层** | 错题集 KB（结构 + 指针 + 脚本 + bootstrap） | ✅ |
| **L2 过程层** | 复盘套件 5 技能 + 归置决策树 + 常驻轮询规则 | ✅ |
| **L3 闭环层** | 自迭代（skill 进闭环）+ 三维度趋势指标 | ⏸ 见 §11.1 |
| **L4 分析层** | 独立 agent 跨项目分析与复盘 | ⏸ 见 §11.1 |

### 1.3 非目标（明确不做）

- 不替代代码审查（走 `open-code-review`）、不替代 bug 定位（走 `systematic-debugging`）
- 不做规则自动过期 / 命中率统计、KB 导出备份、`doctor` 库体检、规则冲突消解序列、规则源入库 —— 均登记为**初始候选**（§11.2）

## 2. 核心契约：归置决策树

**这是整套技能的价值内核**——回答「一条教训往哪放」，且判据**可被第三方复核**，不凭感觉。

```
一条复盘经验
  │
  Step 0  它的「修复方案」是什么？
  │       答不出 → 复盘未完成，回炉（禁止往下走）
  │
  Step 1  既有承载里有相似的吗？
  │       （查五处：user_rules/ + <项目>/.trae/rules/ + memory/*.md + 错题集 KB + 既有 skills）
  │       ┌ 有 → 【升级，不新增】为什么既有没拦住？
  │       │        a. 触发面未覆盖（新场景） → 扩既有触发面（globs/description/作用域）
  │       │        b. 既有约束本身有问题     → 修既有（太宽/太窄/判据错）
  │       │        c. 载体选错了             → 换载体（goto Step 2）
  │       └ 无 ↓
  │
  Step 2  能否机械判定？（正则 / 脚本 / 测试 / CI 可验，且有执行点）
  │       能 → 【自动化】写进测试 / lint / 校验脚本 —— 不写成文档
  │       否 ↓
  │
  Step 3  是多步过程 / 技法吗？（有步骤、判断点、反例集）
  │       是 → 【skill】
  │       否 ↓
  │
  Step 4  能想象出「违反」的具体形态吗？（即是否「可证伪」）
  │       能（约束）     → 【rule】
  │       不能（事实/偏好） → 【memory】
  │
  Step 5  归属（rule 与 memory 通用）
  │       完全可抽象为通用       → 全局
  │       有通用内核 + 项目外壳  → 【拆两条】内核→全局，外壳→项目
  │       完全绑项目             → 项目
```

### 2.1 Step 1 是强制前置

**默认动作是升级既有，新增是必须举证的例外。** 三种归因的修法不同：

| 为什么旧承载没拦住 | 判据 | 修法 |
|---|---|---|
| 新场景 | 旧规则的触发面 / `globs` 不覆盖本次场景 | **扩旧规则**作用域，而非新增 |
| 旧约束有问题 | 旧规则本身太宽 / 太窄 / 判据错（本次是它导致误判或漏判） | **修订旧规则**（记录为什么改 + 备份旧版，见 §3.5） |
| 载体选错 | 这类问题本不该用该载体管（如机械可判定的却写成 rule） | **换载体**，并移除 / 降级旧载体 |

### 2.2 Step 2 的双约束：自动化优先 **且** 性能不妥协

`writing-skills` 明确要求：*"Mechanical constraints (if it's enforceable with regex/validation, automate it — save documentation for judgment calls)"*。理由：写成文档后 agent 与人**都会忘**；写成测试不会忘。

**但自动化必须带成本等级，并按等级分配到执行点**（呼应既有「两级编译检查」惯例）：

| 等级 | 形态 | 执行点 | 预算 |
|---|---|---|---|
| **L-fast** | 单文件级校验（类型、单文件测试、格式） | 每次编辑后 | < 数秒，增量 |
| **L-slow** | 全量套件、跨文件校验、依赖扫描 | 提交前 / CI | 分钟级 |

**闸门**：新增自动化前必须回答「它跑在哪个执行点？单次成本多少？」——答不出则不许加。**自动化优先 ≠ 自动化无预算。**

### 2.3 四载体对照

| 载体 | 落点（Windows） | 加载方式 | 管什么 |
|---|---|---|---|
| **自动化** | 项目内（`tests/`、校验脚本） | 执行时**强制** | 机械可判定的约束 |
| **rule（全局）** | `%userprofile%\.trae-cn\user_rules\rule-<epoch>.md` | **全量注入**（无 frontmatter、无条件） | 声明式约束 |
| **rule（项目）** | `<项目>/.trae/rules/*.md`（frontmatter 可控 `alwaysApply` / `globs` / `description` / 手动；可子目录作用域，3 层嵌套） | 注入（可条件） | 绑项目的约束 |
| **skill** | 本仓库 `skills/<名>/`，安装到运行时目录 | **按需加载** | 多步过程 / 技法 |
| **memory（全局）** | `%userprofile%\.trae-cn\memory\user_profile.md` | 注入 | 事实 / 偏好 |
| **memory（项目）** | `…\memory\projects\{project_path}\project_memory.md` | 注入 | 项目事实 / 偏好 |

**全局 rule 落点证据**：官方文档（`docs.trae.cn/ide_rules`）指定 `~/.trae-cn/user_rules/`。同机另有 `~/.agents/rules/`（4 个 md），但**本次会话注入的 `<rules>` 只含 `~/.trae-cn/user_rules/` 的 2 条**，判定后者才是 Trae 的权威落点；`.agents/rules/` 对 Trae 不生效（建议用户后续清理，避免「写了以为生效」）。

**关键区别（易错）**：`alwaysApply` / `globs` / `description` **只存在于项目规则**。全局规则是纯 markdown、无条件全量注入——**没有也不需要 frontmatter**。

## 3. 规则写法与冲突

### 3.1 规则写法规范

| 规范 | 出处 |
|---|---|
| **可证伪的祈使句**——能想象出「违反」的具体形态。❌「注意代码质量」✅「对同一文件禁止一轮内并行两次 SearchReplace」 | 本套件（与 §2 Step 4 共用同一判据，故仅定义一次） |
| 一条规则一件事，控制粒度 | Trae 官方文档「最佳实践」 |
| 规则之间不得冲突或相互覆盖 | Trae 官方文档「最佳实践」 |
| 路径一律用**相对项目根** | Trae 官方文档「最佳实践」 |

### 3.2 provenance（强制）

每条规则**必须**带出处，放在正文顶部**可见位置**（不是 HTML 注释——agent 读到「为什么」有助于遵守）：

```markdown
# <规则标题：一句祈使句>

> 来源：<KB 条目 ID>｜证据：<原始证据指向>｜落地：YYYY-MM-DD

<正文：规则 + 反例>
```

- **必填**：来源、证据
- **来源一律用 KB 条目 ID**（不用文件路径——迁移后路径会失效）
- **选填**：落地日期
- **理由**：没有出处的规则，将来没人敢删、也没人知道为什么存在

### 3.3 真冲突判定（保留；仅判定，不含消解序列）

两条规则算**真冲突**，当且仅当**同时**满足：① 作用域重叠 ② 对同一动作给出**不相容**指令。

否则不算冲突：作用域不相交 → 各自生效（最常见的「假冲突」）；一条被另一条包含 → 更具体者生效。

**真冲突的消解序列**登记为初始候选（§11.2），当前不进本期。

### 3.4 防重复检查（写入前必做）

写入任何规则前，grep 既有：`user_rules/` + `<项目>/.trae/rules/` + `memory/*.md` + 错题集 KB。有同义规则 → **改既有，不新增**。

### 3.5 修订既有规则：备份 + 一次性确认

**问题**：修订既有规则会永久丢失旧版本（且规则源未入库，无 git 历史）。

**规则**：

1. **先备份**旧版到 `<KB>/projects/<项目标识>/rules-history/<规则名>-<YYYYMMDD-HHmmss>.md`（必做，零成本，彻底消除不可逆性）
2. **一行式确认**：展示「旧 → 新」摘要（各一行），用户 y/n。仅**修订既有**时触发；**新增**不确认
3. 备份失败 → **中止修订**（不得在无备份的情况下覆盖）

**为什么只对修订确认、不对新增确认**：Step 1 的默认路径是新增（无命中），修订是少数分支 → 低频 + 改变长期行为 = 值得一次确认。

### 3.6 写入顺序（崩溃安全）

`retro-institutionalize` 涉及**两处状态**（KB 条目 + 规则文件），顺序固定：

```
① 先在 ledger 落条目（状态 open，含拟载体与拟落点）
② 再落规则 / 自动化 / skill 改动
③ 成功后把条目状态改为 landed(→载体)
```

**任何一步中断**：条目停在 `open`（拟落点已记）→ 重跑时 Step 1 查重会发现它 → **续做而非重复落规则**。① 永不后于 ②，否则中断会留下「规则已落但无记录」→ 重跑必然重复。

## 4. 错题集 KB（L1）

### 4.1 位置与指针

**位置由用户指定，不默认落 C 盘**（错题集会持续增长）。

```
%userprofile%\.agents\lessons.config.json      ← 指针（约 100 字节，固定位置，C 盘占用可忽略）
{ "store": "D:\\Seed\\lessons", "schemaVersion": 1 }
```

**解析优先级**：

```
1. 环境变量 LESSONS_DIR
2. 指针文件 ~/.agents/lessons.config.json 的 "store"
3. 都没有 → 触发 bootstrap（见 §4.1.2）
```

#### 4.1.1 读取点校验（`resolve` 必做）

读到 `store` 后逐项校验，任一失败 → **报错 + 引导重建，不得静默继续**：

| 校验 | 失败提示方向 |
|---|---|
| 路径存在且**是目录** | 「KB 路径不存在或不是目录：<路径>。重建请运行 bootstrap」 |
| 可写 | 「KB 路径不可写：<路径>」 |
| **不在任何 git 仓库内**（防违反 §8.2） | 「KB 位于仓库内：<路径>——错题集含个人数据，不得入库。请迁移到仓库外」 |
| `schemaVersion` 已知（当前仅 `1`） | 「KB schemaVersion=<v> 不受支持（支持 1）。迁移或重建」 |
| 指针 JSON 可解析且 `store` 非空串 | 「指针文件损坏：<路径>」 |

#### 4.1.2 bootstrap 的两个边界

| 边界 | 处理 |
|---|---|
| `~/.agents/` 目录不存在 | 先创建该目录；创建失败 → 退到 `~/.trae-cn/lessons.config.json`，并告知用户实际落点 |
| 指针**已存在但损坏** | **禁止静默覆盖**：先备份为 `lessons.config.json.bak-<时间戳>`，再写新指针，并报告备份路径 |

### 4.2 目录结构

```
<KB 根>/
├── index.md                       ← 全机索引：项目 × 时间 × 维度 + 「候选与推迟」节（**运行态权威**）
├── projects/
│   └── <项目标识>/
│       ├── ledger.md              ← 该项目错题条目（累积索引，一行一条）
│       ├── rules-history/         ← 被修订规则的旧版备份（§3.5）
│       ├── 2026-09-27-facts.md    ← 事实包（单次）
│       └── 2026-09-27-retro.md    ← 复盘长文（单次）
└── universal/
    └── <topic>.md                 ← 从项目条目抽象出的跨项目通用经验
```

**项目标识规范化（必做）**：取自仓库目录名，但入库前须清洗——移除/替换 `|`、换行、`/` `\` 等路径分隔符、控制字符；空白折为 `-`；保留中文与字母数字。**理由**：标识会进目录名与 ledger 表格，非法字符会破表或破路径。

- **不用绝对路径**（项目搬家不断链）
- **条目间引用一律用稳定 ID**（避免迁移断链）
- `/universal/` 即「分析不与项目绑定」的落点——对应 §2 Step 5 的「通用内核」

### 4.3 条目 schema（`ledger.md` 一行一条）

```markdown
| ID | 日期 | 项目 | 来源 | 问题 | 根因 | 维度 | 修复 | 载体 | 状态 |
```

| 字段 | 取值 |
|---|---|
| ID | `L-YYYY-MM-DD-NNN` |
| 来源 | OCR 评审 / multi-lens 评审 / session 总结 / 复盘 |
| 维度 | 健壮度 / 用户体验 / 性能 |
| 载体 | 自动化 / rule(全局) / rule(项目) / skill / memory / 未定 |
| 状态 | `open` / `landed(→载体)` / `watch(触发条件)` / `closed(理由)` |

**转义规则（必做）**：`问题` / `根因` / `修复` 等自由文本栏位内——

- `|` 一律写作 `\|`
- 换行一律写作 `<br>`
- 表格本身用 markdown 管道表；**不做转义即视为格式错误**（会破整份 ledger）

**为何保留行内「项目」列**（与目录路径构成轻度第二份真相）：`index.md` 做跨项目汇总时直接读列，无需解析路径；此冗余是刻意的，代价（漂移）由「标识由 §4.2 规范化产生，且写入时同源」控制。

**条目 ≠ 复盘**：条目是**累积索引**（可扫、可统计）；复盘是**单次过程分析**（长文）。复盘的产出 = 若干条目 + 若干规则。

### 4.4 多源归档

| 来源 | 落点 |
|---|---|
| OCR 评审原文 | `~/.agents/sdd/<阶段>/ocr-out.txt`（统一路径；当前 lpm 有落在仓库根的不一致，见 §15 O4） |
| OCR 修复 / 复审报告 | 同目录 |
| multi-lens 评审结论 | **已定（2026-09-28）**：multi-lens 自身的教训**不落在技能目录里**（隐私 + 发布物纯净），改记 KB 的 `skills\multi-lens-review\`——与 A2/B2 同一条路。定版见 `docs/architecture.md` §6 A2 与 §10 H2（挂账，随首次进化 multi-lens 时执行） |
| session 总结 / 复盘 | 由 `retro-collect` / `retro-analyze` 直接写入 KB |

### 4.5 脚本（收窄职责，YAGNI）

**只做三件机械且有风险的事**，其余（add/list/stats）用 Read / Write / Grep 直接操作——agent 本来就干这个。

位置：`skills/managing-lessons-store/scripts/lessons.mjs`（Node 单文件，无第三方依赖）

| 命令 | 职责 |
|---|---|
| `lessons resolve` | 解析 + **校验**（§4.1.1）后打印 KB 根 |
| `lessons migrate --to <path>` | 迁移（§4.6） |
| `lessons deferred` | 打印「候选与推迟」节 + 逐条信号命中判定（每 session 轮询用） |

### 4.6 迁移的崩溃安全设计

**第 3 步的四条硬校验（防自覆盖/递归）**：

| 校验 | 拒绝条件 |
|---|---|
| 目标 ≠ 当前源 | 相等 → 拒绝（自我覆盖） |
| 目标不在源内 | `realpath(目标)` 以 `realpath(源)` 为前缀 → 拒绝（无限递归复制） |
| 目标不是源的祖先 | 反向前缀比对 → 拒绝 |
| 目标为空或不存在 | 已存在且非空 → 需用户二次确认（不默认合并） |

**主流程**：

| 步 | 动作 | 失败后果 |
|---|---|---|
| 1 | `lessons resolve` 拿当前位置 | — |
| 2 | 用户指定目标位置 | 中止，原库无损 |
| 3 | **四条硬校验** + 校验目标可写 + 空间充足 | 中止，原库无损 |
| 3.5 | 在源根写**迁移锁** `<KB>/.migrating`；其他写操作见锁即拒绝（**读锁方责任**：`retro-collect` / `retro-analyze` / `retro-institutionalize` 三者的「写库前置检查」——写库前先查 `<KB>/.migrating`，存在即拒绝并报告） | 中止，原库无损 |
| 4 | **复制**（不用 move，先保底） | 中止，原库无损 + 半副本（清单记录） |
| 5 | **校验**：条数一致 + 逐文件哈希一致 | 中止，原库无损 + 副本标记为不完整（**不自动删**，报告路径由用户处置） |
| 6 | **切指针**（原子写：临时文件 + rename） | ← **唯一有风险的一步，且原子** |
| 7 | 删锁 → 报告 + 询问是否删旧 | 旧库仍在，可回退 |

**两个设计点**：
- **切指针放最后**：任何一步中断，旧库都仍有效——中断只留下无害副本
- **迁移锁**：防「迁移复制中另一流程正在写库」→ 复制到半写状态。锁是标记文件，写操作启动时检查；锁的存在由调用方在开始时提示用户「当前若有其他 retro/lpm 流程在写库，请先停」

**重复执行**：迁移成功后源已变为新位置 → 再次迁移到同一路径会被步 3「目标 ≠ 源」拦住（自我覆盖）✓；迁移到第三个位置合法。

**单一写入者**：指针只有本技能会写，避免两个技能各写一份配置而打架。

## 5. 两个模板

### 5.1 事实包模板（`<日期>-facts.md`）

**只放事实，零判断**——由**模板结构**承载该约束（`writing-skills` 实测：「输出形状错」类问题用 recipe 优于禁令）。

**结构化隔离（关键）**：凡可能含**原文**的内容（错误消息、命令报错、他人表述）一律放进**引用块 / 代码块**；「零判断」的检查只作用于**非引用块**。**这样不需要写豁免条款**——`writing-skills` 实测：*"Exemption clauses don't scope"*，加「引用不算」会整体削弱规则；把豁免做成结构才有效。

```markdown
# 事实包：<session/阶段标识>

- 范围：<起止锚点>
- 生成：<日期>｜生成者：<agent/人>

## 1 时间线锚点
| 时刻 | 事件 | 来源（文件 mtime / git log / 命令输出） |

## 2 计数
| 项 | 值 | 来源 |
（子代理运行次数 / 测试运行次数与形态 / 评审轮次 / 产物文件数 …）

## 3 异常事件
| # | 现象 | 证据 |
> 证据栏内的原文一律用引用块或代码块：
> ```text
> <命令输出 / 报错原文 / 日志片段>
> ```

## 4 证据清单
（本次可复核的文件路径 / hash / 命令）

## 5 未取得的数据
（诚实列出——哪些数据拿不到、为什么）

## 6 声明
本文件不含判断、不含方案、不含优先级。分析见 <同日>-retro.md。
```

**硬规则**：证据只能是**本次实跑的命令输出**或**文件直读**；**禁用推测值**（如在被归一化的 mtime 上做推断——本次 S6 复盘的真实教训）。

### 5.2 复盘模板（`<日期>-retro.md`）

**做薄**：只引用事实包条号 + 加判断，不复制事实。由**必填栏位**承载「每条问题必须指向事实包条号」。

```markdown
# 复盘：<session/阶段标识>

- 事实包：<路径>

## 1 问题清单
| # | 事实包条号 | 问题 | 根因 | 维度 | 方案 | 是否普遍 | 优先级 |

## 2 归置结果
| 条目 ID | 教训 | 走 Step 几 | 落点（载体 + 路径）|

## 3 附录：规则裁决
（真冲突时的裁决记录：冲突双方 / 采用 / 判据 / 若错代价 / 推翻方式）

## 4 未决与待验证
```

**硬规则**：优先级必须带**判据**，不得只给结论。

## 6. 五个技能契约

**description 只写触发条件、不总结流程**——`writing-skills` 有对照实验证明：description 写了流程摘要后，agent 会照 description 办事、跳过正文。故不沿用用户既有技能（`multi-lens-review` / `prd-to-specs`）带流程摘要的写法。

| # | name | description（中英双语，仅触发） | 输入 | 输出 |
|---|---|---|---|---|
| 0 | `using-retrospective` | Use when 阶段/里程碑收口、session 即将结束、用户说「复盘/回顾/总结一下这个过程」「这段是不是可以沉淀一下」、或要判断一条教训该进全局还是项目规则时。Do not use for 代码审查（走 open-code-review）、bug 定位（走 systematic-debugging）、或仅要一份过程时间线（那是 retro-collect 单独可做）。 | 当前会话/阶段范围 | 路由决定 |
| 1 | `retro-collect` | Use when 需要采集一段开发过程的客观事实（时间线/计数/异常事件）作为复盘依据，或用户说「收集复盘信息/盘点一下这个 session」时 | 阶段标识 | 事实包文件；**首次触发 KB bootstrap** |
| 2 | `retro-analyze` | Use when 已有事实包，需要产出问题清单、原因、解决方案、普遍性与优先级；或用户说「做复盘/分析一下」时 | 事实包路径 | 复盘文件 + KB 条目 |
| 3 | `retro-institutionalize` | Use when 复盘结论已定，需要把教训写回能自动生效的规范（全局规则/项目规则/自动化/技能/记忆）时 | 复盘文件路径 | 规则文件 / 测试 / 技能改动 |
| 4 | `managing-lessons-store` | Use when 需要初始化错题集库、迁移库到新位置、或轮询推迟项是否到复活时机时 | — | KB 目录 / 指针 / 推迟项报告 |

### 6.1 内容归属（谁执行谁承载）

架构从「入口承载全部共享规范」改为**「谁执行谁承载」**——共享内容变多后集中会造出臃肿入口。

| 内容 | 归属技能 |
|---|---|
| 归置决策树（§2）+ 规则写法/provenance/备份/写入顺序（§3） | `retro-institutionalize` |
| KB 结构 + 迁移 + bootstrap（§4） | `managing-lessons-store` |
| 事实包模板（§5.1） | `retro-collect` |
| 复盘模板（§5.2） | `retro-analyze` |
| 时机判断 + 路由 + 推迟项三要素 + 产物关系图 | `using-retrospective`（**薄路由**） |

### 6.2 产物关系图（入口技能承载）

```
多源输入（OCR 原文 / multi-lens 结论 / session 总结 / 用户的复盘请求）
      │
      ▼
  ① 事实包  <日期>-facts.md        ← 本质：本次过程的证据集（纯事实、零判断）
      │                              由 retro-collect 产出
      ▼
  ② 复盘    <日期>-retro.md        ← 本质：本次过程的分析（只引条号 + 加判断）
      │                              由 retro-analyze 产出；**做薄**
      ├──────────────► ③ KB 条目     ← 本质：跨 session 累积索引（一行一条，稳定 ID）
      │                  ledger.md     由 retro-analyze 写入，retro-institutionalize 更新状态
      └──────────────► ④ 落地载体     ← 本质：生效物（自动化 / rule / skill / memory）
                                       由 retro-institutionalize 产出

引用方向：②引①的条号；③④引②的产物；规则 provenance 引③的 ID
反方向不存在——**永不把下游内容回抄到上游**（防第二份真相）
```

### 6.3 链式、独立与错误传播

- 每个技能结束输出一行「下一步：用 `<技能名>`」，实现链式
- 每个技能**均可独立入口**（`retro-analyze` 只要给事实包路径即可跑），互不强制
- 跨技能引用一律**只用技能名**（`REQUIRED SUB-SKILL: managing-lessons-store`），不用 `@` 链接（会 force-load 烧上下文）

**前置未满足时的行为（统一契约）**：**拒绝并给出下一步，不得降级猜测**。

| 场景 | 行为 |
|---|---|
| `retro-analyze` 收到的事实包路径不存在 | 拒绝；建议先跑 `retro-collect` |
| `retro-institutionalize` 的复盘文件不存在 | 拒绝；建议先跑 `retro-analyze` |
| KB 未初始化（`resolve` 报无指针） | 拒绝；转为引导 bootstrap（`managing-lessons-store`） |
| `resolve` 校验失败（§4.1.1 五种） | 拒绝；按其提示引导重建/迁移 |

**为什么拒绝而非降级**：降级会产出「看起来对但依据缺失」的产物，污染 KB——污染比中断贵得多。

## 7. 推迟项机制

### 7.1 三要素（缺任一 → 不是「推迟」，是「丢弃」）

① 编号（可引用）② 动机锚（挂在 KB 的 `open` 条目上）③ **可观测复活信号**（可 grep，不是日期）

**不用日期**：日期到点会诱使「为做而做」；信号到点才是真需求。

**三要素缺一即拒收**：例如「动机锚 = —」的占位候选属不合格，应在登记时补齐或直接丢弃（不登记）。

### 7.2 常驻轮询（跨 session 不蒸发的引擎）

**关键**：推迟项存在 KB 里（**运行态权威**），靠一条**全局规则**保证每次开工必然检查——**不靠 handoff 逐条转抄**（那正是会漏的环节）。

**落点**：`%userprofile%\.trae-cn\user_rules\rule-<epoch>.md`

**注意**：全局规则是**纯 markdown、无条件全量注入、没有 frontmatter**——**不要写 `alwaysApply`**（那是项目规则字段，写了无效）。本机制依赖的正是「全局规则每次必然注入」这一性质，而非条件触发。（P5 已按此落地：`%userprofile%\.trae-cn\user_rules\rule-<epoch>.md` 为纯 markdown、无 frontmatter；实测见 §8.5。）

规则正文（**不带 frontmatter**）：

```markdown
# 开工时轮询推迟项

> 来源：<KB 条目 ID>｜证据：<本条规则的落地依据>｜落地：YYYY-MM-DD

会话开始时先用 `managing-lessons-store` 技能跑 `lessons deferred`，逐条核对「复活信号」。

- 有命中 → 动手前先向用户提出：命中项编号 + 信号证据，并说明是否升格为独立 spec。
- 无命中 → 一句话报告「推迟项 N 条，均未命中信号」。

报告必须含**当前计数**（让进度可见，防轮询退化成形式主义）。
理由：规则只指向技能与脚本，**不硬编码 KB 路径**——换位置无需改规则。
```

**双保险**：项目 handoff 的「开工前先做」里再放一行同样的检查（此条依赖用户在用 handoff 技能；若不使用则仅靠全局规则，属可接受的降级）。

**条件触发的候选**：若日后需要「只在特定文件/场景才轮询」，需迁到项目规则（全局规则无 `globs`/`description`）——登记为初始候选 **§11.2 的 C6**（常驻轮询改为条件触发）。

### 8.5 安装实验实测结论（V1–V4）

> 实测环境：本机 Node v22.12.0 / npm 10.9.0 / `skills@1.7.0`（Windows），2026-09-27。原始命令与输出见 `.superpowers/sdd/2026-09-27-retro-suite.md/task-9-report.md`。

| V4 | `npx skills add` 是否按 `<repo>/skills/*` 枚举全部技能 | **是，一次装齐 5 个**，无需逐个 `--skill`。`npx skills add d:\Seed\retro-skills --agent trae-cn -g -y` 报 `Found 5 skills` / `Installing all 5 skills` / `Installed 5 skills` | `Found 5 skills`；`Installed 5 skills`（5 个技能名全列） |

## 9. 测试策略

`writing-skills` 的硬门槛：`NO SKILL WITHOUT A FAILING TEST FIRST`，**且明确适用于对既有技能的编辑**；并规定 `STOP：不要批量创建未测试的技能`。

→ **5 个技能 = 5 个独立 RED-GREEN-REFACTOR 周期，顺序交付，禁止一把写完。**

### 9.1 RED（先看没有技能时会怎么错）

| # | 场景 | 给谁 | 观察什么 |
|---|---|---|---|
| R1 | 「把这个 session 的开发过程收集成复盘信息」 | `retro-collect` | 会混入判断词吗？会编造数据吗（如用被归一化的 mtime 做推断——S6 真实教训）？ |
| R2 | 给一份事实包，问「复盘」 | `retro-analyze` | 会给问题不给出处吗？优先级凭感觉吗？ |
| R3 | 给一份复盘结论，问「沉淀」 | `retro-institutionalize` | 会把项目专属规则写进全局吗？不查重就写吗？覆盖旧规则前会备份+确认吗？中断后重跑会重复落规则吗？ |
| R4 | 「复盘一下，该从哪进？」 | `using-retrospective` | 路由是否正确？会不会跳过事实包直接给分析？ |
| R5 | 「错题集放哪？」/「库未建时想记一条教训」/「有什么推迟项该做了？」 | `managing-lessons-store` | 会静默落 C 盘吗？会引导 bootstrap 吗？轮询报告是否带计数？ |

### 9.2 GREEN / REFACTOR

- **GREEN**：写最小技能，同场景复跑，验证守住硬边界
- **REFACTOR**：收集新借口（「证据拿不到就略过」「这条很明显不用查重」「备份太麻烦」）→ 逐条加反制
- **压力叠加**（discipline 型必需）：时间压力（"快点随便复盘下"）+ 沉没成本（"都写了 3 条了第 4 条不查了吧"）+ 权威（"用户说不用较真"）

### 9.3 各技能验收判据

| 技能 | 判据 | 验证方式 |
|---|---|---|
| `using-retrospective` | 5 个路由场景正确 5/5 | **人工** |
| `retro-collect` | ① 事实包零判断词（见下词表）② 每条事实带证据 | ① **自动**（grep）② 人工抽检 |
| `retro-analyze` | 每条问题带事实包条号 + 优先级带判据 | 人工 |
| `retro-institutionalize` | 落点全经决策树 + 每条规则带 provenance + 有查重记录 + 修订有备份 | 人工 |
| `managing-lessons-store` | `resolve` / `deferred` 输出正确；迁移四校验生效；中断后旧库仍有效 | **自动**（脚本断言）+ 人工 |

**「零判断词」验收 fixture（属验收，不进 SKILL.md 正文——正文靠模板结构，见 §5.1）**：

```
黑名单（评价/建议类）：应该 | 建议 | 需要 | 值得 | 更好 | 显然 | 糟糕 | 不足 | 优化 | 改进 | 问题

作用范围：事实包中「非引用块」的叙述文本（引用块/代码块内的原文不扫——靠 §5.1 的结构化隔离，不加豁免条款）

正例（应通过，含 0 命中）：
  1. 「子代理派发 22 次，其中 19 次返回有效结果」
  2. 「verify 运行 12 次，耗时区间 40–75 秒」
  3. 「文件 mtime 被批量归一化至 09-27 10:13，故未用作时间线证据」
反例（应拦下）：
  1. 「派发次数过多，应该合并」            → 命中「过多/应该」
  2. 「建议以后减少全量复跑」              → 命中「建议」
  3. 「这个问题显然是设计缺陷」            → 命中「问题/显然」
```

**迁移中断的确定性构造**（替代「kill 进程」这类不可重复场景）：手动制造**半副本**——复制源库的一部分文件到目标 → 直接把指针指向半副本所在目录 → 跑校验逻辑断言「不认为是完整库、且旧库仍有效」。确定性、可重复。
