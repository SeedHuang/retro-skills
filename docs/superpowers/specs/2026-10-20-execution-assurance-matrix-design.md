# 执行力度矩阵：三类文档（agent/skill/rule）检查项统一组织 + agent 专属可执行性判据 + 置信度评级

> 日期：2026-10-20｜状态：**已定稿**（议会评审通过：4 轮、18 项 P0/P1 全清零；2026-10-20 用户裁定定稿）｜来源：用户当场裁定（2026-10-20）
> 测试用例文件：`docs/superpowers/specs/2026-10-20-execution-assurance-matrix-design-testcase.md`
> 依赖：rule-inspector 判据（`skills/rule-inspector/references/criteria.md`，单源）、skill-authoring-convention 规则（`rules/skill-authoring-convention.md`）、docgen 组件（`tools/docgen/`，S2 已收口）
> 前置：S2（reviewer-audit 试点）已巩固；本 spec 完成后才进 S3（用户 2026-10-20 裁定「先独立完整做线 E，再做 S3」）

## 0 为什么

本仓对「AI 会不会照着执行」的检查体系目前**三套各写各的**：rule 有完整判据（执行力度 8 项 + 通用 17 + X1/X2/X3），skill 有工程硬判据（skill-authoring-convention + check.mjs），agent 只有数据层断言（validateAgentData 1-14）+ 字节一致性测试。三套判据互相独立、无共享、无统一组织。

三个问题因此产生：

1. **判据各自定义、必然漂移**：同样语义的检查项（如「触发机制」「验证闭环」）在 rule/skill/agent 三处可能有三种写法，改一处其他两处不跟着改。
2. **agent 是最薄的一档**：它既没有 rule 的语义判据（执行力度），也没有 skill 的工程判据（check.mjs），只有「数据字段对不对」和「字节对不对」——**没有「这张卡执行起来好不好」的检查**。S3/S4 迁移 13 席时，这个缺口会跟着放大。
3. **没有正反例积累与置信度**：哪些写法在什么场景下执行力度好/不好，没有按场景索引的记录；每种方案都要完整验收，成本大。

本 spec 把这件事做成一个体系：**检查项按「出现于哪些类型」归桶（最大复用），agent 补专属可执行性判据（含「让 AI 自己证明」的贯穿自证），并设计执行力度置信度评级（省成本但不豁免高风险）**。

## 1 全貌确认

| 维度 | 内容 |
|---|---|
| 本质 | 把 agent/skill/rule 三类的执行力度检查项组织成「共享归桶 + 各类型专属」的矩阵；为 agent 补齐专属可执行性判据（A/B/C 三组）；建立按场景索引的正反例模式表；设计置信度评级决定验收强度 |
| 同族 | 同类失败面：判据重复定义 → 两处漂移 → 批次返工（本仓已踩：判据重复定义 → 批次漂移 → 多轮返工）；只设 allShared 不设两两 shared → 共享不彻底；agent 判据越界去查运行时 → 与 parliament/review-loop 重复；评级豁免验收 → 自证偏差绕回 |
| 边界 | **不做**：运行时产出验证（归 parliament/review-loop）；rule/skill 判据正文的改写（那是 line B）；S3/S4 迁移（本 spec 只建检查体系）；新 agent 角色（复用现有角色）。**只做**：检查项归桶组织 + agent 判据定义 + 模式表种子 + 评级设计 |
| 验收 | ①检查项矩阵：每类文档的 checklist 完整、共享项零重复定义（allShared/两两 shared 归桶正确）；②agent 判据：A/B/C 三组在 reviewer-audit 卡上全部可判（机器查通过、AI 判有判据）；③模式表：种子条目 ≥5 行、每条能指回来源；④评级：三档定义完整、三条硬约束生效 |
| 影响面 | `skills/rule-inspector/references/criteria.md`（新增归桶索引，不复制判据）、`rules/skill-authoring-convention.md`（新增归桶索引，不复制）、`tools/docgen/`（新增 agent 判据检查，若走脚本则新增组件）、`docs/after/pending-work-overview.md`（线 E 素材，定稿后瘦身）、各类型 checklist 载体（载体落点见 §6 开放问题） |

**联动四问**：

- **治本了吗**：归桶消除三套判据各自漂移（一次定义多处引用）；agent 判据补齐「可执行性」缺口；评级把「验收强度」从拍脑袋变成可复算决策。
- **有副作用吗**：新增判据可能对现有卡报出「本来就有但没被查过」的问题（如 B2 fixedList 判据可判）——这是**发现存量问题**，不是引入问题；评级若设计成「可豁免」则绕回自证偏差（已在 §3 R4 堵死）。
- **跨问题联动吗**：与 line B（rule 判据体系重构）有交集——本 spec 只建归桶索引、不改判据正文，两者错位；与 parliament（运行时验证）必须划清边界（§3 R2）。
- **跨文件吗**：检查项载体若新建脚本/技能，会被三类文档的检查流程引用；共享项定义一次，改共享项影响所有引用方——**共享项变更必须走「改前 vs 改后对照 + 用户确认」硬闸门**（对齐 rule-writer 硬闸门模式）。

## 3 核心决定（不可违反）

| # | 决定 | 为什么 |
|---|---|---|
| R1 | **归桶命名**：`allShared`（三者共有）/ `agentAndSkillShared` / `agentAndRuleShared` / `skillAndRuleShared`（两两共有）/ 各类型独有。共享项定义一次、各类型 checklist 引用；独有项放各类型自己的 checklist | 公共最大化；「不只三种都有的才叫共有」——两两交集如果不设桶会被迫重复定义或硬塞进 allShared（用户 2026-10-20 拍板） |
| R2 | **检查范围边界**：agent 可执行性判据（A/B/C 组）**只查卡文本本身**（渲染后的 `agents/*.md`），**不查运行时产出**。运行时验证归属：议会评审产出 → parliament（侦探行为核对 + 审计证据核对）；改动验证 → review-loop（复查轮独立重审）。判据越界查运行时 = 与它们重复 | 防重复是硬线；静态判据管「卡写得好不好」，运行时归独立方验证「产出对不对」 |
| R3 | **「谁验证」职责分离**：运行时产出的证据由独立方复核，不交给产出的 AI 自评（防自证偏差）；证据必须可重跑（复核 = 真重跑命令/读文件，不是相信证据文本）；「我检查过了」类描述不算证据 | 用户担心「AI 回答会造假、如何判断证据不造假」——分离增加可信，可复算是根基 |
| R4 | **置信度评级决定验收强度、不豁免高风险**：高（同场景实测 ≥N 次零回归，**N 为待裁占位，见 §6 开放问题 4**）→ 简化验收；中 → 标准验收；低（新模式/新场景）→ **必须完整验收，不可豁免**。三条硬约束：①评级可复算（基于模式×场景实测记录数，推导逻辑落点见 §6 开放问题 2 与 4）；②评级低 → 强制完整验收；③高风险（不可逆操作/跨体系改动/用户要求全验）永不免验。**评级结果不持久化**——每次按实测记录现算（记录增长 → 档位自动更新，无残留旧评级） | 「评级替代完整验收」= 自证偏差绕回；成本省在「已证明可靠的模式不用每次重头验」，不省在「低置信度跳过验」；评级现算避免「旧评级残留误导验收强度」（后端/前端评审共识） |
| R5 | **agent 专属判据三组，按判定性质拆层**：**A 结构项机器查**（A3 必答清单存在 / A4 必答闭环 / A5 证据约束 / A6 边界声明 / A7 输出格式指定——节与字段存在性，可 grep）+ **A 语义项 AI 判**（A1 职责单一定位 / A2 触发信号可判——语义判断，走 R8 annotations）+ **B 内容 4 项 AI 判**（B1 identity 真实 / B2 fixedList 判据可判 / B3 职责边界一致 / B4 自由探索触发）+ **C 贯穿自证 4 项**（C1 固定清单逐条自证 / C2 自由探索逐条自证 / C3 结论可复算 / C4 自证贯穿不只在开头）。**模板形态适配**：A 组判定词须兼容两种模板形态（parliament 模板与 senior-sdet handwritten 模板），判定词按「存在性 + 语义」而非「逐字模板句」书写（如 A3 判「有固定清单表格且每条有『必答/必问』列头」，A4 判「含『缺答/只答固定清单 = 不合格』任一字样」） | 用户 2026-10-20 裁定的中心主旨「让 AI 自己证明——不是开头问一下，而是所有给结论的环节都要加追问」落成逐环节强制；四席评审共识（后端/前端/测试/AI）：A1/A2 是真语义判断，「机器查」定性无法兑现，拆层后验收② 才可机械判 |
| R6 | **模式表是判据的附属模式库，不复制进判据正文**：按场景索引的正反例（什么场景下好/不好），种子条目从仓库已有正反例提取，后续每轮实测积累 | 两处维护必漂移（本仓已踩：判据重复定义 → 批次漂移 → 多轮返工）；模式表是评级的依据 |
| R7 | **共享项变更硬闸门**：共享项（allShared/两两 shared）变更必须「改前 vs 改后两版留齐 + 用户确认」后才落地 | 对齐 rule-writer 硬闸门模式；共享项影响所有引用方 |
| R8 | **AI 判的资产化**：A 语义项（A1/A2）+ **B 组 4 项 + C 组全 4 项**（C1/C2/C3/C4 均为 AI 判）走 rule-inspector 的「AI 判 + annotations 资产化」模式（结果入 annotations 文件，脚本只接收），不另造机制。**annotations 值三态**（对齐 AI 评委评审共识）：`pass`（判过且合格）/ `fail: <理由>`（判过且不合格）/ `pending`（未判）——**禁止压成布尔**（布尔会把「判 0 不合格」与「未判过」混为一个 false，脚本机械接收后静默放行、下轮不重判 = 自证偏差回绕）。**落点**：与 rule-inspector 共用 `rules/.inspector-annotations.json`，**键命名 = `agent 卡名:判定项名`（如 `reviewer-audit:B2`），值 = 三态对象**（`{"reviewer-audit:B2": "pass", "reviewer-audit:C4": "fail: 证据位缺失"}`），键值语义以 criteria.md §3.3b「判定资产化」段为准，实现后逐键核对对齐，缺对齐 = 不合格 | 复用已有模式；脚本不判语义，AI 判后脚本机械接收；三态堵死「判 0 被当已资产化」的静默放行（AI 评委 Q-1-2）；C 组全落避免 C1/C2/C3 判定落点悬空（后端复查 Q-2-3） |

## 4 归桶草案（送议会时细化）

> 图例：**当前归属** = 该检查项此刻定义在哪类 checklist（一处定义，不重复）；**候选升格** = 拟从两两桶升格为 allShared 的待裁项，升格前仍在原桶定义，升格条件与裁决见 §6 开放问题 4。每一检查项机械上恰有一处「当前归属」（对齐 TC-002）。

| 归桶 | 内容（草案） | 当前归属 / 候选升格 | 依据 |
|---|---|---|---|
| **skillAndRuleShared** | 来源覆盖④ / 冲突裁决⑤ / 例外从严⑥ / 验证闭环⑧（**触发机制⑦ 已升格候选，此处不再定义**） | ④⑤⑥⑧ 当前归属此桶；⑦ 候选升格 allShared（条件见 §6 开放问题 4） | skill-authoring-convention 与 rule 禁令类结构几乎逐节同构 |
| **allShared 候选** | 触发机制⑦（rule「触发时机」/ skill「触发时机」/ agent `when` 字段） | ⑦ 候选升格目标桶；**升格前 ⑦ 仍只定义在 skillAndRuleShared**，此处仅登记候选，不重复定义 | 三类都有「何时触发」概念，是最大公约数；是否升格按 §6 开放问题 4 裁决 |
| **rule 独有** | 通用 17 结构性判据、执行力度 ①②③、X1/X2/X3 | 当前归属此桶 | 行为指令，语义判据密集 |
| **skill 独有** | 跨技能路径引用、脚本守卫、目录语义 | 当前归属此桶 | 工程形态，机器可查 |
| **agent 独有** | A 组 7 项（结构项 A3-A7 机器查 + 语义项 A1/A2 AI 判）+ B 组内容 4 项 + C 组自证 4 项 | 当前归属此桶 | 角色卡，既不是规则也不是技能 |
| **agentAndSkillShared / agentAndRuleShared** | **当前判定无交集** | 两桶空置 = 已裁决无共享检查项 | rule 是行为指令、skill 是工程形态、agent 是角色定义，agent 与另两者两两无共享检查项；若未来发现交集按 R7 硬闸门增补 |

> 注：验证闭环⑧ 的归属说明——当前 skillAndRuleShared 两桶定义（对应 rule 执行力度⑧ / skill 验证节）；若 agent 侧 C 组自证判据定稿成立，⑧ 具备 allShared 候选资格，届时按 §6 开放问题 4 一并裁决，不重复定义。

## 5 验收（本 spec 的验收锚点）

| 检查 | 判据 | 执行时点 |
|---|---|---|
| 归桶正确 | 每类文档 checklist 完整；共享项在各 checklist 中零重复定义（引用而非复制） | spec 定稿 + 施工后 |
| agent 判据可判 | A 结构项（A3-A7）在 reviewer-audit 渲染卡上机器全过；A 语义项（A1/A2）+ B 组 4 项 + C 组（含 C4）AI 判有明确判据且判后落 annotations（三态） | 施工后 |
| 模式表种子 | ≥5 行，每行「好/不好场景」+ 来源可复算（文件/行号） | 施工后 |
| 评级生效 | 三档定义 + 三条硬约束写入载体；高风险永不免验逻辑存在 | 施工后 |
| 不越界 | A/B/C 组检查范围 = 卡文本，运行时验证仍归 parliament/review-loop（R2） | 评审核对 |
| 不豁免验收 | 评级只决定验收强度，低评强制全验、高风险永不免验（R4） | 评审核对 |

**不测**：运行时产出验证（parliament/review-loop 覆盖）；rule/skill 判据正文改写（line B）；S3/S4 迁移。

## 6 开放问题（送议会时一并裁）

1. **共享项载体落哪**：新建脚本（如 `tools/execution-matrix/` 或复用 docgen 组件）vs 新建技能 vs 只做文档索引？本 spec 建议「脚本 + 文档索引」双层（脚本机械查 A 结构项，AI 判 A 语义项/B/C 组走 annotations）。
2. **实测记录如何落 + 评级推导逻辑落点**：复用 lessons（managing-lessons-store）还是 retro 复盘，还是新建模式表登记文件？本 spec 建议模式表文件本身即登记处（每轮实测补行），且**模式表行结构须含「实测记录数 / 最近 N 次是否零回归」字段**（否则评级「依据可复算」无取数对象，对齐后端/前端评审共识）；评级由模式表记录数按固定映射现算（推导命令写入评级载体，使 TC-034/035 有明确断言对象）。
3. **reviewer-audit 的 B/C 组初评**：施工后先对 reviewer-audit 卡做一次全判，报出存量问题（如 C3 结论节证据要求可能缺失）——这些问题是否立即修（改卡 = 改组件数据 → 生成 → 替换，走 parliament 替换确认流程），还是记入模式表留待 S3/S4？本 spec 建议记入模式表，不阻塞 S3/S4。
4. **触发机制⑦ 升格 allShared + 评级 N 阈值**：⑦ 是否升格（三类「何时触发」语义同构核对，按 TC-046 判据逐项核对，不同构则留 skillAndRuleShared）；评级「高」档的 N 取值（如 N=3）。两条裁决结果均写入归桶索引落地说明。

## 7 交付物

1. 执行力度矩阵归桶索引（三类型 checklist 各自一份，共享项引用）；
2. **agent 专属可执行性判据正文**（A/B/C 三组 + 判定实现：A 结构项脚本或复用 docgen 组件、A 语义项/B/C 组 AI 判 + annotations 三态）。**判据正文载体 = 单源文件**（路径与每项四要素：名称/判定对象/判定方式（机器查 or AI 判）/落位——spec 定稿后 pending-work-overview 线 E 的 A/B/C 细节并入该载体并瘦身，实现一处定义，对齐 R6 与后端/读者评审共识）；
3. 执行力度模式表（按场景索引的正反例，种子 ≥5 行；行结构含「实测记录数 / 最近 N 次零回归」字段供评级取数）；
4. 执行力度置信度评级定义（三档 + 三条硬约束 + 评级现算口径）；
5. 与 parliament/review-loop 的边界声明（R2/R3）。

## 8 测试与验收

**测试用例文件**：`docs/superpowers/specs/2026-10-20-execution-assurance-matrix-design-testcase.md`（由 `senior-sdet` 独立编写；每条用例五要素、负例 ≥ 正例、覆盖总表指回本 spec 的 R 编号与 §5 验收锚点）

**测什么 / 为什么**：归桶的正确性（共享项零重复、两两 shared 不并入 allShared）、agent 判据的可判定性（A 组机器可查、B/C 组判据明确）、模式表种子完整性（来源可复算）、评级硬约束（不豁免高风险）、边界不越界（R2/R3）。为什么：这套体系的全部价值建立在「归桶不漂移、判据可判、评级不退化」三件事上，任何一个出错都回到三套各写各的的老路。
