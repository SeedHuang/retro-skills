## 0. 失败场景（先立靶子，全部有实测）

| # | 现状拦不住的场景 | 新管道拦截机制 |
|---|---|---|
| F1 | **方案写了没人执行**：10-16 出 10 问题修复方案，10-17 债变 41（方案 ≠ 施工） | 环③方案成文 → 环④议会审批 → 环⑤强制施工；**每环有产出物，任一环没跑完 = 流程没结束** |
| F2 | **逐条修 = 头痛医头**：同根问题散在多条，改 A 引 B（review-all R4-R7 四轮才统一一个判据） | 环①**按病根聚类**，同根一起修（改一处 = 多个都好） |
| F3 | **方案本身错了没人拦**：上手就改，改完才发现方向错 | 环④方案过议会（方案是文档，走议会点将矩阵） |
| F4 | **修完没人独立复查**：「测试绿」当成「修好了」 | 环⑥复查：OCR 审代码 + 议会审文档 + 对账段审缝 |
| F5 | **复查重复劳动**：判过的文件没动过还重判，烧 token | 验证状态缓存（hash/git）：**只有动过的文件才需要重判** |
| F6 | **修一半 / 修错 / 引入回归没人抓** | 环⑥接 review-loop 修复纪律 A1-A4 + 每轮锁基线 |

## 1. 缺口归因：为什么必须新建，而不是改现有的

### 1.1 三工具分工（先划清边界，防重叠）

| 工具 | 修什么 | 范围单位 | 起手判据 |
|---|---|---|---|
| `review-loop` | OCR 报的单条评论 | 一次改动范围（工作区 / N 次 commit） | 有改动要审 |
| `evolving-skills` | 单个载体（rule / skill / automation）的修订 | 一个载体 | 要改「某个载体本身」 |
| **`systematic-repair`（新）** | **一批已发现问题（按病根聚类）当整体系统化修掉** | 一份问题清单 | 手上有**成批**问题要系统修 |

### 1.2 本质

**把「问题清单 → 系统化修复 → 复查」固化成一条可重复执行的管道。** 现有链路只到「发现问题」（OCR / 议会 / 报告）和「修单个问题」（review-loop / evolving-skills），中间**「把一批问题当整体修掉并闭环」这一环没有执行者** —— 这就是 F1 的根因。

### 1.3 边界

- **做**：聚簇 → 画失败面全貌 → 写方案 → 过议会 → 施工 → 复查，直到整批问题清零。
- **不做**：不发现新问题（发现归 OCR / 议会）；不替代 review-loop 的代码改动循环审查（环⑥**复用**它的复查能力）；**不改载体正文**——改 rule / skill 正文归 `evolving-skills`，本管道只到「确认要改哪个载体」，之后转接。
- **不新增角色**：方案编写者 = 议会答辩方的方向架构师 leader；施工者 = 每簇一个全新子代理；审批 = 议会；复查 = 议会 + OCR + 对账段。

### 1.4 联动四问（事前三步）

| 问 | 答 |
|---|---|
| 治本了吗 | 治的是 F1 根因「批量问题无执行者」。不是给单条打补丁，是补体系缺失的一环 |
| 有副作用吗 | 新增流程层 = 套娃风险（为管修复造的机制自己被审）。预防：产物限**机械脚本 + 测试**（累计 ≤150 行），脚本不进 LLM 审查面；方案文档属修复基础设施，不进 OCR |
| 跨问题联动吗 | **是设计目的**：环① 聚类就是让同根问题一次修完 |
| 跨项目吗 | 通用技能：任何项目的问题清单都能跑，不绑定本仓 |

## 2. 管道结构（六环 + 一次修复的生命周期）

```
输入：问题清单（来自 OCR / 议会 / 报告，带条号）

① 聚簇诊断 ──→ 簇表（每条问题落进某簇）
      ↓
② 失败面全貌 ──→ 每簇六维全貌（本质/同族/边界/验收/影响面 + 联动四问）
      ↓
③ 方案成文 ──→ 每簇一份修复方案（先红后绿）
      ↓
④ 方案过议会 ──→ 议会三态结论（通过/有条件通过/不通过）
      ↓（仅「通过」放行）
⑤ 施工 ──→ 每簇一个全新子代理执行；改动留工作区
      ↓
⑥ 复查与循环 ──→ 代码→OCR ／ 文档→议会 ／ 缝→对账段
      ↓
   有新增问题？ ──有──→ 回 ①（新发现并入清单重聚类）
                 └─无──→ 该簇停机
```

### 2.1 三引擎分工（发现 / 修复 / 复查）

| 引擎 | 发现环节 | 修复环节 | 复查环节 |
|---|---|---|---|
| OCR（代码） | ✔ 对编辑的 code 出评论 | — | ✔ 对修复完的 code 评审 |
| 议会（文档） | ✔ 文档问题 | ✔ 环④审批方案 | ✔ 对修复完的 doc 复审 |
| 对账段（缝） | — | — | ✔ 文档断言 ↔ 代码事实对账 |
| **本管道** | — | ✔ 环①~⑤ | ✔ 环⑥编排 |

> **为什么三者都要**：代码 + Markdown 同时在场时，两段各自绿、缝里仍可能「文档说两个参数、代码只读一个」——对账段专门抓这个。这正是用户 2026-10-17 的洞察「code + markdown 两者结合好像就不行了」。

### 2.2 一次完整修复的生命周期（自指）

本 spec 自己也走这条管道：**①写本 spec → ②本 spec 过议会 → ③通过后写 plan 施工**。设计决策风险高，所以要过议会；而管道产出的**脚本**属机械层，不进 LLM 审查面——两者的区别就在这里。

## 4. 六环详解

### 环① 聚簇诊断

- **做什么**：读问题清单，按**病根**聚类 —— 不按文件、不按严重度。病根聚类模板（6 类）在 `references/cluster-method.md`（词表/口径不一致、链路不完整、判定结果没留档、命名多口径、文档模板旧内容、测试覆盖不全）。
- **产出物**：`cluster-table.md`（簇号 / 病根一句话 / 含哪些问题条号 / 影响文件 / 预估规模）。
- **判据**：**输入清单每条问题必须落进某个簇**（簇表含全部条号；漏一条 = 环①没完成）。

### 环② 失败面全貌

- **做什么**：每簇按事前三步画全貌（本质 / 同族 / 边界 / 验收 / 影响面 + 联动四问）。
- **产出物**：写进该簇修复方案（环③）的「全貌确认」节。
- **判据**：每簇六维非空 + **影响面列到具体文件** + 验收带取数命令。

### 环③ 方案成文（先红后绿）

- **做什么**：每簇一份修复方案，按 `assets/fix-plan-template.md` 填；**先红后绿** —— 先写失败测试（断言现存缺陷会红），再写实现（转绿）。
- **产出物**：方案文档（每簇一份），含六节：全貌确认 / 修复步骤 / 失败测试 / 验收命令 / 牵连副作用 / 不做什么。
- **判据**：每簇方案齐六节；**每条验收都是「命令 + 预期输出」**（不可执行的「加强 / 优化」类写法不算）。

### 环④ 方案过议会

- **做什么**：把方案文档交议会审批。点将按 `parliament` 的点将矩阵（`references/assembly-matrix.md`）：方案是文档型产出 → 以「纯文档仓库」为底（读者代表 + 审计），按每簇触碰的领域加席（碰 code → 测试 / 后端 / 前端；碰 rule/skill → AI 评委）。
- **产出物**：议会三态结论（**通过 / 有条件通过 / 不通过** —— 复用议会 `assets/delivery-audit.md`）。
- **判据**：**没有议会「通过」的方案 = 不许进环⑤**；「不通过」或「有条件未满足」= 打回环③。

### 环⑤ 施工（每簇一个全新子代理）

- **做什么**：**每簇派一个全新子代理**（无状态；提示词 = 该簇方案 + 判类表 + 收尾动作「改动留工作区，不 commit」）；子代理按方案的先红后绿执行。
- **产出物**：改动（留工作区）+ 子代理回报（改了哪些文件 / **失败测试红转绿两段输出**）。
- **判据**：每簇**先红后绿**必须有两段证据 —— 只贴绿 = 没做先红 = 不算。

### 环⑥ 复查与循环

- **做什么**：对本轮修复的改动跑三引擎复查 —— 代码 → OCR（`ocr review`）；文档 → 议会；缝 → `review-loop` 段三（对账段）。按 review-loop 停机判据循环（**修复轮 + 复查轮都干净才停**）。
- **产出物**：复查报告 + 增量账本。
- **判据**：该簇范围「修复轮 + 复查轮干净」；有新增 → 回环①（新发现并入清单重聚类）。

## 5. 判类表（环⑥核心：哪些对账能机械、哪些只能 agent）

| 层 | 判据 | 谁做 | 漏什么 |
|---|---|---|---|
| **结构投影** | 两边是同一份结构的拷贝（数字 / 字段名 / 路径 / 计数）→ 逐字比对 | 机械（脚本 / grep） | 保「不漂移」**不保「正确」** |
| **浅语义模式** | 句式 / 词表 / 格式：机器能查字面存在，语义要人 | 半机械（机器筛 + agent 判） | 必须记**判别力水位** = 这条机械检查漏了什么 |
| **语义本身** | 逻辑闭环 / 矛盾 / 盲点 | 永远 agent（OCR / 议会） | 无 |

**实测比例**（41 族问题）：机械 31（76%）/ 半机械 6（15%）/ agent 4（10%）。

**三条硬规矩**：
1. **半机械最不靠谱**（机器绿了语义可能仍错）→ 半机械项必须**同时**保留「机械筛 + agent 判」，且**显式记判别力水位**（防「机械绿 = 语义合格」的假安全）。
2. **机械守卫保「不漂移」不保「正确」** —— 所以机械层和 agent 层必须同时存在，缺一不可（用户 2026-10-17 结论）。
3. 判类不按成本看，按**判据形态**看：结构投影天然机械、语义天然 agent；分类成本 = 写守卫的第一步（评委卡顺带供给），运行机械侧归零。

## 6. 验证状态缓存（管「动过没」，不管「配不配套」）

- **目的**：决定「要不要重新跑 agent 判断」——**只有内容变过的文件才需要重判**。
- **机制**：以 **git 为准**（`git diff --name-only <baseline> HEAD -- <paths>`）；辅以 `scripts/verify-cache.mjs` 产出的 `verify-cache.json`（文件 → 已验 hash + 结论），落 `.session/`（不进 git）。**hash 变了 = 需重判；没变 = 复用上次结论。**
- **边界（关键）**：缓存只覆盖**单文件自洽**类判据；**跨文件 / 跨章节一致性**的判据**不缓存** —— 文件本身没动、但它的邻居动了，仍要重判（这是「镜像断言」的活，不是缓存的活）。
- **脚本约束**：`verify-cache.mjs` ≤150 行 + test，**不挂 `npm run check`**（依赖 `.session/`，同 `review-audit.mjs` 先例，挂进流程必经路径即可）。

## 8. 停机与升级

- **单簇停机**：该簇「修复轮 + 复查轮干净」（review-loop 停机判据，不重定义）。
- **整批停机**：全部簇都停 **且** 输入清单**每条问题有终态** —— 已修 / 关闭（带理由）/ 候选（带触发信号）。**留白 = 没修完。**
- **不成环（3 轮不收敛）**：按议会升级报告（`assets/escalation-report.md`；双方摸查记录 + 各自解法必填；无摸查 = 臆想争端）。
- **不设轮数配额**：轮数是结果不是旋钮；超过 5 轮 → 触发过程复盘（沿用 review-loop 绊线逻辑）。

## 11. 风险与已声明局限

- **套娃风险**：本管道产物本身须小体量（机械脚本 ≤150 行）+ spec 自身不进 OCR（属修复基础设施）；但**本 spec 要过议会** —— 区别：设计决策过议会，产物脚本不过 OCR。
- **半机械最危险**：机械绿 ≠ 语义合格；靠「判别力水位」记录兜底，不假装覆盖。
- **缓存边界**：跨文件一致性判据不缓存，别把「文件没动」误当成「不用重判」。
- **施工质量不保一次到位**：方案对不对归环④，修得全不全归环⑥ + 子代理证据；新代码可以有新缺陷（沿用 review-loop 已声明局限）。
- **首场即验收**：41 问题既是债也是考试 —— 全抓 = 通过，漏 = 环①/判据返工。
- **路径 C 降级**：无调度能力时第四层防线打折，报告必标「降级模式」。
