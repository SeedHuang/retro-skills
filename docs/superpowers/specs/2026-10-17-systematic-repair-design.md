## 1. 这个工具解决什么

**输入**：一批已知问题（来自 OCR / 议会 / 报告，带条号）。
**输出**：每条问题都有终态——已修 / 关闭（带理由）/ 候选（带触发信号）/ **工单已产出**（载体簇）。

- **做**：按病根分组 → 每组写方案 → 议会审批 → 一组一组修 → 换人复查，直到每条有终态。
- **不做**：不发现新问题（归 OCR / 议会）；不替代 `review-loop` 的代码改动审查；**不直接改规则 / 技能正文**——只出「载体修订工单」交给你。
- **边界**：本版只支持有子代理调度能力的环境（路径 A/B）；没有就明确拒绝运行（见 §6）。

> 术语：**族 = 按病根聚类后的问题族**。本文的「首场 41 条」指 2026-10-17 议会验收账本的输入；F/G/H/J 等族号属评审过程账，不进本工具的运行数据。

## 2. 六步主线

```

   ↓
① 按病根分组 ──→ clusters.md
   ↓
② 每组画全貌 ──→ 写进方案
   ↓
③ 每组写方案（先红后绿；载体组另出工单）──→ plans/<簇号>.md
   ↓
④ 方案与工单过议会（闸门 1）──→ approval.md
   ↓（通过 / 有条件且条件已核销）
```

**产出物**（运行期目录 `.session/reviews/<YYYY-MM-DD-HHMM>-repair-<kebab>/`，复用 reviews 的过程账语义，处置完即删；不进 git）：

## 3. 角色

| 角色 | 谁 | 权限 | 禁令 |
|---|---|---|---|
| 主持人 | 主 agent 兼 | 编排、调度、记账 | 不得代填审计 |
| 方案编写者 | 议会答辩方方向架构师 leader（按清单主领域选） | 写方案与工单 | 无 git 写权限 |
| 审批者 | 议会（评审团 + 侦探 + 审计） | 通过 / 打回 | 只读 |
| 施工者 | 每簇一个**全新**子代理 | 改文件（留工作区） | 不 commit / 不 push；不越出方案的影响文件清单 |
| 复查者 | 议会 + OCR + 对账段 | 只读复查 | 不出方案 |

**执行路径**：A（Trae Agent / SOLO，点名用户级子代理）或 B（Builder / IDE，Task 派通用子代理）。**两者都不可用时拒绝运行**，报告写「本环境无调度能力，本工具不降级」。

## 4. 六步怎么做

### ① 分组

- **输入校验**：空清单 → 停机报「无待修项」；条号重复 → 同号同描述去重、同号不同描述拒收要求改号；缺号/非法 → 拒收；多份清单 → 条号加清单前缀后合并。
- **分组依据**：按病根，不按文件、不按严重度。簇表用「主病根 + 关联病根」两列；都不命中 → 能命名主病根就新建簇，命名不出但能写「出现什么信号时归类」→ 待定簇。
- **判据**：**输入清单每条问题都有簇号**，缺一条 = ① 未完成。

### ② 画全貌

- 每簇六维：本质 / 同族 / 边界 / 验收 / 影响面 + 联动四问（治本 / 副作用 / 跨问题 / 跨文件）。
- **判据**：六维非空；**影响面列到具体文件**；验收每条带命令或明确的人工判据。

### ③ 写方案（先红后绿）

- **簇类型**：施工 / 载体 / 混合。**混合簇在 ③ 拆成施工簇 + 载体簇**（一个条号只属于一个簇）。
- **六节**：全貌确认 / 修复步骤 / 失败测试 / 验收 / 牵连副作用 / 不做什么。
- **验收写法**：三列——`类型（自动/人工）` | `命令或判据` | `预期结果`；人工项写「谁看、看什么」。
- **红绿证据（两类形态，仅施工簇）**：
  - 代码簇：红 = 失败测试（退出码非 0）；绿 = 同一条命令（退出码 0）。
  - 文档簇：红 = 可执行断言（目标文本 grep 计数 > 0；或两处标识符必须互指的 `grep` 断言）；绿 = 同一条命令结果反转。
  - 两段都写「命令 + 退出码 + 输出」；**命令只填一处**，红绿共用。
- **载体工单**（载体簇）：5 字段——目标载体 / 改什么 / 验收命令 / 交付对象 / 备注。**工单写入 `plans/<簇号>.md` 即算该簇完成（条目终态 = 工单已产出）**；本版不转交、不等待、不收执。

### ④ 过议会（闸门 1）

- **点将**：底板 = `parliament` 矩阵的项目类型行（本仓 = 纯文档仓库：读者代表 + 审计），再按簇领域补按需席（碰代码 → 后端 + 测试；碰规则/技能 → AI）。增席按矩阵「轮间补点」留痕。
- **结论三态**：通过 / 有条件通过 / 不通过。
- **放行（以 `parliament` 的交付审计表为准）**：通过 → 放行；有条件通过 → 相关条目转「候选（带触发信号）」，该簇可停机；不通过 → 打回 ③。**本版不自造「条件核销」机制。**

### ⑤ 一组一组修

- **串行**：一簇收口后再派下一簇；**不并行**（本版不做并行归属，见 §6）。
- **提示词五要素**（每簇派发前写全，缺一不派）：
  1. 身份与所在环节（你在修某一簇，只按方案执行，改完停手）；
  2. 该簇方案 + **影响文件边界清单**；
  3. 红/绿两段证据的格式；
  4. 收尾动作（改动留工作区，不 commit / 不 push）；
  5. 回报格式（改了哪些文件 / 红段 / 绿段）。
- **越界请求**：必须改边界外文件时停手回报「要改的文件 + 理由」，由主持人决定：排到别簇 / 回 ③ 改方案 / 记新增问题。**禁止自行扩范围**。
- **判据（仅施工簇）**：红、绿两段证据齐。**红段必须在开工前写入 `repair-progress.md`**，并附「开工前 `git status --porcelain -- <影响文件>` 为空，或只有本簇声明的新增测试文件」；只贴绿 = 没做先红 = 该簇回报作废，**重开簇**（先列出已有改动文件，再手工回滚或接受现状后重跑）。**载体簇不进 ⑤。**

### ⑥ 换人复查（闸门 2）

- **路由**：`.md` → 议会；代码文件 → OCR（按 `review-loop` 段一口径：`--preview` 清单逐条审完并登记）；「文档断言 ↔ 代码事实」的缝 → `review-loop` 段三。对账段**只借段三方法，不建 review 分支、不 commit**。跨类型簇三段并列跑、报告分列。
- **载体簇不进 ⑥**：其终态在 ④ 放行后即为「工单已产出」，簇直接置「已停机」。
- **全量复查**：本版**不缓存**——每次复查把该簇涉及的文件全部重判。
- **复查报告五节**：① 簇与改动文件；② 红绿复跑结果；③ 判类与判别力水位；④ 终态与条号；⑤ 未解决项。缺节 = ⑥ 未完成。
- **判类**：三层——结构投影（机械逐字比对）/ 浅语义（机器筛 + 人判）/ 语义（只能人判）。判定顺序：是否同一结构拷贝 → 机器能否查字面存在 → 否则语义。**半机械项必须记水位三要素**（漏检哪类反例 / 至少 1 个样例 / 语义由谁兜），**水位为空 = 该轮不算数**；水位只记在 `recheck-report.md` 第③节这一处。
- **停机**：修复轮 + 复查轮都干净才停。**干净 = 本轮新增条号为 0、复查报告第⑤节未解决项为空、无未处置的 P0/P1。** 有新增 → 回 ①（已停机簇冻结，新增只在未停机簇之间重聚；无未停机簇则新建簇）。

## 5. 终态与停机

- **条目终态（四值）**：已修 / 关闭（带理由）/ 候选（带触发信号）/ **工单已产出**（载体簇：工单写入 `plans/<簇号>.md` 即算）。
- **簇状态（三值）**：未开工 / 在修 / 已停机。转移：⑤ 派发 → 在修；⑥ 判定干净 → 已停机；**载体簇 ④ 放行 → 直接已停机**；重开簇 → 未开工。
- **`repair-progress.md` 固定字段**：簇号 / 轮次 / 簇状态 / 红段（命令 + 退出码 + 输出，开工前写入）/ 绿段（同一命令）/ 改动文件清单 / 越界结论 / 终态。
- **条号守恒**：`（输入条号 ∪ 新增条号）= 各终态条号`；新增条号由 ⑥ 按 `R<轮次>-<序号>` 当场分配并入账。**本版不支持重开条目**；重开簇沿用原条号。
- **整批停机**：全部簇已停机 **且** 每条有终态；留白 = 没修完。
- **轮数**：3 轮 = 议会答辩轮（超 3 轮走议会升级报告）；5 轮 = 修复-复查轮（超 5 轮触发过程复盘）。不设提前停机配额。
- **升级**：按 `parliament` 的升级报告（双方摸查记录 + 各自解法必填）。
