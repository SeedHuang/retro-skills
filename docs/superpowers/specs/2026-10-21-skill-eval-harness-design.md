# Skill 行为评测：仓库内用例工装（skill-up 本地化）

> 日期：2026-10-21｜状态：**待评审（未定稿）**｜触发：用户 2026-10-21 决定「参考 skill-up 的测法与脚本，做本地化并入库」
> 测试用例文件：`docs/superpowers/specs/2026-10-21-skill-eval-harness-design-testcase.md`（由独立 `senior-sdet` 子代理在全新上下文编写）
> 依赖：无。本 spec 不动 `skills/` 下任何技能正文、不动 `npm run check`、不动 `tools/`
> 实测依据：`.session/eval-trial/`（三轮试跑，2026-10-21）

## 0 为什么

我们现有的验证只有两层，中间缺一层：

| 层 | 工具 | 管得到 | 管不到 |
|---|---|---|---|
| 静态 | `npm run check` | 文件结构、引用一致、markdown 形态 | agent 读完 SKILL.md 会不会照做 |
| 单元 | `node --test` | 脚本逻辑 | 同上 |
| 长期 | `retro-verify` | 复发率（需攒够机会数） | 单次改动、发布前 |

后果是具体的：改一条技能的判据措辞、改一条纪律，**要等下一次真实 session 才知道有没有生效**，而且要攒够样本才敢下结论。

skill-up 提供了这一层：同一道题、同一个模型，跑「装技能 / 不装技能」两遍，比差值。2026-10-21 实测确认它在本机可跑（Windows 原生、不用 Docker），并且抓到了真实差异：

- 用例「命令替换必须 review」：装技能 3/3 通过，不装 0/3 通过；
- 不装技能时的理由是「跑一遍绿了就提交」，装技能时是「跑绿只证明脚本自己跑得通，不证明这次替换是对的」——**这正是该技能要纠正的行为，现在可以被量化**。

本轮只做一件事：**把这套测法固化成仓库里的工装**——用例进 git、路径不进技能目录、输出不污染仓库、断言有写法规矩、结论有价值判据。不引入 skill-up 作为 `npm run check` 的依赖。

## 1 全貌确认

| 维度 | 内容 |
|---|---|
| 本质 | 缺一层「行为回归」：技能的约束力没有被任何机器证据覆盖 |
| 同族 | ① `retro-verify`（长期复发率）② checklist（人工逐条核对）③ 议会评审（人/代理读文档判断）。三者都在，但都不是「同一 prompt 装/不装对比」 |
| 边界 | 只管**用例工装**（放哪、怎么跑、断言怎么写、结果怎么判）。不管技能正文、不管 CI、不管 Trae CLI（企业旗舰版限制，个人不可用）、不改 `check-all` |
| 验收 | 用例进 git 且不出现在 `skills/` 下；`npm run check` 仍全绿且仍零依赖；一条技能两条例跑出「装/不装」差值且理由正确；断言写法有可判定的规矩 |
| 影响面 | ① 新增 `evals/`（用例 + fixture）② `package.json`（一条 npm script）③ 新增 `scripts/run-eval.mjs`（解析二进制、固定输出目录、强制迭代次数）④ `.gitignore`（评测产物）⑤ 不改 `skills/`、`tools/`、`scripts/check-all.mjs` |

**联动四问**：

- **治本了吗**：治的是「技能约束力无证据」这个根，不是某一条技能的具体错。用例与技能同仓同版本演进，改技能后能立刻看到差值有没有掉。
- **有副作用吗**：① `npm run check` 的 markdown 检查会扫到新增的 `.md`（若有），必须合规；② 默认产物目录会落在技能目录旁边（skill-up 的默认行为），必须在脚本里显式改道，否则 `skills/` 会被污染；③ 会花模型调用，必须与 `check` 隔离。
- **跨问题联动吗**：与「断言必须盯错误形态」「fixture 要能实跑判据」两条经验同源——它们不是 skill-up 的知识，是我们写用例时必须遵守的规矩。
- **跨项目吗**：`evals/` 是仓库级工装，不进 `skills/` 就不会随 `npx skills add` 发给用户；不影响使用者。

## 2 核心决定（不可违反）

| # | 决定 | 为什么 |
|---|---|---|
| R1 | **用例放 `evals/`（仓库根），不放 `skills/`**。结构 `evals/<技能名>/{eval.yaml,cases/*.yaml,fixtures/}`，`eval.yaml` 的 `skills[].path` 指回 `skills/<技能名>`（实测：外部路径可正常安装并跑出与内置路径一致的差值） | 技能是产品、评测是工装。放 `skills/` 内会随 `npx skills add` 一起打包，也违反技能目录三档约定（`scripts/` / `references/` / `assets/`） |
| R2 | **不进 `npm run check`**。评测走独立 npm script，`check` 保持零外部依赖、确定性、每次必跑 | `check` 的契约是「不花钱、跑得快、结果确定」；评测会花模型调用且结果有抖动，混进去会让 `check` 失去可信度 |
| R3 | **产物目录强制改道**：runner 必须显式传 `--output-dir .session/eval-out/<技能名>/`，禁止依赖默认值 | skill-up 默认产物落在「技能目录旁边」，即 `skills/<技能名>-workspace`——会污染 `skills/`，且被判成垃圾目录 |
| R4 | **断言只盯错误形态，不盯模板字眼**。① `must_not_contain` 只放「正确答案不会出现的错误推理」（如 `低风险`、`纯文档`、`不涉及代码`）；② 不得把分档标题（`必须 review`）写进 `must_not_contain`——正确答案也会打印 `⚠️ 必须 review：无`；③ 每条用例必须同时具备「正例证据词」与「负例禁令词」 | 实测两次踩中：只看结论词会放过错误理由；只看标题会误杀正确答案。断言的职责是区分**理由**，不是区分**排版** |
| R5 | **凡技能判据要求「实跑命令」的用例，必须给真 fixture 仓库**（`context.repo_fixture` + `git.init` + `apply_diff`），不得在 prompt 里粘贴 diff 充当证据 | 实测：空目录下技能按自己的硬约束（免审必须报命令名 + 实跑结果）把粘贴的 diff 判成必审——**这是忠于规则**，不是缺陷；用例环境不成立，结论就不成立 |
| R6 | **单次结果不作数**：runner 强制 `--iteration >= 2`，报告必须打印 flaky 判定；任一条用例出现 flaky → 该用例结论为「无效」，先改用例，不得据此判定技能好坏 | 实测：同一条用例两遍一过一挂。单次通过率当门禁，会今天绿明天红 |
| R7 | **基线必开**（`benchmark.enabled: true`）。指标是「装 / 不装」的差值，不是绝对通过率 | 绝对通过率说不出「技能有没有用」；差值才能。R4 的断言质量通过差值体现 |
| R8 | **本轮范围只到 `review-triage` 两条用例**。不铺开到 18 个技能，不建 CI 门禁 | 先证明方法论对我们成立，再谈规模。铺开是成本决定，不是技术决定 |
| R9 | **结论带引擎与模型边界**：报告必须记录实际引擎与模型；结论只对该组合成立。经 CCR 转发时实际模型可能不是 Claude（实测为 GLM-5.3-Flash），**不得把结论写成「Claude 也这样」** | 换模型/换引擎后行为会变；不标注边界的结论会被直接误用 |
| R10 | **事前写死判据**（预期值先定，跑完再对）：<br>· 用例「命令替换必须 review」：装技能 ≥ 2/2 通过，不装 ≤ 1/2 通过<br>· 用例「纯勾选可免审」：装技能 2/2 通过且理由含实跑证据（`diff` / `字面核对`）；不装技能至少 1/2 出现禁令词（`低风险` / `纯文档` / `不涉及代码`）<br>实测不达 → **判用例无效并改用例**，不得改技能去迁就用例 | 没有事前预期值的验收，跑完总能自圆其说；把「不达怎么办」先写死，才拦得住事后编理由 |

## 3 细节

### 3.1 目录结构

```text
evals/
└── review-triage/
    ├── eval.yaml
    ├── cases/
    │   ├── 01-checkbox-mechanical.yaml
    │   └── 02-command-swap-semantic.yaml
    └── fixtures/
        ├── repos/checkbox-demo/notes/plan.md      # 改动前版本（仍为 [ ]）
        └── diffs/checkbox.patch                    # 把 [ ] 改为 [x]
```

- 用例文件名即用例 ID（工具约定），不以中文命名。
- `fixtures/` 只放用例真正用到的素材；不复制整仓。
- 新增技能用例时按同一结构追加 `evals/<技能名>/`，不改已有目录。

### 3.2 `eval.yaml` 契约（本轮固定值）

| 字段 | 值 | 说明 |
|---|---|---|
| `schema_version` | `v1alpha1` | 工具固定值 |
| `environment.type` | `none` | 本轮不隔离沙箱；副作用由「只读 prompt + fixture 仓库」兜住 |
| `skills[0].source` | `local_path` | 指向仓库内真技能目录 |
| `skills[0].path` | `skills/review-triage` | **相对仓库根**；不用 `.`（那是「与本文件同级」） |
| `engine.name` | `claude_code` | 本机唯一已验证可用的引擎 |
| `engine.model` | 由 runner 从环境决定，报告中必须落账 | 不得在用例里写死一个本机未必存在的模型名 |
| `cases.defaults.timeout_seconds` | `240` | 单用例 4 次调用的实测耗时留足余量 |
| `cases.defaults.max_turns` | `8` | 本技能是单轮分流任务，不需要长流程 |
| `benchmark.enabled` | `true` | R7 |
| `report.formats` | `[json, html]` | json 供机械核对，html 供人读 |

> **已知缺口（实测 2026-10-21）**：`skills[].path: .` **不会**被 `skill-up validate` 拒绝（实测 exit 0）。也就是说 R1 的「必须指向 `skills/<技能名>`」**没有工具级强制**，只能靠 §5① 的结构断言（`evals/` 下不得出现 `SKILL.md`、`skills[].path` 必须以 `skills/` 开头）兜住。这条缺口不得被写成「工具会拦住」。

### 3.3 runner 契约（`scripts/run-eval.mjs`）

**不做**任何判分逻辑——判分全在 skill-up 内。runner 只做四件事：

1. **定位二进制**：依次取 `SKILL_UP_BIN` 环境变量 → `PATH` 中的 `skill-up`；都找不到 → 打印安装指引并非 0 退出（**不得静默跳过**）。
2. **固定参数**：`run evals/<技能名>/eval.yaml --output-dir .session/eval-out/<技能名> --iteration <N> --baseline`，`N` 默认 2。
3. **透传退出码**：skill-up 非 0 → runner 非 0（供未来接 CI），但**不把非 0 解释成「技能坏了」**——报告里必须同时打印 flaky 判定。
4. **打印结论边界**：把实际引擎 / 模型、迭代次数、每条用例的 flaky 判定打到 stdout（R9）。

不写日志文件、不做结果聚合、不做历史对比——这些由 skill-up 的 `json` 报告承担。

### 3.4 用例写作规矩（新增用例必须遵守）

| 规矩 | 判据 |
|---|---|
| 正负例配比 | 每条技能至少 1 条「应通过」+ 1 条「应拒绝/应升级」；负例不得少于正例 |
| prompt 只给输入，不给答案 | 不得在 prompt 里暗示该走哪一档 |
| 断言双面 | 每条用例同时有「必须出现」与「必须不出现」，且两者都是**理由级**词 |
| 环境可判据 | 若技能要求实跑命令，必须给 fixture 仓库（R5） |
| 不写绝对路径 | `skills[].path`、fixture 引用都用仓库内相对路径 |

### 3.5 判据对照（本轮两条用例）

| 用例 | 测什么 | 装技能预期 | 不装技能预期 |
|---|---|---|---|
| `02-command-swap-semantic` | 执行动作替换（`npm run check` → `check:all`）是否被判「必须 review」，且理由是「跑绿 ≠ 判据对」 | 通过 | 失败：给的是「跑一遍绿了就可以提交」 |
| `01-checkbox-mechanical` | 纯勾选改动是否被判「可直接提交」，且**报出实跑证据** | 通过（理由含 `diff` / `字面核对`） | 至少 1 次用「低风险 / 纯文档」当免审理由 → 失败 |

## 4 施工步骤

1. 建 `evals/review-triage/`，迁入两条用例（`02` 断言沿用已验证版本；`01` 按 R5 补 fixture 仓库与补丁，断言按 R4 重写）。
2. 写 `evals/review-triage/eval.yaml`（§3.2）。
3. 写 `scripts/run-eval.mjs`（§3.3），`package.json` 加 `"eval:review-triage": "node scripts/run-eval.mjs review-triage"`。
4. `.gitignore` 加评测产物目录（`.session/` 已在忽略列表内，确认无需新增条目即可；若改道目录不在 `.session/` 下则必须新增）。
5. 跑 `npm run eval:review-triage`，按 R10 对预期值。
6. 跑 `npm run check`（应全绿；本 spec 不新增 `.md`，markdown 检查不受影响）。
7. 改动留工作区，提交方式由用户决定（不执行任何 git 写操作）。

## 5 验收

| # | 检查 | 判据 |
|---|---|---|
| ① | 用例位置 | `evals/` 存在且 `skills/` 下无 `evals` 子目录；`eval.yaml` 的 `skills[].path` 以 `skills/` 开头（工具不校验 `.`，见 §3.2 已知缺口）；`git status` 中新增文件全在 `evals/` 与 `scripts/` |
| ② | 不污染 `skills/` | 跑完评测后 `skills/` 下无新增目录（特别无 `review-triage-workspace`） |
| ③ | `check` 契约不破 | `npm run check` 全绿；`check-all.mjs` 零改动；`package.json` 仅新增一条 script |
| ④ | 差值成立 | 用例 02 达到 R10 的预期值；用例 01 达到 R10 的预期值 |
| ⑤ | 断言质量 | 两条例的 `must_not_contain` 中不含分档标题；每条同时有正例证据词与负例禁令词 |
| ⑥ | 稳定性有账 | 报告含 flaky 判定行；若任一条 flaky → 结论记为「无效」并停下改用例 |
| ⑦ | 结论带边界 | runner 输出与报告均含引擎名与实际模型名 |
| ⑧ | 素材可重建 | 删掉 `.session/eval-out/` 后重跑，结果与用例文件一致（fixture 不依赖残留产物） |

## 6 硬约束

1. **不改 `skills/` 下任何技能正文**。用例不通过时先怀疑用例，不迁就改技能（R10）。
2. **不改 `scripts/check-all.mjs`**，不把评测挂进 `npm run check`（R2）。
3. **不改 `tools/`**，不引入 skill-up 作为仓库运行依赖（二进制是外部可选工具）。
4. **断言不得用分档标题充当禁令词**（R4-②）。
5. **要求实跑判据的用例必须有真 fixture 仓库**（R5）。
6. **结论必须标注引擎与模型**（R9）。
7. **不执行任何 git 写操作**；改动留工作区由用户决定提交方式。

## 7 测试

| # | 测什么 | 为什么 |
|---|---|---|
| 1 | 用例位置与打包边界（`evals/` 不在 `skills/` 内） | R1 的全部价值在于「产品与工装分离」；放错位置就把它变成产品的一部分 |
| 2 | 产物改道（跑完 `skills/` 不变） | 默认产物落在技能目录旁边，不改道就污染仓库 |
| 3 | `check` 零依赖契约不破 | 评测一旦进 `check`，`check` 会变成「要钱、会抖」的检查，可信度崩塌 |
| 4 | 两条用例的双面断言（正例证据词 + 负例禁令词） | 断言质量直接决定差值有没有意义 |
| 5 | fixture 仓库可实跑（`git diff` 有输出） | 技能硬约束要求实跑证据，环境不成立则用例无效 |
| 6 | 迭代稳定性（≥2 次，输出 flaky 判定） | 单次结果不可用 |
| 7 | runner 找不到二进制时的行为 | 静默跳过会让「没跑」看起来像「通过」 |
| 8 | 报告含引擎与模型 | 结论边界不可丢失 |
| 9 | `npm run check` 全量绿 | 判据只在真入口上算数 |

**测试用例文件**：`docs/superpowers/specs/2026-10-21-skill-eval-harness-design-testcase.md`（由 `senior-sdet` 在全新上下文独立编写；按「位置与产物 / 断言质量 / 稳定性 / runner 行为」分组，不按施工步骤复制；覆盖总表须指回本 spec 的 R 编号与 § 号）。

**执行环境**：Windows + PowerShell；skill-up 二进制由 `SKILL_UP_BIN` 或 PATH 提供（本机实测路径 `D:\devtools\skillup\skill-up.exe`，v0.14.0）。**评测需要模型凭据**：无凭据时只跑 `skill-up validate` 与 `--dry-run` 作结构验证，真跑用例需人工在具备凭据的环境执行。

**只手动验证**：读一遍用例 01 改 fixture 之后的真实回复，确认它报的是「实跑得到的证据」而不是「复述 prompt 里的 diff」。

**不测**：其他技能的用例（R8）；Trae CLI 引擎（企业旗舰版限制，个人不可用）；CI 接入。

## 8 不在这一轮

- 其余 17 个技能的用例（先证明方法论成立再扩）。
- CI 门禁 / 提交前自动跑（需先定重复次数、阈值、谁承担调用成本）。
- 自定义引擎适配层（把其他 agent 包装成 skill-up 引擎）。
- `agent_judge`（模型打分）：贵且不稳，本轮全部用确定性判分；需要语义判断时优先改成「理由级关键词」。
- Trae CLI 引擎：官方限制仅企业旗舰版可用，个人不可用，不作为前置。

## 9 与既有体系的关系

- **不取代** `npm run check`（静态）、`node --test`（脚本层）、`retro-verify`（长期复发率）、议会评审（判断质量）。四者分别回答不同问题；本 spec 只补「同一 prompt 装/不装的差值」这一格。
- **不取代** checklist：checklist 是「这一次动作有没有按规矩做完」，评测是「这条技能对模型有没有约束力」。
- **与 `skill-inspector` 的边界**：`skill-inspector` 体检技能文档的写法，评测验技能对模型的行为；前者判文档，后者判行为。
- **本 spec 不产生新的判据单源**：用例写作规矩（§3.4）是评测工装内部的规矩，不外溢成全局规则；若后续证明它对多类任务都成立，再单独走规则落地。
