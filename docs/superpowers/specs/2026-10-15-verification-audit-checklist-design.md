## 1. 要解决的问题（病根，三层）

用户指令原话背景：「AI 很多时候自作主张跳过我规定一定要做的事，还经常骗我说已经做过了，直到我问他才承认没做。」

| 病层 | 机理 | 「写清楚」治得了吗 | 对症的修法 |
|---|---|---|---|
| ① 看不懂 | 判据文本缺失或含糊 | ✅ 治 | 判据写清楚 |
| ② 不在场 | 检查躺在出处文件里，执行那一刻不在注意力里——规则对人是持续生效的约束，对 agent 是**被动文本**，恰好读到才存在 | ❌ 治不了 | **把检查钉进每轮结论模板**——完成一轮的必经路径上，不填不算数 |
| ③ 声称无成本 | 「我查过了」和「我猜它没问题然后说查过」生成**同构文本**；触发条件要 agent 现场语义归类，归类偷懒 = 掠过 | ❌ 治不了 | **确认执行必须贴命令 + 实际输出**（可复跑复核）+ **用户抽查**（跳过的期望成本从零变成会穿帮） |

本仓实测证据（都在 review-all-to-death 账本）：R9 复盘「写 ✅ 的那条恰恰是没查的那条」；R11「拿想要的结论当证据（序 6 机械信号全仓不存在）」；loop.md §3 实测注记「第 4 轮违规问要不要提交」；2026-10-15 标题一致性漏检（硬闸门 6 明文存在、review 流程从未接入）。

## 2. 机制

### 2.1 每轮「验证查账」表（模板节，必填）

- **固定 34 项全清单**，每轮逐行过——不适用也写「不适用」，防「漏触发 = 漏检」（2026-10-15 实测：标题一致性就是这么漏的）。
- 与 progress「验证」节的分工：**验证节记「修复的验证细节」（改的对不对）**；**查账表记「全部该做检查的执行状态」（该做的做了没）**——两回事，不许合并。
- **三态状态**：
  - **确认执行**：必须贴命令 + 实际输出，用户可复跑复核。**禁止只写「已检查」**。
  - **未执行**：必须附真实理由 + 归因（见 2.2）+ 载体修复去向。**无归因的「未执行」= 无效**。
  - **不适用**：写明哪个触发条件没发生（如「本轮没改规则正文」）。
- **算数判据**：任何一行空着、或存在无归因的「未执行」→ **该轮不算数，停下**——补做，或经用户裁定豁免（对应用户硬约束「没做就停下来」）。

### 2.2 归因三选一（未执行项必填）

| 归因 | 判定 | 修法落点 |
|---|---|---|
| **rule 缺 / 没写清** | 全局规则里没有这条约束，或约束含糊 | 补 rule（**先按 how-i-must-reason 收尾审计落点表定载体层**——通用推理纪律→本规则；通用项目约定→docs-convention 等；只在技能内生效的纪律→该技能 references/*.md） |
| **skill 缺 / 没写清** | 约束存在但没接进执行路径，或措辞弱（「建议」给了 agent 自行决定的空间） | 补 skill |
| **载体写清了、执行侧没做** | 载体有明文（可引用位置），漏在执行 | 进复盘 / KB 记机制教训，**不改载体**；同一处**反复复发 → 升级工程化**（机器可判，如 score.mjs 文件断言——结构上不依赖 agent 在场与自觉），不是改措辞 |

归因示例（2026-10-15 实录）：标题一致性漏检 → **skill 缺**（rule-inspector 硬闸门 6 只在体检流程生效、review 流程未接入 → 修法 = 查账表第 23 行）；preview 未跑 → **skill 措辞弱**（「建议」级）→ 查账表明示建议级、仍须交代状态。

### 2.3 三处显示（用户查账的三个入口）

| 载体 | 显示什么 |

| progress.md 每轮小节 | 查账表全 34 行（明细 + 命令 + 输出） |

## 3. 全库体检授权边界

- `rule-inspector --dir` 全库体检 = 高影响动作，**须用户明确要求**（「体检全部规则」类指令）。
- agent 在修复 / 审查流程中，只对**本次改动过的规则**跑 `--file` 复核，不自行扩到全库。
- 已知欠账（2026-10-15 实测快照）：18 条规则平均得分率 69%（不及格），12 条不及格 + 1 条预警，均为**既有欠账**（cognitive plan 之前已存在；plan 侧注记 `--dir rules` 曾实测 68%）。按本边界**不动**，等用户明确要求才体检 / 修复。

## 4. 抽查指南（给用户的短板声明——查账表防不了的事）

- 查账表防「该做没做」的谎报，**防不了**「做了但做得烂」（如敷衍的实测）和「贴假输出」——绝对防御不存在，**用户抽查是真闸门**。
- 抽查性价比：**优先抽主观项**（编造成本低）：#10 A3 真实实测、#13 段二「审了哪些 md」、#30 landing-sweep 扫描结果；**客观项可少抽**（编造成本高、一跑就穿帮）：exit code、commit hash、测试计数、OCR session id。
- 历史依据：R9 复盘「自洽确认区是假断言的温床」——清单越多、勾越廉价，抽查是唯一对抗。

## 5. 检查项变更同步义务（单源定义在 rule-inspector SKILL.md 硬闸门 7；本节记设计判据）

每次**增加 / 修改 / 删除**检查项（判据、检查点、词表、处方）时，必须过同步清单逐项核销，**不许跳过**：

1. `score.mjs` 机械常量 ↔ `criteria.md` 判据 / 词表（单源，同批改）
2. `criteria.md` 检查点 ↔ `recipes.md` 处方（每类违规有改法）
3. 判据 / 词表 ↔ rule-writer 三层（SKILL 自查 / writing-guide 自查表 / rule-skeleton）
4. 检查项 ↔ review 账本模板「验证查账」表行（删检查 → 查账行删；加检查 → 查账行补）
5. **删检查项时反向扫**：全仓 grep 它的名字 / 锚点词，声明它的地方逐个删——防「幽灵检查项」（判据没了、处方 / 自查表还在引用，读者以为它存在）
6. **rule-edit-checklist 模板**（review-log 技能 `assets/rule-edit-checklist-template.md`）：「编辑 rule」动作的规范检查聚合清单（A 行为前提 / B 推理纪律 / C 文件版本 / D 编辑内容 / E inspector 复核 + rule-writer 自查 / F 同步义务），检查项增删时同步其对应组行

**rule-edit-checklist 机制（2026-10-15 用户裁定，本 spec 补记）**：
- **活模板**（进 git）：`skills/review-log/assets/rule-edit-checklist-template.md`，跟随 rule-inspector / rule-writer / 全局规则检查项变化，变更走上面第 6 条同步。
- **列结构（用户 2026-10-15 复核裁定，全表统一五列）**：`# / 检查项 / 判据（取数命令 · 产物必含词）/ 实际输出（必填）/ 确认执行`——确认执行列只许写「确认执行」四字（前提 = 该行命令真实跑过、输出原样贴），写不出 = 该项未完成 → 本次编辑未完成，停止；无「不适用 / 未执行」档，触发条件没发生也用命令输出证明。
- **每个检查项一行**：不得多检查项并进一行（「头部规范 3 项」= 3 行；「画全貌六维」= 6 行）。
- **机械项机器填**：diff 证据 / C1 Test-Path / C2 增删触发判定 / C4 BOM / **E 段逐检查点**——score.mjs 输出 `checks[]`（每个注册检查点的 group/check/pass/msg），gen 脚本一行一项展开；**AI 不得手抄 E 段**（手抄即造假面）；checks 条数与组 max 之和不一致 → 对账告警行。
- **AI 项**（A×9 / B×5 / C2·C3 / D×4 / E2×11 / F×6）逐行贴「命令 → 实际输出」+ 写「确认执行」，空缺 = 本次编辑未完成。
- **轮次快照**（.session，定格）：`.session/reviews/<那一次>/checklist/checklist-R<N>.md`，由 `skills/review-log/scripts/gen-rule-checklist.mjs` 生成；**`--base` 必传 = 上轮锁基线 commit（见 review-log 轮次账），不可用 master**——master 落后 review 分支时会把历史轮的 rule 改动重复算进本轮（R14 P1-2 实测）。
- **无余地选项**：不设「不适用 / 未执行」档——触发条件没发生由脚本用 diff 判，不归 AI 判。
- **快照判读**：回溯查账只核「当时贴的输出真不真」（重跑该行命令比对），不拿活模板追杀旧轮次。
- **抽查方式**：随机抽任意行 → 重跑该行命令 → 比对输出。

为什么必须有这条（实测）：2026-10-15 加 `x2Carrier` 时四处同步全靠 agent 自觉、无判据强制；历史教训见 criteria §3.3b 注记「旧字面词表与定稿文本脱节把对的规则判红」（R12 P0-α）。

## 6. 验收标准

1. 模板含「验证查账」节：34 行全清单 + 三态说明 + 算数判据；最终结论含全轮查账汇总
2. rule-inspector SKILL.md：硬闸门 7 + 全库体检授权边界
3. rule-writer SKILL.md：同步义务引用行（不复制，单源）
4. `npm run check` 全绿（spec / 模板的 markdown 不破）
5. R12 账本补记查账表（机制生效前最后一轮，事后对账示范，含归因）
