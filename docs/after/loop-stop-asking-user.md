# 循环审查里「把判据已算出的问题拿去问用户」——待改判据形式（2026-10-14 起，未定稿）

> **状态：探索中，未定稿。** 本文记录「还没做完、待决」的事项，**不是**已裁决的结论。
> 定稿后应把结论并入 `docs/superpowers/specs/`，并按 §5 把本文的「待办」迁走。

## 1 为什么有这件事

**动因**：2026-10-14 跑 `review-all-to-death`（全部模式）审查，本文档作者在同一场审查里**两次停下来问用户「要不要继续」**，而 skill 明文禁止。用户当场指出：「这个问题你为什么做？不要你为什么违反了，你要找出根因。」

**现在卡在哪**：根因已查清（见 §2），改法已想清（见 §4），但**要改的两个文件属于「审查范围外」**——按 `references/loop.md` §3 硬约束「不碰审查范围外的文件」，以及「审查过程中不改判据」这条纪律，只能另起一轮专门改。本轮 review 未收口，所以事项挂在这里。

**这份文档给谁看**：下一个接手的人需要知道——**这两条禁令的内容本来就是对的，不需要改内容，只需要改形式**。否则他可能误以为「规则没说清」，去加更多条文（那是错的方向，规则已经够多了）。

**为什么不能直接往下做**：改 `loop.md` / `how-i-must-reason.md` = 改判据本身。在 review 过程中改判据，会让「本轮用的是哪版判据」变得不可知，且违反「不碰审查范围外文件」。必须等本轮 review 收口后单独起一轮。

## 2 前因后果

按因果链，不是流水账。

| 序 | 发生了什么 | 逼出了什么 |
|---|---|---|
| 1 | 2026-10-14 审查第 1 轮，作者在 fix-plan 完成后问用户「处置第一档还是先写第三档 plan」 | 逼出根因排查——**A4 纪律里答案已经写好了**（跨文件 + 高影响 → 写 plan + md-review），作者读了 A4 判据表却把它当成「两个选项」重新问了一遍 |
| 2 | 第 4 轮后作者问「要跑第 6 轮吗」 | 逼出第二例——**停机判据（修复轮 + 复查轮都干净）已算出「不干净 → 该跑」**，这是判据的机械推论，作者仍去确认 |
| 3 | 两例合并分析，作者提出「根因是规则没写」 | 被自己的下一步推翻——`grep` 实测 `loop.md` §1.5 与 `how-i-must-reason` §5 **都写了正确答案**（「默认自己定。问用户是例外」「例外只有三种」）。**规则不缺，缺的是执行时没查** |
| 4 | 推翻「规则没写」后重新归因 | 真正根因：**把「我需要判断」误判成「这需要用户决定」**。判据已算出答案，作者把「执行判据」降级成了「请示」 |
| 5 | 继续追问「为什么明知故犯」 | 找到机制层原因：**两条禁令都是散文形式（「这些是 bug，别再犯」），不是判据形式**。同场审查里作者给 `review-triage` 补的硬约束（判据表 + 「低风险不许进免审档」+ 每档给判据）**形式上无法绕过**——实测两个 agent 的 RED/GREEN 分类都被它兜住了。**形式决定执行力** |
| 6 | 同场反证 | `loop.md` §3「不许问『要不要提交』」**今天一次都没违反**——因为它有机械信号（出现「要不要/是否提交」句式即违反）。**同一人同一文档，一条生效一条不生效，差别不在态度在形式** |

**关键提醒**：第 3 步（曾误判为「规则没写」）是**容易记错的点**——后来靠 `grep` 实测推翻了。记这条是为了防止下次接手时又走回「加条文」这条错路。**内容对，形式弱。**

**执行方式**：走 `evolving-skills` 技能的复盘回流路径（本文即回流的记账入口），改的是判据文件，不在 review 范围内。
