# 现成方案对照报告：docgen「生产 agent skill / rule」方案

> 数据截止：2026-10-19 ｜ 检索方式：WebSearch + WebFetch 多轮，核心论断 ≥2 个独立来源 ｜ 性质：独立参考文档，可脱离对话上下文阅读
> 对照对象：本仓库 docgen（`tools/docgen/`）方案，判据取自 `docs/prd/docgen-index.md` D1–D18 与 `tools/docgen/cli.mjs` 实现

## 0. 摘要（结论先行）

**市面上不存在「整机」现成方案——没有任何一个工具同时满足 docgen 的全部五个特征。但五个特征每一个都有成熟先例，其中「代码作唯一源 + 幂等生成 + 禁手改 + CI 逐字节比对」这套机制，在真实生产仓库里已经完整落地。**

docgen 五个特征对照行业现状：

| # | docgen 特征 | 行业现状 | 结论 |
|---|---|---|---|
| 1 | 逻辑进代码组件，markdown 是生成视图（D1） | 代码生成器标准实践（protobuf / swagger-codegen / graphql-codegen） | 成熟，数十年 |
| 2 | 固定模板，漏格 = 生成失败（D4） | 生成器编译期校验 + Anthropic 官方 skill 校验清单 | 成熟 |
| 3 | 生成物禁手改（D6） | `DO NOT EDIT` 文件头 + 重生成覆盖 | 成熟 |
| 4 | `npm run check` 只读重渲染并逐字节比对（D6） | CI 字节门（`git diff --exit-code`），已有真实生产实例 | 成熟 |
| 5 | 目标载体 = agent skill / rule 整文件 | 生态工具集中在「脚手架生成 / 分发安装 / 单源派生」 | **唯一无整机先例的部分** |

两个最接近的候选：

- **Agentic Skill Mill**（[cite:5]）：碎片 markdown → 编译 7 个 IDE 目标、编译产物进 git、碎片「编辑一次 → 全量重编译」。目标载体最像 docgen，但「唯一源」是 markdown 碎片而非代码组件，且公开渠道未见 CI 逐字节门。
- **AI Agent Assembly docs-metadata 生成器**（[cite:11]）：纯 Node 幂等生成器 + `BEGIN/END GENERATED` 哨兵块 + CI 跑 `git diff --exit-code`。机制与 docgen 完全同款，但目标是普通 README/docs，不是 agent skill/rule。

**对 docgen 的意义**：不是在发明新机制，而是把软件工程里成熟多年的「生成物防漂移」机制，搬到 agent skill/rule 这个 2025 年才出现的新载体上。机制风险低（有生产先例背书），组合是新的（无现成工具可替代）。

## 1. 范围与方法

### 1.1 对照对象

「我们这侧」是 docgen，其机制按 `tools/docgen/cli.mjs` 与 `docs/prd/docgen-index.md` 定义：

| 特征 | 实现证据 |
|---|---|
| 逻辑进代码组件，markdown 是生成视图 | `components/*.mjs` 承载数据与渲染；`templates/*.tpl` 是模板（D1） |
| 固定模板，漏格 = 生成失败 | 模板占位符 `{{NAME}}` 等，缺数据抛 `MissingComponentData`（D4） |
| 生成物禁手改 | `replace` 子命令前置 `DraftDrift`（草稿必须与重渲染逐字节相等）；原子替换 `renameSync`（D6） |
| `npm run check` 只读重渲染逐字节比对 | `gate` 子命令：`validateAgentData` → baseline.json 逐字节 → 生成 rule 逐字节 → agent 描述派生断言（D6） |
| 生成物进 git、落原路径 | baseline 21 rule + 14 agent（`components/baseline.mjs`）（D15） |
| 跨组件引用 `comp:<Name>`、组件名全局唯一 | D7；组件单一职责、跨组件只 import 不复述（D8） |

### 1.2 数据与方法

- 检索多轮：先广撒网定位候选族，再对高相关候选逐一深挖（官网 / GitHub / npm / arXiv）。
- 来源分级：P0 = 官方文档与仓库源码；P1 = 权威技术媒体；P2 = 社区博客与工具页。
- 时效标注：agent skill/rule 格式演进很快，涉及格式细节处标注时间点，超过 6 个月的按规范提示复核。

## 2. 现成方案四族

### 2.1 族 A：通用「生成物禁手改 + CI 防漂移」工程实践（机制同款，载体不同）

这一族证明 docgen 的核心机制（特征 1/3/4）在软件工程里不是新东西，而是标准做法。

| 方案 | 唯一源 | 防漂移手段 | 载体 | 来源 |
|---|---|---|---|---|
| 标准代码生成器（protobuf / grpc / entproto） | IDL / schema | 生成文件头 `Code generated by X. DO NOT EDIT.`，重生成覆盖、产物进 git | 代码 | [cite:25][cite:26] |
| graphql-codegen | GraphQL schema + operations | CI 里生成的类型必须随操作一起提交，schema 变更 → 类型错误 → CI 拦截 | 代码 | [cite:30] |
| **AI Agent Assembly docs-metadata** | `package.json` + `metadata/sdk.json` | 纯 Node 幂等生成器 + `BEGIN/END GENERATED` 哨兵块 + CI `git diff --exit-code`，文档过期即 CI 红 | README / docs / TS 模块 | [cite:11] |
| @sesamehut/design-tokens-md | 设计 token 源 | 输出字节可复现并提交，`tokens:check = generate && git diff --exit-code` 守卫 | CSS / token markdown | [cite:12] |
| OpenAPI 从代码生成 | 代码内注解 / 路由 | CI 里 `generate:spec && git diff --exit-code`，过期 spec 无法合并 | OpenAPI 文档 | [cite:13] |
| gp-foundry | 单引擎 | `build --check` → `git diff --exit-code`；产物带 `DO NOT EDIT` 头；同一引擎打包为 Claude skill + CLI 双前端 | skill + CLI | [cite:14] |

**要点**：AI Agent Assembly 那一例与 docgen 的 D6 机制几乎逐条对应——幂等生成器（两次运行同输入同输出）、哨兵块声明「此段生成、勿手改」、CI 里重渲染后 `git diff --exit-code` 判定漂移。它证明了「代码唯一源 → 生成视图 → 禁手改 → 逐字节门」的闭环在生产规模下可行。

### 2.2 族 B：agent skill 生成 / 编译 / 管理工具（载体同款，机制不同）

| 方案 | 本质 | 与本方案的关系 | 来源 |
|---|---|---|---|
| **Agentic Skill Mill** | 碎片（fragments）markdown 组合 → 编译到 7 个 IDE 目标（Claude / Cursor / Windsurf / OpenCode / Codex）；`compiled/` 产物进 git 发布；CLI 提供 inspect / validate / audit | 目标载体最像；但唯一源是 markdown 碎片而非代码组件；公开渠道未见 CI 逐字节门 | [cite:5] |
| **SkillCreator** | macOS 桌面 IDE：SQLite 本地库 + AI 从 prompt/URL/文档生成 SKILL.md + 6 维质量评分 + 事务式安装（预览 diff、可回滚） | 面向「人写 skill」的工作台，不是「代码作唯一源」；无 CI 字节门 | [cite:6] |
| skills CLI（agskills.dev / terragonlabs 系） | `npx skills add <repo> --skill <name>` 的安装/分发 CLI | 只管分发安装，不管生成 | [cite:31] |
| Skilldex | 技能包管理器 + 注册表，三档作用域（global / project / …），CLI + MCP | 分发层；与本方案正交 | [cite:27] |
| agent-skill-kit（ASK） | 一次定义、同步分发到 Gemini / Claude / Codex / Cursor 等 | 分发层；与本方案正交 | [cite:28] |
| @rackerlabs/agent-skills-cli | 把 markdown 指令集「作为代码管理」，安装 / 更新 / 版本锁定进仓库 | 分发层；与本方案正交 | [cite:29] |
| Anthropic 官方 skill-creator 插件 | 脚手架 + 校验（kebab-case、SKILL.md 存在、frontmatter 齐全、禁 XML 标签） | 提供「漏格 = 失败」的官方判据集 | [cite:3][cite:4][cite:32] |

### 2.3 族 C：agent rules 单源 / 生成工具

| 方案 | 本质 | 来源 |
|---|---|---|
| **devtoolkits AI Rules Generator** | 表单填一次 → 生成 AGENTS.md（单源）+ CLAUDE.md / .cursor/rules/*.mdc / copilot-instructions.md / .windsurfrules / GEMINI.md（派生），口号「rules 永不漂移」 | [cite:18] |
| webtoolkit Agent Rules Generator | 同类表单式生成器 | [cite:19] |
| ainit.dev | 「AI 代理的 git init」：一条命令生成 ignore + rules 文件 | [cite:20] |
| ai-rulez（PyPI） | 按工具 preset 生成规则文件（cursor / copilot 等） | [cite:21] |
| Claude Code `/init` | 分析代码库自动生成起始 CLAUDE.md | [cite:22] |

**要点**：族 C 是「单源 → 多工具派生」在 rules 上的最早落地，但都是**一次性表单/脚手架生成**：没有固定模板的强校验（空节自动省略）、没有禁手改约束、没有 CI 逐字节门。它是 docgen 在 rules 载体的「雏形」，不是同款闭环。

### 2.4 族 D：文档即代码 / 文学编程 / 文档唯一源（方法论祖先）

| 流派 | 主张 | 与本方案的关系 | 来源 |
|---|---|---|---|
| 文学编程（Knuth 1984） | 程序当作文学来写，代码与文档互生，同一逻辑只在一处 | 特征 1 的理念源头 | [cite:23] |
| docs-as-code | 文档与代码同仓、同版本、走 CI/CD；单源多输出 | 特征 3/4 的社区实践基础 | [cite:7][cite:9][cite:10] |
| docguard-cli（CDD） | 文档即唯一源（canonical docs），`docguard guard` 在 CI 校验「文档声称 vs 代码实际」，`collections` 用文件计数核对文档数字 | 把「文档与实现一致性」工程化；但方向相反（文档是源，代码是验证对象） | [cite:16][cite:17] |
| docsync | 从代码事实自动写 README，CI 中文档过期直接 fail build | 特征 4 的直接先例 | [cite:15] |
| freeze-and-thaw 确定性门 | 模型草稿文档须两次独立运行逐字节一致才锁定；后续编辑须显式「解冻」转移所有权 | 特征 4（逐字节判定）的方法论文献 | [cite:24] |

## 4. 差距分析：整机为什么不存在，对 docgen 意味着什么

### 4.1 逐维归位

- **机制维度**（特征 1/2/3/4）：族 A 与族 D 证明每一个特征都有生产级先例，尤其「纯 Node 幂等生成器 + 逐字节门」在 AI Agent Assembly 仓库已完整落地 [cite:11][cite:12][cite:15][cite:24]。docgen 不是拍脑袋设计。
- **载体维度**（特征 5）：agent skill / rule 生态（2025 年才成型，[cite:33][cite:34]）的工具集中在三条线——脚手架生成（族 B 部分 + 族 C）、分发安装（B3 族）、单源派生（族 C1）。**没有任何工具把「规则 / 技能的语义逻辑」放进可编程组件并持续重渲染。**

### 4.2 中间地带的空位

把所有候选摊开看，横轴上「唯一源的可编程程度」存在一个明确空位：

```
人写 markdown（SkillCreator / Anthropic / docguard / 族 C）
        │
        │ ←—— 空位：把逻辑放进代码组件，markdown 只是渲染结果
        ▼
markdown 碎片组合（Agentic Skill Mill，include 粒度复用）
        │
        │ ←—— 已有，但仍是「文档进、文档出」
        ▼
纯代码组件（docgen：JS .mjs 承载状态机 / 终态 / 守恒断言，D1/D7/D8）
```

Skill Mill 做到「markdown 碎片 → include → 编译多目标」，但碎片本身仍是人工维护的 markdown；docgen 把它推进一步——**语义进组件、视图是派生**。这正是族 A 在通用文档上已验证、却没人搬到 skill/rule 上的组合。

### 4.3 对 docgen 的三条具体建议

1. **字节门写法对齐行业标准**：族 A2/A3/A4 一致用「重渲染 + `git diff --exit-code`」[cite:11][cite:12][cite:13]；docgen 已有 `gate` 等价实现，无需改，但报告基线可沿用同样约定（`npm run check` 已如此）。
2. **「漏格 = 失败」判据集可对齐官方清单**：Anthropic 的 skill 校验清单（kebab-case、frontmatter 字段、禁 XML 标签、description 含 what/when）[cite:3][cite:32] 可直接作为 skill 模板漏格判据的权威来源；rule 侧官方无同等清单，需自建。
3. **不需要借用的部分**：SkillCreator 的桌面 IDE + SQLite、B3 族的分发安装，与 docgen 正交，不碰。

### 4.4 潜在威胁（诚实标注）

- 生态演进快：Agentic Skill Mill 这类「碎片 → 多目标」方案若后续加上 CI 字节门，将与 docgen 的机制面重合（目标载体仍以多 IDE 兼容为主，与 docgen 的本仓单一载体不同）。
- 官方格式若强化校验工具链（Anthropic 已提供校验插件），「漏格 = 失败」的人工实现可能被官方工具取代——但那只覆盖 skill，不覆盖规则与 agent。

## 5. 局限与未核实项

- **Agentic Skill Mill 是否内置 CI 逐字节门**：其 CLI 有 `audit-exports` / `validate`，`compiled/` 随 release 分支发布，但公开渠道（官网 / GitHub README）未找到 `git diff --exit-code` 级别的漂移门声明 → 标 [unverified]。
- **时效性**：agent rule 文件格式（AGENTS.md / .cursor/rules 等）演进快，本报告引用的格式细节需按各工具最新文档复核（数据截止 2026-10-19）。
- **检索覆盖**：以中英文 Web 检索为主，未穷尽 GitHub 长尾仓库；若需要可对特定候选（如 Skill Mill dev 分支）做仓库级代码核实。
