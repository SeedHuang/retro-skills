## 结论先行

**3 矛盾（P0）+ 5 盲点（P1）+ 2 优化（P2）**。最危险项：**P0-1 草稿评分链路断裂**——writer 产出的草稿按 SKILL 教的命令去评分，`--file` 路径断言与引用检查全部指向草稿箱而非仓库根，且会话载体型认知规则（x2Carrier）在整条「写→评→落地」链路上**没有合法评分通道**，正确写法必然被判红，修复选项全部违反 recipes 自己的「不补假落点」禁令——生产闭环对一类合法规则死锁。

**总评**：这套体系的**设计质量显著高于平均水准**——双轴模型自洽（满分表 17+max 逐项验算全对）、硬闸门双向对齐（「分数是体检不是验收」在 inspector 硬闸门 3 / writer 硬闸门 1 / README §7 三处一致，无悖论）、X 组判据有真正的对抗性测试（墓碑测试、fail-closed 多路径、explicit-覆盖-默认）。**但执行层（score.mjs 的词表/枚举）与判据层（criteria）已经发生静默漂移，且同步义务（硬闸门 7）六条清单全是「AI 手工核销」，零机器兜底**——恰好违反了 core-working-principles 自己的「能工程化解决的优先工程化」。

## P0 矛盾（3 条）

### P0-1 草稿评分链路断裂：写出来的 rule 无法被正确检查

**证据链**（四处合谋）：

1. `skills/use-rule-skills/references/flows.md` §四 step 5（L65-67）教的评分步骤只说「`score.mjs` 传 `--cognitive`」，**没写 `--rules-dir`、没写 `--repo-root`**；
2. `scripts/score.mjs` L441-443 自己注释承认：「草稿在草稿箱，引用会全部误判」，须指 `--rules-dir`；`base` 缺省 = `resolve(rulesDir, '..')` = **草稿箱父目录**（`C:\Users\<名>\.retro-skills`）；
3. 草稿名带 `--<YYYYMMDD-HHMMSS>` 后缀（rule-writer SKILL.md），而 annotations 按落地后的文件名索引（实测 `rules/.inspector-annotations.json` 键均为裸文件名）→ **草稿永远命中不了 annotations**；
4. CLI 参数表（score.mjs L414-424）逐个核对：`--dir/--file/--rules-dir/--json/--tri-check/--cognitive/--baseline/--type/--annotations/--repo-root`——**没有 `--x2-carrier`**。

**触发序列**：写一条认知动作型规则，产物去处是会话载体（如 how-i-must-reason 的既有形态，annotations 里 3 条规则有 2 条标了 `x2Carrier:true`）→

- writer 按 `assets/rule-skeleton.md` 指示「产物去处确为会话载体时此项不填，改标 annotations x2Carrier」——**骨架教的正解，评分时无法执行**（草稿进不了 annotations，CLI 又没参数）；
- 评分 → X2 强制评估 → 「无三段齐全的声明」红；
- 按 `references/recipes.md` §R8.2 修：两条路是「改规则指向真实槽位」或「先建槽位」——**两条都是假落点**，而 recipes 同一行明文禁令「不补假落点」。

**判定**：逻辑悖论实锤——判据要求 A，修复处方禁止达成 A 的所有路径。同时不传 `--repo-root` 时 X1/X2 路径断言对草稿箱解析，真落点也全红（假红引发异常循环空转，flows.md step 6）。

**修复建议**：① flows.md step 5 补 `--rules-dir <rules/> --repo-root <仓库根>`；② score.mjs 加 `--x2-carrier` / `--x3-done` CLI 参数（补全 annotations 键的命令行镜像）；③ 骨架改为「在评分命令里传对应参数或落地后补标注」。

### P0-3 判定词表三层漂移：「一律」有判据、无实现、无测试、无机器防线

## P1 盲点（5 条）

### P1-1 ⑥ 例外从严：自家样板规则过不了自家检查

**证据**：
- score.mjs L31：`EXCEPTION_RE = /只有[^。；\n]{1,40}才算/`——强制「只有…才算」字面；
- writing-guide §五 把 no-git-write 当 ⑥ 样板，**原文引用**「**『用户明确要求』唯一成立的情形**：用户在当前对话中直接说出对具体 git 操作的指令」；
- 实测 `rules/no-git-write.md` L23：无「只有…才算」措辞；L93「只有当用户…明确说出…**才可以**执行」——「才可以」也不匹配「才算」。

**后果**：教学样板本身 0 分。writer 照样板写 ⑥ → score 判红 → AI 面临「按样板写被扣分 / 按正则写偏离样板」的二义性。另外 `{1,40}` 窗口是隐藏约束：例外句超 40 字（中文例外句极常见）→ 红，等于「例外还必须写得短」——criteria 里没有这条判据。

**修复建议**：EXCEPTION_RE 放宽为 `/只有[^。；\n]{1,60}(才算|才可以|才可|时，才)/` 或「唯一成立的情形/唯一豁免」并行模式（README §8 已承认「只有…时 vs 只有…才算」是已知变体，但没改进正则）；writing-guide 样板改为展示能过检的写法。

### P1-2 X3 评分语义二义：x3Done 是「判过」还是「合格」

**证据**：score.mjs L325-328：`g('执行力度', 'X3触发前置', x3Done)`——**脚本只认标注不认正文**。criteria §3.3b X3 的判定列写「触发点在应激时刻（被质疑/出错时）**且未前置显式化**」——这是 fail 条件，但 score 拿 x3Done 当 pass 条件。

**逻辑裂缝**：x3Done 字面语义是「AI 已判定过」。那么 AI 判定**不合格**（触发在应激时刻且无前置声明）时 x3Done 该标什么？标 true → X3 得 1 分（不合格拿满分）；标 false → 与「没判过」无法区分，且 score 判 0 分进 findings 的 msg 是「触发在应激时刻且未前置显式化」——但**真正该出的处方（补前置句）只有在判「不合格」时才需要，而这时分数语义已经乱了**。三态（未判/判过合格/判过不合格）被压成布尔，无法表达「判过且不合格」。

**零测试覆盖**：测试只测了 `x3Done:true → pass` 和缺省 `false → red`，从未测「x3Done:true 但规则正文实际无前置声明」的语义应该是什么。

**修复建议**：把 x3Done 改名 `x3Pass`（AI 判定的结论而非动作），或加第三态；annotations 里为每条写明判定依据（SKILL.md 已要求「依据一行写进报告」，但分数语义没跟上）。

### P1-3 同步义务自身的账不平：M3 双名、硬闸门计数三处口径

**证据**：
- 同一个检查点三个名字：criteria.md §3.6 / report-template.md / README.md §4 均为「M3 **切换判据明确**」，score.mjs L321 输出 `'M3 切换依据明确'`——机器输出名 ≠ 判据权威名，AI 手填报告时按模板行名对 checks 行名会错位（测试用 `startsWith('M3')` 躲开了，恰恰说明作者知道全名对不上）；
- 硬闸门计数三个口径：SKILL.md 列 **7 条**硬闸门；README.md §7 写「**硬闸门（6 条**，见 SKILL.md）」；SKILL.md 执行顺序 step 4 写「每条过硬闸门（**上面 1–6**）」——第 7 条（检查项变更同步义务）在「修复」步骤被显式排除在必过清单外，**而它恰恰管「改判据/检查点」，修复时最该过**；
- report-template 的检查点行**不在**硬闸门 7 同步清单的六处核销对象里（①score↔criteria ②criteria↔recipes ③判据↔writer 三层 ④检查项↔查账表 ⑤删检查反向扫 ⑥checklist 模板）——M3 漂移正是漏的这一层。

**修复建议**：三处口径改齐（7 条 / 上面 1–7）；M3 统一命名为「切换判据明确」（score.mjs 输出名避开「判据」词的动机可疑——输出规避只限「判据」「建议删除」两个完整词，score.mjs 已用「标题为一句可执行规则（非主题名）」安全别名处理过同类问题，M3 应同法处理）；同步义务第 ⑦ 处补 report-template。

### P1-4 假阳性无账：README §8 只有假阴性清单，反向缺失

README §8 「已知代理假阴性清单」自我认知做得好，但**假阳性（词命中即过 = 检查形同虚设）完全没有账**。具体证据：

- **①极性明确判别力 ≈ 0**：`POLAR_RE` 含「要」——「需要」「重要」「主要」「不要」全命中。真实中文规则正文基本不可能不含「要」。测试的 NO_POLAR fixture 是刻意回避所有高频词的实验室句子（「代码提交前，先查看 git 状态」）；
- **②动作内容具体**：`SPECIFIC_TOKEN_RE` 含「文件|目录|命令|文档|代码」——正文出现「文件」二字即 pass。判据意图「可枚举或具体描述」被实现成「有任一超高频词」；
- **⑧验证闭环**：`VERIFY_RE` 含「确认」——GOOD fixture 靠「先确认已获用户明确指令」过检，这是行为描述不是验证闭环定义；
- **引号 ≠ 原话**：score.mjs L157 hasQuote 逻辑只清掉「来源：类型（日期）」前缀，证据字段里的合法「一句话现象」若含「」（landing-sweep 实测含大量「」）→「无原话引用」假红。criteria 判据是「不含**用户原话**」，实现是「不含任何引号」——又一处意图≠实现；
- **DIR_HEADING_HINTS 惩罚「规范/踩坑」**：criteria §3.1 明说「『规范』不是极性，是体裁」——判据层体裁化认可，标题层当目录式特征词惩罚。标题含「规范」二字的合法判据式标题必假红；
- **「严禁」零覆盖**：BAN_RE 四个禁令词里「严禁」在全部测试 fixture 里一次未出现——第四分支零覆盖。

**后果**：①②⑦⑧ 四个「执行力度」检查点对真实规则的判别力趋近常数（①②⑧ 恒绿、⑦ 看词运），**「不跳过需要判断的环节」在机械层就是「词在场」**，而 SKILL 执行顺序的 6 步里也没有「①–⑧ 语义质量 AI 复核」环节（AI 只判类型/认知/三检验/M 组）——语义层没人接住。

**修复建议**：① 建「假阳性清单」（README §8 镜像），对每个词表标注判别力水位；② ①的极性匹配改按句定位（含极性词的句子须含动词——数据已有 ACTION_RE，两者从「全文任一命中」改成「同句共现」成本极低且立刻提升判别力）。

### P1-5 --dir 全库体检的系统性假红：缺省 type=条件触发 + 三检验必然 0

**证据**：
- score.mjs L227：`opts.type` 缺省 → **条件触发**；annotations 的 per-file type 机制存在（score.mjs L393-395），但实测 `rules/.inspector-annotations.json` **只有 cognitive/x3Done/x2Carrier 三个键，没有任何 type 标注**（20 条规则标了 3 条认知判定）；
- SKILL.md 执行顺序 step 1 的命令 `node ... --dir <rules目录> --json` **不带 `--tri-check`** → `opts.triCheckDone` 缺省 false → 全库每条规则「三检验报告已做」0 分。
- README 盘点：5 条持续适用（如 no-git-write）——按缺省条件触发评会加评 ③⑦，no-git-write 无「落地后/开工时」类时机词 → ⑦ 假红。

## P2 优化（2 条）

### P2-1 测试质量：不是敷衍，但有五处具体盲点

先给正面结论：**测试整体不是迎合式**——每个 0 分路径有独立 fixture（25 检查点全覆盖）；有墓碑测试（COG_OLD_KEYWORDS：「旧假判据给它 1 分，新判据必须 fail」——这是防判据退化的对抗性设计）；有 fail-closed 多路径 all-exist 测试（「真路径+假路径混合 → fail，只查首个的坏实现会误过」——点名防特定坏实现）；有 explicit-覆盖-默认 的参数合并顺序测试（OCR R14 :443）；有坏 JSON fail-fast。**这是「想抓 bug」的测试。**

但有五个具体盲点：

1. **词表成员零覆盖**：P0-2（「评审第 N 轮」）、P0-3（「一律」）、BAN_RE 的「严禁」——三个词表成员在所有 fixture 中零出现，三个漂移/bug 全部因此存活。**判定：fixture 是按「让现有实现通过」挑的词，不是按「词表全成员」挑的——这就是「迎合逻辑」的具体形态，虽然可能不是有意的**；
2. **真实规则零 fixture**：所有 fixture 都是「完美长方体」（只缺目标检查点、其余全绿的实验室文本）。README §8 自己列的假阴性清单（裸「…中」前提、「只有…时」变体、无来源行时来源精简组）**一条都没有固化为回归测试**——已知误判有文档、无防线，下次改正则时这些误判会静默回归；
3. **正则副作用零测试**：「要」误伤面（P1-4）、「规范/踩坑」标题惩罚、「写」单字进 ACTION_RE——这些副作用从未被任何测试断言过（哪怕是断言「这是已知误伤」的墓碑测试）；
4. **gen-rule-checklist 的 main() 分支缺测**：`c4` 的 D 型（已删除文件）防崩分支（OCR R14 :167 修复）在 gen-rule-checklist.test.mjs 中无对应测试——修复了但没钉住；
5. **CLI 硬编码绝对路径**：score.mjs L413 `dir: 'D:\\Seed\\retro-skills\\rules'`——对比 gen-rule-checklist 用 `resolve(__dirname,'..','..','..')` 的正确做法，score.mjs 硬编码机器路径，跨机即失效，且「缺省 --dir」路径无测试。

### P2-2 知识库盘点快照过时：三处三个数

criteria §2.1 表列 12 条规则、README §2「现有 16 条实际盘点（2026-10-15）」、实测 `rules/` 目录 **20 个 .md**（Glob 确认）——data-support-triple、core-working-principles、skill-authoring-convention、reference-read-output-loop 四条不在 criteria 表内。这些表的用途是「类型判定参考」，过时盘点会误导 AI 判型。建议改成指针（「以 `ls rules/*.md` 实测为准」）或加同步检查点。
