## 二、问题清单

### A 组｜现象层：什么在重复发生

#### Q1 每一次修复动作本身会带出新的缺陷

- **现象**：第 5 轮修完 2 个 P0 + 33 个 P1，第 6 轮审出 7 个新 P0；逐条追，7 个都能追到第 5 轮的改动上。
- **证据**：`problems.md` §10.1（第 5 轮改了哪些）对 §11.1（第 6 轮 7 个 P0）；`progress.md` L38–40。
- **现在为什么没挡住**：第 5 轮的修复由作者自评「已修」，评审只在下一次全量重审时才发现——发现时已经过去一整轮。
- **待决点**：这 7 个里，有几个是「本来就存在、只是上一轮没看见」，有几个是「上一轮真的新造出来的」？两种性质对应完全不同的治法，而这笔账**目前没分**。
- **候选项（未定）**：a) 修复后强制重读**被改规则的所有出现处**；b) 修复者必须交「副作用清单」；c) 不区分，直接接受「新缺陷是修复的正常副产物」，只优化发现速度。
- **裁决**：（未讨论）

#### Q2 「自评修好了」与「真的修好了」之间有系统性偏差

- **现象**：第 5 轮两个 P0 记「已按作者自评修复」，第 6 轮查出其中一个只改了正文、漏了流程图（P0-1）。
- **证据**：`problems.md` §10.1「处置（已落 spec）」与 §11.1 P0-1；spec L31 流程图仍写「有条件且条件已核销」，而 §4④ 正文写「本版不自造核销机制」。
- **现在为什么没挡住**：修复和验收是同一个实例；「我改完了」这个判断没有第二个人/第二个信号复核。
- **待决点**：这个偏差是**能力问题**（没看见）还是**动机问题**（看见了但觉得不重要）？前者可以用检查清单补，后者只能靠换人。
- **候选项（未定）**：a) 改完必须换实例复核；b) 改完必须跑一条与该修改一一对应的命令；c) 两者都要，成本另算。
- **裁决**：（未讨论）

#### Q3 范围砍小，不等于问题变少

- **现象**：v4 → v5 从 413 行砍到 191 行，删掉 15 项功能（spec §6），P0 从 2 个涨到 7 个。
- **证据**：`progress.md` 轮次账 L29–36；spec §6 全表。
- **现在为什么没挡住**：砍功能时同时改了「运行目录怎么处置」「终态怎么算」这些**被其他章节引用**的东西，删掉的是一处，引用它的地方还在。
- **待决点**：这是不是说明「先砍再修」这个策略本身有问题——砍完应该**重写**而不是**打补丁**？
- **候选项（未定）**：a) 大改后强制重写受影响章节；b) 大改后重跑一次全量评审（已经在做）；c) 承认砍范围只降低「问题上限」，不降低「每分钟问题密度」。
- **裁决**：（未讨论）

#### Q4 同类问题在其他场景也在发生（不是本 spec 独有）

- **现象**：2026-10-16 的报告里，两次长审查（12 轮 / 14 轮）有同一形态：同一文件连吃 23 条评论、连改 5 轮；「修一半」连环复发；验证不足升级成「假验证」。
- **证据**：`docs/reports/2026-10-16-2-over-10-rounds-reviews-accounting/problems.md` §2.1、§三·3.2、§五（A1/A2/A3）。
- **待决点**：这两个场景（改代码 vs 改文档）是不是**同一个根因**？如果是，治法可以一次做一套；如果不是，两套分开做，别硬统一。
- **候选项（未定）**：a) 按「改动对象」分两套；b) 先统一成一套「修复影响面」机制，再看代码场景需不需要特化。
- **裁决**：（未讨论）

### B 组｜机制层：这 7 个 P0 可以归成四类病

> 归类依据：`problems.md` §11.1 逐条读原文后按「缺陷形态」归组。归类是**判断**，条目本身是事实。

#### Q5 同一条规则被写在多个地方，改一处漏一处（3 个 P0）

| P0 | 同一件事的落点 A | 落点 B | 结果 |
|---|---|---|---|
| P0-1 | spec §4④ 正文：「本版不自造核销」 | spec L31 流程图：「有条件且条件已核销」 | 两处说法相反 |
| P0-2 | spec L6 头部：账本在 `D:\Seed\lessons\...` | spec L40 产出物表：账本在运行目录（处置完即删） | 批 0 / 批 5 不知道核哪份 |
| P0-3 | spec L87：工单写入即算终态 | spec L119：载体簇 ④ 放行 → 才已停机 | 终态有两个时点 |

- **待决点**：这类错误，是「作者不小心」，还是「文档结构允许一件事有多处落点」？前者靠细心，后者靠结构。
- **候选项（未定）**：a) 一条规则只允许一处定义，其余位置只写指针；b) 关键定义加「同义句禁止表」，评审时 grep 检查；c) 维持现状，只在评审时人工比对。
- **裁决**：（未讨论）

#### Q6 两条各自正确的规则，合起来互斥（1 个 P0）

- **现象**：① 允许「同号同描述去重」（spec L69）；批 0 要求「ledger 条数 = 输入源计数」（L169）；§5 要求条号守恒（L121）；批 5 要求「41 条全有终态」（L174）。被去重掉的条目既不在账本、又没有终态 → 按判据必红。
- **证据**：spec L69 / L121 / L169 / L174；`problems.md` §11.1 P0-6。
- **待决点**：这类「组合冲突」是**评审才看得见**的，有没有办法在写的时候就发现？还是只能接受「写时不管、评审必查」？
- **候选项（未定）**：a) 每条守恒式列出它依赖的所有定义，改动时逐条核；b) 建「不许互相引用」的分层（守恒式只引用终态，不引用输入校验）；c) 允许去重，但去重必须留「合并记录」占住条号。
- **裁决**：（未讨论）

#### Q7 砍掉一个功能，引用它的地方没跟着改（1 个 P0）

- **现象**：删掉「运行期归档」后，运行目录改成「处置完即删」（spec L40 / L51 / L138）；但工单正好存在这个目录里（L87）。目录一删，条目终态「工单已产出」就落空。
- **证据**：spec L40、L51、L87、L138；`problems.md` §11.1 P0-4。
- **待决点**：砍功能的收尾动作，应该固定成「列出所有引用 → 逐处处置」吗？还是说这就是 Q5 的一个具体表现（同一件事的落点没扫全）？
- **候选项（未定）**：a) 归入 Q5 一起治；b) 单独建「删除清单」，每删一项附引用扫描结果。
- **裁决**：（未讨论）

#### Q8 状态机漏分支（2 个 P0）

- **现象**：
  - 新增「混合簇拆成施工簇 + 载体簇」（spec L80），但拆分后**原簇号去哪**没定义 → 整批停机不可达（P0-5）。
  - 流程图只有「有新增 → 回① / 无 → 停机」两条路（spec L36–39），而「干净」的定义还要求「未解决项为空」（L114）→ 「不干净且无新增」无路可走（P0-7）。
- **证据**：spec L36–39、L80、L114、L122；`problems.md` §11.1 P0-5 / P0-7。
- **待决点**：这是不是说明「流程图」和「判据正文」天然会分叉（图是摘要，正文是定义）？如果是，图要不要干脆不写判据、只写顺序？
- **候选项（未定）**：a) 流程图与正文由同一处生成（图是派生物）；b) 每个状态转移必须穷举所有条件组合，评审专门查「有没有漏的那一格」；c) 图只画理想路径，异常全部写进正文的表。
- **裁决**：（未讨论）

### C 组｜环境层：为什么这些缺陷一直没被挡住

#### Q9 现有机械检查完全不覆盖「文档内部一致性」

- **现象**：六轮结束时 `npm run check` 全绿（275 pass / 0 fail / 0 findings / 172 文件 510 表），同时 spec 里躺着 7 个 P0。

- **候选项（未定）**：a) 先只做能查的那几类，剩下的明确标注「只能人查」；b) 不做检查，靠评审；c) 把关键定义抽成结构化数据（YAML / JSON），文档由它生成。

## 三、解释候选（未裁决，附可检验判据）

> 你说「不认为哪个对哪个错」——那就把两种解释都当假设，给每个假设一条能证伪的观测。三者不互斥，可能同时成立。

| 假设 | 主张 | 可检验判据（下次观测） | 本仓已有数据支持度 |
|---|---|---|---|
| **H1 范围过大**（外部模型） | 一次改得越多，偏移越大；把范围收到「可独立验证的最小闭环」即可 | 把每轮改动按「影响文件数 / 复述点数」分组，看新问题率是否显著相关 | **弱**：砍半（413→191）后 P0 反涨（2→7），与「范围越小越好」不一致 |
| **H2 多点复述、无机械边界**（本次） | 新缺陷集中在「被改规则还有别处复述」或「参与守恒式」的地方 | 把第 6 轮 7 个 P0 按「是否属复述/守恒冲突」分类，应 ≥4 个 | **部分**：7 个里 3 个是复述（Q5）、1 个是守恒冲突（Q6）、1 个是删功能留引用（Q7）、2 个是状态机漏格（Q8）——**按形态 7/7 可归类**，但归类本身需要第三人复核 |
| **H3 修复者与验收者同源**（外部模型） | 同一实例自评会有确认偏差，换独立实例即可减少 | 第 5 轮 → 第 6 轮：自评修 2 个 P0，独立复审查出 7 个新 P0（部分是新造、部分是漏看） | **中**：有偏差的实例（P0-1 只改正文漏图），但样本只有一次 |

**待决**：要不要先做一件便宜的事——把第 6 轮 7 个 P0 逐条判「新造 vs 漏看」，用这个结果给 H1/H2/H3 排序？这决定了后面往哪使劲。

## 四、建议的讨论顺序（先定性，再选路）

1. **Q1 + Q2**：先分清「新造」和「漏看」。这两条定不了，后面选什么方法都是猜。
2. **Q5–Q8**：确认这四类病的归类认不认。认了，才谈怎么治；不认，先改归类。
3. **Q9 + Q10**：讨论「哪些能机械查」，这直接关系到「要不要写脚本」。
4. **Q4 + Q12**：先看这次是接旧方案还是另起，避免重复。
5. **Q11**：账本缺口怎么处理（可以不阻塞主线）。
6. 最后再谈路径（交接词里的 A 建骨架 + 3 条试跑 / B 表 + 校验脚本）——**在 1–5 有结论前不选路**。
