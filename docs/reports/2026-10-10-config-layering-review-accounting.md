## 一、review-loop 侧（流程问题，换更聪明的 agent 也会发生）

|---|---|---|---|
| L1 | 全量重审，审查面只增不减——OCR 每轮审全部未提交 diff，修复产生的新代码又进审查面 | OCR session 全是 `reviewMode: workspace`；FILES 16→19，diff 持续膨胀；第 4 轮降到 2 条后，第 5 轮大重构立刻反弹到 10 条 | ✅ 实锤 |

| L3 | 清单逼模型凑数——审查清单强制检查重复代码/硬编码等，模型觉得没真问题也得报 | 第 15 轮 thinking 原文：「the plan's 5 issues mostly turn out to be non-issues or trivial」「I give up hunting; the code is well-written」「the user's checklist literally asks to check for Duplicate Code and Hardcoding. | L4 | 无收敛判据，循环靠外部喊停 | 18 轮评论数从未归零（12/9/10/2/10/12/7/4/6/7/7/9/10/2/3/5/7/5）；第 18 轮由用户手动停止 | ✅ 实锤 |

### 人话解释

- **L1**：像老师每次只批改你交上去的**全部**作业，而不是「这次新写的那几道题」。每轮修复产生新的 10 行代码，下一轮 OCR 又把全部 diff 从头看一遍——修得越多、要看越多，永远看不完。第 4 轮降到 2 条本来快完了，第 5 轮因为动了 `config.mjs`（+132 行）立刻反弹到 10 条。**这是 18 轮修不干净的最根本原因。**
- **L2**：OCR 每次跑都是「失忆」状态。problems.md 里写「不改/误报必须留下，下一轮会重新纠结」——预言成真，只是重纠结的是 OCR 这边，agent 还得花一轮解释「这题答过了」。
- **L3**：模型审完第 15 轮代码，内心认为「没啥真问题」，但清单要求它必须产出（重复代码/硬编码/死代码检查项），它纠结一番后报了 2 条 low 级维护性建议交差。**这不是模型能力问题，是清单设计逼出来的。**
- **L4**：流程里没写「什么时候算完」，只能一直跑，跑到外部喊停。第 18 轮实际是**被中断**的——session 跑了、产出 5 条评论，但 progress 表当时是空的。

| # | 问题 | 实锤证据 | 状态 |

| A2 | 全修策略，low 级样式建议也修 → 制造新 diff 继续养 L1 | 第 17 轮修了「重复调用三次纯函数」这类纯样式建议（`catalog.mjs` expandHome 提变量） | ✅ 实锤 |
| A3 | 修复后验证不足，npm test 全绿 ≠ 行为正确 | 第 2 轮 env-only 回归、第 14 轮 commander 传参回归，测试都没抓住（测试用例只用绝对路径，没覆盖真实用法）；progress 第 2/14 轮后来才补「真实场景实测」 | ✅ 实锤 |

### 人话解释

- **A1**：修的人只盯着 OCR 给的那一行建议改，没问「这条修复要覆盖的整个失败面在哪」。第 16 轮 OCR 说「骨架错误被误标成用户配置问题」，agent 只把 `loadConfig` 挪出 try，但同一个 try 里还有 `normalizeConfig`——第 17 轮同类问题再报一遍。**7 条自伤性回归，等于白白多跑了约 4 轮复查。**
- **A2**：problems.md 图例写得清楚「不改的必须留下」，但实际是「来者全修」。修一个没价值的问题 = 制造一个新 diff = 下一轮 OCR 多一个审视对象。**A2 配合 L3 共同放大了循环。**
- **A3**：测试绿 ≠ 行为对。第 2 轮回归测试 124/124 全绿，因为用例都用绝对路径，没覆盖「只设环境变量」这个真实用法。这个纪律 progress 中途才养成，第 1 轮没有。

## 三、因果链（谁是根，谁是放大器）

```
L1 全量重审（根）
   ↓ 放大
A1 半成品修复 → 新 diff → 又进 L1 审查面 → 新评论（7 次自伤）
L3 清单逼凑数 + A2 全修策略 → low 噪音也产生 diff → 继续养 L1
L4 无收敛判据 → 循环跑到外部喊停（第 18 轮中断）
```

**一句话**：根在 review-loop（L1 全量重审 + L4 无收敛判据 + L3 清单逼凑数），agent 的 A1/A2 是放大器。把 L1 修了（增量审查），评论数自然下降，A1 的 7 条自伤也没地方藏；把 L4 修了（收敛判据），18 轮会在第 14 轮附近就停下来。

## 四、解决方案（按成本排序）

| 方案 | 成本 | 效果 |
|---|---|---|
| 每轮锁定 diff 基线，OCR 只审增量 | 改调用方式 | 治 L1 根因，评论数自然下降 |
| 定收敛判据：连续 2 轮 ≤2 条且无 high/medium → 收敛 | 改流程规则 | 治 L4，避免无限循环 |
| 把 problems.md 的「不改/误报/关闭」喂给 OCR 当上下文 | 约 30 行 | 治 L2，避免重复报已关闭问题 |
| 评论按 bug/样式/测试覆盖分组，样式级一律「不改」 | 改 prompt | 治 L3，防凑数 |
| 修「错误归因/降级」类问题时先列全失败面（读/校验/推导/归一） | agent 纪律 | 治 A1 |
| 修复后跑真实场景实测，不只跑 npm test | agent 纪律 | 治 A3 |
