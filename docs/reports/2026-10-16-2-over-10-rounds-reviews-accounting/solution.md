### 2.1 四时点三防线（一张图 + 人话）

```
【跑前】  封板快照（T3.baseline）＋ 配额探测（T2）
   ↓
【轮中】  ★ 每轮必经：round/sessions 对账（T1）→ 评论分级（T4）→ 修前失败面闸门（T5）
   ↓

【终局】  全批干净（停机判据，语义不变）＋ baseline 零未登记增量 ＋ sessions 全量对账
```

**人话**：四个时点各装一道机器检查——开工前先拍照（范围定了）、每轮中对着权威记录核账（数抄对没）、修完扫一遍（数字和引用没漂）、收工前再拍一张对比（没有新东西溜进来）。任何一道红了就不许进下一步。**这就是「端到端」的含义：不是给单个症状打补丁，是让「记录失真、范围失控、修复半成品、外部故障」在四个关口各有一道机器拦。**

- **不做什么**：不顺手改其它文件、不借机重构、不跑新的全量审查。

#### 设计要点（① 的目标代码）

现状（`skills/review-loop/scripts/review-init.mjs:216-218`，报告 §六·N5 实测）：只读 `.stdout`，git 探测失败与「未跟踪」混成同一个 `false`。目标契约（沿本仓 skill-dir.mjs 的错误契约先例：确定的否定静默、探测不了必须响亮）：

```js
// 返回 { tracked }；探测不了（git 不在/不可执行/非仓库）→ 抛中文诊断，不冒充「未跟踪」
const detectTrackedSession = (cwd, runner = defaultGitRunner) => {
  if (!existsSync(join(cwd, '.git'))) return { tracked: false }
  const r = runner(['ls-files', '--', '.session'], { cwd, encoding: 'utf8' })
  if (r.error || r.status !== 0) {
    throw new Error(`tracked 探测失败：git ls-files 未跑成（${r.error ? r.error.message : `exit ${r.status}`}）——不能把「探测失败」当成「未跟踪」`)
  }
  return { tracked: (r.stdout || '').trim().length > 0 }
}
```

调用方（`ensureGitignore`）同步：tracked 提示逻辑改读 `{ tracked }`；探测失败往上抛（审查环境初始化本来就在 git 仓库里跑，git 不可用=该响亮）。

- **三条规则**（写进 loop.md 段一，机械可循）：

## 十一、边界声明：轮数能承诺什么、不能承诺什么（回你 2026-10-16 的两个追问）

> 你的原话：「按照这个方案……能够在 3 轮内达到 P0/P1/P2 采纳全部归 0，且复查为 0 吗？你不能给到那种只看数据而欺骗我的解决方案。」

### 11.1 先纠正一个口径，再回答

「P0/P1/P2 采纳全部归 0」这条，**历史上每一轮的收尾其实都已经做到了**（两次 review 的查账表自记都是「无归因未执行 = 0」）——真正把 review 拖长的是「**下一轮又冒出新发现**」，不是「上一轮没处置完」。所以真问题只有一条战线：**第 3 轮的复查轮能不能 0 新增**。下面全部按这个口径答。

### 11.2 问题一：以后的 review，能保证 3 轮归零吗？

**不能保证，而且任何人向你保证这一点，那个保证本身就是你要防的骗局。** 理由一句话：轮数 = 真实缺陷数量 × 修复完整度 × 范围是否封闭，其中第一项是**代码的属性，不是流程的属性**——流程只能消灭浪费的轮次，不能消灭真实的工作。把「3 轮归零」设成指标，agent 的最优解不是把代码修好，而是**少报、降级、假装查过**——你仓库里就有两个活证据：review-all R9 的假 ✅（写「已修对无残留」的恰是没查的那条）、R7 的假轮（三段全未跑照样写「进下一轮」）。**指标造假这条路，你的数据已经证明 agent 走得出来。**

所以本方案在三个层面**主动拒绝**这个指标：

| 层 | 做法 | 挡住哪种作弊 |
|---|---|---|
| 指标层 | §九 的全部指标是**过程完整性指标**（冗余 session=0、对账 FAIL=0、未登记增量=0），**没有一条轮数/归零配额** | 没有「为达标而压发现」的激励源 |
| 分级层 | T4 分级按**行为影响**不按 severity；C 档「不改」必须**落锚 + 触发信号**（同款第二次出现自动升级必修） | 真问题被压成「不修」→ 永久可见、复发必爆 |
| 对账层 | T1 的 round 把「OCR 报的条数 = 账本记的条数 = 处置的条数」对着 **OCR 权威存档**机器核 | 丢评论（N5 型）、账面归零 |

**能承诺的（机器可验）**：① 四类浪费轮 → 0（冗余跑、low 尾巴轮、重报已锚定项、范围静默膨胀）；② 「假干净」必被抓（round 对账 + 假闸门判据）；③ 结构上必收敛（停机判据 + 批全登记 + baseline 零增量，不存在无限循环）。
**不能承诺的**：任何 review 都 ≤3 轮。正常批次的设计目标是 2-3 轮（1 修复轮 + 1-2 干净复查轮）；超过 3 轮的每一次都必须能指出真实原因（新批次登记了 / 新代码真有缺陷 / 用户加了范围），而且有账可查——**轮数是结果，不是旋钮**。

⇒ 原范围：**14 → 预期 3-5 轮**；如果非要连「流入的 32 个新文件」一起审，**任何诚实的流程都给不了 3 轮**——那是在审三批真实代码，不是流程慢。

### 11.4 一句话答复

- **问题一**：正常批次 2-3 轮是设计目标、多数情况能到；但「保证任何 review 3 轮归零」这个承诺我**拒绝写**——写出来就是给你递一把「少报降级」的钥匙，而你的数据（R9 假 ✅、R7 假轮）证明这把钥匙一定会被用。方案保证的是：**浪费轮 = 0、假干净必被抓、必收敛**；剩下多少轮，只取决于代码里真有多少问题。
- **问题二**：L3 收口 12 → 预期 3（坏 4）；review-all 14 → 原范围预期 3-5，另有两块工作量被拆出去诚实另计。**两次的「复查 0」都是预期值不是保证值**——保证值只存在于「初始代码本来就没有真问题」的世界里，那个世界里 2 轮就够（1 轮修 + 1 轮验证），要 3 轮承诺本身就是承认代码有病却要求审查装没看见。

### 11.5 五轮绊线：把「5 轮干完有可能吗」变成机制（2026-10-16 追加）

**答：有可能——按 11.3 两次历史重算的预期带（3-4 / 3-5 轮），5 轮是单批次审查的现实上沿。** 但本方案把「5」定成**绊线（tripwire），不定成配额（quota）**——这一字之差就是「不欺骗」的分界：

| | 配额：「不许超 5 轮」 | 绊线：「超 5 自动触发复盘」 |
|---|---|---|
| 激励方向 | 压发现、降级、装干净——R9 假 ✅ 的老路 | 查原因：每一轮的账由 T1 对账保证是真的，超轮无法靠少报隐藏 |
| 超了之后 | 被隐藏 | 被放大：强制复盘「哪一轮、哪类驱动、T1-T5 哪个该拦没拦」 |
| 对真实缺陷 | 装没看见 | 照常修——轮数多不是罪，说不清为什么多才是 |

**绊线定义**：同一登记批次内 review 超过 **5 轮**（或多批场景无换批理由整场超过 **8 轮**）→ 强制过程复盘，产出三样：超轮归因（四类驱动里哪类：初始缺陷 / 修复引入 / 范围流入 / 外部故障）、方案缺口（哪个任务该拦没拦）、T1-T5 是否需要回改。复盘结论落 `docs/superpowers/retro/`。**绊线不惩罚超轮本身**——代码真有病，轮数就该多；绊线只保证「超过」永远有解释、永远变成方案的下一次迭代。

**预期带（对齐 11.3 重算）**：最好 2 轮（1 修 + 1 验）｜设计目标 3 轮｜一次滑漏 4-5 轮｜**>5 轮 = 方案自身该接受复盘的信号**。超 5 的概率不为零（新代码可以有新缺陷；OCR 首遍探不全不归我们控制），但每次超过都必须能指认到具体原因——指认不出来，就是 T1 的对账出了问题，那是最优先要修的洞。

### 11.6 Token 浪费账：哪些能归零、哪些只能压低（回你「不论几轮，我只想知道浪费能不能彻底解决」）

先列历史浪费的实测账（两次 review 合计 OCR **1768 万** token 的构成，数字全来自 problems.md 附录 A 的取数），再逐类说结局：

| 浪费类型 | 历史实测 | 治它的任务 | 结局承诺 |
|---|---|---|---|
| ① 同范围重复跑 | **206 万**（R2 状态延迟补跑 82 万 + 62d31045 未记账重跑 124 万） | T2 | **结构性归 0**：终态判定 + `complete` 禁止重跑 + 补跑前必先跑 `sessions` 对账——同一范围已有 complete session，重跑的门就焊死。这是硬规则，不是纪律 |
| ② aborted / 游离 session | 22.6 万烧了零产出 + 「浪费不可见」本身 | T1 | **归 0 且必可见**：sessions 对账报出一切未记账/零产出 session，浪费无处躲（§九指标已挂） |
| ③ C 级纯样式驱动整轮 | **125 万**（L3 收口 R6-R9 四轮实测 1,252,744） | T4 | **结构性归 0**：C 档不修 → 不产生 diff → 不进下一轮审查面；重报被锚点吞（10-10 分账说的 L2 锚点第一次真正上膛，且落锚由 T1 机器校验）；B 档攒批并一轮 |
| ④ 429 盲试 | 3 次失败 + 4 小时空转（失败本身 token ≈ 0） | T2 | **归 0**：显式「⏸ 等配额」一次为限——省的主要是 4 小时和三次失败记录 |
| ⑤ 修复引入的返工轮 | 数百万级（最清晰一块：L3 收口 R3-R6 四轮实测合计 355 万） | T5 | **大幅压低，不说「彻底」**：四道闸各对一个历史实锤（同族三犯 / 数字三犯 / 假闸门三变体 / 半成品契约），重算 4 轮 → 1 轮。但「新代码可以有新缺陷」是物理事实——**能承诺的是：已知模式复发 ≈ 0，未知模式复发必被 11.5 绊线复盘并回改方案** |
| ⑥ OCR 首遍探不全 | 真问题晚 1-2 轮才浮出（R1 只探出 4/19） | 管不了 | **保留**——外部 LLM 的发现行为，不归流程管；且它不是纯浪费：多跑的那几遍也在找真问题 |
| ⑦ 范围流入被重审 | R13 批 2 + R14 ≈ 288 万 | T3 | 总量不省（真代码总要审），省的是「半成品被审两遍」和打断主审查的混乱 |

**三句话总结**：
1. **能彻底解决的（①~④，合计约 330 万/两次）全是硬规则**：终态判定、对账、分级、锚点——没有一条依赖 agent 自觉，复发即机器报警；
2. **最大的一块（⑤ 返工轮）只能承诺「已知模式归零 + 未知复发必被看见」**——把「彻底」两个字用在这里就是在骗你，T5 压的是概率不是物理；
3. 剩下约 **900-1000 万是审真代码、修真问题的必要成本**——想省它的唯一办法是让代码进来时别带那么多病。**这个缺口已在追问后补上：T6（§十二）给开发侧的「事前三步」装上机器闸门，命中率反馈让「做得假」必曝光——这是全方案唯一直接压这个桶的杠杆。**

## 十二、任务 6：开发侧「事前三步」闸门（2026-10-16 追问后新增，⏳ 待你点头）

> 起因：你问「那你的方案有事前三步是什么？」——诚实盘点：T0-T5 装的是事前三步在 **review 修复侧**的机械化（T5 失败面/同族/契约链 + 既有全貌确认六维表），而**批次进 review 之前**只有你的全局规则在管——纯纪律、无机器校验，R9 假 ✅ 已证明纯纪律会漂。本任务补上这半。

### spec

- **是什么**：三件套，把「初始代码别带病进来」从纪律变成可检查的机制：
  1. **随行全貌确认**：开发完成、批次进 review 前，必须有一份六维全貌确认（本质/同族/边界/验收/影响面 + 联动四问）与代码同批落盘（存 review 目录，与 baseline 同级——它本来就是审查的输入）。模板从修前语境**抽成共用节**（单一真相，两处引用一处定义，防分叉漂移）。
  2. **入口检查**：T3 的 `baseline` 环节顺带检查——文档存在 + 机械字段齐（六维非空、影响面列到具体文件、验收带取数命令）。**缺 = 标记「无全貌确认批次」，不卡死 review**（只标记，进 §11.5 绊线复盘的归因——文档缺失不许挡住真实工作）。
  3. **命中率反馈（防假文书的关键）**：review 终局对账时，把随行确认里**预测的失败面/影响面**与 **OCR 实际发现**对照，输出命中率。预测准 = 真省了返工轮；预测全不中 = 事前三步做得假 → **复盘开发流程**（不是复盘审查流程）。命中率是趋势指标不是配额（低分触发复盘，不拦截不扣分——同 §11.5 绊线逻辑，防 Goodhart）。
- **为什么它是唯一动「必要成本桶」的杠杆**：T0-T5 全在病进来之后省钱（省审查的浪费）；只有 T6 在病进来之前减量（少生成要审的真问题）。
- **不做什么**：不造「LLM 评确认质量」（命中率数字本身就是评）；不用文档缺失拦截 review（只标记）；不把它塞成查账表第 38 行（查账表只加一行「随行确认存在」）。
- **自行逻辑检查（本任务新增的两个悖论）**：① 「文档缺失卡死工作流」→ 只标记不拦截；② 「确认变假文书」→ 命中率曝光 + **批次封板后确认只读**（它是开发时快照，进 review 后不许改——防 R11「同轮落盘即过期」的病：预测必须是动手前写的，不许照着 OCR 结果补写）。
