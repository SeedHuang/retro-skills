# Multi-Lens Review（多透镜评审引擎）

## 理念

产出物质量 = 透镜覆盖度 × 透镜知识密度。透镜 = **流程手法（保广度） × 角色面板（保深度）**——缺任何一半都会漏：流程没有领域地雷，角色没有覆盖纪律。每换一个透镜就照出新问题，所以评审是"多透镜枚举 + 收敛判定"，不是"再仔细看一遍"。

## 总流程

1. 判定场景（PRD / 技术方案 / 通用文档）→ 读 `references/role-panels.md` 取对应角色面板
2. 通读全文，标记五类要素：所有操作/命令、所有持久化数据字段、所有用户输入点、所有表格与图、所有验收标准
3. 六手法顺序执行（不许跳）
4. 角色面板逐角色过必问清单——**必问必答**，"问过，无问题"也要显式记录，防角色扮演流于形式
5. 按输出格式报告 + 建立问题列表
6. 修复后：重跑手法 3 + 对每个修复项做同族扫描
7. 收敛判定（见收敛协议）；未收敛回到 3，已收敛则停

## 六个手法

### 手法 1：操作序列推演（产出最高，最先做）

把每条操作当状态转移函数，走查四类序列：

- **重复执行** op → op：再跑一次，数据被污染吗？（幂等性）
- **交叉执行** A → B → A：另一个操作会冲掉这个操作的记录吗？
- **中断恢复**：任意步骤崩溃 → 重跑幂等还是卡死？
- **接管时刻**（实战教训固化）：操作集不只包括本工具的命令——**用户在工具接管之前手动制造过的任意脏状态**（手动改文件、半配置、外部工具产物）都要当作合法输入推演。接管逻辑必须校验前提，不得假设干净世界。

心法：优先攻击"最普通的操作 × 最坏时机"。

### 手法 2：数据字段生命周期审计

四问：谁写？谁读？何时失效？失效后残留会怎样？重点核对**读取点合法性**——字段读取时是否校验了"当前值来自合法来源"（防被外部状态污染后当作有效值持久化）。

### 手法 3：跨章节一致性矩阵

- 表格 × 表格（依赖表 vs 执行顺序、命令表 vs 章节引用）
- 文字 × 图（描述分支 vs 时序图/流程图分支）
- 验收 × 现状（验收标准 vs 代码库/环境事实）——断言"X 问题不存在"前，先列全 X 的失败模式（爆炸式/静默式）逐个取证（实战教训固化：hooks 不炸 ≠ 无双实例，antd 双实例是 context 级静默失败；产物与结论矛盾即复检信号）
- 引用 × 定义（正文引用的编号在文档内必须有定义或对照表——评审编号落进产出物时，对无对话记忆的读者是悬空引用）

### 手法 4：输入空间枚举

每个输入点过一遍：空 / 不存在 / 非法格式 / 含空格 / 多个 / 重复 / 指向异常结构。

### 手法 5：假设显式化

挖出没写出来的前提假设，逐个标记：已验证 / 待验证 / 需写成前置条件。扫描范围三处：

- 明示的技术依赖（目录结构、工具行为、目标项目配置）
- **平台机制断言**（实战教训固化）：每个"用 X 机制实现 Y"，验证 X 在目标平台的真实行为（如 lstat 对 junction 返回 false、CRLF/BOM、路径大小写）
- **决策背后的隐含假设**：每条"不做 X"的非目标决策，背后假设了用户的什么状态？（如"不代写依赖"隐含"lib 都发布过"）

### 手法 6：可逆性 → 确认策略一致性

破坏性操作按可逆性排序，核对确认策略：可逆不确认、不可逆必确认。

## 跨角色必问（每个 P0/P1 确认后立即执行）

**同族扫描**：这个漏洞的抽象模式是什么（如"非法值覆盖持久化字段""外部状态未校验即接管"）？按此模式枚举所有同族入口。实战教训：发现"存续期外部改动覆盖"后没做同族扫描，同族的"接管前外部状态污染"相隔两轮才被发现。

## 收敛协议

- 一轮 = 六手法 + 角色面板全过 + 修复 + 手法 3 重跑 + 同族扫描
- **收敛条件：连续 2 轮零新增 P0/P1**（P2 只记录不阻塞）。为什么 2 轮：修复本身会引入新问题（实战案例：加依赖关系忘了同步执行顺序表）
- 每轮产出问题列表：编号 | 级别 | 来源透镜（手法 N / 角色 N）| 状态
- 每个问题做**成分归因**：

| 归因 | 含义 | 对策 |
|---|---|---|
| 流程缺失 | 手法没覆盖此检查路径 | 强化手法条目 |
| 知识缺失 | 有流程无领域知识 | 角色面板加必问条目 |
| 修复引入 | 上轮修复造成 | 修复纪律补检查点 |
| 假设未显式化 | 隐含前提没被列出 | 手法 5 扩围 |

- 归因分布是透镜进化路线图（知识缺失多 → 优先扩角色面板）
- 收敛即停：透镜固定后第 3 轮边际收益骤降，是完美主义空转。精力转投复盘回流。

## 复盘回流（评审飞轮）

后续阶段（开发/测试/使用）发现**本应评审期发现**的问题时：

1. **先记录不阻塞**：按复盘套件流程落错题集 KB——`retro-collect` / `retro-analyze`，条目进 `<KB>/skills/multi-lens-review/ledger.md`（教训落点 = 本技能的手法条目 / 角色面板必问项；**不写进本技能目录**，目录保持发布纯净）
2. **提示用户**：「这暴露了评审透镜的盲区（归因 X），可固化进 skill。现在优化还是稍后批量？」
3. 用户同意优化 → 走 `evolving-skills`（六步协议 + 差异卡：失败场景先行、攒批、独立合并、体积守卫）——**不在评审当场顺手改**

飞轮：评审 → 发现 → 修复 → 归因 → 透镜进化 → 更强的评审。

## 输出格式

### 严重性三级（不许混报）

| 级别 | 判据 |
|---|---|
| 矛盾（P0） | 两处规定冲突 / 操作序列导致不可逆数据损坏 / 文档自相矛盾 |
| 盲点（P1） | 场景真实会发生但未定义行为 |
| 优化（P2） | 逻辑成立但可更好 |

### P2 处置协议（实战教训固化）

P2 不阻塞收敛，但**禁止凭对话流失**——每个 P2 必须显式处置为三态之一并落进产出物文档：

- **采纳**：评估用户体验增量 / 实现成本 / 风险后并入，标注落点（章节 / spec ID）
- **关闭**：写明理由（伪需求 / 被替代 / 已有等价覆盖），防未来重复讨论
- **候选**：标注触发信号（何种实际信号出现时再评估，如"该场景真实发生 ≥ 2 次"）

处置结果沉淀为产出物文档的 **Backlog 章节**（三张表：已采纳 / 已关闭 / 候选）。

### 报告结构

1. 结论先行：X 矛盾 + Y 盲点 + Z 优化，一句话点出最危险项
2. 分级详述：问题 + 触发序列/证据 + 修复建议
3. 自洽确认区：攻过但没攻破的点（防重复劳动）
4. 修复对照表（若已修复）：问题 → 落点一一对应

### 修复纪律

- 每发现带具体修复落点，修复完出对照表
- 修复即二次评审：改完必重跑手法 3
- 修复 diff 自审：改动涉及的所有交叉点（表格/图/验收）同步检查
- 每个修复项做同族扫描
