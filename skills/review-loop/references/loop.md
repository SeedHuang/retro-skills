# review 循环的共享口径（三条命令共用）

> 本卡是 `review-code-to-death` / `review-md-to-death` / `review-all-to-death` 的**唯一口径来源**。
> 改这里等于改全部三条；三条命令文件里**不再重复**这些内容。

## 1 停机判据

**判据是「清单核销干净」，不是「轮数够了」。轮数不是任何一段的停止条件。**

### 话术约定（一个词只指一个东西）

| 词 | 固定指什么 | 会不会变 |
|---|---|---|
| **一轮** | 整套流程从头走一遍：段一 → 段二 → 段三，各走一遍 | 会变（第 1 轮、第 2 轮…） |
| **段** | 流程里的第几步，**永远是那三步** | 编号永不改变 |

**一轮之内不回头重跑任何一段。**要重跑就是进下一轮。

### 每段各自的闭环判据（别混用）

| 段 | 这一轮内要做完的事 | 什么时候算核销 |
|---|---|---|
| **段一 · 代码** | 按 OCR `--preview` 的 `Will review` 清单逐个审完；报出的问题**逐条登记** | 本轮清单审完 + 问题都登记了 |
| **段二 · 文档** | 按 `multi-lens-review` 自己的收敛协议走完（**判据见 `multi-lens-review`，本卡不重定义**） | 本轮报告出，且 P2 已按三态登记 |
| **段三 · 对账** | `mode-all.md` 里的断言逐条取证（含反向扫） | 本轮全部断言都有结论 |

**段二的收敛判据（P0/P1/采纳 P2 = 0 的清单口径，权威定义在 `multi-lens-review`）不外借给段一/三。** OCR 没有 P 分级，它只报问题清单——段一的判据是「OCR 清单逐条登记完」（见本表上一行）。把段二的 P 级判据套到 OCR 上，等于给自己一个「跑够几轮就算完」的假依据。

⚠️ **2026-10-08 收敛为指针**：本卡曾复述那句判据**两次**（表格里 + 紧跟一段注解）。**两份不一致时我用了错的那份** —— 实测 9 轮审查里我一度拿它当整轮停机条件，而它只管段二。

### 整体停机

**某一轮里三段都核销完（段一 OCR 清单逐条登记完、段二 P0/P1/采纳 P2 = 0、段三断言全取证），且修复后重扫一遍确认无新增 → 才停。**

为什么不能「一轮就停」：修复合并本身会引入新问题（加了字段忘了同步模板、改了栏名忘了改下游提取）。一轮就停等于只审了一遍。

### 一轮不算数的三种情况

| 情况 | 为什么这轮不算 |
|---|---|
| OCR 输出被截断 / 超时 / 只列出部分文件 | 那不是「零发现」，是「没看完」 |
| 段二只审了部分 md（没列全） | 同上 |
| 某段空转跳过（如纯代码改动时第三段） | 要在报告里写明「空转」，**不能算「已跑」** |

### 收尾（核销完之后必做，不做等于没审完）

| 收尾 | 为什么必做 |
|---|---|
| **建/更新过程账（技能 `review-log`）** | **没有账本就没有「这条处理过没有」这个概念** —— 实测 2026-10-08：第 8、9 轮 OCR 报同一批 3 条，我处置了两遍，因为轮次编号是口头数的。**每轮 OCR 跑完立刻把 `session id` 记进轮次账表** |
| 扫一遍「声明它的地方」 | 改了实现，文档/注释/README 里的旧说法不会自动跟着变 |
| 跑一次全量测试 | 验证没修出新问题 |
| 报最终结论 | 说清几轮、每段各修了什么、是否核销干净 |
| **收尾审计**（全局规则 `how-i-must-reason` 收尾审计一节） | 问一句「这次有没有**本该被管、但压根没想起来查**的」——不是「有没有违反已知规则」 |

### 每一轮的开场动作（不许跳）

**一轮开始前，先读过程账的轮次表**（`.session/reviews/<那一次>/progress.md`），回答三件事：

1. **上一轮是第几轮**——轮次编号**从表里数**，不许口头数
2. **上一轮 OCR 的 session id 是哪个、报了几条、逐条处置完没有**
3. **本轮的增量范围是什么** —— **不是全量 diff**，是上一轮修完之后的增量

⚠️ **实测失败模式（2026-10-08）**：范围一直是全量 diff → 每轮都在重审同一批文件 → 第 8、9 轮报同一批 3 条。**范围不收窄，核销就是假的** —— 后一轮永远在追前面的账。

### 工具跑起来没输出时：先查状态，别干等、别打断

OCR 正式跑之前会先出 `--preview` 清单，之后可能**长时间没有任何输出**。这时候**不要干等也不要打断**——去查它自己的状态：

```powershell
ocr session list    # 看最近几次 session 的 STATUS 与评论数
```

| STATUS | 含义 | 该做什么 |
|---|---|---|
| `complete` | 跑完了 | 直接取结果 |
| `aborted` | **被打断的** | 评论可能已经落盘 → `ocr session comments <id>` 先取出来，再决定要不要重跑 |
| 没这一行 | **两种可能，别混**：① 这次还没落进列表（刚启动，历史 session 是跑完/中断才写进去的）→ 等；② 你看的是列表的**前几行**而这次在更后面 → 往下翻 |  |

**实测补充（2026-10-08，第 6 轮）**：跑完时终端输出里**没有** `STATUS` 那一行（`ocr session list` 里才有），而且第 5 轮那次输出很长、**尾部被截断**——所以「终端输出里找不到 STATUS」**不等于**还在跑。**唯一可靠的判据是查 `ocr session list` 最新的那一行**（对比跑之前的列表，看有没有多出新的一行）。第 5 轮就是靠它发现评论已落盘、不用重跑。

**别打断**：`StopCommand` 会让这次落成 `aborted`，评论虽已落盘但**流程算中断**——第 5 轮的实测教训正是「干等 6 分钟零输出，凭 CPU 0.03 秒推断它在等 LLM、可能配置有问题」，**两个都是猜的**；查一下就知道 STATUS 是 `aborted`（被我打断的），**配置本来没问题**。

判据：**「进程在但没输出」推不出任何结论，要看工具自己怎么说。**

## 1.5 什么时候才问用户

> **通用纪律在全局规则 `how-i-must-reason.md` §5**（禁把选择权推回用户；例外只有三类：只能靠偏好定的取舍 / 不可逆操作 / 越出授权范围）。本节只写**本审查流程特有的**那些。

**默认自己定。问用户是例外，不是常态。**

**属于「例外」的，本流程里只有这一类**：**越出审查范围** —— 审 A 技能时发现 B 技能有同样问题 → 要不要顺手改 B。
（另两类属全局规则：不可逆操作按 `no-git-write`；只能靠偏好定的取舍。）

**不属于例外的（这些是 bug，别再犯）**：

- **顺序问题** —— skill 已经把段序排好了，照做
- **「怎么跑通某个工具」** —— 自己查配置、查历史记录（例：`ocr review --commit <tag>` 收不收 tag，本仓 0 个 tag 测不了，那就写「未验证 + 给替代路径」，**不是「需要你定」**）
- **「某段代码该怎么改」** —— 取证之后直接改

**自查一句话**：*「这个问题我能自己查到吗？」* —— 能，就去查，别问。

⚠️ **2026-10-08 收敛**：本节曾复述全局规则的三阶段表 + 三类例外。**两处各自演化**，而我读的是本节那份 —— 判据不一致时用了错的。**权威在全局规则**，本节只留本流程特有的一类。

## 1.6 本流程特有的取证判据

> **通用的「判据必须能被查出来」在全局规则 `how-i-must-reason.md` §1/§2/§3**（判据三问、来源三档、禁「成本高 / 感觉」当判据）。本节只留**审查流程特有**的。

**每条判断在被当成依据之前，先问一句：用什么命令能验它？**

| 说出口的话 | 是不是判据 | 为什么 |
|---|---|---|
| 「深度 3 够用」 | ❌ **不是** | 说不出拿什么命令验「够用」。真判据是「仓库里最深有几层 md / 超过 3 层有几个」——那是要去数的（取数：`Get-ChildItem -Recurse -Filter *.md` 按路径层级统计；2026-10-08 实测 retro-skills 本仓分布 `{0:3, 1:20, 2:40}`，最深恰好 2、无文件卡在第 3 层。所以这句话不查就等于在赌「再深一层也不放文件」） |
| 「CRLF 下会匹配不到」 | ✅ 是 | 可以把模板读成 CRLF 再跑一遍，看它坏不坏 |
| 「`--to` 没登记在 `CLI_FLAGS`」 | ✅ 是 | 跑那条守卫（删掉它看会不会红），或直接读 `CLI_FLAGS` 那一段的字面量 |
| 「这写法有风险」 | ❌ **不是** | 「风险」多大？说不出来就是感觉 |

**危害**：没有判据的话**说出来特别像结论**，而且往往正好是你想听的那句（「够用」「应该没问题」「影响不大」）。它比明说「我不知道」危险得多。

**这是不改判据的另一种形式**——「我不知道所以问你」至少诚实；**「我猜了个数所以不问你」是把猜测冒充结论**。两者都违反「先查」。

**配套**：验证完还要能说出「**它因为什么红**」。跑一遍 ≠ 测到东西——
本仓库实测（2026-10-08）：一条 CRLF 守卫报红，我当它有效；实际它红的原因是**反例构造失败**，不是它真的测到了 CRLF。**红 ≠ 有效。**

## 2 取数方式（工作区 / N 次 / 单个 commit）

**范围由用户给的那句话决定**：给了数字 N 就是最近 N 次 commit，给了 hash / tag 就是那一个，都没给就是工作区未提交。

| 用户给的 | 范围 | 代码侧命令 | 文档侧取数 |
|---|---|---|---|
| 不给 | 工作区未提交 | `ocr review` | `git status --porcelain` |
| 1 | 最近 1 次 commit | `ocr review --commit HEAD` | `git show --numstat HEAD` |
| N | 最近 N 次 commit | `ocr review --from HEAD~N --to HEAD` | `git diff --numstat HEAD~N HEAD` |
| 一个 hash | **那一个** commit（**不是**最近 N 次） | `ocr review --commit <hash>`（实测 `--preview` 正常出清单；官方帮助里 `--from/--to` 是给两条 ref 的，单 commit 有专门的 `--commit`） | `git show --numstat <hash>` |
| 一个 tag | 同上，**⚠️ 未实测**（本仓 0 个 tag） | 先 `git rev-parse <tag>^{commit}` 换 hash，再用上一行 | 同上 |

**为什么 hash 单列一行**：它和「N 次」不是一回事——`--from HEAD~3 --to HEAD` 是**两个端点之间**的 diff（一个文件中间改过多轮就只剩净额），`--commit <hash>` 是**那一次**。混用会审出一个「从没存在过的文件版本组合」（2026-10-08 段二对账发现：SKILL.md 给了 hash 这一档，但本表没有对应行）。

**根 commit 没有父，写 `hash^` 会 fatal**（实测 2026-10-08：本仓根 commit `fb439a09`，`git show --numstat fb439a09^` 报 `unknown revision`）。文档侧一律写 `git show --numstat <hash>`，**不要**自作聪明加 `^`。

### commit 范围内读文件的关键判据

**agent 直接读磁盘，读到的是「最新内容」，不是「那个 commit 时的内容」。**

判据：**这个文件在那次 commit 之后是否还有新改动？**

```powershell
# 1) 那次范围改了哪些文件 —— 取名单 A
#    N 次：git diff --name-only HEAD~N HEAD
#    单个：git show --name-only --format= <hash>
git diff --name-only HEAD~N HEAD

# 2) 这些文件此后是否又被动过 —— 对名单 A 里的每个路径查
git diff --name-only HEAD~N HEAD -- <路径>
```

第 2 条的两个端点别搞混：`git diff A B` 比的是 A 与 B 两个快照。**左边 `HEAD~N` = 那 N 次 commit 结束的那一刻，右边 `HEAD` = 现在**。若某路径在第 2 条里有输出，说明它此后又被改过。

（实测 2026-10-08：N=1 时第 1 条列出 9 个文件，第 2 条对其中 7 个有输出——即工作区里还在改。）

**单 commit 范围（`--commit <hash>`）同理，把两端换掉**：

```powershell
git show --name-only --format= <hash>                        # 名单 A = 那一次改的文件
git diff --name-only <hash> HEAD -- <路径># 该文件此后有没有再被改
git show <hash>:<路径>                                         # 那时刻的全文
```

**「此后」指 `<hash>` 到 HEAD 之间**，不是「那次范围之外」——单 commit 范围下没有 `HEAD~N` 那个左端点，别照抄上面的写法。

- **没再被改** → 直接 `Read` 磁盘，内容就是对的。
- **还有新改动** → **必须**取 commit 时刻的版本：

```powershell
git show HEAD~N:<路径>                # 该文件在该 commit 时刻的全文
git diff HEAD~N HEAD -- <路径>        # 它后来又改了什么
```

漏了这一步就会审错对象：**审出来的是「最新文件配旧 diff」，结论会指向一个当时并不存在的问题。**

## 3 硬约束（不许商量）

| 约束 | 为什么 |
|---|---|
| **不 commit、不 push** | 提交是用户的决定，agent 不代劳 |
| **不许手动判断「应该没问题了」提前停** | 停机判据在 §1，是「清单核销干净」，不是「轮数够了」，不许自行放宽 |
| **不许跳段** | 指定哪段就跑哪段，`code` 模式不许顺手改文档 |
| **不碰审查范围外的文件** | 修bug 时顺手重构会污染 diff |
| **循环中不许停下来问用户** | 判据在 §1.5。顺序是「先查 → 再定 → 最后才问」，跳到第三步就是甩锅 |
| **不许问「要不要提交 / 要不要先存一下」** | 提交从来不在 agent 的选项里（上一条已定），所以这问题**没有答案**。实测 2026-10-08：review 进行到第 4 轮问「继续还是先提交」——用户从头到尾说过不提交。更糟的是我还在问句里带了「改动已 1353 行，风险在上升」这种**暗示该提交的理由**——那不是提供信息，是拿信息推一个我不该提的建议 |
| **不许拿「我不确定」当停机理由** | 不确定时该**去查**（`ocr session list` 看状态、读源码确认现状），不是把选择权推给用户。「不确定」和「该问你」是两件事 |

## 4 输出格式

**每轮末尾（三段分开列，不许混成一张表）**：

```
段一 ·代码：清单 N 个文件 → 发现 M 条 → 修了 M 条 → 验证：跑的命令 + 结果
段二 · 文档：扫了 K 个 md → 发现 J 条 → 修了 J 条 → 验证：<multi-lens 的收敛结论>
段三 · 对账：X 条断言逐条取证 → 发现 Z 条漂移 → 修了 Z 条
本轮结论：三段是否都核销｜是否进下一轮
```

**全部结束后**：

```
共 N 轮 ｜ 每轮修了多少 ｜ 最终状态：核销干净 / 未核销（未核销要说清卡在哪一段）
```

数字必须是**实测值**，不是记忆值，用了哪些命令拿到的要写出来（通用口径见全局规则 `how-i-must-reason` §6）。**本流程特有的两条**：
- **OCR session id 必须写出来** —— 它是唯一能回溯「当时报了哪些」的凭据；
- **未验证 / 无法验证的项要单独列** —— 没测过的东西下一轮会被当成「已验证」（例：`ocr review --commit <tag>`，本仓 0 个 tag测不了）。
