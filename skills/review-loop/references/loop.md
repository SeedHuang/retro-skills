# review 循环的共享口径（三条命令共用）

> 本卡是 `review-code-to-death` / `review-md-to-death` / `review-all-to-death` 的**唯一口径来源**。
> 改这里等于改全部三条；三条命令文件里**不再重复**这些内容。

## 1 停机判据

**判据是「清单核销干净」，不是「轮数够了」。轮数不是任何一段的停止条件。**

### 话术约定（一个词只指一个东西）

| 词 | 固定指什么 | 会不会变 |
|---|---|---|
| **一轮** | 整套流程从头走一遍：段一 → 段二 → 段三，各走一遍 | 会变（第 1 轮、第 2 轮…） |
| **段** | 流程里的第几步，**永远是那三步** | 编号永不改变 |

**一轮之内不回头重跑任何一段。**要重跑就是进下一轮。

### 每段各自的闭环判据（别混用）

| 段 | 这一轮内要做完的事 | 什么时候算核销 |
|---|---|---|
| **段一 · 代码** | 按 OCR `--preview` 的 `Will review` 清单逐个审完；报出的问题**逐条登记** | 本轮清单审完 + 问题都登记了 |
| **段二 · 文档** | 按 `multi-lens-review` 自己的收敛协议走完（**判据见 `multi-lens-review`，本卡不重定义**） | 本轮报告出，且 P2 已按三态登记 |
| **段三 · 对账** | `mode-all.md` 里的断言逐条取证（含反向扫） | 本轮全部断言都有结论 |

**段二的收敛判据（P0/P1/采纳 P2 = 0 的清单口径，权威定义在 `multi-lens-review`）不外借给段一/三。** OCR 没有 P 分级，它只报问题清单——段一的判据是「OCR 清单逐条登记完」（见本表上一行）。把段二的 P 级判据套到 OCR 上，等于给自己一个「跑够几轮就算完」的假依据。

⚠️ **2026-10-08 收敛为指针**：本卡曾复述那句判据**两次**（表格里 + 紧跟一段注解）。**两份不一致时我用了错的那份** —— 实测 9 轮审查里我一度拿它当整轮停机条件，而它只管段二。

### 整体停机

**停机 = 修复轮 + 复查轮，两轮都干净才停：**

- **第 N 轮（修复轮）**：**第 1 轮审本次范围的原始内容；第 N（≥2）轮审「第 N-1 轮修复后的增量」**，发现的问题全部修掉、登记完（段二口径：P0/P1/采纳 P2 = 0）。
- **第 N+1 轮（复查轮）**：**必须真的跑**——把第 N 轮的修复当新内容，重新过完整段（段二口径同修复轮：P0/P1/采纳 P2 = 0）；查出新问题 → 修 → 再进一轮；查出 0 条 → 停。

⚠️ **复查轮的「重新过完整段」必须包含段二（md），不是只重跑段一 OCR**：上一轮修复若动了 md（文档 / 操作卡 / 注释 / spec），复查轮必须对「修复涉及的 md 增量」重跑 multi-lens-review 六手法。**账本段二列必须写出「审了哪些 md 增量 + 六手法结论」**——只写「0 发现」不算跑，那只是「没审」不是「零发现」（实测 2026-10-11：retro-skills L3 落地 review 第 2/3/4 轮段二只标 0 没真跑，收尾审计才发现并补跑）。

⚠️ **轮内的「修复后手法 3 重跑 / 同族扫描」不是复查**——它是修复纪律（防当场引入），代替不了下一轮的独立复查。

为什么不能「一轮就停」：修复合并本身会引入新问题（加了字段忘了同步模板、改了栏名忘了改下游提取）。一轮就停等于修复后的内容没被独立审过——实测 2026-10-09：round 1 修 6 条后自审报「复查后 P0=0」即停，round 2 一查就抓到 1 条修复引入的 P1（待拆未定报告形态未定义）。

### 一轮不算数的三种情况

| 情况 | 为什么这轮不算 |
|---|---|
| OCR 输出被截断 / 超时 / 只列出部分文件 | 那不是「零发现」，是「没看完」 |
| 段二只审了部分 md（没列全） | 同上 |
| 某段空转跳过（如纯代码改动时第三段） | 要在报告里写明「空转」，**不能算「已跑」** |
| **复查轮段二只写「0 发现」、没写「审了哪些 md 增量 + 六手法结论」** | **「没审」≠「零发现」**——没跑六手法就标 0，等于这轮段二没跑（2026-10-11 实测：L3 落地 review 第 2/3/4 轮就是这种假核销） |

### 收尾（核销完之后必做，不做等于没审完）

| 收尾 | 为什么必做 |
|---|---|
| **建/更新过程账（技能 `review-log`）** | **没有账本就没有「这条处理过没有」这个概念** —— 实测 2026-10-08：第 8、9 轮 OCR 报同一批 3 条，我处置了两遍，因为轮次编号是口头数的。**每轮 OCR 跑完立刻把 `session id` 记进轮次账表** |
| 扫一遍「声明它的地方」 | 改了实现，文档/注释/README 里的旧说法不会自动跟着变 |
| 跑一次全量测试 | 验证没修出新问题 |
| **合并回母分支（SKILL.md「收尾」小节，用户确认后才做）** | 工作区检查（清单外改动先问）→ 范围预检 → 展示 diff → 用户确认 → rebase → 删分支。**这是唯一允许问「是否提交/合并」的场景** |
| 报最终结论 | 说清几轮、每段各修了什么、是否核销干净 |
| **收尾审计**（全局规则 `how-i-must-reason` 收尾审计一节） | 问一句「这次有没有**本该被管、但压根没想起来查**的」——不是「有没有违反已知规则」 |

### 每一轮的开场动作（不许跳）

**一轮开始前，先读过程账的轮次表**（`.session/reviews/<那一次>/progress.md`），回答三件事：

1. **上一轮是第几轮**——轮次编号**从表里数**，不许口头数
2. **上一轮 OCR 的 session id 是哪个、报了几条、逐条处置完没有**
3. **本轮的增量范围是什么** —— **不是全量 diff**，是上一轮修完之后的增量

**分支确认（SKILL.md「分支前置」的延续）**：确认当前在 review 分支上（`git branch --show-current` 以 `review/` 开头），
且上一轮已 commit（`git log --oneline` 末位是带 【review】标记的提交）。
**第 1 轮的增量基线 = 建分支时的工作区快照**（分支前置已做）；第 N（≥2）轮的增量基线 = 第 N-1 轮的 commit。
**中断恢复**：若上一轮 commit 后会话中断、这次接着审（分支前置第 1 步已识别当前在 `review/*` 上）→
第 1 轮的增量基线 = 中断前最后一次 commit（不是建分支时快照）——**先读 progress.md 确认中断在那一轮**。

⚠️ **实测失败模式（2026-10-08）**：范围一直是全量 diff → 每轮都在重审同一批文件 → 第 8、9 轮报同一批 3 条。**范围不收窄，核销就是假的** —— 后一轮永远在追前面的账。**分支 + 每轮 commit 就是把这个「范围收窄」落成可验证的机制**。

### 处置前的重复判定过滤（防 L2 重复劳动，段一处置时执行）

> L2 是什么：OCR 无跨轮记忆，已判定「不改/误报」的问题可能原样再报一遍（实测 2026-10-10：第 16 轮关闭「catalog 盘符判定」、第 18 轮原样再报）。
> 根治靠**处置侧过滤**：不管 OCR 报几次，重复的都自动吞掉，成本恒为零——**不靠喂清单求 OCR 别报**（那是概率性的）。

**每轮 OCR 评论产出后，先过滤再处置，不许直接逐条修：**

1. **规则过滤**（确定性，可测试）：本轮评论 vs `problems.md` 的「不改/误报」锚点
   - 命中条件（三要素同时满足）：文件相同 **且** 行号范围重叠 **且** 关键词有重合
   - 命中 → 处置状态直接写「不改（重复，见 problems.md #N）」，**不计入本轮问题数、不修、不产生新 diff**
   - 三要素不全中但文件 + 关键词重合（如行号漂移）→ **不放行、也不算命中**，落到第 2 步语义裁决
2. **语义裁决**（规则没命中，但疑似同一问题）：agent 读 problems.md 那条的理由 + 本轮评论内容，判断是否同一问题
   - 同 → 按「不改（重复）」处置
   - 不同 → 当新问题正常处置
3. **两个方向的失败都低成本**：误吞真新问题 → 代码没改、后续轮 OCR 还会再报（有第二次机会）；误当新问题 → 多判一次。**都不需要问用户**（判据：§1.5「先查→再定→最后才问」）。

⚠️ **只过滤「不改/误报」，不许过滤「已修」**：已修的问题移出了 problems.md，若后续轮次再报，**必须按新问题正常处置**——它更可能是「修复引入的回归」（实测 2026-10-10：第 2/14/16/17 轮各抓到的回归全是「上轮修完再报」的形态），不是重复劳动。把已修当重复吞掉 = 放走回归，比 L2 严重得多。

⚠️ **锚点不全的旧记录**：本轮前 problems.md 里的「不改/误报」可能没有锚点——规则过滤命不中就走语义裁决，别因为缺锚点就放弃过滤。

### 修复纪律（A1/A2/A3，防 agent 侧放大器，修复时执行）

> A1-A3 是什么：18 轮审查的 agent 侧放大器（7 条自伤回归 + 纯样式建议也修 + 测试全绿但行为错）。L1/L2/L3 治流程，A1-A3 治手，两条线都要——不治手，修出来的还是半成品。

1. **A1 · 修复前列全失败面**：修一条建议前，先问「这条修复要覆盖的整个失败面在哪」——同源同类（读 / 校验 / 推导 / 归一 全链路）逐处列出核对，**不是只改 OCR 点名的那个函数**。实测教训：第 16 轮只把 `loadConfig` 挪出 try，漏了同 try 里的 `normalizeConfig`，第 17 轮同类问题再报一遍。
2. **A2 · 样式/优化类评论判不改**：OCR 报的**不改行为的样式/优化类建议**（提变量、命名、格式化、注释、死代码等）→ 默认「不改」，登记进 problems.md「不改/误报」锚点，**不修、不产生新 diff**。来者全修 = 制造新 diff = 喂 L1。**判据按「性质」，不按级别**：改不改**影响行为/正确性**（bug 类，哪怕 OCR 标 `low` 级）→ 改；改不改**不影响行为**（纯样式/优化，哪怕标 `high` 级）→ 不改。**重复类评论不靠目测**——跑 `npx jscpd --reporters json <OCR 点名的文件/目录>`（限定范围扫，全仓扫会慢）。jscpd 没查出来 → OCR 误报 → 按「不改」处置。jscpd 查到（几处几行）→ **再过「合并价值」判据**：命中跳过条件（两边语义不同 / 故意样板 / 生成代码 / 抽象命名只能叫 `processData` / 少于约 10 行）→ 合并意义不高 → 按「不改」处置；只有「合并后能删代码 + 能精确命名」才值得改（判据以 `dry-refactor-newadd` 技能第 3 步分诊为准）。**判「值得改」的重复合并，接 A1 列全失败面（所有调用点，不止 jscpd 报的那两处）→ 改完接 A3 真实场景实测**——A2 只管判改不改，怎么改归 A1、改完怎么验归 A3，三条是链不是单点。**不引 dry-refactor-newadd 全套流程**（它要求工作区干净、审最近一次提交，与 review 中状态冲突）。判「改」必须有明确理由（影响正确性/可读性）。**与 L3 的区别**：L3 治源头（规则对症、减少凑数），A2 治处置侧（凑数来了也吞掉），两条都做。
3. **A3 · 修复后真实场景实测**：修完除跑测试外，用**真实用法**实测一遍（设环境变量跑 CLI、真实传参路径），**不只信 `npm test` 全绿**。实测教训：第 2 轮 env-only 回归，测试 124/124 全绿——用例只用绝对路径，没覆盖「只设环境变量」这个真实用法。

### 工具跑起来没输出时：先查状态，别干等、别打断

OCR 正式跑之前会先出 `--preview` 清单，之后可能**长时间没有任何输出**。这时候**不要干等也不要打断**——去查它自己的状态：

```powershell
ocr session list    # 看最近几次 session 的 STATUS 与评论数
```

| STATUS | 含义 | 该做什么 |
|---|---|---|
| `complete` | 跑完了 | 直接取结果 |
| `aborted` | **两种，别混**：① **状态延迟**（常见）——session 实际已跑完，但 STATUS 还没落盘，稍后自动变 `complete`；② **真被打断**——StopCommand / 进程被杀，评论可能已落盘 | **别急着重跑**。先看**实际进程输出的末尾**有没有 `Review complete: N finding(s)`：有 = 跑完了（状态延迟），直接取评论；没有 = 真被打断，`ocr session comments <id>` 取落盘的评论再决定 |
| 没这一行 | **两种可能，别混**：① 这次还没落进列表（刚启动，历史 session 是跑完/中断才写进去的）→ 等；② 你看的是列表的**前几行**而这次在更后面 → 往下翻 |  |

**实测补充（2026-10-08 第 6 轮 + 2026-10-09 修正）**：跑完时终端输出里**没有** `STATUS` 那一行（`ocr session list` 里才有），而且第 5 轮那次输出很长、**尾部被截断**——所以「终端输出里找不到 STATUS」**不等于**还在跑。

⚠️ **2026-10-09 修正「唯一可靠判据」**：`ocr session list` 的 STATUS **本身会延迟**——实测 `1ce83f12` 已跑完（job 输出 `Review complete: 0 finding(s)`、退出码 0），但 list 先显示 `aborted`，约 10 分钟后才变 `complete`。因此：
- **别把 `aborted` 当成「被打断」的充分判据**——它可能是状态延迟（本次即如此，差点被误判成需要重跑）；
- 可靠判据 = **实际进程输出的末尾**（`Review complete: N finding(s)` = 真跑完）+ **评论是否落盘**（`comments` 列有值 = 有产出，取出来即可）；
- `session list` 只用来**对比跑前后有没有新增 session**（确认这次真的启动了），**STATUS 列别当准**。

**别打断**：`StopCommand` 会让这次落成 `aborted`，评论虽已落盘但**流程算中断**——第 5 轮的实测教训正是「干等 6 分钟零输出，凭 CPU 0.03 秒推断它在等 LLM、可能配置有问题」，**两个都是猜的**；查一下就知道 STATUS 是 `aborted`（被我打断的），**配置本来没问题**。

判据：**「进程在但没输出」推不出任何结论，要看工具自己怎么说（进程输出的 Review complete 行 / 评论是否落盘），`session list` 的 STATUS 列会延迟，别当准。**

## 1.5 什么时候才问用户

> **通用纪律在全局规则 `how-i-must-reason.md` §5**（禁把选择权推回用户；例外只有三类：只能靠偏好定的取舍 / 不可逆操作 / 越出授权范围）。本节只写**本审查流程特有的**那些。

**默认自己定。问用户是例外，不是常态。**

**属于「例外」的，本流程里只有这一类**：**越出审查范围** —— 审 A 技能时发现 B 技能有同样问题 → 要不要顺手改 B。
（另两类属全局规则：不可逆操作按 `no-git-write`；只能靠偏好定的取舍。）

**不属于例外的（这些是 bug，别再犯）**：

- **顺序问题** —— skill 已经把段序排好了，照做
- **「怎么跑通某个工具」** —— 自己查配置、查历史记录（例：`ocr review --commit <tag>` 收不收 tag，本仓 0 个 tag 测不了，那就写「未验证 + 给替代路径」，**不是「需要你定」**）
- **「某段代码该怎么改」** —— 取证之后直接改

**自查一句话**：*「这个问题我能自己查到吗？」* —— 能，就去查，别问。

⚠️ **2026-10-08 收敛**：本节曾复述全局规则的三阶段表 + 三类例外。**两处各自演化**，而我读的是本节那份 —— 判据不一致时用了错的。**权威在全局规则**，本节只留本流程特有的一类。

## 1.6 本流程特有的取证判据

> **通用的「判据必须能被查出来」在全局规则 `how-i-must-reason.md` §1/§2/§3**（判据三问、来源三档、禁「成本高 / 感觉」当判据）。本节只留**审查流程特有**的。

**每条判断在被当成依据之前，先问一句：用什么命令能验它？**

| 说出口的话 | 是不是判据 | 为什么 |
|---|---|---|
| 「深度 3 够用」 | ❌ **不是** | 说不出拿什么命令验「够用」。真判据是「仓库里最深有几层 md / 超过 3 层有几个」——那是要去数的（取数：`Get-ChildItem -Recurse -Filter *.md` 按路径层级统计；2026-10-08 实测 retro-skills 本仓分布 `{0:3, 1:20, 2:40}`，最深恰好 2、无文件卡在第 3 层。所以这句话不查就等于在赌「再深一层也不放文件」） |
| 「CRLF 下会匹配不到」 | ✅ 是 | 可以把模板读成 CRLF 再跑一遍，看它坏不坏 |
| 「`--to` 没登记在 `CLI_FLAGS`」 | ✅ 是 | 跑那条守卫（删掉它看会不会红），或直接读 `CLI_FLAGS` 那一段的字面量 |
| 「这写法有风险」 | ❌ **不是** | 「风险」多大？说不出来就是感觉 |

**危害**：没有判据的话**说出来特别像结论**，而且往往正好是你想听的那句（「够用」「应该没问题」「影响不大」）。它比明说「我不知道」危险得多。

**这是不改判据的另一种形式**——「我不知道所以问你」至少诚实；**「我猜了个数所以不问你」是把猜测冒充结论**。两者都违反「先查」。

**配套**：验证完还要能说出「**它因为什么红**」。跑一遍 ≠ 测到东西——
本仓库实测（2026-10-08）：一条 CRLF 守卫报红，我当它有效；实际它红的原因是**反例构造失败**，不是它真的测到了 CRLF。**红 ≠ 有效。**

## 2 取数方式（工作区 / N 次 / 单个 commit）

**范围由用户给的那句话决定**：给了数字 N 就是最近 N 次 commit，给了 hash / tag 就是那一个，都没给就是工作区未提交。

| 用户给的 | 范围 | 代码侧命令 | 文档侧取数 |
|---|---|---|---|
| 不给 | 工作区未提交 | `ocr review` | `git status --porcelain` |
| 1 | 最近 1 次 commit | `ocr review --commit HEAD` | `git show --numstat HEAD` |
| N | 最近 N 次 commit | `ocr review --from HEAD~N --to HEAD` | `git diff --numstat HEAD~N HEAD` |
| 一个 hash | **那一个** commit（**不是**最近 N 次） | `ocr review --commit <hash>`（实测 `--preview` 正常出清单；官方帮助里 `--from/--to` 是给两条 ref 的，单 commit 有专门的 `--commit`） | `git show --numstat <hash>` |
| 一个 tag | 同上，**⚠️ 未实测**（本仓 0 个 tag） | 先 `git rev-parse <tag>^{commit}` 换 hash，再用上一行 | 同上 |

**为什么 hash 单列一行**：它和「N 次」不是一回事——`--from HEAD~3 --to HEAD` 是**两个端点之间**的 diff（一个文件中间改过多轮就只剩净额），`--commit <hash>` 是**那一次**。混用会审出一个「从没存在过的文件版本组合」（2026-10-08 段二对账发现：SKILL.md 给了 hash 这一档，但本表没有对应行）。

**根 commit 没有父，写 `hash^` 会 fatal**（实测 2026-10-08：本仓根 commit `fb439a09`，`git show --numstat fb439a09^` 报 `unknown revision`）。文档侧一律写 `git show --numstat <hash>`，**不要**自作聪明加 `^`。

### commit 范围内读文件的关键判据

**agent 直接读磁盘，读到的是「最新内容」，不是「那个 commit 时的内容」。**

判据：**这个文件在那次 commit 之后是否还有新改动？**

```powershell
# 1) 那次范围改了哪些文件 —— 取名单 A
#    N 次：git diff --name-only HEAD~N HEAD
#    单个：git show --name-only --format= <hash>
git diff --name-only HEAD~N HEAD

# 2) 这些文件此后是否又被动过 —— 对名单 A 里的每个路径查
git diff --name-only HEAD~N HEAD -- <路径>
```

第 2 条的两个端点别搞混：`git diff A B` 比的是 A 与 B 两个快照。**左边 `HEAD~N` = 那 N 次 commit 结束的那一刻，右边 `HEAD` = 现在**。若某路径在第 2 条里有输出，说明它此后又被改过。

（实测 2026-10-08：N=1 时第 1 条列出 9 个文件，第 2 条对其中 7 个有输出——即工作区里还在改。）

**单 commit 范围（`--commit <hash>`）同理，把两端换掉**：

```powershell
git show --name-only --format= <hash>                        # 名单 A = 那一次改的文件
git diff --name-only <hash> HEAD -- <路径># 该文件此后有没有再被改
git show <hash>:<路径>                                         # 那时刻的全文
```

**「此后」指 `<hash>` 到 HEAD 之间**，不是「那次范围之外」——单 commit 范围下没有 `HEAD~N` 那个左端点，别照抄上面的写法。

- **没再被改** → 直接 `Read` 磁盘，内容就是对的。
- **还有新改动** → **必须**取 commit 时刻的版本：

```powershell
git show HEAD~N:<路径>                # 该文件在该 commit 时刻的全文
git diff HEAD~N HEAD -- <路径>        # 它后来又改了什么
```

漏了这一步就会审错对象：**审出来的是「最新文件配旧 diff」，结论会指向一个当时并不存在的问题。**

## 3 硬约束（不许商量）

| 约束 | 为什么 |
|---|---|
| **每轮收尾 = commit 到 review 分支**（message 带 【review】标记；**只 add 本次审查清单内的文件，禁止 `git add -A`**） | 锁基线：OCR workspace 审的是「HEAD vs 工作区」，只有 commit 了 HEAD 才前进，下一轮才只审增量。这是本技能能收敛的前提。git 写权限例外见全局规则 `no-git-write` 段 2 |
| **不 push、不 merge、不 reset** | review 分支不推送远程；合回母分支用 rebase，且必须用户确认后才做（见 §1 收尾） |
| **不许手动判断「应该没问题了」提前停** | 停机判据在 §1：**修复轮 + 复查轮都干净才停**，轮内自审（手法 3 重跑 / 同族扫描）不算复查，不许自行放宽 |
| **不许跳段** | 指定哪段就跑哪段，`code` 模式不许顺手改文档 |
| **不碰审查范围外的文件** | 修bug 时顺手重构会污染 diff |
| **循环中不许停下来问用户** | 判据在 §1.5。顺序是「先查 → 再定 → 最后才问」，跳到第三步就是甩锅 |
| **不许问「要不要提交」** | commit 是流程必需（每轮锁基线），没有「要不要」。**唯一允许问「是否提交/合并」的场景 = 收尾合并回母分支**（§1 收尾）。实测 2026-10-08：review 进行到第 4 轮问「继续还是先提交」——用户从头到尾说过不提交。更糟的是我还在问句里带了「改动已 1353 行，风险在上升」这种**暗示该提交的理由**——那不是提供信息，是拿信息推一个我不该提的建议 |
| **不许拿「我不确定」当停机理由** | 不确定时该**去查**（`ocr session list` 看状态、读源码确认现状），不是把选择权推给用户。「不确定」和「该问你」是两件事 |

## 4 输出格式

**报告只用一张表（问题明细，一行一个问题，级别带处置后缀）；表外全是直白短句。不跑 / 空转的段明确写出，不许把空转当已跑。**

> ⚠️ **「三段分开报」≠ 三段各写一段文字**（2026-10-09 实测踩坑，见 `<KB>/skills/review-loop/ledger.md` L-001）：all 模式命令里「前两段的问题不要和第三段混在一张表里」只约束**段三单列**（放在模板的「段三」行），**不是取消问题明细表**。无论跑几段，都先出一张逐条的问题明细表（# / 级别 / 问题 / 处置），段三的漂移在表内标「（段三）」或表后单独一行，不写成并排的三段叙述。

**每轮末尾（一张表 + 必写结论行；最后一轮结论写「停」不写「进下一轮」）**：

```
【第 N 轮】

| # | 级别 | 问题 | 处置 |
|---|------|------|------|
| 1 | P0 | <一句话问题> | 已修 |
| 2 | P1 | <一句话问题> | 已修 |
| 3 | P2（采纳） | <一句话问题> | 已修 |
| 4 | P2（关闭） | <一句话问题> | 不修，理由：<判据> |
| 5 | P2（候选） | <一句话问题> | 待信号：<触发信号> |

本轮：发现 N 条（P0 a / P1 b / P2 c）→ 已修 d、关闭 e、候选 f。OCR session <id>（跑了 OCR 才写）。段一/段二/段三 <跑了 / 不跑（模式原因）/ 空转（原因）>。进下一轮（增量：…）。
```

**级别写法**：`P0` / `P1` / `P2（采纳）` / `P2（关闭）` / `P2（候选）` —— 处置含义直接挂在级别上（P2 三态：采纳=必修 / 关闭=拒绝不修 / 候选=触发信号再评估）。P0/P1 只有「已修」一档，没有采纳/关闭/候选那套。

**全部结束后（只写文字汇总，不再出「共 N 轮 + 总表」）**：

```
复查后 P0 = 0，P1 = 0，P2（采纳）= 0 → 核销干净 ✅
（未归零：剩余 N 条，卡在 …）
验证：<关键取数命令> → <结果>（数字实测依据）。
段三：<跑了 X 断言 → Z 漂移 → 修 Z 条 ／ 空转：本次无代码改动，文档断言无对应物可验，不算已跑>。
未验证 / 无法验证：<逐条列>。
```

数字必须是**实测值**，不是记忆值，用了哪些命令拿到的要写出来（通用口径见全局规则 `how-i-must-reason` §6）。**本流程特有的两条**：
- **OCR session id 必须写出来** —— 它是唯一能回溯「当时报了哪些」的凭据；
- **未验证 / 无法验证的项要单独列** —— 没测过的东西下一轮会被当成「已验证」（例：`ocr review --commit <tag>`，本仓 0 个 tag测不了）。
