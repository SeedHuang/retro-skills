# 三路径流程 + 草稿箱交互

> 口径来源：spec §3.1（位置与脚本）/ §3.2（命名约定）/ §3.3（入口交互）/ §3.4（生命周期与删除规则）/ §4（新建路径流程）/ §5（优化路径流程）/ §6（拆分路径流程）。逐字落地，遇歧义以 spec 为准。

## 一、草稿箱交互（唯一识别机制 = 用户选择）

**入口不自动认领任何草稿**——识别权全给用户。时间戳只用于排序展示，绝不用于自动选择（"最新的"不自动用；出现更新的草稿只是排前面，用不用由用户决定）。

```
入口处理规则 X：
  drafts ls X：
  ├─ 无草稿 → 直接新建
  └─ 有（N 个，全部列出，带创建时间）→ 问「是否继续使用？」
       ├─ 选了一个 → 续用（保留它）；若 N>1 再问「删除其余的？」
       │    ├─ 是 → 删除该规则名下【除选中的之外】的所有草稿（`drafts rm --rule X --keep <选中>`）
       │    └─ 否 → 都留着
       └─ 不用 / 新建 → 删除该规则名下所有草稿，重新建
```

## 二、生命周期与删除规则

| 时机 | 动作 |
|---|---|
| 入口启动 | `drafts ensure`（幂等建目录） |
| 发现旧草稿 | **永不静默删**：列出（带时间）→ 问继续/不用（见 §一） |
| 采纳落地 | 删除该规则名下所有草稿——**采纳 = 已授权整组落地（写文件 + aas sync + 批量删草稿），不再单独确认删除**；仅当草稿箱里**存在其它规则的草稿**时，提示一次「只删本规则名下草稿，别的规则草稿不动」防误删。**不主动追问采纳——报告末尾给出「【采纳】/【不采纳】」两个文字选项，等用户回复；用户不回复就停住，不弹窗、不反复问** |
| 多草稿收敛 | 选续用 → 答"删其余"= 删除除选中外的全部；答"否"= 保留 |

**硬约束**：

- 删除永不静默（有草稿必问；采纳即授权删本规则名下草稿，不单独确认——见「采纳落地」行）。
- 无哈希/归属机制（内容一动哈希就变，无法当身份确认用——已否决）。
- 采纳删除按规则名 scope（只删该 rule 名下草稿，跨 rule 不动）。

## 三、草稿箱位置、命名与 drafts 命令

### 位置与脚本

- **位置**：`<用户目录>/.retro-skills/rule-drafts/`（`os.homedir()` 解析，跨平台；Windows = `C:\Users\<名>\.retro-skills\rule-drafts\`）。
- **脚本**：`scripts/drafts.mjs`，四个子命令：
  - `drafts ensure` —— **幂等**：目录存在则跳过，不存在则新建（含父级 `.retro-skills`）。入口每次运行第一步必跑。
  - `drafts ls [规则名]` —— 列出草稿；可按规则名过滤；**按文件名时间戳倒序**；每行显示 `<名字>（创建 <时间>）`。
  - `drafts rm <草稿>` —— 删除指定草稿。
  - `drafts rm --rule <规则名> [--keep <草稿>]` —— 按规则删除：不带 `--keep` = 删该规则名下所有草稿（采纳清箱、答"不用"全删）；带 `--keep <草稿>` = 保留指定草稿、删其余（"删其余"场景用）。

### 命名约定

```
<规则名>--<YYYYMMDD-HHMMSS>.md
```

- **优化路径**：规则名 = 现有文件名（如 `global-ask-before-acting--20261009-1830.md`）。
- **新建路径**：规则名未定 → 用主题 slug 占位（落地时才定正式文件名）。
- **拆分路径**：拆出部分 = 新规则名（用主题 slug 占位）；旧 rule 无新草稿（直接在源上改被拆部分）。
- 一规则可多草稿（时间戳区分、可排序）；`--` 分隔安全；符合 kebab-case（无中文/空格）。

## 四、新建路径流程（8 步）

```
1. 收需求        用户先写出他想表达的 rule 内容（需求原文）
2. 澄清四要素     AI 明确范围/条件/动作极性/宾语四要素的内容；只问真正缺的、一次一个、
                  给 2-3 推荐选项 + 自定义出口（不逐字段盘问）
3. 草稿箱交互     drafts ensure；草稿名 = 主题 slug + 时间戳；有同主题旧草稿 → 按 §一交互（继续=选一个 / 删掉重生成 / 取消）
4. 起草 + 自查    rule-writer 按已澄清的四要素落成规则文档 + 判定词归一 + 标题三句 + 冗余度自查（产出草稿，不跑 inspector）
5. 评分           use-rule-skills 调 inspector 对草稿评分
6. 异常循环       有 findings → 逐项：现状 + 推荐修改方案 / 用户自定义 → 改 → 再评
                  → 核销干净（0 findings）或用户明确接受残留
7. 报告           入口报告（意图/评分明细/改动清单/落地结论；新建无"改前"，对比段写"不适用"）
8. 落地           确认最终 rule 名 → 写 rules/ + aas sync → 删该 rule 名下所有草稿（见 §二：采纳即授权删本 rule 名下草稿，不单独确认）；按报告 §五的「【采纳】/【不采纳】」两个文字选项走——用户回「采纳」才落地；回「不采纳」保留草稿继续
```

## 五、优化路径流程（6 步）

```
1. 先诊断         use-rule-skills 调 inspector 对现有规则评分 → 处方（findings）
2. 草稿箱交互     drafts ls <rule>：
                   无 → 直接起草
                   有（列带时间）→ 问「继续 / 删掉重生成 / 取消」（§一）
3. 起草修订版     rule-writer：按处方 + 四要素 + 归一 + 标题三句 + 冗余度（产出草稿）
4. 评分 + 异常循环  同新建（改 → 再评 → 核销干净或用户接受残留）
5. 报告           入口报告：评分明细 + 【before/after 对比表】+ 改动清单 + 落地结论
6. 落地           写 rules/ + aas sync → 删该 rule 名下所有草稿（见 §二：采纳即授权删本 rule 名下草稿，不单独确认）；按报告 §五的「【采纳】/【不采纳】」两个文字选项走——用户回「采纳」才落地；回「不采纳」保留草稿继续
```

## 六、拆分路径流程（从既有 rule 拆出独立部分）

```
1. 先诊断         use-rule-skills 调 inspector 对源规则评分 → 处方（findings，含「该拆」提示）
2. 澄清四要素     明确拆出部分的范围/条件/动作极性/宾语四要素——拆出部分的边界是什么（哪些内容独立成新 rule）
3. 草稿箱交互     drafts ls <新规则名>：
                   无 → 直接起草
                   有（列带时间）→ 问「继续 / 删掉重生成 / 取消」（§一）
4. 起草           rule-writer **按新建路径起草拆出部分**（从需求四要素重新构思；受「禁止搬运」硬闸门约束，
                   旧 rule 原文只当参考来源，不原样复用）——产出新规则草稿
5. 评分 + 异常循环  同新建（改 → 再评 → 核销干净或用户接受残留）
6. 报告           入口报告：评分明细 + 改动清单（含旧 rule 删了哪段）+ 落地结论；
                   按报告 §三按「拆分」形态开 diff（源 vs 草稿）——diff 窗口并排已含草稿全文，不用再单独开草稿
7. 落地           确认最终 rule 名 → 写 rules/<新规则名>.md + **改 rules/<旧规则名>.md（删被拆部分）**
                   + aas sync → 删该新 rule 名下所有草稿（见 §二：采纳即授权删本 rule 名下草稿，不单独确认）；
                   按报告 §五的「【采纳】/【不采纳】」两个文字选项走——用户回「采纳」才落地；回「不采纳」保留草稿继续
```
