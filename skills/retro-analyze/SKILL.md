# 复盘分析（retro-analyze）

## 前置

输入是一份**事实包**路径。**没有事实包就拒绝**并建议先跑 `retro-collect`——凭印象分析会污染 KB。
事实包路径不存在 → 拒绝，不做降级猜测。
**KB 未初始化时**（`lessons resolve` 报「未找到错题集指针」）→ 拒绝写入，并 **REQUIRED SUB-SKILL:** 用 `managing-lessons-store` 完成 bootstrap（其第一步须由用户指定 KB 位置，**禁止默认落 C 盘**）。

## 唯一产出（两件）

1. 复盘文件：同 session 目录内的 `retro.md`（= `<KB>/projects/<项目标识>/<日期>-<sid>-<摘要>/retro.md`）
2. KB 条目：向该项目的 `ledger.md` **追加行**（状态**先写 `open`**，落置成功后由 `retro-institutionalize` 改为 `landed`）

写入顺序固定为「**先条目 → 后落地 → 再改状态**」（防止中断后重跑重复落规则）。

## 写库前置检查（必做）

写 KB 前先查 `<KB>/.migrating`：**存在 → 拒绝写入**，报告「错题集正在迁移中，请等迁移结束后重试」；不存在 → 继续。

## 说人话（硬规则）

复盘文件是**写给用户看的**，正文必须遵守用户全局规则「大白话、讲机理、落到例子」：

- 内部标记（`P1`、`§3-1`、`Step 3` 这类）**首次出现必须先用一句人话说明它指什么**；
- 表格保留（记账用），但**每个问题下面必须跟一段人话说明**：这事怎么发生的、为什么算问题，用聊天口吻写，不用表格话。

## 复盘模板 + 账本条目格式（逐字使用 → 见 `assets/retro-template.md`）

复盘四节结构（`1 问题清单` / `2 归置结果` / `3 附录：规则裁决` / `4 未决与待验证`）、账本条目行格式、列口径与去重转义规则**以 `assets/retro-template.md` 为准**，本文不复制——**该文件是权威定义方**。

**每个问题在表格下方跟一段人话说明**（见「说人话」），说明里补 ⚠️ 可选字段：**可复现性**（稳定/偶发/不可，未知可空）。

## 硬约束（三条）

1. **第 2 列「事实包条号」必填**。写不出条号 → 这不是基于事实的问题，删掉它，或先回 `retro-collect` 补事实。
2. **「优先级」必须带判据**，不得只给「P1」。判据口径（并入该单元格）：**直接后果 / 时间代价 / token 代价（注明估算）/ 触发频率**。示例：
   - `P1 — 后果不可逆 + 触发频率高（本次 3 次）`
   - `P2 — 一次返工，约 3 轮讨论 + 2 万 token（估算）`
3. **问题必答清单，缺一不合格**：① 谁受影响、什么场景触发（人话一句）② 后果 + 量化 ③ 根因（**标注：事实 or 推断**）④ 怎么修（可执行一句）⑤ 怎么验证修好了。

## 口径表

| 栏 | 含义 | 取值 |
|---|---|---|
| **维度** | 影响的改进面 | **健壮度 / 产品体验 / 协作体验 / 性能 / 安全**（五选一） |
| **影响范围** | 后果波及多广 | 单点 / 本项目 / 跨项目 / 全局 |
| **可逆性** | 能否回退 | 可逆 / 不可逆 |
| **隐蔽度** | 失败是否可见 | 显式 / 静默（**静默更危险**——会潜伏） |
| 是否普遍 | **已删除** | 由「影响范围」取代 |
| 方案 | 修复动作 | 一句可执行的话；不写「加强 / 优化」这类不可执行词 |
| 根因 | 为什么会这样 | 区别于现象：现象是「重复落规则」，根因是「写规则与写记录的顺序未定义」 |

**量化字段的档位**：影响范围 / 可逆性 / 隐蔽度 **必答**；可复现性（稳定/偶发/不可）**选答**——需多次观察，未知就留空。
**事实量 vs 判断量分开标**：事实量（复发次数 / 耗时 / token / 讨论轮数）= 可测；判断量（严重度 / 影响范围 / 可逆性 / 隐蔽度）= 判断。

## 结束时的固定动作

产出复盘文件与条目后，输出一行「本次复盘完成。教训已记入账本（状态 open）。落地由你在 lessons 发起。」

## 常见错误

| 错误 | 纠正 |
|---|---|
| 问题没有条号 | 补号或删掉该问题 |
| 优先级只有 P1 没有判据 | 必写 后果 / 时间 / token / 频率 中至少一项 |
| 维度写成「用户体验」或旧值 | 用新五维：健壮度 / 产品体验 / 协作体验 / 性能 / 安全 |
| 影响范围 / 可逆性 / 隐蔽度 空着 | 必答；判断不出就标「未知」，但不得留空 |
| 根因没标「事实 / 推断」 | 归因是我的判断，必须显式标注。**标注口径**（哪句话算「查过的」、哪句算「推测」、两者必须给什么）见全局规则 `how-i-must-reason` §2——**本文件只要求产物里有这两列，不重定义口径** |
| 复盘中复述了事实包全文 | 只引条号——复盘要做薄，防第二份真相 |
| 条目状态直接写 landed | 先 open，落地成功后才改 |
| 同一条教训重复追加条目 | 先查既有条目，有则复用 ID |
| 迁移进行中仍写库 | 先查 `<KB>/.migrating`，存在即拒绝 |
| 自创一套结构、不用上面的模板 | 模板必须逐字使用 |
| **写完后追问「要不要落地」** | **禁止**——落地由用户在 lessons 发起，本技能不得追问 |
| 只有表格、没有「人话说明」 | 每个问题下必须跟一段人话说明 |
