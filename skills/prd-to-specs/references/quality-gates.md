# 评判标准（拆分质量门）

## 拆分六规则

| # | 规则 | 判定方法 | 违反的典型症状 |
|---|---|---|---|
| 1 | **垂直切片** | 每个 spec 端到端可验收：做完后用户能感知一个完整能力 | "先做完所有 DB 层再做 UI"式水平分层；spec 做完没有任何可演示结果 |
| 2 | **依赖成 DAG** | 画出依赖图；存在并行独立集；无环 | 串行锁死全部顺序；A 依赖 B 的文档而非 B 的产物 |
| 3 | **变更半径不重叠** | 两个 spec 的 plan 不会改同一批文件；对齐真实模块边界 | 两个 spec 都要动同一个文件；并行开发必然冲突 |
| 4 | **风险前置** | 最不确定的技术点（新 ABI、外部 API 行为、平台机制）放最早的 spec 或独立 spike | 风险藏在最后一个 milestone，爆雷时返工全部 |
| 5 | **规模上限** | 单个 spec 展开成 plan 后约 ≤8 个 Task（1-2 天量级） | spec 大到 plan 要写 15+ task；或小到只有一个 task |
| 6 | **验收锚定** | 每个 spec 的验收标准能回溯到 PRD 的里程碑/验收条目，写成"验收锚点：M1 前半（…）" | spec 做完不知道算没算完成；验收锚点找不到 PRD 出处 |

## shared 判定（只判定，不建文件）

- **标记为 shared 候选**：同一内容预计被 ≥2 个 spec 的 plan 实际引用（数据模型、测试策略、日志规范、前端设计语言是典型）→ 在路线图中标注候选名 + PRD 出处章节
- **文件创建时机**：第一个引用它的 spec 开工时才创建（内容用引用指向 PRD，不抄写），或用户明确要求时提前
- **不提**：引用不明确时先留在第一个用到的 spec 里，等第二个引用真实出现再标记（bfm 原则："拆分依据是哪些章节被哪个 plan 实际引用"）
- **禁止**：为"看起来通用"而提前抽取——会造成只有一份引用的假 shared；更禁止把 PRD 已定稿内容复制成 shared 文件（双份真相）

## JIT 门（防规格返工，硬性）

路线图阶段的产出粒度：

| 允许 | 禁止 |
|---|---|
| spec 标题、边界一句话 | 字段级设计、表结构 |
| 大纲要点（5-6 条动词短语） | SQL、接口签名、函数签名 |
| 依赖关系 | Task 级步骤拆解 |
| 验收锚点 | "以后再说"式含糊边界 |

原理：拆分产物里混着两类变更频率不同的信息——**切片结构**（会随认知加深而变，写在便宜的载体上）与**规格细节**（应推迟到信息最全、最不可能错的时刻）。过早细化 = 瀑布 = 规格不停改。plan 阶段同理："后续里程碑不展开到步骤级——现在写就是猜"。

## 自检清单（产出路线图后逐条过，结果向用户汇报）

- [ ] 每个 spec 能独立运行、独立验收吗？（不依赖"另一个 spec 先写完文档"）
- [ ] 没有主 spec？（全部平等，索引用"你要做的事 → 读这些"组织）
- [ ] 每个验收锚点能回溯到 PRD 具体条目吗？
- [ ] 声称可并行的 spec 之间真的零共享文件吗？
- [ ] 大纲有没有越界写出字段级细节？（JIT 门）
- [ ] 每个决定/约束带"为什么"了吗？
- [ ] 命名符合 `shared-*` / `m{N}[a-z]*-<slug>` 吗？追溯标记加了吗？
- [ ] 待定决策标为开放问题了吗（没有假装已定）？
- [ ] 有没有把 PRD 已定稿内容复制进新文件？（双份真相 = 打回，spec 只许引用"见 PRD §X"）
- [ ] 是否在用户确认路线图之前生成了任何 spec/shared/索引文件？（默认只改 PRD）
- [ ] 建议用户对每个 spec 走 multi-lens-review 了吗？

## 与其他技能的衔接

- spec 文档定稿后 → `multi-lens-review` 评审（六手法 + 角色面板）
- 评审收敛后 → `writing-plans` 产出实施计划（plan 句式见 conventions.md §4）
- 计划执行 → `subagent-driven-development`（推荐）或 `executing-plans`
