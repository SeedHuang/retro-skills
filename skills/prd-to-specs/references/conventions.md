# 句式与结构规范（提取自 bilibili_favorite_manager 实践）

本文件是拆分产出的**唯一**写作标准。四个来源：`docs/prds/规则与标签.md`（PRD）、`docs/superpowers/specs/README.md`（索引）、`specs/m4c-folder-rules.md`（milestone spec 最佳样本）、`plans/2026-09-14-M1-handshake.md`（plan 最佳样本）。

---

## 1. 文档族与命名

| 文档 | 路径 | 命名 |
|---|---|---|
| PRD | `docs/prds/` | `<主题>.md`（中文主题名可用） |
| Spec 索引 | `docs/superpowers/specs/README.md` | 固定名 |
| Spec | `docs/superpowers/specs/` | `shared-<主题>.md` 或 `m{N}[a-z]*-<slug>.md` |
| 实施计划 | `docs/superpowers/plans/` | `YYYY-MM-DD-<slug>.md` |

- `shared-*` = 跨 spec 通用规则（数据模型、测试策略、日志、前端语言）
- `m{N}-*` / `m{N}{字母}-*` = milestone 专属（m4c 中的 c 表示同一 milestone 内的第 3 份 spec）
- **不存在主 spec**，每个文件地位平等；原 PRD 的章节号可以延续到 spec 内（如 `## 9C.` / `## 12.`），作为跨文件引用锚点
- spec 首行放追溯标记：`> split from <PRD 路径> (<日期>)`

## 2. PRD 句式

按顺序：

1. **标题 + 定稿注**：日期、一句话定位；声明"每一步都写了两层：它是干什么的（大白话）+ 怎么做的（技术）"
2. **`## 一句话版本`**：用大白话把完整闭环讲一遍，用户视角，无术语
3. **`## 背景`**：为什么现在做；核心交付物加粗
4. **`## 已确认决策`**：`| 问题 | 决策 |` 表，一行一条，来自与用户的拍板记录
5. **`## 名词小词典`**：`| 名词 | 大白话 |`，面向未来的自己/非专业读者；关键概念给小例子
6. **机制章节统一双层句式**：
   ```
   **它是干什么的**：<用户视角一句话>
   **怎么做的**：<技术方案>
   ```
7. **流程**：mermaid 时序图（带阶段 Note）+ 每阶段 `| 步骤 | 干什么 | 为什么 |` 表
8. **`## 明确不做（YAGNI 记录）`**：每条带理由，防止未来重复讨论
9. 量化表述：能定数字的定数字（如"预计夹子数区间"">2h 或 >500MB"），拒绝"快/好/直观"

## 3. Spec 句式

按顺序（节可按需增减，编号延续原文档）：

1. **追溯标记**（首行）
2. **`### X.0 为什么`**：从真实事故/用户洞察出发，引用原话并标注日期。没有"为什么"的 spec 不许通过
3. **`### X.1 核心决定(不可违反)`**：`| # | 决定 | 为什么 |`，编号 R1、R2…；每条为什么必须具体到"不这么做会发生什么"（bfm 样本："不加正则……表达力换'你一眼看懂它在干什么'"）
4. **数据模型**：SQL 直接写，注释里说明**设计取舍**（为什么建新表而不 ALTER、为什么用 CASCADE）
5. **运行方式 / 机制**：编号流程（①②③），每步标注成本属性（0 token / 实跑 / 一次调用）
6. **界面（如有）**：ASCII 线框图 + "界面上的 N 条规矩"编号列表
7. **硬约束**：编号列表，与核心决定表交叉引用
8. **`### X.7 测试`**：`| 测什么 | 为什么 |` 表 + 两行固定收尾：
   ```
   **只手动验证**：<列出的真实环境项>
   **不测**：<明确排除项及理由，如"Fastify 路由(太薄)">
   ```
9. **`### X.8 不在这一轮`**：YAGNI，每条带理由
10. **`### X.8b 将来才会撞上的一件事`**：可预见的未来决策冲突，点名即可、不定案（"本轮只在这里点名，免得靠撞上才发现"）
11. **`### X.9 与既有 spec 的关系`**：取代 / 保留清单，精确到节号

## 4. Plan 句式

1. **头部**：`# <名称> — 实施计划` + agentic workers 说明 + 四行元数据：
   ```
   **Goal:** <一句话，讲清这个 plan 回答什么问题>
   **Architecture:** <架构边界，哪个目录"可脱离一切外部依赖单测"这类关键性质>
   **Tech Stack:** <具体版本号>
   **Spec:** <spec 相对路径>
   ```
2. **`## Global Constraints`**：版本红线（"不要用 typescript 7"式具体警告）、架构红线（"该目录不许 import 任何 db/"式依赖禁令）、注释与 commit 语言
3. **`## 已实测确认的前提(<日期>)`**：黄金值表格，"直接写进测试当黄金值，不要改动"；实测结论决定设计时要写明
4. **`## File Structure`**：`| 文件 | 职责 |`（职责列标注"纯函数,无 IO"这类性质）+ 一句"依赖方向：a → b → c。没有任何反向依赖"
5. **`### Task N: <标题>`**：
   ```
   **Files:** Create: … / Test: …
   **Interfaces:** Consumes: … / Produces: <函数签名级>
   - [ ] Step 1: 写失败的测试 → Step 2: 跑测试确认失败 → Step 3: 写实现
     → Step 4: 跑测试确认通过 → Step 5: Commit
   ```
   代码块必须完整可运行（禁省略号）；每 Task 收尾 commit（中文 message）
6. **`## Self-Review`**：三件事——Spec 覆盖表（spec 要求 ↔ Task 映射）、"未覆盖且刻意如此"（说明归到哪个里程碑）、占位符扫描（声明无 TBD/TODO）+ 类型一致性（跨 Task 的接口名核对）
7. **`## 后续里程碑`**：表格列出，但**不展开到步骤级**——原文："现在不展开到步骤级——因为实测结果会改变它们的字段映射细节，现在写就是猜"（JIT 的原始出处）
8. **`## 执行交接`**：两种方式二选一（subagent 驱动 / 本会话内联 executing-plans）

## 5. 索引 README 句式

```
# Spec 索引

> 拆分自 `<PRD>`(<日期>)。任何 milestone 实施前,按"你要做的事"读以下文件:

## 你要做的事 → 读这些
| 你要做 | 必读 |
|---|---|

## 拆分原则
- shared-* = 跨里程碑通用规则(任何 milestone 都可能参考)
- m{N}-* = 该 milestone 专属内容
- 拆分依据是"哪些章节被哪个 plan 实际引用",不按数字顺序硬切
- 拆分后不存在"主 spec"文件,每个文件地位平等

## 跨文件关键设计决定(<日期> 评审定)
- <在多个文件里交叉引用的决定,逐条列出>

## 注意
- 文件开头的追溯标记可删,不影响内容
```

## 6. 全局句式铁律

- **为什么列是灵魂**：决定表、约束、测试表、"不在这一轮"，缺为什么 = 打回
- **表格优先**：枚举型内容一律表格，散文只用于叙事（为什么/背景）
- **编号可引用**：C1、R1、S1、Task N——跨文件引用必须能定位
- **双层表述**：面向用户的概念给大白话，紧跟技术实现
- **来源与日期**：洞察、实测、拍板都要标（"用户的洞察(2026-09-16)"）
- **禁占位符**：TBD / TODO / 稍后补充 / 待定（待定决策应显式列为开放问题并标注 owner）
