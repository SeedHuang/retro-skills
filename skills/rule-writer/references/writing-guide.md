# rule-writer 写作指引：四要素 + 8 项自查 + 判定词归一 + 标题一致性

> 判据权威在 `rule-inspector/references/criteria.md`（单源）；本文件把判据落成「怎么写/怎么改」的写作指引。
> 适用两种路径：**新建**（从需求起草）与**优化**（拿 inspector 处方改已有规则，改前 vs 改后两版都留）。

## 一、四要素写作指引（起草）

一条规则的核心判据 = 四要素齐全，缺一个就不可执行（对应 criteria §2.4 执行力度 ①②③）：

| 要素 | 要回答的问题 | 合格 | 不合格（记 0 分） |
|---|---|---|---|
| 范围（在哪） | 这条管哪类场景？ | 明确到「具体类型」（如「在 typescript 场景」「写实现计划时」） | 只写「全部情况下」或没写 |
| 条件（何时） | 什么时机套用？ | 有可观测触发信号（「落地后」「开工时」「编辑后」） | 无触发描述 |
| 动作（做/不做） | 极性是什么？ | 有「禁止/不得/不要/必须/应/要」+ 动作 | 无极性词（不知道要做什么） |
| 宾语（对什么） | 动作的对象是什么？ | 可枚举项（如 `git commit`）或具体描述 | 空泛（「合理处理」「适当」类） |

> **核心洞察**：范围大 ≠ 会被掠过。「禁止在 typescript 场景下使用 console.log」范围大但宾语可枚举，直接匹配不掠过；掠过发生在「触发描述需执行者做语义归类」时——「git 写操作」是抽象类别，执行者要把「执行 plan 的 commit」归类进去，归类失败 = 掠过。宾语能枚举就枚举，不能枚举就给出归类判据（例子见第五节）。

## 二、执行力度 8 项自查表（自查）

写完后逐项对照，缺项即缺口（criteria §2.4 执行力度）：

| # | 检查点 | 自查问题 | 类别 |
|---|---|---|---|
| ① | 极性明确 | 正文有「禁止/不得/不要/必须/应/要」+ 动作？ | 语义完整（A） |
| ② | 动作内容具体 | 对象是可枚举项或具体描述，非空泛？ | 语义完整（A） |
| ③ | 适用条件精细 | 明确到「具体类型+条件」，非「全部情况下」？ | 语义完整（A） |
| ④ | 来源覆盖（禁令类） | 声明「不因来源豁免」（含计划/子代理/脚本/工具模板）？ | 抗绕过（B） |
| ⑤ | 冲突裁决（禁令类） | 声明「与具体指令/模板冲突时以本规则为准」？ | 抗绕过（B） |
| ⑥ | 例外从严（禁令类） | 例外条件明确（「只有…才算」），无「一般/通常/可能允许」？ | 抗绕过（B） |
| ⑦ | 触发机制 | 有可观测触发信号/时机（「落地后」「开工时」「编辑后」）？ | 闭环（C） |
| ⑧ | 验证闭环 | 定义了「怎么确认遵守了」（自检命令/检查点/报告要求）？ | 闭环（C） |

> **禁令类判定**（决定 ④⑤⑥ 是否适用）：正文有「禁止/不得/不要/严禁」类极性词 = 禁令类（8 项全查）；纯「必须/应」正向义务或流程类 = 非禁令类（④⑤⑥ 省略，按适用项计 5/5）。
> **记分**：每检查点 1 分（有=1/无=0），不适用项不计入满分。

### 判定词归一（封闭词表，必做）

极性判定词是**封闭词表**，正文极性一律用表内词，**不引入表外词**：

| 极性 | 封闭词表 |
|---|---|
| 禁令（不做） | 禁止 / 不得 / 不要 / 严禁 |
| 义务（做） | 必须 / 应 / 要 / 一律 |

- **写/改规则时**：从表里挑最贴近语义的词；遇到表外词（「不允许」「不可」「切勿」…）→ 读懂语义 → 换成表内词（例：「不擅自开始执行」→「不得擅自开始执行」）。
- **优化已有规则时**：体检发现表外极性词 → 归一成表内词（改前 vs 改后写进报告，按硬闸门 2 等确认）。
- **目的**：极性判定可靠、假阴性在源头减少（不再有「不得↔禁止」等价问题）。

## 三、来源行（模板）

```
> 来源：<类型>（<YYYY-MM-DD>）｜[证据：<一句话，仅实测/踩坑类>]｜落地：<YYYY-MM-DD>
```

- 类型 ∈（用户当场指令 / 评审第 N 轮 / 实测踩坑 / 项目约定）——权限标记，不决定约束力
- 来源行在头部（前 10 行内）、不在文末；≤2 渲染行（>200 字符即视为超 2 行）
- 不含「」引号内的用户原话；不含「合并/补于/补记」等历史叙述词
- 证据字段**仅「实测/踩坑」类写一句话现象**，其余三类不写

## 四、标题一致性收尾三句（定稿前必做，criteria §2.4 标题第 4 项）

对照标题与正文，逐句核对，三句全一致才算收尾：

1. **范围**：标题体现的范围/前提与正文适用范围一致？（内容有明确适用范围时标题必须体现，如「沟通中」——漏前提 = 误匹配风险）
2. **极性**：标题的做/不做方向与正文极性一致？
3. **对象**：标题的动作对象与正文宾语一致？

> 标题是「匹配线索」——AI 扫上下文时靠标题对动作「对号入座」。标题必须是一句话可执行判据（含极性 + 动作 + 对象 + 关键前提），不是主题名（`# 测试踩坑笔记` = AI 要读全文才知道管什么 = 静默掠过风险）。

## 五、例子：no-git-write 的防掠过写法（④⑤⑥ 样板）

写禁令类规则时，参考 `my-rules/rules/no-git-write.md` 的「防掠过」小节——它是执行力度 ④⑤⑥ 的样板：

**④ 来源覆盖（不因来源豁免）**——把「最容易被认为是豁免」的路径逐条列出并明确判为不豁免：

> 本禁令**不因指令来源而豁免**——以下任何一种情况都**不算**「用户明确要求」：
> - 实现计划 / plan 里写了 commit 步骤（哪怕用户说「执行这个计划 / 用 SSD / 子代理执行」）；
> - 子代理 / 子任务执行过程中的 git 写操作；
> - 脚本、自动化、工具模板要求 commit / push；
> - 用户「选择了某个执行方式」≠ 授权了其中的具体 git 写操作。

**⑤ 冲突裁决**——声明冲突时以本规则为准：

> **冲突裁决**：任何指令 / 模板 / 计划与「禁止主动执行 git 写操作」冲突时，以本禁令为准；拿不准就先停下说明，等用户直接确认再动。

**⑥ 例外从严**——例外框成「只有…才算」，不给宽松词留口子：

> 「用户明确要求」唯一成立的情形：用户在当前对话中**直接说出**对具体 git 操作的指令（如「帮我 commit」「执行 git push」「把这段提交了」）。

> **为什么值得这样写**（实测证据）：2026-10-08 implementer 执行 plan 的 commit 步骤绕过当时只写「核心约束」的 no-git-write——它把「用户选 SSD 执行计划」误判成「授权了计划里的 commit」。「防掠过」节就是把这类已实测的掠过路径**显式列出来**，让执行者不用做语义归类就能对号入座。
