# rule-writer 写作指引：四要素 + 执行力度 9 项 + 冗余度 4 项 + 判定词归一 + 标题一致性

> **单源声明**：判据权威在 `rule-inspector` 技能（评分/判据定义，按该技能指引读判据）；本文只写写作落地提示，**不再复制判据表格全文**；若与判据冲突以判据为准。**本文中「criteria / 判据」均指 rule-inspector 技能的判据**。
> 适用两种路径：**新建**（从需求起草）与**优化**（拿 inspector 处方改已有规则，改前 vs 改后两版都留）。

## 一、四要素写作指引（起草）

一条规则的核心判据 = 四要素齐全，缺一个就不可执行（对应 criteria §2.4 执行力度 ①②③）：

| 要素 | 要回答的问题 | 合格 | 不合格（记 0 分） |
|---|---|---|---|
| 范围（在哪） | 这条管哪类场景？ | 明确到「具体类型」（如「在 typescript 场景」「写实现计划时」） | 只写「全部情况下」或没写 |
| 条件（何时） | 什么时机套用？ | 有可观测触发信号（「落地后」「开工时」「编辑后」） | 无触发描述 |
| 动作（做/不做） | 极性是什么？ | 有「禁止/不得/不要/必须/应/要」+ 动作 | 无极性词（不知道要做什么） |
| 宾语（对什么） | 动作的对象是什么？ | 可枚举项（如 `git commit`）或具体描述 | 空泛（「合理处理」「适当」类） |

> **核心洞察**：范围大 ≠ 会被掠过。「禁止在 typescript 场景下使用 console.log」范围大但宾语可枚举，直接匹配不掠过；掠过发生在「触发描述需执行者做语义归类」时——「git 写操作」是抽象类别，执行者要把「执行 plan 的 commit」归类进去，归类失败 = 掠过。宾语能枚举就枚举，不能枚举就给出归类判据。

## 二、执行力度 9 项自查表（自查）

写完后逐项对照，缺项即缺口（criteria §2.4 执行力度）：

| # | 检查点 | 自查问题 | 类别 |
|---|---|---|---|
| ① | 极性明确 | 正文有「禁止/不得/不要/必须/应/要」+ 动作？ | 语义完整（A） |
| ② | 动作内容具体 | 对象是可枚举项或具体描述，非空泛？ | 语义完整（A） |
| ③ | 适用条件精细 | 明确到「具体类型+条件」，非「全部情况下」？ | 语义完整（A） |
| ④ | 来源覆盖（禁令类） | 声明「来源不豁免」（含计划/子代理/脚本/工具模板）？ | 抗绕过（B） |
| ⑤ | 冲突裁决（禁令类） | 声明「与具体指令/模板冲突时以本规则为准」？ | 抗绕过（B） |
| ⑥ | 例外从严（禁令类） | 例外条件明确（「只有…才算」），无「一般/通常/可能允许」？ | 抗绕过（B） |
| ⑦ | 触发机制 | 有可观测触发信号/时机（「落地后」「开工时」「编辑后」）？ | 闭环（C） |
| ⑧ | 验证闭环 | 定义了「怎么确认遵守了」（自检命令/检查点/报告要求）？ | 闭环（C） |
| ⑨ | 判据可观察 | 验证节内 ≥1 行命中标记（跑 `scs check observable --check`，末行 `check-observable ok` 且 exit 0）？ | 闭环（C） |

> **禁令类判定**（决定 ④⑤⑥ 是否适用）：正文有「禁止/不得/不要/严禁」类极性词 = 禁令类（执行力度 9 项全查）；纯「必须/应」正向义务或流程类 = 非禁令类（④⑤⑥ 省略，按适用项计 6/6）。
> **记分**：每检查点 1 分（有=1/无=0），不适用项不计入满分。

### 执行保障自查（认知动作型必做；判据见 criteria §3.3b，不复制全文）

规则含认知动作（画全貌/深度思考/自省/追根/列同族/算账等脑内动作）时，写完后自查：

| # | 自查问题 |
|---|---|
| X1 | 每个认知动作的产物是否带**去处**（载体词表或仓内路径，路径能用 `Select-String` / `Test-Path` 查到）？ |
| X2 | 是否指名**挂进哪个文件的哪个槽位**，且目标文件真有该槽位（用 Select-String 验命中）？（产物去处确为会话载体时改标 annotations `x2Carrier`，不补假文件绑定） |
| X3 | 触发点是否在应激时刻（被质疑/出错）？若是，是否声明了「前置显式化」（任务开头先声明）？ |

缺任一 = 该动作仍可能被静默跳过 = 草稿不合格，回写。

### 判定词归一（必做；词表判据见 criteria §3.1）

极性判定词是**封闭词表**，正文极性一律用表内词、**不引入表外词**——词表全文在 rule-inspector 技能判据 §3.1 极性轴（§2.4 执行力度①同源），不在此复制。

- **写/改规则时**：从表里挑最贴近语义的词；遇到表外词（「不允许」「不可」「切勿」…）→ 读懂语义 → 换成表内词（例：「不擅自开始执行」→「不得擅自开始执行」）。
- **优化已有规则时**：体检发现表外极性词 → 归一成表内词（改前 vs 改后写进报告，按硬闸门 2 等确认）。
- **目的**：极性判定可靠、假阴性在源头减少（不再有「不得↔禁止」等价问题）。

### 冗余度 4 项自查（判据见 criteria §2.4 冗余度）

| # | 检查项 | 自查问题 |
|---|---|---|
| ① | 无完全重复句 | 正文去重后没有重复 ≥2 次的相同非空句子？ |
| ② | 无空泛引导段 | 没有以「总之/综上/需要注意的是/换句话说/由此可见」开头的空泛段？ |
| ③ | 无来源行历史叙述 | 来源行没有「合并/补于/补记」等历史叙述词？ |
| ④ | 三检验报告 | 对可删文字逐条过三检验（①判据不变 ②边界例子不变 ③引用不断）并写进报告？ |

> ①②③ 脚本可查；④ 由 AI 逐段三检验并报告「可删 N 段 + 理由」——判定定义见 criteria §2.4 冗余度，不在此复制。

## 三、来源行（模板 + 落地提示；判据见 criteria §2.1 / §2.4）

```
> 来源：<类型>（<YYYY-MM-DD>）｜[证据：<一句话，仅实测/踩坑类>]｜落地：<YYYY-MM-DD>
```

- 类型从 criteria §2.1 的四种枚举里选（判据见 criteria §2.1，不在此复制）；来源行放头部（前 10 行内）、不在文末，别超过 2 渲染行（判据见 criteria §2.4 头部规范/来源精简）
- 证据字段**仅「实测/踩坑」类写一句话现象**，其余三类不写
- 不写用户原话、不加「合并/补于/补记」等历史叙述词（判据见 criteria §2.4 来源精简 / 冗余度）

## 四、标题一致性收尾三句（定稿前必做；判据见 criteria §2.4 标题）

「①范围 ②极性 ③对象」三句的判定定义在 criteria §2.4 标题（标题 ↔ 内容一致性），不在此复制；写作时的落地问法：

1. **范围**：标题体现的范围/前提与正文适用范围一致？（内容有明确适用范围时标题必须体现，如「沟通中」——漏前提 = 误匹配风险）
2. **极性**：标题的做/不做方向与正文极性一致？
3. **对象**：标题的动作对象与正文宾语一致？

> 标题是「匹配线索」——AI 扫上下文时靠标题对动作「对号入座」。标题必须是一句话可执行判据（含极性 + 动作 + 对象 + 关键前提），不是主题名（`# 测试踩坑笔记` = AI 要读全文才知道管什么 = 静默掠过风险）。
