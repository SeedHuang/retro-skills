# 写「未完成事项」文档（writing-after-docs）

## 什么时候用这个技能

**判据一句话**：**这件事还没做完 / 还有待决项 / 结论还不能当依据引用** → 用本技能。

| 情况 | 用什么 |
|---|---|
| 需求还在探索、方案有争议、待决项没拍板 | ✅ 本技能（`docs/after/`） |
| 设计已定稿 | ❌ `docs/superpowers/specs/` |
| 一次 session 的收尾交接 | ❌ `docs/handoffs/`（**性质不同，见下**） |
| 已经做完了，只是想留个记录 | ❌ **不留**——见「做完之后怎么办」 |

## 与 handoffs 的区别（别混用）

| | `handoffs/` | **`after/`** |
|---|---|---|
| 记什么 | **一次 session 的收尾**：干了什么、现在什么状态、下次从哪接 | **一件事没做完的状态**：待决项、待触发时机、探索中的方案 |
| 时效 | **完成即定格**，永不改写 | **持续更新**，做完就迁走 |
| 数量 | 一次 session 一份 | 一个主题一份，可长期存在 |
| 读它的人 | 接手同一个 session 的人 | 任何人（哪怕几个月后） |

**为什么 handoffs 不归本技能管**：handoff 是**一次性快照**，写完就定；after 是**活的账本**，要维护状态。硬合一份技能会写出一堆「如果是 handoff 则…如果是 after 则…」的分支，反而难用。**各管各的。**

## 落点

**落点只有一个：`docs/after/<主题>-<阶段>.md`。**

**待决该落哪（判据「等多久、谁来解」）、以及为什么 `.session/` 里不设第二处 —— 以规则 `docs-convention`「待决事项只有一处」为权威定义方，本文不复制。**

**⚠️ 一个用途只能有一个地方。** 待决项**只写 `docs/after/`**；某次审查的过程进度写 `.session/reviews/<那一次>/progress.md`（走技能 `review-log`）。**两份说法必然会漂移** —— 实测 2026-10-08 就在两处各记了一份「改动规模采哪个范围」。

**⚠️ 待办文件里不许有「已完成」档。** 一件事做完就**从待办里删掉**（它已经变成代码 / 规则 / 断言了）。判据：**它现在还在等什么？** 等不到任何东西了 = 完成 = 删。

**⚠️ 别用「标记已完成」来保留历史** —— git 就是历史。在待办文件里再造一份历史 = 第二份真相，且必然漂移。完整理由与清账判据见规则 `docs-convention`「待办文件的语义」。

**两个容易混的落点（分工按「记录什么」，不按「多久之后还在」）**：

| | `.session/reviews/<那一次>/progress.md` | `docs/after/<主题>-<阶段>.md` |
|---|---|---|
| 装什么 | **过程**：跑了几轮、三段各做了什么、改了什么、**核销判定** | **待决与未完成**：等拍板的、等外部答复的、未做的方案 |
| 进 git | ❌ 不进（做完即删整个目录） | ✅ 进（可跨 session 长期存在） |

**命名形态、`<阶段>` 取值表、「一主题一份」的例外条件，一律以规则 `docs-convention`「文件命名」一节为权威定义方**（`my-rules\rules\docs-convention.md`）——本文不复制，只写一句提醒：**小写 kebab-case、不加日期前缀**。

**`.session/` 的目录语义（封闭清单、什么该进什么不该进）与全局规则 `docs-convention`「临时记录」一节为权威定义方** —— 本文不复制。

**为什么要有 `<阶段>` 这一段**：它让文件**不打开就知道处在哪个阶段**——`exploration`（还在探索）/ `gap-analysis`（在查差距）/ `open-decisions`（只剩待决）/ `done`（已收口）。

**目录语义、「什么时候该搬走」等全局约束以规则 `docs-convention` 为权威定义方**（`my-rules\rules\docs-convention.md`，已同步生效）——**本文只写操作规程，不复制那份约束**，防两处分叉。

## 模板

**唯一模板**：`assets/after-template.md`（五节骨架 + 条目状态三分 + 硬约束）

**必须逐字使用。** 自创结构是本技能明列的常见错误。

各节的写法细则（尤其 §2「前因后果」怎么写、§4「完成判据」怎么判断）见 `references/section-guide.md`。

## 五个必答问题（写之前先答）

1. **为什么会有这件事？** —— 动因是什么，谁发现了什么不对。
2. **现在卡在哪？** —— 一句话说清停在哪、为什么不能继续。
3. **每一环是怎么被上一环逼出来的？** —— §2 的因果链，不是流水账。
4. **做到什么程度算完？** —— §4 每条待办的完成判据。**写不出判据的，别挂进来**。
5. **押后的话，什么时候做？** —— §5 的触发时机，**必须是可判断的条件**，不是「以后有空」。

## 常见错误

| 错误 | 纠正 |
|---|---|
| **只写「现在有什么」，不写「为什么有」** | §1 §2 必写。**这是本技能最核心的一条**——只列结论不写推导，下次接手会重新推导一遍，等于白记 |
| §2 写成流水账（「先做了 A，然后做了 B」） | 写因果（「因为 A，所以必须 B」）。**区别在于有没有「逼出了」那一列** |
| §3 写「完成度不错」「基本符合」 | 每行都要有**取数命令**。没有取数命令的评价一律不写 |
| §4 待办**不写完成判据** | 写不出判据说明还没想清楚，**别挂进来当待办** |
| **做完直接删条目** | 改成墓碑行 `~~<事项>~~ → 已并入 <spec>（<日期>）`。删了会丢判断依据，且「做完」和「没做」在文件里长得一样 |
| **做完不迁走** | 条目挂着不动 = 僵尸账，每次扫「未完成」都要重新判断它做没做 |
| 押后写成「暂不处理」 | 用 **parking / 押后 / 待触发时机**。前者会被误读成已放弃 |
| 押后不写触发时机 | 「以后有空」不可判断，等于永远不做 |
| 把结论同时留在 after 和 spec 两处 | **双份真相**。定稿后只留 spec 一处，after 改指指针 |
| 建一篇新的「已完成」总结段 | 墓碑行即可。**不需要仪式感** |
| 在 after 文档里写「已验证没问题」 | 验证结论属 spec；after 只记「还没做完的」 |
| 旧的历史文档（handoffs / 已被取代的 spec）回头改 | 属历史记录，**保留不改**。after 文档只更新自己的待决项 |

## 做完之后怎么办

**这是本技能的第二核心**——`after/` 是「哪些没做」的唯一入口，**做完了却留着 = 挂账；做完了直接删 = 丢依据**。

三步（细则见 `references/migration.md`）：

1. **把结论并进 `docs/superpowers/specs/`**——结论不能丢，得有正式落点。
2. **对应待办改成墓碑行**——`~~<事项>~~ → 已并入 <spec 路径>（<日期>）`。**不删条目。**
3. **某篇文档的全部待办都做完后** —— 整篇迁走（结论已在 spec，这篇只是索引）。

**⚠️ 第 2 步和第 3 步的冲突及解法**（照着做，否则墓碑白写）：

第 3 步「整篇迁走」会把文档**连墓碑行一起删掉**——那就**抵消了第 2 步的作用**（墓碑的意义就是保留「做过」的痕迹）。所以：

| 时机 | 动作 |
|---|---|
| **条目做完时** | 只改墓碑行，**文档不动**（此时文档还有 §4 待办要维护） |
| **全部待办做完时** | **先把所有墓碑行汇总进文末「已完成区」（保留）→ 再删掉正文骨架** |

**结果**：文档瘦成一份「已完成清单 + 一句话说明」，**推导过程和做过什么仍留在 git 历史与墓碑区里**，但不再占着「未完成」的入口。**详见 `references/migration.md` 第三节。**

**例外**：条目本身是错的（结论被推翻、需求不存在）→ **直接删**，但在该节末尾留一句「曾有 X，因 Y 删除」，否则下次会有人重新提同一个想法。

## 收尾自查

写完 / 更新完，扫一遍：

- [ ] **文件名是 `<主题>-<阶段>.md`**（小写 kebab-case、无日期前缀）——不符就改名
- [ ] §1 写清了动因、卡点、给谁看
- [ ] §2 是**因果链**（每行都有「逼出了什么」），不是流水账
- [ ] §3 每行都有取数命令，无评价词
- [ ] §4 每条待办都有完成判据
- [ ] §5 每条押后都有**可判断的触发时机**（**没有押后项时写「本期无押后项」，不留空**）
- [ ] 状态为「已做」的条目**已改成墓碑行**，没有直接删的
- [ ] 结论**没有同时**留在 after 和 spec 两处
- [ ] 入口处写明「未决」和「何时该搬走」
