# 各节写法细则

> `assets/after-template.md` 定义**结构**（有哪几节）；本文定义**写法**（每节怎么写才算合格）。
> SKILL.md 只指向，不复制。

## §1 为什么有这件事

**必答四问，缺一即不合格**：

| 问 | 写什么 | 反例 |
|---|---|---|
| 动因 | 是什么事逼出了这份文档 | 「为了整理」——谁整理、为什么现在 |
| 卡点 | 现在停在哪、为什么不能继续 | 「有待决项」——哪一项、卡住谁 |
| 给谁看 | 下一个接手的人需要知道什么，才不用重新推导 | 省略——**这是本文存在的意义** |
| 为什么不能往下做 | 缺什么前提 / 什么不可信 | 「还没准备好」——哪个环节不可信、为什么 |

**「给谁看」这一问是本文档之所以写下来的唯一理由。** 想清楚这句话：「下一个接手的人（可能是几周后的自己）读完这四行，能不能不重新问一遍为什么」。

## §2 前因后果（最容易漏的一节）

### 区别在哪

| 写法 | 例子 | 判定 |
|---|---|---|
| **流水账** | 「先备份了 KB，然后删了产物，然后改了守卫」 | ❌ **只是做了什么** |
| **因果链** | 「用户判定产物与设计不一致 → 决定清空重来 → 备份到 `_archive/` → 删 13 个文件 → **删完发现工具链失效** → 改守卫」 | ✅ **每一步因为什么所以发生** |

**机械判据**：表格里有没有「逼出了什么」这一列。**没有就是流水账。**

### 必写的两类信息

**① 哪一环是别人的前置条件，哪一环是自己引起的**

例：「工具链失效是**清库的副作用**，不是清库本身的问题」——这类话不写，下次会有人去查错方向。

**② 哪一步当时犹豫过 / 判断错过**

例：「我先按文件格式分类，被判错——markdown 在这套体系里就是代码」——**记这个是为了下次不重犯**，不是为了追责。

### 常见退化

- **只写最后一步**（「已加规则 X」）——读者不知道为什么会走到这一步。
- **每步都写「然后」**——「然后」是时间顺序，不是因果。**换成「因为…所以…」**。
- **把结论当原因**（「因为结论不对所以改」）——那是循环论证，因果链要从**外部事实**起（用户说了什么、实测发现什么）。

## §3 现状

**只写事实 + 取数命令。**

| 要求 | 说明 |
|---|---|
| 每个数字有取数命令 | 全局规则 `numbers-must-be-measured`：数字取终态实测并附命令 |
| 表格三栏：项 / 值 / 来源 | 缺「来源」列的数字视为可疑 |
| 无评价词 | 「完成度不错」「基本符合」——**没有取数支撑的评价一律不写** |

**为什么要这么严**：这份文档是**几个月后**的读者看的，他没法验证你的数字，只能信你。**一个没有来源的数字，和没有这个数字一样有害**——甚至更糟（它看起来像有依据）。

## §4 要做什么

### 完成判据怎么判断

**判据 = 一个能被验证的终点状态**，不是「做完了」这种主观描述。

| 不合格 | 合格 |
|---|---|
| 「优化 collect 的采集能力」 | 「`facts.md` §2 出现一行改动规模，值能从 `git show --numstat` 复算」 |
| 「整理一下现有产物」 | 「6 份产物全部标注形态（齐全/旧六节/标识不合规），无未标注项」 |
| 「补上完成判据」 | 「本文 §4 每条待办都有判据列，无空白」 |

**写不出判据 = 还没想清楚。** 这种条目**别挂进来**——挂进来就是欠账，扫的时候每次都要重新判断它到底做没做。

### 三种状态

| 状态 | 处理 | 为什么 |
|---|---|---|
| **待做** | 留原文 + 完成判据 | — |
| **已做** | 墓碑行：`~~<事项>~~ → 已并入 <spec 路径>（<日期>）` | **不删**。删了丢判断依据（「当初为什么觉得要做」），且「做完」和「压根没做」在文件里长得一样，没法统计推进量 |
| **不做了 / 做错了** | **直接删**，留一句「曾有 X，因 Y 删除」 | 留一条错的比删掉更糟；但**必须留那句**，否则下次有人重新提同一个想法 |

## §5 parking

**「押后」≠「废弃」。** 两者在文档里必须可区分。

| 要素 | 要求 | 反例 |
|---|---|---|
| 认可到哪一步 | 说清哪部分已认可、哪部分还没定 | 「基本认可」——哪部分？ |
| **触发时机** | **可判断的条件** | 「以后有空」「视情况」 |
| 押后理由 | 为什么现在不做 | 省略——读者会以为你没想到 |

**触发时机怎么写才算可判断**：

- ✅ 「真出现一次扁平 `moments.md` 时」——有明确信号
- ❌ 「以后遇到相关问题」——无法判断是否已触发
- ❌ 「等积累够数据」——多少算够？说不清就是不可判断

**为什么必须写触发时机**：parking 项没有触发条件，就会一直躺在待决清单里，**每次扫都要重新决定一次「现在要不要做」**——这正是 parking 机制失败的样子。

## 附：什么时候该新建一篇 vs 追加到已有篇

| 情况 | 动作 |
|---|---|
| 新发现的未完成事项，**跟已有的是同一个主题** | **追加**到已有文档（一个主题一篇） |
| 新发现的**是另一个主题** | 新建一篇 |
| 只是同主题下的又一条待办 | 追加到 §4 表格 |
| **§4 表格已超过 15 条** | **按主题内再分一类一文件**（如 `xxx-exploration.md` + `xxx-template-rewrite.md`），**两篇开头互相写指针** |

**为什么要「一个主题一篇」**：一篇文档讲一件事，读的时候不用在七件事里找那件。**混在一篇里，等于没有索引。**

**为什么 15 条是分界线**：再往上，一篇里塞两种不同性质的事项会让人搞混「哪条属于哪类」——**此时该拆，但拆出来的必须是「同一主题的不同类别」，不是「同主题的两个独立主题」**。
