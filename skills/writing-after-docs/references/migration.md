# 迁走清单：把做完的事从 `after/` 移出去

> **核心判据**：`docs/after/` 是「**哪些没做**」的唯一入口。
> **做完了却留着 = 挂账**（每次扫都要重新判断它到底做没做）；**做完了直接删 = 丢依据**（下次不知道当初为什么做、做成什么样算够）。
> 唯一解是**墓碑式改写**。

## 一、三步（缺一不可）

| 步 | 动作 | 漏了会怎样 |
|---|---|---|
| 1 | **把结论并进 `docs/superpowers/specs/`** | 结论没有正式落点，下次找不到 |
| 2 | **对应待办改成墓碑行** | 状态不明，「做完」和「没做」长得一样 |
| 3 | **全篇待办清空后，整篇迁走** | 文档永远占着，扫的时候永远是「未完成」 |

**顺序不能颠倒**：先写 spec 再改墓碑。反了就出现「墓碑指向一个不存在的 spec」。

## 二、墓碑行怎么写

```markdown
| ~~把 §6 改成结构化三栏~~ | 模板已改，下一份 collect 生效 | 已并入 `docs/superpowers/specs/2026-10-xx-xxx.md`（2026-10-20） | 已做 |
```

三个要素缺一不可：

| 要素 | 例子 | 缺了会怎样 |
|---|---|---|
| **原事项**（划掉） | `~~把 §6 改成结构化三栏~~` | 不知道做过什么 |
| **完成的终点状态** | 「模板已改，下一份 collect 生效」 | **只有「已做」没有结果 = 等于没记录** |
| **spec 路径 + 日期** | `specs/2026-10-xx.md（2026-10-20）` | 结论找不到了 |

**最容易漏的是中间那项。** 只写「已做」等于没写——**下次接手会问「做完了什么样子」，答不上来。**

## 三、什么时候可以整篇迁走

**本文档 §4 的待办全部为「已做」或「不做了」，且没有 §5 parking 项** → 整篇迁走。

**⚠️ 迁走 ≠ 删除**（这是最容易做错的一步）：

直接把文档删掉，**会连带删掉第二步写下的墓碑行**——墓碑的意义就是保留「做过」的痕迹，删了就白写了。正确做法：

| 序 | 动作 | 结果 |
|---|---|---|
| 1 | 把所有墓碑行**汇总**到文末新增的「## 已完成区」（含 spec 路径 + 日期 + 终点状态） | 做过什么集中可查 |
| 2 | 把 §1–§5 的正文骨架**删掉**，只留「## 已完成区」+ 一句话说明（本主题已收口，结论见 `<spec 路径>`） | 不再占着「未完成」的入口 |
| 3 | 改文件名 → `<主题>-done.md`，或按 `docs-convention` 移到 `specs/` 下留档 | 从 `after/` 的「未完成」清单里消失 |

**为什么第 3 步要改名**：`after/` 的语义是「还没做完」。留一个叫 `xxx-exploration.md` 却全做完的文档，下个扫的人会困惑——**文件名必须反映当前状态**（这也是命名规范里要带 `<阶段>` 的原因）。

**推导过程还会保留吗**：会——它在 git 历史里。**`after/` 不需要长期保存推导过程**，需要时从 git 历史翻；留在活文档里的只有「做过什么 + 结论在哪」。

**迁走后要回头扫引用**——见下一节。

## 四、迁走时的引用清扫

| 引用方 | 怎么处理 |
|---|---|
| KB `index.md` | 指向 after 文档的指针**改成指向 spec**，或删掉该条 |
| 其它 after 文档 | 「相关文档」类链接同步改 |
| skills / rules 正文 | 若提到过本文档的路径，**改指 spec** |
| spec / plan / handoff 里的旧路径 | **保留不改**——历史记录 |

**判定口径**：这次扫的是「**当前有效的声明**」还是「**当时的记录**」。前者改，后者不动。

## 五、什么情况直接删（不走三步）

**条目本身是错的** —— 结论被推翻、需求不存在、方向已取消。

**直接删条目**，但在该节末尾留一句：

```markdown
> 曾有「legacy 单文件接管」候选，因本次 spec 已取代该问题而删除（2026-10-20）。
```

**为什么不能默默删**：删掉之后，下个接手的人（可能就是你）看到同一个问题会**重新提一遍**，因为找不到「这个想法被否定过」的痕迹。**留那句话是给未来的自己看的。**

## 六、验算清单

迁走前逐条对：

- [ ] 结论已写进 `specs/`（**不是只写了个「已做」**）
- [ ] 每条墓碑行有**三个要素**（原事项 / 完成的终点状态 / spec 路径 + 日期）
- [ ] §4 无「待做」残留
- [ ] §5 无 parking 残留（有的话是还没做完，**不许迁**）
- [ ] 指向本文档的指针全部更新（KB 索引 / 其它文档）
- [ ] 历史文档里的旧路径**保留未改**
- [ ] 删掉的错误条目都留了「曾有 X，因 Y」

## 七、常见失败模式

| 失败 | 后果 | 防 |
|---|---|---|
| 只在原地方写「已完成」，没进 spec | 结论无落点，下次找不到 | 步 1 先行 |
| 墓碑只写「已做」 | 不知道做成什么样 | 强制写终点状态 |
| 整篇永远不迁走 | 扫「未完成」时永远有它 | §4 清空 + §5 无残留才准迁 |
| 迁走时漏扫指针 | 下次从旧路径找，找不到 | 第六节清单 |
| 删错误条目不留痕 | 同一个想法被重新提 | 留「曾有 X，因 Y」 |
| 改 spec 时顺手改 after 的历史记录 | 历史被抹掉 | 历史记录**保留不改** |
