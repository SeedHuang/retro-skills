# 改法处方（rule-optimizer recipes）

> 本文件是 rule-optimizer skill 的改法处方：每类违规 → 可复制的改法（spec B5）。由 `scripts/score.mjs` 的 findings 或人工体检命中违规类目后，跳到对应 `§R#` 节取改法。判据全集见 `references/criteria.md`，头部规范见 `assets/rule-template.md`。

## 使用方式

1. 体检（脚本或人工）给出违规类目（§R1–§R7），定位到对应小节。
2. 每节按「判据 → 改法 → 例子」执行：先确认命中，再照改法动手，最后对照例子自查。
3. 改完跑一次 `scripts/score.mjs` 确认对应维度分数上升；分数没涨 → 回退（`git restore` 该文件）再重看判据。

### §R1 来源行超长

**判据**：头部来源行字符数 **> 200**（操作锚点，对应 D3「来源行 ≤ 2 渲染行」；不许用「物理 1 行」糊弄）。典型形态：合并记录（「合并 X + Y」）、多段用户原话、补记日期（「2026-10-08 补」）全挤进一行。2026-10-08 实测命中：`how-i-must-reason.md`（来源行 329 字符 ≈ 10 渲染行）、`docs-convention.md`（两次补记挤一行）。

**改法**：对照 `assets/rule-template.md` 重写为单行：

```
> 来源：<类型>（<YYYY-MM-DD>）｜[证据：<一句话，仅实测/踩坑类>]｜落地：<YYYY-MM-DD>
```

- **删合并记录**（「合并 no-unverified-claims.md」这类）——历史归 git，来源行不留。
- **删多段用户原话**——只保留一个来源类型 + 一个日期。
- **删补记日期**——日期只留一个，不写「落地：2026-10-07，2026-10-08 补」。
- 证据字段**仅「实测/踩坑」类写一句话现象**，其余三类不写。

**例子**：

- `how-i-must-reason.md` 现状：`> 来源：合并 no-unverified-claims.md（2026-10-07，用户当场指令「如果每次都要人来鉴别…」）+ own-judgment.md 全文（2026-10-01，「就算遇到问题你很难抉择…」）+ numbers-must-be-measured.md（L-2026-09-27-006，…）｜补于 2026-10-08（用户当场指令：「不要考虑成本…」…）｜落地：2026-10-08`
  → `> 来源：用户当场指令（2026-10-07）｜落地：2026-10-08`
- `docs-convention.md` 现状：`> 来源：用户当场指令（2026-10-07）｜证据：…用户原话「…」「…」｜**2026-10-08 补**：用户原话「…」「…」→ 新增「临时记录（.session/）」一节｜落地：2026-10-07，2026-10-08 补`
  → `> 来源：用户当场指令（2026-10-07）｜落地：2026-10-07`

### §R2 无来源行

**判据**：规则头部（第 1–3 行内）缺 `> 来源：` 行。2026-10-08 实测命中：`no-git-write.md`、`ts-expect-error.md`、`vitest-queued-alternative.md`；2026-10-15 命中：`code-style.md`（拆前合集，已拆为 `import-path-choice` / `list-empty-state` / `styled-component-file`，拆后各自补了来源行）。

**改法**：

1. 先查这条规则的来源（git log、`docs/`、对话记录）；来源类型按 `references/criteria.md` §1 四类判定（用户当场指令 / 评审第 N 轮 / 实测踩坑 / 项目约定）。
2. 补：`> 来源：<类型>（<YYYY-MM-DD>）｜落地：<YYYY-MM-DD>`
3. **来源不明时如实写「来源：未记录」——禁止编造用户原话**。来源行是自称的章（见 criteria §诚实边界），编造等于造假。
4. 从旧文件拆出的规则（`ts-expect-error.md` / `vitest-queued-alternative.md` 拆自 `testing-pitfalls.md`）：**继承原文件的来源类型与日期**，不重编。
5. 若 §R6 判定该规则整条要搬走/删除：先不补来源行，等搬移结论（避免白补）。

**例子**：

- `vitest-queued-alternative.md`（拆自 `testing-pitfalls.md` §2，内容未动）→ `> 来源：项目约定（2026-10-08）｜落地：2026-10-08`（类型/日期继承原文件，拆条日期如实）
- `import-path-choice` / `list-empty-state` / `styled-component-file`（拆自 `code-style.md` §1/§2/§3，继承原「项目约定」来源类型，补 `> 来源：项目约定（2026-10-10）｜落地：2026-10-15`）
- 查遍 git 与文档都无来源 → `> 来源：未记录｜落地：2026-10-08`（落地填体检/记录当天，如实标注）

### §R3 来源行错位在文末

**判据**：`> 来源：` 行不在标题下第 2 行（文件第 3 行），而在文末或正文中间。2026-10-08 实测命中：`import-guard.md`（来源行在最后一行）。

**改法**：把来源行剪切到 `# 标题` 下方、空一行之后（第 3 行）。**移动时顺手把来源类型归一到四类枚举**（`L-019` 这类 lessons 编号不在枚举内 → 归为「实测/踩坑」并补日期，因为证据字段已有一句话现象，符合该类格式）。

**例子**：

- `import-guard.md` 文末（原第 96 行）：`> 来源：L-019｜证据：上一 session 工具回显污染（假 diff → 假路径 → 假 git 输出 → 伪造完整工具调用，多步编辑被吞，靠用户提交 fa06619/d2819b0 收口）｜落地：2026-09-29`
  → 移到标题下第 2 行，归一为：`> 来源：实测/踩坑（2026-09-29）｜证据：上一 session 工具回显污染（假 diff → 假路径 → 假 git 输出 → 伪造工具调用，多步编辑被吞）｜落地：2026-09-29`

### §R4 标题是目录式

**判据**：H1 是主题名/目录名而不是可执行判据——`# 测试踩坑笔记`、`# 代码风格规则`、`# XX 规范` 这类，看不出「什么时候该做什么」。判据式标题的对照：`# 编辑代码时禁止丢失 import`、`# 有想法先沟通，拿到授权再动手`、`# 项目文档按「生命周期状态」分目录，未完成的进 docs/after/，临时的进 .session/`。目录内含多条**不相关**规则时还要拆条。

**改法**：

1. 标题改为「一句话可执行判据」：`<动词> + <对象> + <条件/边界>`。
2. 目录内含多条不相关规则 → **拆条**：每条独立成文件，各自判据式标题、各自来源行（继承原文件来源）、各自 H2 结构。判定「不相关」：删掉一条，另一条的判据不受影响。
3. 拆完删原文件，**回头扫指向原文件的引用**（KB 索引、其它规则里的指针）一并更新（`landing-sweep`）。

**例子**：

- ✅ 已拆（2026-10-08 实测）：`# 测试踩坑笔记` → `# @ts-expect-error 只在 TS 实际报错时使用`（`ts-expect-error.md`）+ `# Vitest 在受限环境 stuck 时改用替代验证`（`vitest-queued-alternative.md`）——一条管类型注释、一条管测试环境兜底，互不相关。
- ✅ 已拆（2026-10-15 实测）：`# 代码风格规则` → `# 在写前端代码 import 时，路径必须按归属使用相对路径或 @/ 别名`（`import-path-choice.md`）+ `# 在列表数据为空时，空态必须使用 antd Empty 渲染，不得用纯文本占位`（`list-empty-state.md`）+ `# 在使用 styled-components 的项目中，styled.xxx 定义必须使用独立 sc.tsx 文件，不得写在业务组件文件内`（`styled-component-file.md`）——三条互不相关。
- 目录式标题反例：`# 测试踩坑笔记`、`# 代码风格规则`、`# 笔记`、`# 规范`——全是主题名，不是判据。

### §R5 层级混用

**判据**：核心判据用 `**加粗**`（或引用块+加粗）承载，而不是 H2/列表（`criteria.md` §2：**核心判据必须由 H2 或列表承载**；`**加粗**` 仅句内强调）。同一含义两种标记并存即是混用：`global-ask-before-acting.md` 用加粗承载 vs `no-git-write.md` 用 `## 核心约束`。

**改法**：

1. 把承载核心判据的加粗句改为 `## <大节名>` + 正文，或转为列表。
2. `**加粗**` 只保留在句内强调处（修饰词、例外标注），不再承担结构职责。
3. H3 标题不用 emoji 装饰（`### 🔥 xxx` → `### xxx`）。

**例子**：

- `global-ask-before-acting.md`：`**先沟通清楚，拿到授权，才有写权限。顺序不能颠倒。**`（加粗承载核心约束）→ `## 核心约束` 下写：`先沟通清楚，拿到授权，才有写权限。顺序不能颠倒。`
- `import-guard.md`：`> **🚨 一切编辑的前置自检：…**`（引用块 + 加粗 + emoji 承载核心约束）→ `## 核心约束` + 正文，删 `🚨`（emoji 不承载判据、不做标题装饰）。
- 正确对照：`no-git-write.md` 的 `## 核心约束`（H2 承载，加粗仅句内）。

### §R6 项目事实混入全局规则

**判据**：全局规则（`rules/`，对每个项目生效）里出现**只对某个项目成立**的事实——特定文件路径（`src/pages/404/index.tsx`）、特定框架/组件库（antd、UmiHistory、styled-components、`@/` 别名）、特定项目名。这些事实在其它项目里要么不成立、要么是错的。2026-10-08 实测命中：`import-guard.md` 的「已知的已有编译错误」清单、`code-style.md` 全篇（后者 2026-10-15 已拆为 `import-path-choice` / `list-empty-state` / `styled-component-file`，各标注「仅适用使用 antd / styled-components / @/ 别名的项目」）。

**改法**：

1. 逐节判断「通用判据」还是「项目事实」：删掉这条后，通用判据是否还成立。成立 → 项目事实。
2. 项目事实两种处置：
   - **移到项目内文档**（该项目仓库的 CONTRIBUTING / 项目 README / 项目内 rules）；
   - 或留在原规则但**标注「仅适用于 X 项目」**（当全局场景仍需引用它时）。
3. **跨仓搬移（规则库 → 项目仓库）需用户确认**（spec §5.4）：本 skill 只提出建议 + 给出裁剪方案，**不自动搬**。报告里列「搬哪节 / 搬到哪 / 原规则留什么」。
4. 搬完回头扫引用（`landing-sweep`）。

**例子**：

- `import-guard.md`「已知的已有编译错误」清单（`src/app.tsx` — `location` 不在 `UmiHistory` 类型上 等 3 条，某 Umi+antd 项目既存错误）→ 移到项目内文档；通用判据（「编辑后 tsc 验证」）对任何项目成立，保留，项目清单处只留指针。
- `import-path-choice` / `list-empty-state` / `styled-component-file`（拆自 `code-style.md`，antd `Empty` / styled-components `sc.tsx` / `@/` 别名）→ 各在「例外」小节标注适用范围（「未配置 `@/` 别名的项目」「不使用 antd 的项目」「不使用 styled-components 的项目」不适用），保留在全局规则库。

### §R7 规则矛盾

**判据**：两条规则对同一动作给出相反判决。2026-10-08 实测命中：`import-guard.md` 硬规则 3「**禁止**使用 `GetDiagnostics`（TS Server 编辑后缓存不可靠）」vs `vitest-queued-alternative.md`「1. **GetDiagnostics** — 对改动的文件调用 IDE 诊断，确认零错误」。同一动作，两个判决。

**改法**（人工判断题，脚本不查语义，spec §5.4）：

1. 各自列出适用范围：各管什么场景、什么时机。
2. 判「真矛盾」还是「范围不同没写清」：
   - **范围不同** → 各自补一句范围说明，把边界写清；
   - **真矛盾** → 按 `landing-sweep` 改两处 + 报告。
3. **补说明 / 改措辞属于「改动判据措辞」→ 按硬闸门 2：报告「改前 vs 改后」→ 等用户确认 → 才落地**。不自行拍板。

**例子**（`GetDiagnostics` 案）：

- 范围分析：`import-guard` 管「编辑后**立即**验证」（TS Server 缓存延迟，时效性敏感）；`vitest-queued-alternative` 管「测试环境不可用时的**兜底**验证」（无即时性要求）→ 倾向判「范围不同没写清」。
- 各自补范围说明：
  - `import-guard.md` 硬规则 3 补：「本条禁令仅限『编辑后立即验证』；非即时场景（如测试环境不可用时的兜底检查）不受限。」
  - `vitest-queued-alternative.md` 补：「本方案仅用于测试环境不可用时的替代验证，不用于『编辑后立即验证』（后者见 `import-guard` 硬规则 3）。」
- 若判「真矛盾」：按 `landing-sweep` 两处一起改 + 报告改前改后 + 等用户确认。

### §R8 认知动作无落点（X1/X2/X3，仅认知动作型规则；判据全文见 `references/criteria.md` §3.3b，不在此复制）

**判据**：规则被 annotations 判为认知动作型（`rules/.inspector-annotations.json` 标 `cognitive: true`），但 X1/X2/X3 任一 fail。2026-10-15 实测命中：`core-working-principles.md`（产物「全貌确认」块无去处、无路径绑定——旧关键词判据 96% 健康，落点断言后 86% 预警）。

**改法**（按命中的 X 逐条；词表/窗口语义以 criteria §3.3b 为准）：

1. **X1 fail（产物无去处）**：产物声明补「去处动词 + 去处」——产物写进**哪个文件**（反引号路径，`Test-Path` 必须为真）**或哪个载体**（回复/回答/报告/commit body/账本/对话记录）。反例（必须红）：「随任务记录可查」——无动词、无锚点载体，是「声称有落点实际无锚点」的原型。正例：「先输出「全貌确认」块，写进当次回复」。
2. **X2 fail（无路径绑定 / 声称的槽位不存在）**：补「挂进/绑进 + `路径` + `「槽位名`」」三段齐全，**且目标文件真有该槽位**（`Select-String -Path <目标文件> -Pattern '<槽位>'` 命中才算）。声称的槽位不存在时**两条路**：改规则指向真实槽位，或先在目标文件里建槽位（后者是「规则要求一个尚不存在的流程槽位」的正解——落点没槽位正是洞本身）。**例外**：产物去处确为会话载体（回答/回复等 X1 载体词、无自然文件落点）→ 走 annotations `x2Carrier:true` 标记（X2 不评，该规则满分 +2），**不补假落点**。
3. **X3 fail（应激触发未前置显式化）**：AI 判——触发在应激时刻（被质疑/出错）且规则无「任务开头先声明」类前置句 → 补前置句；判完把 `x3Done: true` + 判定依据一行写进 annotations。

**⚠️ 改规则正文措辞前过 rule-inspector 硬闸门 2**：报告「改前 vs 改后」→ 等用户确认 → 才落地。

**例子**（X2 正例，判据锚点）：`core-working-principles.md` 产物行声称落点为 `review-log` 技能资产 `review-progress-template.md` 的「全貌确认」节——该文件先有「全貌确认」节（`Select-String` 命中），断言过；没有该节 → X2 红，此时该先补模板槽位而不是改规则措辞。
