# 段③：技术实现

## 入口条件

- 计划门的 `gate-record.md` 行已齐六列，审计已本人读并签字。
- 施工所用的 spec 与 testcase 已定稿（不是「边做边补」的草稿）。

## 出口判据

1. plan 中每条执行步骤都有对应产出（文件 / 命令 / 提交），没有「计划里有、盘上没有」的步骤。
2. 全仓检查绿：`npm run check` exit 0，日志里 `# fail 0`、`0 findings`、markdown 检查通过、docgen gate 计数与清单派生值一致。
3. 每份改动都能指回 spec 的一节或一个 R 编号；plan 阶段新增的设计决策为零（有则必须回流 spec）。
4. 交付物只落在 plan 声明的路径白名单内；白名单外出现改动必须在记录里写明理由。

## 谁签

- **申报人**：开发（施工者）。
- **签字人**：开发；由 ④ 的 sdet 复核执行结果。
- 签字必须附：`npm run check` 的完整输出首尾行（含 `# fail 0` 与 `check 全部通过`）、白名单外改动清单（应为空）。

## 三权归属

| 权 | 谁 | 判据 |
|---|---|---|
| 申报 | 开发 | 申报四条出口已齐，附 `npm run check` 输出与白名单核对结果 |
| 定性 | 开发本人（施工完整性） | 只定性「计划步骤是否都落地」，不定性「是否符合 spec」——后者归 ④ 的 sdet |
| 核对 | sdet（段④） | 独立复核验收项；施工者不得同时自判验收通过 |

## 常见漏项

- 只跑局部测试就宣称完成 → 全仓门没跑，跨文件的计数漂移看不见。
- plan 阶段发现 spec 没写清，顺手自己定了 → 属新增设计决策，必须回流 spec（见强制约束 R4）。
- 白名单外顺手改了无关文件 → 提交面与验收面脱钩。
- 测试文件写成「只在正常路径断言」→ ④ 段会打回。
- 施工中改了生成器默认值、只跑单测不跑逐字节比对 → 群体回归看不出来。

## 收口后

产出 `gate-record.md` 里 ③ 的那一行：六列齐，「核了什么」写 `npm run check` 输出首行或结论行。缺行不得进入 ④。
