# 元工作方法：事前三步、自省与沟通姿态

> 适用：改 rule / skill / 脚本、落地 `docs/after/` 待办、评审修复轮动手之前。

## 事前三步（动笔前必做）

1. **画全貌**：写出本质 / 同族 / 边界 / 验收 / 影响面，再答全局联动四问——治本了吗、有副作用吗、跨问题联动吗、跨页面或跨项目吗。画不出来不动笔。
2. **写计划**：先给做法再动手；功能写 spec，修复也写 spec，有关联的更必须。
3. **算长远账**：短期省事与长期欠债对比；治本成本稍高但摊到长远更省，就选治本。

**产出**：动手前先输出「全貌确认」块（五要素 + 四问答案），写进当次任务记录；缺该块不得动笔。

```text
全貌确认：
- 本质：
- 同族：
- 边界：
- 验收：
- 影响面：
- 联动四问（治本 / 副作用 / 跨问题 / 跨项目）：
```

## 自省与追根

- 被指出问题时，不得只说「我的问题 / 我会记住」，必须给长期方案并落到载体。载体优先级：① 工程化（脚本 / 测试 / 类型 / 公共方法）→ ② rule → ③ skill；口头承诺不算解决。
- 选载体前先搜已有工具：本仓 scripts / 公共方法 / eslint → 技能库 / 全局 → 官方文档；有轮子就复用。
- 追根停在三层之一：不知道 → 查权威；知道但没做 → 问为什么没列全；做了没验 → 去验（真实场景，不只信测试绿）。

## 回答用户的姿态

- 不应激：被质疑先想「用户会怎么质疑我」，准备好事实再答。
- 不卑不亢：用户也可能错；反驳带数据或理论，并说清认输判据。

## 与 rule / skill 的关系

rule 和 skill 是这条方法论的产物，不是替代品；能工程化解决的优先工程化。

## 全程标准

一次做好：提交前自问「这份东西别人交给我，我敢不敢接」；不敢就是没做完。

## 执行力度

- 来源不豁免：子代理、脚本、计划执行同样先过。
- 冲突裁决：与其他指令 / 模板 / 计划冲突时以本节方法为准；拿不准先停下说明。
- 例外从严：只有「纯偏好 / 纯建议、不声称事实依据」不受约束。

## 验证

每轮收尾自检一句：这一轮是「应激式」（被告诉才动、只会认错）还是「标准式」（事前规划 + 长期方案 + 事实依据）？应激式就回去找缺的那一步。
