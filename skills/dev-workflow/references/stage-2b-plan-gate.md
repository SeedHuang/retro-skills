# 计划门（②→③，不是段）

## 入口条件

- ② 的 `gate-record.md` 行已齐六列，议会 #2 已通过。
- plan 已写出：每个功能块对应哪些执行步骤、步骤间依赖、每步的验收命令。

## 出口判据

三条核对，每条都写成「判据 + 二选一证据」（脚本上线后 / 脚本上线前）：

### 核对一：功能点全覆盖

- **判据**：PRD 的功能点 ID 集合 ⊆ plan 覆盖的功能点 ID 集合（差集为空），且每个被覆盖的功能点至少有一条执行步骤。
- **证据（脚本上线后，S4 起）**：`node scripts/check-plan.mjs coverage --plan <plan 文件> --prd <PRD 文件>`，贴 stdout 首行（应报缺口 0）。
- **证据（脚本上线前，当前适用）**：审计手工核对表——逐条填「核了什么 / 怎么核的 / 结论」，并附上人工取集合的原始命令原文（例如从 plan 与 PRD 各 grep 一次 `F-[0-9]+` 后比对）。

### 核对二：依赖无环

- **判据**：plan 的步骤依赖图是 DAG（拓扑排序可完成，无环）；每个步骤声明的依赖项都存在于 plan 内。
- **证据（脚本上线后，S4 起）**：`node scripts/check-plan.mjs deps --plan <plan 文件>`，贴 stdout 首行（应报环 0）。
- **证据（脚本上线前，当前适用）**：审计手工核对表——写下拓扑序或指出成环的那条边，并附人工检查命令原文。

### 核对三：功能块 ↔ testcase 一一映射

- **判据**：每个功能块恰对应一份 testcase 文件，且该 testcase 覆盖该功能块全部验收项；无功能块缺 testcase，无 testcase 悬空。
- **证据（脚本上线后，S4 起）**：`node scripts/check-plan.mjs map --plan <plan 文件>`，贴 stdout 首行（应报缺映射 0）。
- **证据（脚本上线前，当前适用）**：审计手工核对表——逐功能块写「对应 testcase 文件 + 覆盖的验收项编号」，附文件清单命令原文。

> **脚本未落地期（当前）**：`scripts/check-plan.mjs` 归 S4，现在不存在。本节不得只写命令就当成已落地——三条核对在脚本上线前一律走「审计手工核对表」，表头固定 `核了什么 | 怎么核的 | 结论`，并附原始命令原文。审计只签字不读按**不通过**处理。

## 谁签

- **申报人**：主 agent（plan 作者）。
- **签字人**：脚本 + **审计本人读并签字**；本门**不设议会**。
- 签字必须附：三条核对各自的证据（上线后 = 命令 + 输出；上线前 = 手工核对表 + 命令原文），以及每条核对对应的结论一句话。

## 三权归属

| 权 | 谁 | 判据 |
|---|---|---|
| 申报 | 主 agent | 申报三条核对已过，附三条证据与结论 |
| 定性 | 审计本人 | 审计必须自己读 plan 并填核对表；只签字不读 = 不通过 |
| 核对 | 脚本（上线后）/ 审计（上线前） | 脚本给集合结论，审计给逐条核对表；两者都不由 plan 作者代填 |

## 常见漏项

- 只写三条命令、不写「脚本上线前怎么核」→ 照着跑会报找不到模块（本仓 S4 前脚本不存在）。
- 审计签字但没读 plan → 橡皮章，属不通过。
- 依赖检查只看文字「A 依赖 B」，不看环 → 两项互相依赖时看不出来。
- testcase 映射按文件名猜 → 同名不同功能块会漏。
- 功能点全覆盖只比数量不比集合 → 删一个加一个仍「数量相等」。

## 收口后

产出 `gate-record.md` 里 `②→③` 的那一行：六列齐，「签字人」含审计，「核了什么」含命令输出或 `path:line`。缺行不得进入 ③。
