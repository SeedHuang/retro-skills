# 计划门（②→③，不是段）

## 入口条件

- ② 的 `gate-record.md` 行已齐六列，议会 #2 已通过。
- plan 已写出：每个功能块对应哪些执行步骤、步骤间依赖、每步的验收命令。
- plan 具备三条**结构必备项**（缺任一项，脚本只能给 exit 2，不是判据红）：① `**Testcase:**` 行（首个反引号内是 testcase 路径）；② 「附录 A」节，且节内表格**首列即用例 ID**；③ 「功能点→任务映射表」（表内出现首列含 `F-\d{2}` 的行，且表内任一单元格含 `Task N` / `T<N>`）。
  缺项自检：`node scripts/check-plan.mjs map --plan <plan 文件>` —— **exit 2 = 结构缺项**（补结构后重跑），不是「实现坏了」。

> **旁路（PRD §4.2）**：单点小改跳过议会 #2，「议会 #2 已通过」改为「`gate-record.md` 注明「旁路」+ 审计的集合 diff 结论」；本门只判「依赖无环 + 变更范围在白名单内」，另两条写「不适用（无功能块）」，审计签字不变。**旁路时 `coverage` / `map` 不跑**，证据列改贴审计的集合 diff 结论（脚本**不设旁路特例**：它读不到「旁路」标记，跑照判）。

## 出口判据

三条核对，每条都写成「判据 + 二选一证据」（脚本上线后 / 脚本上线前）：

### 核对一：功能点全覆盖

- **判据**：PRD 的功能点 ID 集合 ⊆ plan 覆盖的功能点 ID 集合（差集为空），且每个被覆盖的功能点至少有一条执行步骤。
- **证据（现行命令，S4 起）**：`node scripts/check-plan.mjs coverage --plan <plan 文件> --prd <PRD 文件> --stage <S#>`，贴 stdout 首行（应报缺口 0）。
- **证据（脚本上线前，历史二选一）**：审计手工核对表——逐条填「核了什么 / 怎么核的 / 结论」，并附上人工取集合的原始命令原文（例如从 plan 与 PRD 各 grep 一次 `F-[0-9]+` 后比对）。

### 核对二：依赖无环

- **判据**：plan 的步骤依赖图是 DAG（拓扑排序可完成，无环）；每个步骤声明的依赖项都存在于 plan 内。
- **证据（现行命令，S4 起）**：`node scripts/check-plan.mjs deps --plan <plan 文件>`，贴 stdout 首行（应报环 0）。
- **证据（脚本上线前，历史二选一）**：审计手工核对表——写下拓扑序或指出成环的那条边，并附人工检查命令原文。

### 核对三：功能块 ↔ testcase 一一映射

- **判据**：每个功能块恰对应一份 testcase 文件，且该 testcase 覆盖该功能块全部验收项；无功能块缺 testcase，无 testcase 悬空。
- **证据（现行命令，S4 起）**：`node scripts/check-plan.mjs map --plan <plan 文件>`，贴 stdout 首行（应报缺映射 0）。
- **证据（脚本上线前，历史二选一）**：审计手工核对表——逐功能块写「对应 testcase 文件 + 覆盖的验收项编号」，附文件清单命令原文。

> **历史注（S4 之前）**：`scripts/check-plan.mjs` 曾不存在，三条核对一律走「审计手工核对表」——表头固定 `核了什么 | 怎么核的 | 结论`，并附原始命令原文。该分支现降为**历史二选一**（旁路或脚本故障时的手工逃生口），日常一律走上面的现行命令。审计只签字不读按**不通过**处理。

> **三条同批为界**：`coverage` / `deps` / `map` **必须同批上线**。只落一两条的过渡期，整门仍走手工核对表——不给「这次只贴哪几条证据」留解释空间。

## 谁签

- **申报人**：主 agent（plan 作者）。
- **签字人**：脚本 + **审计本人读并签字**；本门**不设议会**。
- 签字必须附：三条核对各自的证据（上线后 = 命令 + 输出；上线前 = 手工核对表 + 命令原文），以及每条核对对应的结论一句话。

## 三权归属

| 权 | 谁 | 判据 |
|---|---|---|
| 申报 | 主 agent | 申报三条核对已过，附三条证据与结论 |
| 定性 | 审计本人 | 审计必须自己读 plan 并填核对表；只签字不读 = 不通过 |
| 核对 | 脚本（现行）/ 审计（上线前与旁路） | 脚本给集合结论，审计给逐条核对表；两者都不由 plan 作者代填。**已签的手工门行不复算**：复算一律沿用当期手工命令原文，不得改用 `check-plan`（否则历史记录会被判成新错） |

## 常见漏项

- 只写三条命令、不写「脚本上线前怎么核」→ 照着跑会报找不到模块（本仓 S4 前脚本不存在）。
- 审计签字但没读 plan → 橡皮章，属不通过。
- 依赖检查只看文字「A 依赖 B」，不看环 → 两项互相依赖时看不出来。
- testcase 映射按文件名猜 → 同名不同功能块会漏。
- 功能点全覆盖只比数量不比集合 → 删一个加一个仍「数量相等」。
- **`exit 2` = 结构缺项，不是判据红**：补结构（`**Testcase:**` 行 / 附录 A 首列 / 映射表）后重跑；把 exit 2 当成「实现坏了」或「映射不全」去改 plan 的判据，是本门最常见的误判（Q23：exit 2 恒一行用法/结构错）。
- **验收命令的目标符号没核过**：命令里引用的导出名 / 子命令 / 文件路径没先在源码里 grep 到一次，就写进 plan → 命令一跑就 `TypeError` 或 `unknown command`，施工者误判成「实现坏了」，或换一条能跑的把事糊过去（于是证据链变成「看起来有命令」）。写 plan 时逐条核，并在命令旁标 `path:line`；施工后才存在的符号标「施工后核」并写明由哪个任务产出。

## 收口后

产出 `gate-record.md` 里 `②→③` 的那一行：六列齐，「签字人」含审计，「核了什么」含命令输出或 `path:line`。缺行不得进入 ③。
