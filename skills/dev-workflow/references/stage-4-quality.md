# 段④：质量保证

## 入口条件

- ③ 的 `gate-record.md` 行已齐六列，`npm run check` 已绿。
- testcase 文件是段②定稿的那一版（施工期若有修订，必须有差异记录）。

## 出口判据

1. testcase 全部条目已执行，逐条有结论（通过 / 不通过 / 不适用的理由）；没有「未执行」且没有「略过」。
2. 负例与边界条数 ≥ 正例条数（计数从 testcase 文件现算，不凭印象）。
3. 每条失败过的用例都留下可重跑的构造方式（副本仓 / 环境变量 / 内存注入三者之一），不只留结论。
4. 反向验证至少一条：对守卫类判据做一次「注入坏数据必红」的构造，确认判据有判别力。
5. 已知未覆盖的缺口写清楚（漏检哪类反例、由谁人工兜），不写成「暂无问题」。

## 谁签

- **申报人**：开发（提交被测产物的人）。
- **签字人**：sdet。
- 签字必须附：testcase 逐条结论表（按 `### TC-` 落盘，sdet 用 Grep 自数总数 / 通过 / 不通过与负例、边界标签）、反向验证的构造步骤（命令原文由申报人贴，sdet 核文本与结论一致）。

## 三权归属

| 权 | 谁 | 判据 |
|---|---|---|
| 申报 | 开发 | 申报被测产物与 `npm run check` 输出，不申报「验收通过」 |
| 定性 | sdet | 逐条判 testcase 结论；sdet 不得是被测代码的作者 |
| 核对 | 审计 | 抽查 ≥3 条，**审计自跑**命令复算并比对输出首行（已授 `command` 档，2026-10-24）；他人代跑判无效 |

## 常见漏项

- 只写「全部通过」，不给逐条结论 → 无法抽查，等于没有验收。
- 负例只构造一次、不留复位步骤 → 下次没人敢跑。
- 反向验证省掉 → 判据可能是恒真的，绿得没有意义。
- 把「不适用」当「通过」→ 覆盖账虚高。
- 缺口清单写「暂无」→ 掩盖残余风险，段⑤无法据此签字。

## 收口后

产出 `gate-record.md` 里 ④ 的那一行：六列齐，「核了什么」写**审计本人复算命令 + 输出首行**；sdet 核结论表、审计核命令。缺行不得进入 ⑤。
