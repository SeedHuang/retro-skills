# 新代码冗余清理（dry-refactor-newadd）

## 用途

审查**最近一次提交**引入的复制粘贴重复，抽取合并成公共方法，输出审计报告（改了什么 / 少了多少 / 占原来百分比）。**死代码不做**。

**为什么要求先提交（而不是直接扫未提交改动）**：提交后你的改动有了 git 记录——① 技能改坏了能干净回退（只丢技能的改动，你自己的不动）；② 未提交/未跟踪的改动在 git 里没有记录，改坏了根本无法还原；③ 提交给了技能一个稳定的对比基准。

## 先判提交数，定工作模式

| 提交数 | 模式 | 基准 | 认定「新增」的依据 |
|---|---|---|---|
| ≥2 | A | `HEAD~1` | 克隆带 `isNew: true`（**已实测**） |
| =1 | B | 无 | 全部算新（没有「改动前」可比） |
| =0 | — | — | 拒绝（没有 HEAD） |

## 前置（缺一即拒）

1. **工作区必须干净（= 用户已完成开发并提交）**：`git status --short` 必须为空。非空（有未提交改动或未跟踪文件）→ **停止**，让用户先 `git add` + `git commit` 再来；用户若表示「还在编辑」→ 同样拒绝。**本技能不做任何 git 写操作**——提交必须由用户执行。
2. jscpd v5 可用：`npx jscpd --version` 须 ≥ 5.3（`--baseline-from-ref` 只在 v5 有；v4 直接拒绝并说明）。
3. 至少 1 个提交（0 提交 = 无 HEAD，既没基准也没回退点 → 拒绝）。
4. 扫描路径须真实存在且为目录（含空格用引号包住）；不存在 / 指向单个文件 → 拒绝。
5. **任何命令失败**（`git` / `npx` / `jscpd` 报错）→ 报出错误原文并停止，不降级猜测、不换命令硬闯。

## 流程

### 第 1 步 判提交数、定模式

```bash
git status --short          # 必须为空；非空 → 停止，让用户先提交
git rev-list --count HEAD   # 记下提交数
```

按上表定模式：≥2 → A；=1 → B；=0 → 拒绝。

### 第 2 步 检测「本次提交新增」的重复

统一要求：用 **json reporter**（`--reporters ai` 不输出 `isNew`，会把旧债和新增混在一起，等于白跑）；`--output` 指向**仓库外的临时目录**（json reporter 默认写进仓库内的 `report/`，会污染工作区——实测 `git status` 会多出 `?? report/`）。

**模式 A（提交数 ≥2）**：

```bash
npx jscpd --reporters json --no-tips --baseline-from-ref HEAD~1 --output <仓库外临时目录> <路径>
```

- **已实测（2026-09-30）**：本次提交新引入的克隆标 `isNew: true`，基准 `HEAD~1` 里就有的旧债标 `isNew: false`。**只处理 `isNew: true` 的**。
- 改前基线取 `<临时目录>/jscpd-report.json` 里 `statistics.total` 的 `newClones` 与 `newDuplicatedLines`，记为 X。

**模式 B（提交数 =1）**：

```bash
npx jscpd --reporters json --no-tips --output <仓库外临时目录> <路径>
```

- 只有 1 个提交时 `HEAD~1` 不存在，jscpd 会报 `git ref 'HEAD~1' not found` 并退出（**已实测**）——所以本模式**不加 baseline**。没有「改动前」可比，报出的全部克隆**全部算新**。
- 改前基线取 `statistics.total` 的 `duplicatedLines`，记为 X。

> - 默认只报 exact（完全一样）的克隆；要顺带查改名克隆可加 `--ignore-identifiers --min-tokens 70`，但那是第二遍，先处理 exact。
> - jscpd 尊重 `.gitignore`（**已实测**）：被 ignore 的文件会被静默跳过。若有改动落在 gitignore 范围内，在审计报告里注明「N 个文件被 gitignore 跳过，未参与扫描」。

### 第 3 步 分诊（先读后动）

对每个候选克隆（模式 A 取 `isNew: true`，模式 B 取全部）读两端代码，判断是否值得合并。**跳过并写明原因**，当且仅当命中以下任一：两边语义不同（同形状不同逻辑）；故意的样板（模型 / DTO / 配置表 / 测试夹具）；生成代码；抽象命名含糊（只能叫 `processData`）；少于约 10 行。只有「合并后能删代码 + 能给精确命名」的才进第 4 步。

### 第 4 步 抽取合并（不可逆操作：先确认；回退点=已干净的工作区）

按重复类型选策略（策略内嵌本技能，不依赖外部技能）：

| 重复类型 | 策略 |
|---|---|
| 一段逻辑完全一样 | 抽函数 |
| 只是变量名 / 数值不同 | 参数化 |
| 跨文件、或重复的是数据 | 抽模块 / 抽常量 |
| 结构重复（类形状一样） | 基类 / 模板 |

**动手前先向用户列出计划**：每个将合并的克隆（文件+行号、将抽出的方法名、将更新的调用点清单），等用户确认后才改。改动文件很多（如 30+ 个）时**分批**，每批之间停顿让用户确认。

**回退点**：因为动手前工作区已干净（= 你的提交），改坏了可用 `git restore <文件>` 回到提交时的版本——**只丢技能的改动，你自己的改动不受影响**。注意 `git restore` 属于丢弃工作区改动的操作，**须经用户确认后才执行；本技能不自行跑 git 写操作**。

**编辑顺序：加法优先，减法最后。** 每个合并点按此顺序做，任一步失败都不留残缺代码：
1. 先新增共享方法（只加不删）
2. 再逐个改所有调用点
3. 复测 + 项目测试 / 构建通过
4. **最后**才删原重复块

必须更新**所有**调用点，不止 jscpd 报的那两处。每改一个文件后用磁盘核读确认（不只信编辑回执）。

**中断恢复**：若在批量编辑中中断，工作区已不再干净——不要沿用上次报告，从第 1 步重来（先判当前状态是继续改还是回退到干净状态再重跑）。

### 第 5 步 复测（用第 2 步同一条命令、同一基准）

确认之前认定为「新」的克隆已消失、重复行数从 X 降到 Y（模式 A 看 `newDuplicatedLines`，模式 B 看 `duplicatedLines`）。改完还要跑项目自己的测试 / 构建——jscpd 复测只证明重复消失，不证明行为没变。**项目没有测试时至少跑构建**，构建也没有就明确告知用户「行为验证缺失」。

### 第 6 步 审计报告（三块）

1. **改了什么**：每个合并点——文件+行号、抽出的方法名、用的策略。
2. **跳过了什么 + 为什么**：与重构的分开报告，禁止把「没动」写成「没问题」。
3. **数字对比**：重复行数 X → Y，减少 Z 行，占原来 XX%。数字从第 2 步同一条命令前后各取一次，附取数命令，可复算。

## 自进化

执行中踩的坑（识别不准、合并后测试挂）→ 按本仓库 `retro-*` 体系回流错题集 KB。技能本身不带自改逻辑，进化靠既有复盘套件。

## 硬约束（六条）

1. 只在**工作区干净**时才动手；不干净 → 停止并让用户先提交。
2. 只处理本次提交**新增**的重复（模式 A 过滤 `isNew: true`）；基准里已有的旧债不碰、不报告成问题。
3. **本技能不做 git 写操作**（提交、`git restore` 等一律由用户执行，或经用户确认后才做）。
4. 编辑遵守「加法优先、减法最后」；改完跑项目自己的测试 / 构建（缺测试至少跑构建），不只信 jscpd 复测。
5. 跳过的和改的分开报告。
6. 报告数字必须实测取数 + 附命令，禁止中间态记忆或估计值。
