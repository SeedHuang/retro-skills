# 全局 Git 写操作禁令

## 核心约束
除非用户在当前对话中明确、直接地要求执行某个 Git 写操作，否则你禁止主动执行任何 Git 写操作。

## 写实现计划同样适用（含 skill 模板冲突裁决）
写实现计划（writing-plans 技能 / `docs/superpowers/plans/` 产出）时，本禁令同样适用：
- 计划中**禁止出现** `git add` / `git commit` / `git push` 步骤；
- 每个任务的收尾动作统一为「改动留在工作区，最终交用户决定提交方式」；
- **与技能模板冲突时以本规则为准**——如 writing-plans 模板的 Commit 步骤，那是通用模板的默认；本规则是用户定制，定制优先。判据：技能/模板是工具默认，用户规则是定制覆盖。

> 来源：2026-10-08 用户当场指令（「说了不允许 commit」「写 plan 的时候把不要执行 git 写操作的规则读进去」）｜落地：2026-10-08

## 防掠过（适用范围覆盖任何执行路径）

本禁令**不因指令来源而豁免**——以下任何一种情况都**不算**「用户明确要求」：

- 实现计划 / plan 里写了 commit 步骤（哪怕用户说「执行这个计划 / 用 SSD / 子代理执行」）；
- 子代理 / 子任务执行过程中的 git 写操作；
- 脚本、自动化、工具模板要求 commit / push；
- 用户「选择了某个执行方式」≠ 授权了其中的具体 git 写操作。

**「用户明确要求」唯一成立的情形**：用户在当前对话中**直接说出**对具体 git 操作的指令（如「帮我 commit」「执行 git push」「把这段提交了」）。

**冲突裁决**：任何指令 / 模板 / 计划与「禁止主动执行 git 写操作」冲突时，以本禁令为准；拿不准就先停下说明，等用户直接确认再动。

> 来源：2026-10-09 补（实测：implementer 执行 plan 的 commit 步骤绕过本禁令——它把「用户选 SSD 执行计划」误判成「授权了计划里的 commit」）｜落地：2026-10-09

## 被禁止的 Git 写操作（除非用户明确要求）
以下操作一律禁止主动执行：
- git commit
- git push
- git pull（当它会修改工作区或产生合并时）
- git merge
- git rebase
- git reset
- git revert
- git cherry-pick
- git checkout（当它用于切换分支或丢弃更改时）
- git restore
- git clean
- git stash
- git tag（创建或删除标签时）
- git branch（创建、删除或重命名分支时）
- git remote（修改远程配置时）
- git config（任何写入配置的操作）
- git add（除非用户明确要求暂存文件）
- 任何会修改 .git 目录内容的命令

## 允许的 Git 读操作（无需用户额外要求）
以下读操作可以正常执行：
- git status
- git log
- git diff
- git show
- git branch（仅查看分支列表时）
- git remote -v（仅查看远程列表时）

## review 分支例外（唯一的结构性例外）

> 来源：2026-10-10 用户裁定（review-loop 锁基线方案落地，spec：`docs/superpowers/specs/2026-10-10-review-branch-design.md`）｜落地：2026-10-10
> 为什么要有它：review-loop 靠「每轮 commit 锁基线」来让下一轮 OCR 只审增量（否则 L1 全量重审无解）。这个目的只能靠 git 写操作实现，故开例外；**只此一种例外**。

**只有 review-loop 技能能触发本例外，且分两段，缺一段即不成立：**

### 段 1 · 入口动作（建分支）

当 review-loop 技能声明正在执行入口（建分支）时，允许 `git checkout -b review/*` 这一个动作。
—— 建分支发生在进入 review 分支之前，「在分支上」的条件覆盖不到，必须单独放行。
**中断恢复例外**：若当前已在 `review/*` 分支上（review 中断后续审），**不建分支**、直接继续，
此时不触发段 1（无建分支动作）；残留检查**排除当前所在分支**。

### 段 2 · 分支内操作（已进入 review 分支）

同时满足两个条件才成立：

1. 当前分支是 review 分支（`git branch --show-current` 以 `review/` 开头）
2. 操作属于 review-loop 的锁基线 / 收尾流程：
   - commit（message 带 【review】标记；**只 add 本次审查清单内的文件，禁止 `git add -A`**）
   - checkout（切回母分支）
   - branch（建 / 删 review 分支）
   - rebase（**仅限** review 分支合回母分支时）

**本例外不覆盖**：push（review 分支不推送远程）、reset、merge、`git add -A`、任何会改写 review 分支历史的其他操作。

### 问提交的边界（严格限定）

- **循环过程中的 commit 是流程动作，不许问、不许提示**——「要不要提交」这个问题依然不成立（必须提交，没有要不要）
- **唯一允许问「是否提交/合并」的场景 = review-loop 收尾合并回母分支时**（先展示 diff → 用户确认 → 才 rebase）
- 其他任何时刻，本规则其余部分不变，继续禁止问「要不要提交」

## 例外条件（必须同时满足）
只有当用户在当前对话中**明确说出**类似于以下表述时，才可以执行对应的写操作：
- “帮我 commit”
- “执行 git push”
- “帮我提交代码”
- “创建分支”
- 其他直接、无歧义的 Git 写操作指令

## 遇到不确定情况时的行为
如果你不确定某个 Git 操作是否属于写操作，或者不确定用户是否已明确授权，必须：
1. 暂停执行该操作；
2. 向用户说明你打算执行什么 Git 命令；
3. 等待用户明确确认后再继续。

## 绝对禁止的行为
- 禁止在用户不知情的情况下自动提交代码；
- 禁止使用 --force 或 -f 参数执行任何 Git 操作；
- 禁止修改 Git 全局配置或远程仓库配置；
- 禁止对 main/master 分支执行强制推送。
