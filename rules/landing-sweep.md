# 落地完成后，回头扫一遍所有"声明它的地方"

> 来源：评审第 4 轮（2026-09-28）｜证据：同一形态**已复发两次**——① 评审第 1 轮发现架构文档 §3/§6 与 §8.1 打架；② 评审第 4 轮发现 `my-rules\README.md` 里仍写着"同步脚本未做""文件命名未验证"、表里路径还是旧布局 `rules\`，以及架构文档三处数字仍写"7 条"而实际已是 8 条｜落地：2026-09-28

**每当一件事"落地"（建了脚本 / 加了规则 / 完成了某个"待办"）之后，必须回头扫一遍所有声明它的地方**，把过时描述改掉，然后才宣布完成。

**扫这四类地方**：

1. **源码注释**——脚本头部的用法说明、函数旁的注释
2. **各仓库 README / 说明文档**
3. **架构文档 / spec / plan**——尤其"待办 / 未做 / 缺 / 待验证"这类字样，以及**数字**
4. **规则正文**——里面的路径、命令、计数

**扫描命令**（拿刚落地那件事的**关键词 + 旧状态词**去全文搜）：

`Get-ChildItem <范围> -Recurse -File -Include *.md,*.mjs | Select-String -Pattern '未做|未验证|待建|缺|待定|TODO'`

**数字类**：凡文档里写了数量（"7 条"），优先**只留一处**并**附取数命令**（如 `aas doctor` 输出的"已就位"数）——同一个数字写在多处，必然漂移。

**为什么值得单独立一条**：这个错不是"某次疏忽"，而是**没有检查点**的必然结果——两次复发就是证据。只修当期那一处、不改流程，第三次还会犯。

**反例（本次真实触发）**：架构文档 §3/§6 在第 1 轮评审后就改对了，但 `my-rules\README.md` 里那句"同步脚本未做"**一直没人扫到**，直到第 4 轮评审才发现；同一轮还发现架构文档三处数字写着"7 条"（实际 8 条）、README 表里的路径还是搬家前的 `rules\`。

**正例**：落地后先跑一次上面的扫描，把命中的每一处**逐条对照现状**改掉，再收口。
