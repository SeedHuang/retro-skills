# 在写 skill 文档时，引用 reference 的指令必须接「读→产出」闭环

> 来源：实测/踩坑（2026-10-11）｜证据：L1 spec §三 有 commit 格式规范，agent 在 review 分支操作时没回去翻，照样漏前缀——写读一下类指令被跳过｜落地：2026-10-11

## 四要素声明

- **范围（在哪）**：写 skill 文档时（新建或修订 SKILL.md / references / scripts / assets）
- **条件（何时）**：指令要求 agent 读 reference 才能做对（写 message 前读格式、取数前读口径、动手前读判据）
- **动作（极性 = 义务）**：必须把「读」接进动作完成的必经环节（产出/核对条件）
- **宾语（对什么）**：引用 reference 的动作指令

## 核心判据

在写 skill 文档时，凡是「不读 reference 就做不对」的动作指令，**必须**把「读」接进动作完成的必要条件：指令写成**「按 <reference> 的 X 执行，做完核对/产出 Y，缺 Y 不合格」**——让「不读 → 做不对 → 检查不过 → 流程卡住」，跳过读取的代价大到不可接受。

`读一下` / `建议读` / `见 §N` 这类读完无要求的写法，AI 会跳过（觉得上下文里已有、不想额外读文件），等于没写。

- **正例**：「git commit message 必须按 `references/loop.md` §3 的格式写，写完核对 `<标准前缀>: 【review】` 两个都在，缺一不可；格式不对的 commit 不允许作为锁基线」
- **反例**：「commit 前读一下 `references/loop.md` §3」（读完没有任何必须核对/产出的要求，可跳）

## 为什么

reference 是被动资源，有效不取决于「它在」，取决于「执行路径是否强制经过它」。靠自觉读 = 会漏（实测：L1 spec §三 有 commit 格式规范，agent 在 review 分支操作时没回去翻，照样漏前缀）。

## 触发时机

在写 skill 文档时（新建或修订 SKILL.md / references / scripts / assets）。

## 验证

写完 skill 后自查：逐个检查「引用 reference 的动作指令」——是否停在「去读」？是否接在产出/核对条件上？停在「去读」= 不合格，改写为「读→产出」闭环。
