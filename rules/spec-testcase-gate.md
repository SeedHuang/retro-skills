# 在写或修改 spec 时，必须同批产出独立编写的 testcase 文件，并随 spec 一起送议会

> 来源：用户当场指令（2026-10-18）｜证据：议会评审 PRD 的 105 张卡中 F02 指出——testcase 硬门只写在 `prd-to-specs` 技能里，新 session 不加载该技能就失效；实测仓库 25 份 spec 零 testcase｜落地：2026-10-18

## 四要素声明

- **范围（在哪）**：写或修改 `docs/superpowers/specs/` 下的 spec（含 spike 类 spec；含文件形态与目录形态）
- **条件（何时）**：新建 spec、修订 spec、把 spec 送议会、或让 spec 进入 plan 之前
- **动作（极性 = 义务）**：必须同批产出配套 testcase 文件，由独立子代理编写，spec 用外链指向它，议会把两件一起审
- **宾语（对什么）**：spec 及其测试用例文件

## 核心判据

一条 spec 要算「可交付」，下面五条必须同时成立，缺一不合格：

| # | 判据 | 怎么算合格 |
|---|---|---|
| 1 | **文件存在** | 与 spec 同目录；文件名 = spec 文件名去掉 `.md` 后 + `-testcase.md`（例：`2026-10-17-xxx-design.md` → `2026-10-17-xxx-design-testcase.md`）；spec 是目录形态时用目录内 `testcase.md` |
| 2 | **编写者独立** | 由 `senior-sdet` 子代理在**全新上下文**编写；编写者 ≠ spec 作者、≠ 施工者；文件头写「编写者 / 独立性声明」 |
| 3 | **用例合格** | 每条用例五要素齐（覆盖 / 前置 / 步骤 / 预期 / 判据）；负例与边界条数 ≥ 正例；覆盖总表每行能指回 spec 的节号或 R 编号 |
| 4 | **spec 外链** | spec 的测试节只写「测什么 / 为什么」，并写「测试用例文件：`<路径>`」；**不内联具体用例**（两处维护必漂移） |
| 5 | **一起送审** | spec 与 testcase 作为一件交付物送议会；测试评委主审用例质量，审计核字段与计数；缺 testcase 不得送议会、不得进 plan |

无子代理环境时：只能产出**草稿**并在文件头标「降级模式（角色卡内联）」，**不得定稿**——同一实例写、同一实例判，等于把自评偏差搬进验收。

## 正例 / 反例

- **正例**：写 `2026-10-18-xxx-design.md` 时，同批派 `senior-sdet` 产出 `2026-10-18-xxx-testcase.md`；spec 测试节写「测试用例文件：`2026-10-18-xxx-testcase.md`」；议会开评时开卷清单同时列两份。
- **反例**：spec 写完直接进 plan，测试以后补（验收项等于没有验收）。
- **反例**：spec 作者自己顺手写用例、或在 spec 里内联用例表（自写自判 + 两处维护）。
- **反例**：议会只送 spec、不送 testcase（测试评委没有可审对象，字段核对落空）。

## 为什么

测试用例是验收的执行清单；没有它，spec 的验收项只是一句愿望，谁都可以说「做完了」。而这条规矩如果只写在按需加载的技能里，新 session 不加载该技能就等于没有——这正是「靠自觉必然漂移」的形态，必须由每轮自动加载的规则强制。

## 适用范围（不因来源豁免）

不因来源豁免——子代理、脚本、模板、AI 生成的 spec 同样要过；存量 spec 被修订并进入 plan 时同样要补。

## 冲突裁决

与「先写 spec、测试以后补」「这次先快速交付」「用例由 spec 作者顺手写」冲突时，以本规则为准。拿不准先停下说明，等确认再动。

## 例外

只有一类：**2026-10-18 之前已定稿的存量 spec 不追溯**（用户 2026-10-18 裁定「存量不用管，以后一个个升级」）。除此之外没有例外——包括 spike 类 spec、包括目录形态 spec。

## 触发时机

- 写或修改 spec 时；
- 把 spec 送议会之前；
- 让 spec 进入 `writing-plans` 或 plan 之前；
- 评审/审计发现 spec 无 testcase 时，按本规则打回。

## 验证

送审前逐条核对五条判据：文件存在 → 编写者独立性声明在位 → 五要素与负例比例 → spec 外链在位 → 议会开卷清单含两份。

`testcase-check.mjs` 落地后（PRD 的 S4），改为跑 `npm run check`：存在性、五要素、负例≥正例、覆盖列非空四条全绿才算通过；在脚本落地之前，以上人工核对结果必须写进送审说明。
