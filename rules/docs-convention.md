# 项目文档按「生命周期状态」分目录，未完成的进 `docs/after/`，临时的进 `.session/`

> 来源：用户当场指令（2026-10-07）｜证据：清空 analyze 产物后重启，「collect 够不够用」这项**未定稿**的需求讨论只能留在对话里——用户原话「你记录的东西，需要有一个文档，不是记载 memory 中啊」「我建议这些文档都放到 docs/after 里面，这个可以有效地知道哪些没做以后可以做」｜**2026-10-08 补**：用户原话「好记性不如烂笔头，所有的进度、进展，我给你提的建议都要有地方落地」「每种笔记请都分好类…长期要记的可以放在 docs 下面，短期记忆的可以放在 .xxxx 类似这样的文件夹下，并在 gitignore 中添加」→ 新增「临时记录（`.session/`）」一节｜落地：2026-10-07，2026-10-08 补

**文档目录的第一分类维度不是「主题」，是「生命周期状态」**。同一主题下，「已定稿」和「还在探索」放一起，两者会互相污染——读者分不清哪句是结论、哪句还是猜测。

## 一张表

| 目录 | 装什么 | 状态标记 | 什么时候搬走 |
|---|---|---|---|
| `docs/superpowers/specs/` | **已定稿**的设计 | 定稿即生效 | 被后续 spec 取代时，**原文保留不改**（历史记录） |
| `docs/superpowers/plans/` | **已排期**的执行步骤 | 勾选框 + 进度表 | 全部执行完 → 勾选，**不搬走** |
| `docs/handoffs/` | 某次 session 的**收尾交接** | 一次性 | 永不改写；新 session 另起一份 |
| **`docs/after/`** | **未完成 / 待决 / 悬置** | 明确写「未决」 | 做完了 → 把结论并入 spec，条目迁出 |
| 仓库根 | 体系总图、README | 长期 | — |

## 硬约束

1. **`docs/after/` 只放「还没做完」的**——需求探索中的设计讨论、待决清单、已认可但押后的方案。**判据：这份文档现在能不能当结论引用？** 能 → 进 `specs/`；不能（还在权衡、还有待决项）→ 进 `after/`。
2. **入口处必须写明「未决」和「何时该搬走」**——否则新 session 打开时会把探索稿当定稿引用。**正例**：`docs/after/collect-requirements-exploration.md` 开头写「状态：探索中，未定稿……定稿后应把结论并入 `specs/`，并把本文的「待办」迁走」。
3. **「已认可但细节押后」也要写进 `after/`，并标清押后理由**——**否则下次接手会当成已落地**。押后 ≠ 废弃，两者在文档里必须可区分（用「parking / 押后 / 待触发时机」这类字样）。
4. **搬走时必须回头扫引用**——从 `after/` 迁到 `specs/` 后，指向它的指针（含 KB 索引、其它文档）要一并更新；spec / plan / handoff 里的旧路径属**历史记录，保留不改**。
5. **探索稿不是第二份真相**——结论一旦定稿，**只保留一处**（spec），探索稿里的对应段落改为指向 spec 或直接删掉，**不并列两处说法**。

## 文件命名

| 目录 | 命名形态 | 例子 |
|---|---|---|
| `specs/` | `YYYY-MM-DD-<主题>-design.md` | `2026-10-02-session-dir-layout-design.md` |
| `plans/` | `YYYY-MM-DD-<主题>.md` | `2026-10-02-session-dir-layout.md` |
| `handoffs/` | `YYYY-MM-DD-<主题>.md` | `2026-09-29-session-close.md` |
| **`after/`** | **`<主题>-<阶段>.md`（小写 kebab-case，**不加日期**）** | `collect-requirements-exploration.md` |

**`after/` 为什么唯独不加日期前缀**：它是**活的账本**，会被反复更新——加日期会让人当成「某天的快照」，而它其实是持续更新的。**兄弟目录带日期是因为它们定格（定稿 / 排期完成 / session 收尾），`after/` 不定格。**

**构成**：`after/` 的文件名 = **主题 + 当前阶段**，让人不打开就知道这文档处在哪个阶段。

| 阶段 | 什么时候用 | 例子 |
|---|---|---|
| `exploration` | 还在探索，方案有争议 | `collect-requirements-exploration.md` |
| `gap-analysis` | 在查差距 / 体检 | `xxx-gap-analysis.md` |
| `open-decisions` | 只剩待决项，等拍板 | `xxx-open-decisions.md` |
| `done` | **全部待办已做**（瘦成「已完成区」+ 一句话说明，**不再是未完成入口**） | `xxx-done.md` |

**通用约束**（四个目录都适用）：

- **小写 kebab-case**——跨平台安全（Windows 大小写不敏感），与仓库其它文档一致。
- **禁用**：中文、空格、`YYYY-MM-DD-` 前缀（`after/` 尤其禁）、`.`（除扩展名）。
- **一主题一份**——同一主题的待决项**追加到同一篇**，不新建。混在一篇里等于没有索引。
  - **唯一的例外**：单篇 §4 待办**超过 15 条**时，按**同一主题内的不同类别**拆成两篇（如 `xxx-exploration.md` + `xxx-template-rewrite.md`），**且两篇开头必须互相写指针**。**拆出来的必须是同主题的不同类别，不许是同主题的两个独立主题。**
- **名字写「主题」不写「类别」**——`collect-requirements-exploration` ✅（看得出是什么事）；`exploration-doc-1` ❌（只是编号，看不出指向哪）。

**为什么值得单立一条**：命名不写下来，下次写新文档时就会重新纠结一遍「该叫什么」，目录里很快出现 `collect-explore.md` / `收集需求.md` / `2026-10-07-collect.md` 三种风格——**都合理，但混在一列就等于没有命名规范。**

## 临时记录（`.session/`）：不进 git 的过程账本

**判据一句话**：**关掉 session 之后还需要吗？** 需要 → 进 `docs/`（进 git）；不需要 → 进 `.session/`（不进 git）。

**为什么要有这一档**：`docs/` 四类都是长期的（specs 定稿、plans 排期、handoffs 快照、after 活账本），**没有一档是短期的**。硬把「只在这几个小时有用」的东西塞进 `docs/`，会同时污染两类目录：长期目录里混进草稿，或为短期单开一个 `docs/xxx/` —— 后者与 `after/` 功能重复。

### 封闭清单（只有这两种，加新的先回答「为什么塞不进这两」）

| 落点 | 装什么 | 什么时候删 |
|---|---|---|
| `.session/reviews/<YYYY-MM-DD-HHMM>-<kebab-case 名字>/` | **某次审查的过程账**：跑了几轮、三段各做了什么、改了什么。**两个文件**：`progress.md`（活的，每轮追加）+ `problems.md`（漏斗，修好的移走） | 该次审查全部处置完 → **整个目录删掉** |
| `.session/README.md` | 这个目录现在有什么（**现状**） | 不删 |

**命名**：`reviews/` 下的目录用 **kebab-case + 时间戳**（跨平台安全 + 能排序）；**中文标题写在文件首行**，不写进路径。

### ⚠️ 待决事项只有一处：`docs/after/`，不设第二处

**病根（2026-10-08 实际踩过）**：曾在这本规则的「临时记录」一节里另设一个待办文件当第二落点。当时把分界线画成「临时 vs 长期」（这次 session 内 vs 跨 session）。**判据错了。**

**正确的判据是「等多久、谁来解」，不是「在不在这次 session 里」**：

| 事项 | 该去哪 | 为什么 |
|---|---|---|
| 等用户拍板、可能等三天 | **`docs/after/`** | 它跨 session，且**最不能丢**（待决事恰恰是丢不起的） |
| 等某个外部答复 | **`docs/after/`** | 同上 |
| 等「我下一次动手」 | 不进任何账本 —— **做不出东西的事写下来就是 clutter**；真怕丢就写进代码注释或 `.session/reviews/<那一次>/progress.md` 的未完成小节 | 它随 session 结束而自然失效 |
| 这次审查跑到哪了 | `.session/reviews/<那一次>/progress.md` | 过程账，做完即删 |

**为什么 `.session/` 里不该有待决清单**：
1. 它**不进 git** —— 而待决事恰恰是「session 一断就丢不起」的，放这儿等于主动把它放进易丢区；
2. `docs/after/` 已经能装它，且有目录语义 / 阶段标记 / 迁移规则；
3. **两个落点必然漂移** —— 实测 2026-10-08：同一件「改动规模采哪个范围」在两处各有一份，而本文硬约束第 2 条（一个用途一个地方）就是我自己写的。**规则写完转头就犯，说明「多开一个落点」这个动作本身不可靠。**

### ⚠️ 待办文件的语义：「还没做的事」，不是「做过的事的档案」

**一条待办能不能删，只看一件事：它现在还在等什么？** 等不到任何东西了 = 完成 = **删**。

做完的去处（**删之前先确认它落到位了**）：

| 做完的东西 | 落点 |
|---|---|
| 建议落成规则了 | 规则正文（每轮自动加载） |
| 代码改完了 | 代码 + 测试断言 |
| 结论定了 | `docs/after/`（未决）或 `specs/`（已定稿） |
| 拿不走的（等外部、等授权） | **留**，且必须写清「等什么、谁来满足」 |

**⚠️ 不许出现 ✅ 档 ——「勾选」这个动作本身就是设计错误**（实测 2026-10-08）：

待办表里一旦有「已完成」这一档，做完的条目就有了合法的容身之处，于是：
- 做完不删 → 文件只涨不消（实测：某次待办文件里 8 条已落地的建议 + 5 条已做完的技能层改动，全挂着）；
- 而且**半年后没人知道哪行是活的** —— 满屏 ✅ 会让真正的待办被忽略。

**清账判据**：一个待办文件里如果**超过一半是 ✅**，说明它已经变成历史档案 —— 此时应该①把未完成的迁进新文件，②把已完成的**整段删掉**（它们已经在 git / 规则里了）。**不要靠「标记已完成」来保留历史。**

**为什么不能靠「标记已完成」保留历史**：git 就是历史。**在待办文件里再造一份历史 = 第二份真相**，与本文硬约束 5 直接冲突（且它会漂移 —— git 里的提交记录永远是准的，手抄的「已完成」不是）。

### ⚠️ 硬边界

1. **`.session/` 里不放成果。** 代码、测试断言、定稿结论**都要进 git 或 `docs/`。放进来就是垃圾堆，且会与 git 里的真版本漂移。
2. **一个用途只能有一个地方。** 待决项不要同时写在 `docs/after/` 和 `.session/` 下的任何文件 —— 两份说法必然漂移。**分工**：过程与进度 → `.session/`；结论与待决 → `docs/after/`。
3. **过程账的操作规程走技能 `review-log`**（什么时候建、填哪些小节、什么时候删）；本节只定义**目录语义**，两者不重复。
4. **`.session/` 已在 `.gitignore` 里**，别去掉。它进 git 就没有「短期」的意义了。
5. **与 `.superpowers/` 的区别**：`.superpowers/sdd/` 是 SDD 执行工作区（**实测当前是空壳**：1 个文件，就是它自己的 `.gitignore`），由插件自己用；`.session/` 是**审查过程与待办的账本**，由 `review-log` / `writing-after-docs` 用。两者不合并、不互相替代。

## 与「落地后回头扫」的衔接

`docs/after/` 是「**哪些没做**」的权威入口。`landing-sweep` 扫「已落地的东西有没有全部声明到位」时，**反向也该扫这里**：待决清单里的项若已做完，得从 `after/` 迁走，否则下次会被当成欠账。

- **正例**：2026-10-07 建 `docs/after/collect-requirements-exploration.md`（需求仍在探索，五缺口 + 2 项已确认要做 + 5 条待决 + 1 项 parking），并在 KB `index.md`「重启前待决」下加指针指向它。
- **反例**：把未定稿的需求讨论只留在对话里——session 一关就丢，下次接手完全不知道停在哪（本次即如此：用户不得不重新口述一遍全过程）。
- **反例**：把探索稿直接写进 `specs/`——读者无法区分哪些已裁决，误当结论引用。

## 适用范围

**只管项目文档目录（`docs\`），不管技能目录**——后者归 `skill-assets-convention`（官方 Agent Skills 的 `scripts/` / `references/` / `assets\` 三档）。**判据不同，别混用。**
